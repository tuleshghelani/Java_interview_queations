## 251. How do you build event-driven systems with Spring Boot and Kafka? Explain event sourcing, CQRS, outbox, and idempotency.

Event-driven architectures (EDA) decouple producers from consumers via asynchronous events, improving scalability and resilience (Q234). Combining **Kafka** (Q212), the **transactional outbox** (Q223/Q242), **idempotent consumers** (Q242), and patterns like **Event Sourcing + CQRS** enables traceable, eventually consistent systems that can recover from failures and replay history.

---

### 1. Event-Driven Architecture Basics

| Concept | Meaning | Example |
| :--- | :--- | :--- |
| **Domain Event** | Something that happened in the business (immutable) | `OrderCreated`, `PaymentSucceeded`, `InventoryReserved` |
| **Event Producer** | Publishes events after a state change | Order Service publishes `OrderCreated` |
| **Event Consumer** | Reacts to events, updates its own projection | Payment Service listens and charges |
| **Event Broker** | Durable, ordered transport | Apache Kafka (log-based), RabbitMQ (Q224) |
| **Eventually Consistent** | Downstream views converge over time | Order status becomes "PAID" after Payment event |

---

### 2. Producing Events Reliably — Outbox Pattern

Avoid dual-write (DB + Kafka) inside a transaction — if Kafka publish fails after commit, events are lost; if before, DB rolls back inconsistently. Use **Transactional Outbox** (Q223):

```java
@Entity
@Table(name="outbox_events")
@Data
public class OutboxEvent {
    @Id @GeneratedValue
    private Long id;
    private String aggregateType;
    private String aggregateId;
    private String eventType;
    private String payload; // JSON
    private String traceId;  // Q244
    private Instant createdAt;
    private boolean published;
}
```

```java
@Service
@Transactional
public class OrderService {
    private final OrderRepo repo;
    private final OutboxRepo outboxRepo;
    private final ObjectMapper mapper;

    public Order create(Order cmd) {
        Order o = repo.save(new Order(cmd));
        OutboxEvent e = new OutboxEvent();
        e.setAggregateType("Order");
        e.setAggregateId(o.getId().toString());
        e.setEventType("OrderCreated");
        e.setPayload(mapper.writeValueAsString(o));
        e.setCreatedAt(Instant.now());
        outboxRepo.save(e);
        return o;
    }
    // Commit DB + outbox in same TX — atomic
}
```

**Relay:** A separate process (CDC via Debezium reading `outbox_events` WAL, or a simple poller + KafkaTemplate) reads unpublished events and publishes to Kafka with `key = aggregateId` (for ordering). Mark `published=true` after successful publish (inside idempotent write).

This guarantees **at-least-once delivery** of business events with no lost events.

---

### 3. Consuming Events Idempotently

Consumers must be **idempotent** (Q242) because retries produce duplicates (at-least-once). Store a **processed events** dedup table keyed by `(consumerName, eventId/businessKey)`:

```sql
CREATE TABLE processed_events (
  id BIGSERIAL PRIMARY KEY,
  consumer_name VARCHAR(100) NOT NULL,
  event_id VARCHAR(100) NOT NULL,
  processed_at TIMESTAMP NOT NULL,
  UNIQUE (consumer_name, event_id)
);
```

```java
@KafkaListener(topics="orders")
@Transactional
public void onOrderCreated(String payload, @Header(KafkaHeaders.RECEIVED_KEY) String key) throws Exception {
    OrderCreated evt = mapper.readValue(payload, OrderCreated.class);
    String eventId = evt.getEventId(); // from outbox
    if (processedRepo.existsByConsumerNameAndEventId("payment-service", eventId)) {
        return; // already processed
    }
    paymentService.charge(evt);
    processedRepo.save(new ProcessedEvent("payment-service", eventId, Instant.now()));
    // Both side effect + dedup write in same TX (local TX)
}
```

Use `eventId` (UUID) per outbox event, not just message offset. For Kafka EOS (exactly-once semantics), combine with `enable.idempotence=true` + `transactional.id` on producer and read-committed on consumer (Q212).

---

### 4. Event Sourcing vs. Traditional State Persistence

| Approach | What is stored | Querying | Replay/Audit | Complexity |
| :--- | :--- | :--- | :--- | :--- |
| **Traditional (CRUD)** | Current state only (`orders` table) | Direct SQL | Lost history (unless audit tables) | Simpler |
| **Event Sourcing** | Immutable sequence of events (`order_events` stream) | Build state by replaying events | Full audit trail + time-travel + rebuild projections | Higher (CQRS often needed) |

**Event Sourcing:** The source of truth is the **append-only event log**. Current state is derived by applying events in order.

```java
// Event stream for Order aggregate
interface OrderEvent {}
record OrderCreated(String orderId, String customerId, BigDecimal total) implements OrderEvent {}
record PaymentSucceeded(String orderId) implements OrderEvent {}
record OrderShipped(String orderId, String tracking) implements OrderEvent {}

// Rebuild state
public class OrderAggregate {
    private String status = "NEW";
    public void apply(OrderEvent e) {
        switch(e) {
            case OrderCreated c -> status="CREATED";
            case PaymentSucceeded p -> status="PAID";
            case OrderShipped s -> status="SHIPPED";
            default -> {}
        }
    }
}
```

Store events in an event store (e.g., **Axon**, **EventStoreDB**, or Kafka + a projection DB). On command: validate → append events → apply to aggregate → publish (optional).

**Benefits:** complete audit, temporal queries, easy to build read models, supports compensating actions and debugging (replay). **Trade-offs:** eventual consistency for reads, learning curve, schema evolution for events.

---

### 5. CQRS (Command Query Responsibility Segregation)

CQRS splits reads and writes: **Commands** mutate state (via aggregates/events), **Queries** read from optimized **read models/projections**.

```
Command side (write):  REST/Commands → Aggregate → Events → Event Store (Kafka/EventStoreDB)
                                                  ↓
Query side (read):     Events → Projectors → Read DB (Materialized View: orders_summary)
                                                  ↓
                       REST Queries → Read Model (fast, denormalized)
```

**Example read projection:** Listen to `OrderCreated`, `PaymentSucceeded` events and maintain `order_summary(order_id, status, total, paid_at)` in a separate Postgres/ES table for O(1) queries (no joins). This solves N+1 and gives low-latency reads independent of write model.

**When to use CQRS + Event Sourcing:** complex domains with many read/write patterns, audit requirements, or need to rebuild views. For simple CRUD, YAGNI — adds operational complexity.

---

### 6. Best Practices & Common Pitfalls

| Practice | Rationale |
| :--- | :--- |
| **Use eventId (UUID) per event** | Enables true idempotent consumer dedup (Q242); don't rely only on Kafka offset |
| **Keep events small & immutable** | Easier to evolve, serialize, and replay. Include only necessary fields (avoid deep object graphs) |
| **Version events** (`schemaVersion`) | Handle breaking changes over time (backward/forward compatible). Consider Avro/Protobuf + schema registry (Q212) |
| **Key events by aggregateId** | Ensures per-aggregate ordering in Kafka partitions (critical: `OrderCreated` before `OrderShipped`) |
| **Outbox + CDC (Debezium)** | More reliable than poller (no DB polling load, near real-time, transactional) |
| **Idempotent producers + EOS** | Kafka `enable.idempotence=true`, `acks=all`, `transactional.id` prevent duplicates on retries (Q212) |
| **Trace events** | Propagate `traceId`/`spanId` in event headers (Q244) to correlate across services |
| **Avoid long-running processing in listeners** | Offload to async executor; acknowledge only after successful processing |
| **Plan for eventual consistency** | UI may show "Pending" before projection updates — use webhooks/SSE (Q228) or polling if needed |
| **Compensating transactions (Saga)** | For distributed workflows (order→payment→inventory), prefer **Saga (choreography/orchestration)** over 2PC (blocking). Handle failures with compensating events (Q223) |
| **Snapshot aggregates on replay** | If event streams grow large (10^4+ events), snapshot aggregate state periodically to avoid full replay cost |

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Dual-write (DB+Kafka)** | Lost or duplicate events on crash | **Transactional outbox** + relay (CDC or poller) |
| **Non-idempotent consumers** | Double charges/refunds on retry | Dedup by `(consumer, eventId)` in same TX as business write (Q242) |
| **Losing ordering across aggregates** | Inconsistent state (ship before paid) | Order per aggregateId via partition key; cross-aggregate ordering is hard — prefer choreography carefully |
| **Event schema breaking consumers** | Deserialization errors, poison pills | Schema versioning + Avro/Protobuf + Schema Registry; forward/backward compatibility |
| **Infinite replay loops** | Event handlers re-publish events causing cycles | Mark internal vs domain events; avoid publishing from projections; use correlation IDs |
| **CQRS overkill for CRUD** | Complexity without value | Use only when read/write patterns differ significantly or audit/replay needed |

### Summary

- **Transactional outbox + idempotent consumers** is the foundation for reliable event publishing/consumption with **at-least-once → effectively exactly-once** (Q242/Q223).
- **Event Sourcing** stores immutable events as source of truth (full audit/replay); **CQRS** separates read/write models for scalability and query optimization.
- Use **Kafka** with `eventId` keys, aggregate-based partitioning, and propagate `traceId` (Q244). Prefer **CDC (Debezium)** to relay outbox events reliably.
- For distributed workflows, use **Saga** with compensating events instead of 2PC. Keep events versioned, small, and backward-compatible.
- Apply **EDA + ES+CQRS** only where eventual consistency and audit/replay provide real business value; otherwise, simpler CRUD+outbox is sufficient.

## 252. How do you handle distributed configuration changes and dynamic properties in Spring Boot without restarts? Explain @RefreshScope, @ConfigurationProperties, Spring Cloud Bus, and @EventListener(RefreshScopeRefreshedEvent).

In production microservices you often need to **change configuration at runtime** — feature toggles (Q247), log levels, circuit breaker thresholds (Q213), cache TTLs (Q229) — without redeploying or restarting instances. Spring Boot + Spring Cloud provide several mechanisms: **@ConfigurationProperties** for type-safe binding, **@RefreshScope** for lazily refreshing beans, **Spring Cloud Bus** for broadcast refresh across instances, and **@EventListener(RefreshScopeRefreshedEvent)** for reacting to updates.

---

### 1. The Problem: Static Config & Restarts

| Traditional | Desired (Cloud-Native) |
| :--- | :--- |
| Change `application.yml` → rebuild/redeploy | Change external source (Config Server/Vault/K8s ConfigMap) → propagate to running pods |
| Restart JVM to reload `@Value` | Hot-refresh beans/props without restart |
| Config baked into image | 12-factor: config in environment/external store (Q218) |
| Manual per-instance updates | Centralized, audited change with rollout control (K8s ConfigMap sync + reload) |

**Tools:** Spring Cloud Config Server, ConfigMap/Secret sync (Q243), Vault, Consul, etcd. Broadcast via **Spring Cloud Bus** (AMQP/Kafka) or K8s `Reloader`.

---

### 2. @ConfigurationProperties — Type-Safe Binding

Bind external config (env vars, files, Config Server, Vault) to POJOs. Auto-rebindable via `@RefreshScope` + binder.

```java
@Component
@ConfigurationProperties(prefix = "payment")
@Data
public class PaymentProperties {
    private String gatewayUrl;
    private BigDecimal feePercent = BigDecimal.valueOf(2.5);
    private int retryAttempts = 3;
    private Duration timeout = Duration.ofSeconds(5);
    // getters/setters (Lombok @Data)
}
```

```yaml
# application.yml (or Config Server/Vault)
payment:
  gateway-url: https://pay.example.com
  fee-percent: 3.0
  retry-attempts: 2
  timeout: 3s
```

```java
@Service
public class PaymentService {
    private final PaymentProperties props; // injected, immutable view unless refreshed
}
```

**Note:** `@ConfigurationProperties` beans are **not** refreshed by default. Wrap in `@RefreshScope` (see below) or use `@RefreshScope` on a wrapper component to get updated values.

---

### 3. @RefreshScope — Refreshable Bean Proxy

`@RefreshScope` creates a **CGLIB-scoped proxy**; on refresh, the bean is **destroyed and lazily recreated** on next access (similar to `prototype`).

```java
@Service
@RefreshScope
public class RateLimitService {
    @Value("${rate.limit.requests-per-minute:100}")
    private int requestsPerMinute;

    public int getLimit() { return requestsPerMinute; }
    // New value used after refresh — next access recreates bean
}
```

```java
@RestController
@RequestMapping("/api/limits")
@RefreshScope
public class LimitsController {
    @Autowired RateLimitService service;
    @GetMapping
    public Map<String, Object> limits() {
        return Map.of("limit", service.getLimit());
    }
}
```

**How to trigger refresh (single instance):**

```bash
# Spring Cloud Config: POST /actuator/refresh
curl -X POST http://localhost:8080/actuator/refresh

# Or POST /actuator/refresh with body for specific property sources
```

**Requires:** Actuator + `spring-cloud-starter-config` + `management.endpoints.web.exposure.include=refresh`. The endpoint is **sensitive** — secure it (Q231/Q249).

**Caveats:** `@RefreshScope` proxies can break **final methods**, **this-self calls**, and **@Transactional** self-invocation; also memory overhead (new bean per refresh). Use sparingly.

---

### 4. Spring Cloud Bus — Broadcast Refresh Across Instances

Manually POSTing to each pod is error-prone. **Spring Cloud Bus** (Kafka/RabbitMQ) broadcasts refresh messages.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bus-kafka</artifactId>
</dependency>
```

```yaml
# Config Server (server side) — act as bus source
management:
  endpoints:
    web:
      exposure:
        include: bus-refresh, health, info
```

```yaml
# Each microservice (client side)
spring:
  cloud:
    bus:
      enabled: true
      refresh.enabled: true
  kafka:
    bootstrap-servers: kafka:9092
```

**Flow:**
1. Commit change to **Config Server** backend (Git repo / Vault)
2. POST `/actuator/bus-refresh` to **one** instance (e.g., the config server itself, acting as source)
3. Bus publishes `RefreshRemoteApplicationEvent` on Kafka/Rabbit topic (`springCloudBus*`)
4. **All** subscribed service instances receive event, each POSTs `/actuator/refresh` internally (or handles `EnvironmentChangeEvent`)
5. Each `@RefreshScope` bean lazily recreates on next access; `@ConfigurationProperties` rebinds

**Targeted refresh** (only one service): POST `/actuator/bus-refresh/order-service` or use `destination` param.

---

### 5. @EventListener(RefreshScopeRefreshedEvent) — React to Changes

When config changes, Spring publishes **`EnvironmentChangeEvent`** (always) and **`RefreshScopeRefreshedEvent`** (after refresh scope beans are marked for recreation). You can react to update caches, metrics, or connected clients.

```java
@Component
@Slf4j
public class ConfigChangeHandler {

    @EventListener
    public void onEnvironmentChange(EnvironmentChangeEvent e) {
        // e.getKeys() = changed keys
        log.info("Config keys changed: {}", e.getKeys());
        // e.g., adjust log level dynamically
        if (e.getKeys().contains("logging.level.com.example")) {
            log.info("Log level updated via config change");
        }
    }

    @EventListener
    public void onRefreshScopeRefreshed(RefreshScopeRefreshedEvent e) {
        // All @RefreshScope beans will be recreated lazily on next access
        log.info("Refresh scope refreshed for bean: {}", e.getName());
        // e.g., clear caches that depended on old config
        cacheManager.getCache("rates").clear();
    }
}
```

**Also:** `ApplicationListener<EnvironmentChangeEvent>` works similarly. Use for dynamic side-effects (close/reopen DB pools, re-create Kafka topics, update rate limiters — Q238).

---

### 6. Full Dynamic Config Flow (End-to-End)

```
1. Developer updates config in Git (Config Server backend) or Vault (Q243)
2. Pipeline auto-commits or bot merges PR (GitOps, Q250)
3. POST /actuator/bus-refresh to Config Server (or webhook from Git push via Config Server webhook)
4. Spring Cloud Bus → Kafka topic → all instances
5. Each instance: EnvironmentChangeEvent → rebind @ConfigurationProperties → mark @RefreshScope for recreation
6. Next request hits @RefreshScope bean → CGLIB proxy → new instance with updated @Value
7. Custom @EventListener runs side effects (clear cache, reconnect, etc.)
8. Observability: metric "config_refresh_total", trace log (Q244), alert on failure
```

**Vault-specific (dynamic secrets, Q243):** Use `@RefreshScope` + `spring.cloud.vault.config.lifecycle` or `@Scheduled` lease renewal; for short-lived DB creds, HikariCP `max-lifetime` < TTL (Q248).

---

### 7. K8s Native Alternative — ConfigMap Sync + Reload

For K8s-native stacks, **ConfigMap/Secret** changes + **reloader** (stakater/Reloader) or Spring Cloud Kubernetes (ConfigMap watcher) also work.

```yaml
# K8s ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
data:
  application.yml: |
    rate:
      limit: 250
    features:
      new-checkout: true
```

```yaml
# Deployment — mount as volume + reload annotation
spec:
  template:
    metadata:
      annotations:
        reloader.stakater.com/auto: "true"  # triggers pod restart or Spring reload on ConfigMap change
    spec:
      containers:
        - name: order-service
          envFrom:
            - configMapRef: { name: order-service-config }
          volumeMounts:
            - name: config-volume
              mountPath: /config
      volumes:
        - name: config-volume
          configMap: { name: order-service-config }
```

**Spring Cloud Kubernetes** auto-detects ConfigMap changes (watch) and triggers `RefreshScope` without restart — similar to Bus but native to K8s.

**Trade-off:** Restart vs hot-refresh. For **config-only** changes (log levels, feature flags), hot-refresh via Bus/K8s watch. For **schema/code-level** changes, prefer rolling restart (Q226).

---

### 8. Security & Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Exposed `/actuator/refresh`** | Attackers change config | Secure actuator (OAuth2/JWT, Q249); disable in prod; use Bus+Vault/KMS with audit |
| **@RefreshScope proxy pitfalls** | Self-invocation bypasses proxy; `@Transactional` not applied; final methods not intercepted | Avoid `this` self-calls; use separate beans; don't mark `@RefreshScope` on transactional services |
| **Non-idempotent config change** | Bad value rolled out to all instances | GitOps PR review (Q250), canary config rollout (feature flags Q247), staged Bus refresh (one service, then all) |
| **Missed refresh (no event)** | Some pods keep stale values | Ensure Bus enabled + Kafka topic reachable; use targeted refresh by service name; verify with `/actuator/env` |
| **Race: multiple refresh events** | Bean recreated thrice | Bus dedups by destination; use `@RefreshScope` carefully — recreation is cheap but cache churn possible |
| **Sensitive values in config source** | Secrets leak via ConfigMap (not encrypted) | Use Vault/K8s Secrets (Q243), SealedSecrets, encrypt etcd |
| **No rollback plan** | Bad config persists | Git revert (Q250), versioned config in Vault/Config Server, canary first |
| **Long-running jobs with mid-flight refresh** | Inconsistent behavior mid-transaction | Read config once at start; avoid dynamic refresh inside critical sections |

### Summary

- Use **`@ConfigurationProperties`** for type-safe external config binding; pair with **`@RefreshScope`** to lazily recreate beans after refresh without restart.
- **Spring Cloud Bus** (Kafka/RabbitMQ) broadcasts `/actuator/refresh` across all instances — triggered from Config Server, Git webhook, or Vault (Q218/Q243).
- React to changes with **`@EventListener(EnvironmentChangeEvent)`** and **`RefreshScopeRefreshedEvent`** — update caches, log levels, reconnect clients, clear rate-limit buckets (Q238).
- **K8s-native** alternative: ConfigMap/Secret + Reloader or Spring Cloud Kubernetes ConfigMap watcher — trigger refresh or rolling restart (Q226).
- **Secure** actuator endpoints (Q249), use GitOps-reviewed changes (Q250), and prefer **rolling restart** for schema/code changes vs hot-refresh for pure config toggles (Q247).

## 253. How do you implement multi-tenancy in a Spring Boot application? Explain shared schema vs schema-per-tenant vs database-per-tenant, tenant resolution, and data isolation.

**Multi-tenancy** lets a single application instance serve multiple customers (tenants) while keeping their data isolated. The three dominant models are **shared schema** (row-level `tenant_id`), **schema-per-tenant** (one schema per tenant in one DB), and **database-per-tenant** (separate DB). Choosing the right model is a trade-off between **isolation**, **cost**, **operational complexity**, and **compliance** (e.g., GDPR/data residency, Q243).

---

### 1. Multi-Tenancy Models — Comparison

| Model | Isolation | Cost/Resource | Complexity | Migration | Best for |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Shared Schema (Discriminator column)** | Low (rows share tables; `tenant_id` column) | Lowest — one DB | Simplest app-level, hardest to guarantee isolation | One migration applies to all | SaaS with many small tenants, cost-sensitive |
| **Schema-per-Tenant** | Medium (separate schemas, shared DB server) | Medium | Medium — dynamic schema switching (`search_path`) | Run per schema (loop) | Moderate SaaS, moderate isolation, same DB engine |
| **Database-per-Tenant** | Highest (separate DB + credentials) | Highest | Highest — connection routing per tenant | Run per DB | Regulated data, large enterprise tenants, strong compliance |
| **Hybrid / Bridge** | Varies (mix: big tenants get own DB, small share schema) | Optimized | High | Mixed | SaaS at scale — tiered isolation |

**Rule of thumb:** start **shared schema** for MVP/cost, move large/regulated tenants to **DB-per-tenant** (hybrid) as they grow. Never upgrade the model lightly — it's costly to migrate.

---

### 2. Tenant Resolution — How to Identify the Tenant

The tenant must be resolved from every request **before** data access.

| Strategy | Example | Notes |
| :--- | :--- | :--- |
| **Subdomain** | `acme.app.com` | Clean, SEO-friendly; needs wildcard DNS/cert |
| **Path prefix** | `/api/{tenantId}/orders` | Simple for gateways (Q239); leaks tenant in URL |
| **HTTP Header** | `X-Tenant-Id: acme` | Common for APIs; must validate against authenticated principal |
| **JWT claim** | `tenant_id` claim (Q236/Q249) | Most secure — tenant bound to identity, not client-supplied |
| **Host/domain mapping** | Lookup table `domain → tenant` | Custom domains for white-labeling |

**Security rule:** never trust a client-supplied tenant alone — cross-check with the authenticated principal's tenant claim to prevent **cross-tenant access** (a top vulnerability).

```java
public class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();
    public static void set(String tenantId) { CURRENT.set(tenantId); }
    public static String get() { return CURRENT.get(); }
    public static void clear() { CURRENT.remove(); }  // MUST clear to avoid leaks in thread pools (Q244 MDC analogy)
}
```

```java
@Component
public class TenantFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String tenant = resolveTenant(req); // from JWT claim, subdomain, or header
        try {
            TenantContext.set(tenant);
            chain.doFilter(req, res);
        } finally {
            TenantContext.clear(); // critical for pooled threads (Q241)
        }
    }

    private String resolveTenant(HttpServletRequest req) {
        // Prefer JWT claim (validated), fallback to header/subdomain
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth != null && auth.getPrincipal() instanceof Jwt jwt) {
            return jwt.getClaimAsString("tenant_id");
        }
        return req.getHeader("X-Tenant-Id");
    }
}
```

---

### 3. Shared Schema — Discriminator Column

Every tenant-scoped table has a `tenant_id`; all queries filter by it. Use an ORM filter (Hibernate `@Filter`/`@TenantId`) to enforce automatically.

**Hibernate 6 `@TenantId`:**

```java
@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @TenantId
    private String tenantId;  // auto-populated + filtered by Hibernate

    private BigDecimal total;
    // Hibernate automatically adds WHERE tenant_id = ? and sets it on insert
}
```

```yaml
# application.yml — configure the tenant identifier resolver
spring:
  jpa:
    properties:
      hibernate:
        tenant_identifier_resolver: com.example.CurrentTenantIdentifierResolver
```

```java
@Component
public class CurrentTenantIdentifierResolver implements org.hibernate.context.spi.CurrentTenantIdentifierResolver<String> {
    @Override
    public String resolveCurrentTenantIdentifier() {
        return TenantContext.get() != null ? TenantContext.get() : "default";
    }
    @Override
    public boolean validateExistingCurrentSessions() { return true; }
}
```

```sql
-- Schema
CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  tenant_id VARCHAR(50) NOT NULL,
  total DECIMAL(19,2) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_tenant ON orders(tenant_id);  -- MANDATORY for performance
```

**Pitfalls:** missing `WHERE tenant_id` in native queries → **cross-tenant leakage**. Always index `tenant_id`. Consider **Row-Level Security (RLS)** in Postgres as defense-in-depth:

```sql
-- Postgres RLS: enforce isolation at DB level
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.current_tenant'));
-- App sets: SET LOCAL app.current_tenant = 'acme';
```

---

### 4. Schema-per-Tenant — Dynamic Schema Routing

One DB, one schema per tenant (`tenant_acme`, `tenant_globex`). Switch the schema per request via `search_path` (Postgres) or connection catalog.

```java
public class TenantAwareDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TenantContext.get(); // "acme" → datasource for schema tenant_acme
    }
}
```

```java
@Configuration
public class DataSourceConfig {
    @Bean
    public DataSource dataSource(Map<String, DataSource> tenantDataSources) { // schema-per-tenant mapped
        TenantAwareDataSource routing = new TenantAwareDataSource();
        routing.setTargetDataSources(new HashMap<>(tenantDataSources));
        routing.setDefaultTargetDataSource(tenantDataSources.get("default"));
        return routing;
    }
}
```

For Hibernate multi-tenancy with separate schemas, use `MultiTenantConnectionProvider`:

```java
@Component
public class SchemaPerTenantConnectionProvider implements MultiTenantConnectionProvider<String> {
    private final DataSource dataSource; // single DB

    @Override
    public Connection getConnection(String tenantId) throws SQLException {
        Connection conn = dataSource.getConnection();
        conn.setSchema(tenantId); // or: SET search_path TO tenant_<id>
        return conn;
    }
    // ... other methods
}
```

**Migrations:** run Flyway/Liquibase (Q248) **once per schema** — loop over tenants in a pipeline job. New tenant provisioning = create schema + run all migrations.

### 5. Database-per-Tenant — Connection Routing

Strongest isolation; each tenant has its own DB + credentials (stored in Vault, Q243).

```java
public class TenantRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TenantContext.get();
    }
}
```

```yaml
# Tenant registry (DB or config) → datasource per tenant
tenants:
  acme:
    url: jdbc:postgresql://db-acme:5432/acme
    username: ${ACME_DB_USER}
    password: ${ACME_DB_PASS}   # from Vault (Q243)
  globex:
    url: jdbc:postgresql://db-globex:5432/globex
    username: ${GLOBEX_DB_USER}
    password: ${GLOBEX_DB_PASS}
```

**Pros:** near-total isolation, per-tenant backup/restore/scale, easy compliance. **Cons:** connection pool per tenant (Q232 — watch total connections), migration fan-out, cost per DB.

**Provisioning:** automate with IaC (Terraform) + a tenant onboarding service that creates DB, runs migrations, seeds data, and registers the datasource.

---

### 6. Cross-Cutting Concerns

| Concern | Multi-Tenant Approach |
| :--- | :--- |
| **Caching** (Q229) | Namespace cache keys by tenant (`acme:orders:123`); or per-tenant cache region. Redis: key prefix. Never share a cache entry across tenants |
| **Async / Threads** (Q211/Q241) | `TenantContext` is `ThreadLocal` — **propagate** to async/scheduled (like MDC, Q244) via `TaskDecorator`; clear in `finally` |
| **Messaging** (Q212) | Include `tenantId` in event headers/keys; consumers set `TenantContext` before processing |
| **Observability** (Q244) | Add `tenantId` as a log field/trace tag (careful with metrics cardinality — Q230) |
| **Rate limiting** (Q238) | Per-tenant buckets (`rate:acme`, `rate:globex`) |
| **Security** (Q231/Q249) | Validate tenant claim from JWT; deny mismatch between token tenant and requested resource |
| **Migrations** (Q248) | Shared schema = one migration; schema/DB-per-tenant = fan-out loop; automate + track per-tenant version |
| **Backups/DR** | Shared = one backup; DB-per-tenant = per-tenant backup/SLA |

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Trusting client-supplied tenant** | Cross-tenant data exposure (critical) | Derive tenant from **JWT claim** (Q249); validate against resource ownership |
| **Missing `tenant_id` filter in native query** | Tenant A sees Tenant B's rows | Use Hibernate `@TenantId`/`@Filter`; enable Postgres **RLS** as defense-in-depth; code review native SQL |
| **ThreadLocal leak in pooled threads** | Request served with previous tenant's context | Always `TenantContext.clear()` in `finally`; propagate explicitly to async (Q211) |
| **No index on `tenant_id`** | Queries slow as data grows | Composite indexes starting with `tenant_id` |
| **Shared cache across tenants** | Cache poisoning / data leak | Namespace all keys by tenant; separate cache regions (Q229) |
| **Connection explosion (DB-per-tenant)** | Too many pools exhaust DB connections | Pool-per-tenant sizing, lazy pools, or connection multiplexing (PgBouncer) (Q232) |
| **Migration drift across schemas** | Different tenants on different versions | Automate fan-out migrations (Q248) and track applied version per tenant |
| **Noisy-neighbor** | One tenant's load degrades others | Per-tenant rate limits (Q238), quotas, or isolate large tenants (hybrid) |
| **Backup restores one tenant** | Can't restore single tenant in shared schema | Export/import by `tenant_id` or choose DB-per-tenant for strong per-tenant DR |

### Summary

- **Three models**: **shared schema** (`tenant_id` row filter — cheapest, weakest isolation), **schema-per-tenant** (dynamic `search_path`, medium), **database-per-tenant** (strongest isolation, highest cost). Use **hybrid** for tiered SaaS.
- **Resolve the tenant** from a validated **JWT claim** (preferred) or subdomain/header; store in `TenantContext` (`ThreadLocal`) and **always clear** it; propagate to async/events (Q211/Q212).
- **Enforce isolation** in code (Hibernate `@TenantId`/`@Filter`) **and** DB (Postgres **RLS**); index `tenant_id`; namespace caches (Q229) and rate limits (Q238) per tenant.
- **Fan-out migrations** (Q248) for schema/DB-per-tenant; automate tenant provisioning via IaC + Vault (Q243).
- **Never trust client-supplied tenant IDs** — bind tenancy to authenticated identity to prevent cross-tenant leaks.

## 254. How do you implement a GraphQL API in Spring Boot and when should you prefer it over REST? Explain schema-first vs code-first, resolvers, DataLoader, and the N+1 problem.

**GraphQL** is a query language and runtime for APIs that lets clients request **exactly the fields they need** in a single round trip, solving REST's over-fetching (too much data) and under-fetching (too many calls) problems (Q216/Q222). In Spring Boot, **Spring for GraphQL** (`spring-boot-starter-graphql`) integrates with Spring MVC (blocking) or WebFlux (reactive, Q221), supports both schema-first and code-first, and provides `@QueryMapping`/`@MutationMapping`, `@SchemaMapping`, and **DataLoader** for batching to avoid the N+1 problem.

---

### 1. Why GraphQL? REST vs GraphQL

| Aspect | REST | GraphQL |
| :--- | :--- | :--- |
| **Data fetching** | Multiple endpoints; over/under-fetching | Single endpoint `/graphql`; client specifies exact shape |
| **Round trips** | Often many (e.g., order + customer + items) | One query returns nested data |
| **Schema/Contract** | Documented via OpenAPI (optional) | Strongly typed schema (introspectable, self-documenting) |
| **Versioning** | URI/header versioning, new endpoints (Q246) | Evolve by adding fields; deprecate with `@deprecated`. No versions usually |
| **Efficiency on mobile** | Payload not tailored → more bandwidth | Minimal payload → great for mobile/low-bandwidth |
| **Caching** | HTTP caching (CDN) is natural | Harder — POST-based, needs persisted queries/response cache |
| **Complexity** | Simple, well-understood | Query complexity, N+1, security (depth/complexity limits), tooling |
| **Best for** | Simple resources, public APIs, caching-heavy | Aggregating many services, varied client needs, BFF (Q239) |

**Use REST** when resources are simple, caching is critical, or you have a stable public API. **Use GraphQL** when clients have diverse data needs, you aggregate many microservices, or you want to avoid multiple round trips (mobile/BFF).

---

### 2. Schema-First vs Code-First

| Approach | How | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Schema-first** | Write `.graphqls` SDL; implement resolvers against it | Clear contract, front/back can work in parallel, tooling | Duplication between schema and Java types |
| **Code-first** | Generate schema from annotated Java classes (e.g., `graphql-java` code registry) | Single source of truth in code, type safety | Less explicit contract; harder for front-end to preview |

Spring for GraphQL is primarily **schema-first** (SDL + `@QueryMapping`/`@SchemaMapping`), which is the recommended default.

```graphql
# src/main/resources/graphql/schema.graphqls
type Query {
    order(id: ID!): Order
    orders(customerId: ID!, page: Int = 0, size: Int = 20): [Order!]!
}

type Mutation {
    createOrder(input: CreateOrderInput!): Order!
    cancelOrder(id: ID!): Order!
}

type Order {
    id: ID!
    status: OrderStatus!
    total: BigDecimal!
    customer: Customer!        # nested resolver
    items: [OrderItem!]!       # nested resolver (N+1 risk)
    createdAt: DateTime!
}

type Customer { id: ID!, name: String!, email: String! }
type OrderItem { sku: String!, quantity: Int!, price: BigDecimal! }
enum OrderStatus { CREATED, PAID, SHIPPED, CANCELLED }
input CreateOrderInput { customerId: ID!, items: [OrderItemInput!]! }
```

### 4. @SchemaMapping — Nested Field Resolvers

Fields like `customer` or `items` on `Order` may require separate data access. Use `@SchemaMapping`:

```java
@Controller
public class OrderFieldResolvers {

    private final CustomerClient customerClient;
    private final ItemService itemService;

    @SchemaMapping(typeName = "Order", field = "customer")
    public Customer customer(Order order) {
        return customerClient.getById(order.getCustomerId());  // called per order → N+1!
    }

    @SchemaMapping(typeName = "Order", field = "items")
    public List<OrderItem> items(Order order) {
        return itemService.findByOrderId(order.getId());       // per order → N+1!
    }
}
```

If `orders` returns 100 orders, the `customer` resolver is called **100 times** (one per order) and `items` 100 times — a classic **N+1 problem**. This is the most common GraphQL performance trap.

---

### 5. DataLoader — Solving the N+1 Problem

**DataLoader** batches and deduplicates nested resolver calls within a single request: collect keys during the current tick, then load them in **one** batched call.

```java
@Configuration
public class DataLoaderConfig {

    // Batch customers: given order objects, return Map<customerId, Customer>
    @Bean
    public BatchLoaderRegistry batchLoaderRegistry(CustomerClient customerClient, ItemService itemService) {
        return registry -> {
            registry.forTypePair(String.class, Customer.class).registerMappedBatchLoader((ids, env) ->
                Mono.just(customerClient.getByIds(ids))  // ONE call for all ids
            );

            registry.forTypePair(String.class, List.class).registerMappedBatchLoader((orderIds, env) ->
                Mono.just(itemService.findByOrderIds(orderIds)) // ONE call
            );
        };
    }
}
```

```java
@Controller
public class OrderFieldResolvers {

    // Inject a DataLoader keyed by type/name
    @SchemaMapping(typeName = "Order", field = "customer")
    public CompletableFuture<Customer> customer(Order order,
            DataLoader<String, Customer> customerDataLoader) {
        return customerDataLoader.load(order.getCustomerId()); // batched + deduped
    }

    @SchemaMapping(typeName = "Order", field = "items")
    public CompletableFuture<List<OrderItem>> items(Order order,
            DataLoader<String, List<OrderItem>> itemsDataLoader) {
        return itemsDataLoader.load(order.getId());
    }
}
```

**Result:** 100 orders → 1 query for orders + 1 batch for customers + 1 batch for items (3 queries total), instead of 201. DataLoader caches per-request (deduped, request-scoped).

**Note:** `DataLoader` works seamlessly with both Spring MVC (returns `CompletableFuture`) and WebFlux (`Mono`/`Flux`, fully non-blocking). Combine with `@BatchMapping` for convenience:

```java
@BatchMapping(typeName = "Order", field = "customer")
public Map<Order, Customer> customers(List<Order> orders) {
    return customerClient.getForOrders(orders); // one call
}
```

```java
    @Override

            return GraphQLError.newError()
```

### 7. Security & Performance Guards

| Risk | Mitigation |
| :--- | :--- |
| **Deep/complex queries** (DoS) | Query depth limit, complexity analysis, disable introspection in prod, query allow-listing (persisted queries) |
| **N+1** | DataLoader / `@BatchMapping` (see above) |
| **Circular/recursive types** | Depth limits; avoid unbounded nesting |
| **Auth per field** | Spring Security + method security; check authorization in resolvers (Q207/Q249) |
| **Over-fetching sensitive fields** | Field-level authorization (`@PreAuthorize` in resolvers); never expose secrets |
| **Introspection in prod** | Disable `graphql.introspection.enabled=false`, hide GraphiQL |
| **Batching abuse** | Cap batch size in DataLoader; rate limit per client (Q238) |
| **BFF aggregation timeouts** | Set per-dependency timeouts + circuit breakers (Q213) when GraphQL aggregates services |

```yaml
# application.yml — production hardening
spring:
  graphql:
    graphiql:
      enabled: false
    schema:
      introspection:
        enabled: false
```

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **N+1 in nested resolvers** | Slow queries, DB hammered (hundreds of calls) | **DataLoader**/`@BatchMapping`; verify with tracing (Q244) and SQL logs |
| **Returning entities directly** | Lazy-loading exceptions, leaking internal fields | Map to DTOs (Q208); never expose JPA entities directly |
| **No depth/complexity limits** | Malicious deep query → DoS | Set `MaxQueryDepthInstrumentation`/complexity; allow-list queries |
| **Introspection enabled in prod** | Attackers enumerate full schema | Disable introspection + GraphiQL in production |
| **Blocking calls in WebFlux** | Thread starvation (Q221) | Return `Mono`/`Flux`; never `.block()` in reactive resolvers |
| **GraphQL as database escape hatch** | Clients craft expensive joins | Design schema around use cases; cap page sizes; complexity cost per field |
| **Ignoring HTTP caching** | Can't use CDNs like REST | Use persisted queries + GET for cacheable reads, or app-level cache (Q229) |
| **No request-level batching context** | DataLoader cache leaks across requests | DataLoader is request-scoped by default in Spring — don't reuse across requests |

### Summary

- **GraphQL** gives clients exact-shaped responses in one round trip, ideal for **aggregation/BFF** (Q239) and mobile; **REST** still wins for simple, cache-heavy, public APIs (Q216).
- **Spring for GraphQL** is **schema-first** (`.graphqls` SDL + `@QueryMapping`/`@MutationMapping`/`@SchemaMapping`), running on MVC or WebFlux (Q221).
- **Solve N+1 with DataLoader/`@BatchMapping`** — batch nested field loads per request; this is the single most important GraphQL performance practice.
- **Harden in prod**: disable introspection/GraphiQL, cap query depth/complexity, use persisted queries, enforce field-level auth (Q207/Q249), and set timeouts/circuit breakers for aggregated services (Q213).
- Map entities to DTOs (Q208), prefer **cursor pagination** for large collections, and observe per-field latency with tracing (Q244).

## 255. How do you implement gRPC in Spring Boot and when should you prefer it over REST or GraphQL? Explain Protocol Buffers, HTTP/2 multiplexing, streaming patterns, interceptors, deadlines, and error handling.

**gRPC** (Google Remote Procedure Call) is a high-performance, open-source RPC framework that runs over **HTTP/2** and uses **Protocol Buffers (Protobuf)** as its interface definition language (IDL) and binary wire format. While **REST** (Q216) excels at open, browser-facing, cache-heavy public APIs and **GraphQL** (Q254) excels at client-driven aggregation and BFF architectures (Q239), **gRPC is the gold standard for internal synchronous microservice-to-microservice communication**. It offers 5–10x higher throughput, 7–10x smaller payload footprints, native multiplexing over a single TCP connection, built-in streaming (server, client, bidirectional), and strictly enforced compile-time contracts across heterogeneous languages.

---

### 1. Architectural Comparison — REST vs GraphQL vs gRPC

| Dimension | REST (HTTP/1.1 or 2) | GraphQL (HTTP/POST) | gRPC (HTTP/2) |
| :--- | :--- | :--- | :--- |
| **Transport** | HTTP/1.1 (or HTTP/2) | Usually HTTP/1.1 / HTTP/2 over POST | Strictly **HTTP/2** (requires binary framing) |
| **Data Format** | JSON (human-readable text) | JSON (human-readable text) | **Protocol Buffers** (compact binary wire format) |
| **Contract / Schema** | Optional (OpenAPI / Swagger, Q216) | Strongly typed schema SDL (`.graphqls`) | Strict compile-time contract (`.proto` IDL) |
| **Payload Size & Speed** | Larger (text overhead, key names repeated) | Medium (only requested fields, but still text JSON) | **Smallest** (binary tags, varint encoding, packed fields) |
| **Multiplexing** | Head-of-line blocking on HTTP/1.1 | Head-of-line blocking on HTTP/1.1 | **True multiplexing** (multiple concurrent streams over 1 TCP socket) |
| **Streaming Support** | Unidirectional SSE or WebSockets | Subscriptions via WebSockets/SSE | **Native 4 patterns**: Unary, Server, Client, Bidirectional |
| **Browser Compatibility** | Native (100% browser support) | Native (standard fetch/XHR) | Limited (requires **gRPC-Web** proxy like Envoy) |
| **Language Ecosystem** | Universal | Universal | Strong multi-language code generation (Java, Go, C++, Python, Rust) |
| **Primary Use Case** | Public APIs, CRUD, CDN caching | BFF, front-end aggregation, mobile clients | **Internal microservices**, real-time streaming, high-throughput IPC |

**Decision Rule:**
- Choose **REST** for external, public-facing developer APIs, simple CRUD, or when edge CDN HTTP caching is mandatory.
- Choose **GraphQL** when UI clients have varied, unpredictable data requirements and you need to solve over/under-fetching across multiple downstream services at the edge (BFF).
- Choose **gRPC** for **internal inter-service communication**, latency-critical distributed systems, real-time bidirectional streams, and microservice topologies where CPU, memory, and bandwidth efficiency are top priorities.

---

### 2. Protocol Buffers (Protobuf) & Contract Definition

Protocol Buffers is a language-neutral, platform-neutral mechanism for serializing structured data. Unlike JSON, which serializes field names repeatedly on every message, Protobuf encodes fields using numeric **field tags** (1, 2, 3...) and **varints**, yielding drastically smaller binary footprints.

#### Proto Contract (`order_service.proto`)

```protobuf
syntax = "proto3";

package com.example.grpc.order;

option java_multiple_files = true;
option java_package = "com.example.grpc.order.v1";
option java_outer_classname = "OrderProto";

// The Order service definition
service OrderService {
    // 1. Unary RPC: Single request -> Single response
    rpc GetOrder (GetOrderRequest) returns (OrderResponse);

    // 2. Server Streaming RPC: Single request -> Stream of responses
    rpc StreamOrders (StreamOrdersRequest) returns (stream OrderResponse);

    // 3. Client Streaming RPC: Stream of requests -> Single summary response
    rpc RecordMetrics (stream MetricEvent) returns (MetricSummaryResponse);

    // 4. Bidirectional Streaming RPC: Stream of requests <-> Stream of responses
    rpc LiveOrderSync (stream OrderSyncMessage) returns (stream OrderSyncMessage);
}

message GetOrderRequest {
    string order_id = 1;
}

message StreamOrdersRequest {
    string customer_id = 1;
    int32 limit = 2;
}

message OrderResponse {
    string order_id = 1;
    string customer_id = 2;
    double total_amount = 3;
    OrderStatus status = 4;
    repeated OrderItem items = 5;
    int64 created_at_epoch_ms = 6;
}

message OrderItem {
    string product_id = 1;
    int32 quantity = 2;
    double unit_price = 3;
}

enum OrderStatus {
    ORDER_STATUS_UNSPECIFIED = 0; // Protobuf enum must start with 0
    ORDER_STATUS_PENDING = 1;
    ORDER_STATUS_CONFIRMED = 2;
    ORDER_STATUS_SHIPPED = 3;
    ORDER_STATUS_CANCELLED = 4;
}

message MetricEvent {
    string metric_name = 1;
    double value = 2;
    int64 timestamp = 3;
}

message MetricSummaryResponse {
    int32 total_points_received = 1;
    double average_value = 2;
}

message OrderSyncMessage {
    string sync_id = 1;
    string payload = 2;
}
```

#### Protobuf Backward & Forward Compatibility Rules
1. **Never change numeric tag IDs:** Field names can be renamed, but field numbers (e.g., `= 1;`) must NEVER change; they represent the field identity on the wire.
2. **Never delete a tag without reserving it:** If removing a field, mark its tag and name as `reserved 4, 7; reserved "old_field";` so future developers do not reuse the number and corrupt legacy decoders.
3. **Enum zero-value:** Always define the `0` tag in enums as `*_UNSPECIFIED` to safely handle uninitialized or unknown values.
4. **All fields are optional in proto3:** If a field is missing on the wire, it assumes its default value (`0`, `""`, `false`, empty list).

### 4. Implementing the gRPC Server in Spring Boot

The generated class `OrderServiceImplBase` is extended. Annotating the implementation with `@GrpcService` automatically registers the RPC methods on the Netty gRPC server port (default `9090`).

```java
package com.example.orderservice.service;

import com.example.grpc.order.v1.*;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;
import net.devh.boot.grpc.server.service.GrpcService;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.List;

@GrpcService
public class OrderGrpcServiceImpl extends OrderServiceGrpc.OrderServiceImplBase {

    private static final Logger log = LoggerFactory.getLogger(OrderGrpcServiceImpl.class);
    private final OrderRepository orderRepository;

    public OrderGrpcServiceImpl(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    // =========================================================================
    // 1. Unary RPC: Single request -> Single response
    // =========================================================================
    @Override
    public void getOrder(GetOrderRequest request, StreamObserver<OrderResponse> responseObserver) {
        String orderId = request.getOrderId();
        log.info("Fetching order: {}", orderId);

        if (orderId.isBlank()) {
            // Return gRPC Status with proper semantic error code
            responseObserver.onError(Status.INVALID_ARGUMENT
                    .withDescription("Order ID must not be blank")
                    .asRuntimeException());
            return;
        }

        orderRepository.findById(orderId).ifPresentOrElse(order -> {
            OrderResponse response = OrderResponse.newBuilder()
                    .setOrderId(order.id())
                    .setCustomerId(order.customerId())
                    .setTotalAmount(order.totalAmount())
                    .setStatus(OrderStatus.ORDER_STATUS_CONFIRMED)
                    .setCreatedAtEpochMs(order.createdAt().toEpochMilli())
                    .build();

            responseObserver.onNext(response);       // Send message
            responseObserver.onCompleted();          // Close stream successfully
        }, () -> {
            responseObserver.onError(Status.NOT_FOUND
                    .withDescription("Order not found with id: " + orderId)
                    .asRuntimeException());
        });
    }

    // =========================================================================
    // 2. Server Streaming RPC: One request -> Stream of multiple responses
    // =========================================================================
    @Override
    public void streamOrders(StreamOrdersRequest request, StreamObserver<OrderResponse> responseObserver) {
        String customerId = request.getCustomerId();
        int limit = request.getLimit() > 0 ? request.getLimit() : 50;

        List<Order> orders = orderRepository.findByCustomerId(customerId, limit);

        for (Order order : orders) {
            OrderResponse item = OrderResponse.newBuilder()
                    .setOrderId(order.id())
                    .setCustomerId(order.customerId())
                    .setTotalAmount(order.totalAmount())
                    .setStatus(OrderStatus.ORDER_STATUS_CONFIRMED)
                    .build();

            responseObserver.onNext(item); // Emit each item as it is retrieved
        }

        responseObserver.onCompleted(); // Complete the stream
    }

    // =========================================================================
    // 3. Client Streaming RPC: Stream of client messages -> One summary response
    // =========================================================================
    @Override
    public StreamObserver<MetricEvent> recordMetrics(StreamObserver<MetricSummaryResponse> responseObserver) {
        return new StreamObserver<MetricEvent>() {
            private int count = 0;
            private double sum = 0.0;

            @Override
            public void onNext(MetricEvent event) {
                count++;
                sum += event.getValue();
                log.debug("Received metric: {} = {}", event.getMetricName(), event.getValue());
            }

            @Override
            public void onError(Throwable t) {
                log.error("Client cancelled or failed stream", t);
            }

            @Override
            public void onCompleted() {
                double average = count == 0 ? 0.0 : sum / count;
                MetricSummaryResponse summary = MetricSummaryResponse.newBuilder()
                        .setTotalPointsReceived(count)
                        .setAverageValue(average)
                        .build();

                responseObserver.onNext(summary);
                responseObserver.onCompleted();
            }
        };
    }

    // =========================================================================
    // 4. Bidirectional Streaming RPC: Full duplex client <-> server stream
    // =========================================================================
    @Override
    public StreamObserver<OrderSyncMessage> liveOrderSync(StreamObserver<OrderSyncMessage> responseObserver) {
        return new StreamObserver<OrderSyncMessage>() {
            @Override
            public void onNext(OrderSyncMessage msg) {
                log.info("Received sync message: {}", msg.getSyncId());
                // Echo / process and reply in real-time
                OrderSyncMessage ack = OrderSyncMessage.newBuilder()
                        .setSyncId(msg.getSyncId())
                        .setPayload("ACK: " + msg.getPayload())
                        .build();
                responseObserver.onNext(ack);
            }

            @Override
            public void onError(Throwable t) {
                log.warn("Bidirectional stream terminated by peer: {}", t.getMessage());
            }

            @Override
            public void onCompleted() {
                responseObserver.onCompleted();
            }
        };
    }
}
```

### 5. Implementing the gRPC Client in Spring Boot

In client microservices, use `@GrpcClient("service-name")` to inject client stubs. gRPC provides 3 stub flavors:
1. **BlockingStub (`OrderServiceBlockingStub`):** Synchronous, blocking execution (ideal for standard Spring MVC services and Virtual Threads, Q241).
2. **Async Stub (`OrderServiceStub`):** Asynchronous, event-driven callbacks with `StreamObserver` (required for client/bidirectional streaming).
3. **FutureStub (`OrderServiceFutureStub`):** Returns Guava `ListenableFuture` (interoperable with `CompletableFuture`).

```java
package com.example.orderservice.client;

import com.example.grpc.order.v1.*;
import io.grpc.StatusRuntimeException;
import net.devh.boot.grpc.client.inject.GrpcClient;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.util.concurrent.TimeUnit;

@Service
public class OrderServiceClient {

    private static final Logger log = LoggerFactory.getLogger(OrderServiceClient.class);

    // Injects client stub bound to config "order-service" in application.yml
    @GrpcClient("order-service")
    private OrderServiceGrpc.OrderServiceBlockingStub blockingStub;

    public OrderResponse fetchOrderWithDeadline(String orderId) {
        try {
            // ALWAYS set a deadline on client calls to prevent thread starvation
            return blockingStub
                    .withDeadlineAfter(2, TimeUnit.SECONDS)
                    .getOrder(GetOrderRequest.newBuilder()
                            .setOrderId(orderId)
                            .build());
        } catch (StatusRuntimeException e) {
            log.error("gRPC invocation failed. Status: {}, Description: {}",
                    e.getStatus().getCode(), e.getStatus().getDescription());
            throw handleGrpcException(e);
        }
    }

    private RuntimeException handleGrpcException(StatusRuntimeException e) {
        return switch (e.getStatus().getCode()) {
            case NOT_FOUND -> new ResourceNotFoundException(e.getStatus().getDescription());
            case DEADLINE_EXCEEDED -> new GatewayTimeoutException("Downstream gRPC service timed out");
            case INVALID_ARGUMENT -> new BadRequestException(e.getStatus().getDescription());
            case UNAUTHENTICATED, PERMISSION_DENIED -> new AccessDeniedException("Access rejected by upstream");
            default -> new InternalServiceException("Upstream gRPC service failed: " + e.getMessage());
        };
    }
}
```

### 6. Interceptors, Context & Distributed Tracing

Similar to Spring MVC filters (Q207), gRPC uses **Interceptors** (`ServerInterceptor` and `ClientInterceptor`) for cross-cutting concerns: authentication, authorization, MDC logging, and distributed tracing.

#### Context & Tracing Propagation (`ServerInterceptor`)

```java
package com.example.orderservice.interceptor;

import io.grpc.*;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;

@Component
public class TraceAndAuthServerInterceptor implements ServerInterceptor {

    public static final Metadata.Key<String> TRACE_ID_KEY =
            Metadata.Key.of("X-Trace-Id", Metadata.ASCII_STRING_MARSHALLER);
    public static final Metadata.Key<String> AUTH_HEADER_KEY =
            Metadata.Key.of("Authorization", Metadata.ASCII_STRING_MARSHALLER);

    public static final Context.Key<String> USER_ID_CTX_KEY = Context.key("USER_ID");

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,
            ServerCallHandler<ReqT, RespT> next) {

        // 1. Extract distributed traceId and inject into SLF4J MDC (Q214/Q244)
        String traceId = headers.get(TRACE_ID_KEY);
        if (traceId != null) {
            MDC.put("traceId", traceId);
        }

        // 2. Extract Bearer Token and validate
        String authHeader = headers.get(AUTH_HEADER_KEY);
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            call.close(Status.UNAUTHENTICATED.withDescription("Missing or invalid Bearer token"), headers);
            return new ServerCall.Listener<>() {}; // No-op listener
        }

        String userId = validateAndExtractUserId(authHeader.substring(7));

        // 3. Bind authenticated identity into gRPC Context
        Context context = Context.current().withValue(USER_ID_CTX_KEY, userId);

        try {
            return Contexts.interceptCall(context, call, headers, next);
        } finally {
            MDC.remove("traceId");
        }
    }

    private String validateAndExtractUserId(String token) {
        // Validate JWT token against IdP or public keys (Q249)
        return "user_12345";
    }
}
```

### 7. Deadlines, Timeouts & Cancellation Propagation

One of gRPC's biggest advantages over HTTP/REST is **first-class Deadlines with recursive cancellation propagation**:
- A **timeout** specifies how long a caller waits for a response (e.g., 2 seconds).
- A **deadline** is an absolute point in time (e.g., `2026-10-15 10:30:02.500 UTC`).
- When Service A calls Service B with a 3-second deadline, and Service B calls Service C, the remaining deadline propagates downstream via HTTP/2 headers (`grpc-timeout`).
- If Service A aborts or the deadline expires, **all downstream servers detect cancellation and stop useless work immediately**.

#### Handling Server-Side Cancellation

```java
@Override
public void processHeavyReport(ReportRequest req, StreamObserver<ReportResponse> responseObserver) {
    for (int step = 0; step < 100; step++) {
        // Periodically check if client disconnected or deadline expired
        if (Context.current().isCancelled()) {
            log.warn("Client cancelled request or deadline exceeded. Aborting DB work.");
            return; // Exit immediately, saving DB and CPU resources
        }
        performExpensiveCalculationStep(step);
    }

    responseObserver.onNext(ReportResponse.newBuilder().setStatus("SUCCESS").build());
    responseObserver.onCompleted();
}
```

### 8. Error Handling & The Rich Error Model

Standard gRPC returns a 16-value `Status` code (`OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, etc.).
For production systems, Google designed the **Rich Error Model** (`com.google.rpc.Status`), allowing services to attach structured Protobuf messages (e.g., field-level validation errors, retry delays) directly inside error responses.

#### Spring `@GrpcAdvice` Exception Handler

```java
package com.example.orderservice.exception;

import com.google.protobuf.Any;
import com.google.rpc.BadRequest;
import com.google.rpc.Code;
import io.grpc.StatusRuntimeException;
import io.grpc.protobuf.StatusProto;
import net.devh.boot.grpc.server.advice.GrpcAdvice;
import net.devh.boot.grpc.server.advice.GrpcExceptionHandler;

@GrpcAdvice
public class GlobalGrpcExceptionHandler {

    @GrpcExceptionHandler(IllegalArgumentException.class)
    public StatusRuntimeException handleIllegalArgument(IllegalArgumentException ex) {
        return io.grpc.Status.INVALID_ARGUMENT
                .withDescription(ex.getMessage())
                .withCause(ex)
                .asRuntimeException();
    }

    @GrpcExceptionHandler(OrderValidationException.class)
    public StatusRuntimeException handleValidation(OrderValidationException ex) {
        // Construct Rich Error Model payload with detailed field violations
        BadRequest.FieldViolation violation = BadRequest.FieldViolation.newBuilder()
                .setField(ex.getField())
                .setDescription(ex.getMessage())
                .build();

        BadRequest badRequest = BadRequest.newBuilder()
                .addFieldViolations(violation)
                .build();

        com.google.rpc.Status status = com.google.rpc.Status.newBuilder()
                .setCode(Code.INVALID_ARGUMENT_VALUE)
                .setMessage("Invalid order payload")
                .addDetails(Any.pack(badRequest))
                .build();

        return StatusProto.toStatusRuntimeException(status);
    }
}
```

### 9. Load Balancing & Network Architecture in Kubernetes

A critical architectural gotcha in gRPC is **Load Balancing over HTTP/2**:

```
[ Traditional L4 / K8s ClusterIP LB ]
                 │
                 │ Single Persistent TCP Connection (HTTP/2)
                 ▼
       ┌──────────────────┐
       │   Pod 1 (100%)   │   <-- All RPC streams stuck on Pod 1!
       └──────────────────┘
       ┌──────────────────┐
       │   Pod 2 (0%)     │   <-- Completely starved!
       └──────────────────┘
```

Because HTTP/2 reuses a single long-lived TCP connection for all multiplexed requests, traditional Layer 4 load balancers (like default Kubernetes `ClusterIP` services or AWS classic ELBs) balance the initial TCP connection, **not individual RPC calls**. As a result, one pod receives 100% of traffic while other pods remain idle.

#### Production Solutions:

| Strategy | Architecture | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **1. Client-Side Load Balancing** | Use K8s **Headless Service** (`clusterIP: None`); Client resolves all pod IPs via DNS and balances streams (`round_robin`) | No extra hop, ultra-low latency, zero proxy overhead | Client library complexity, must re-resolve on pod autoscaling |
| **2. L7 Proxy / Service Mesh** | **Envoy / Istio / Linkerd** sits between services; terminates HTTP/2 and distributes individual streams across upstream pods | Transparent to application code, advanced canary/circuit-breaking | Extra network hop (~0.5–1ms latency), proxy memory/CPU cost |
| **3. gRPC Lookaside LB (xDS)** | Client queries centralized control plane (like Envoy xDS) for routing rules | Dynamic, robust, no sidecar proxy hop | Complex control plane infrastructure setup |

In Spring Boot, client-side load balancing is configured with:
```yaml
grpc:
  client:
    order-service:
      address: 'dns:///order-service-headless:9090'
      default-load-balancing-policy: round_robin
```

### 10. Security & Performance Guards

| Concern | Production Best Practice / Mitigation |
| :--- | :--- |
| **Transport Security (mTLS)** | Enforce mutual TLS (`negotiationType: TLS`) for zero-trust service mesh communication; verify client certificates |
| **Thread Starvation** | Configure dedicated gRPC executor pools; in Spring Boot 3.2+ with Java 21, enable **Virtual Threads** (`spring.threads.virtual.enabled=true`, Q241) to handle thousands of concurrent blocking RPCs |
| **Deadlines & Timeouts** | **Always** configure `.withDeadlineAfter()` on every client stub call; never leave gRPC calls unbounded |
| **Cancellation Checks** | Inspect `Context.current().isCancelled()` in long loops or before expensive DB operations to release server resources immediately |
| **OOM via Huge Payloads** | gRPC default message limit is 4MB. Set `max-inbound-message-size` explicitly to reject oversized payloads; use **Streaming** for large data |
| **KeepAlive & Broken Pipes** | Enable `keepAliveTime` (30s) and `keepAliveTimeout` (5s) with `keepAliveWithoutCalls` so dead connections (NAT timeouts) are pruned promptly |
| **Circuit Breaking & Retries** | Integrate Resilience4j (Q213) around client stub invocations or leverage gRPC's native Service Config retry policy |

---

### 11. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **L4 Load Balancing (K8s ClusterIP)** | 1 pod pegged at 100% CPU while 9 pods sit at 0% | Use Kubernetes Headless Service (`clusterIP: None`) with client-side round-robin, or an L7 proxy (Envoy/Istio) |
| **Missing Deadlines on Client Stubs** | Thread pool exhaustion, cascading service lockups (Q245) | Always chain `.withDeadlineAfter(duration, unit)` on the stub before calling RPCs |
| **Reusing Tag IDs in `.proto`** | Silent data corruption or deserialization crashes across microservice versions | Never reuse tag numbers; mark removed tags as `reserved <number>, "<name>";` |
| **Failing to Call `onCompleted()` or `onError()`** | Client hangs waiting indefinitely; connection memory leaks | Always terminate every `StreamObserver` invocation in a `try-catch-finally` block |
| **Calling `onNext()` concurrently** | `IllegalStateException: Already inside onNext` | gRPC `StreamObserver` is **not thread-safe**; synchronize calls or use `ConcurrentLinkedQueue` |
| **Using `null` fields in Protobuf** | `NullPointerException` during message construction | Protobuf 3 does not support `null`; check for nulls or use `com.google.protobuf.StringValue` wrappers |
| **Exposing gRPC directly to Browsers** | Browser JavaScript throws CORS or protocol errors | Browsers cannot frame raw HTTP/2 trailer packets; use **gRPC-Web** with an Envoy proxy or Spring REST gateway |

---

### Summary

- **gRPC** leverages **HTTP/2 multiplexing** and **Protocol Buffers binary serialization** to deliver high-throughput, low-latency communication ideal for **internal microservices** and high-scale backends.
- In contrast to **REST** (public APIs, JSON, caching, Q216) and **GraphQL** (flexible client queries, BFFs, Q254), **gRPC provides compile-time contract enforcement**, cross-language code generation, and 4 streaming models (unary, server, client, bidirectional).
- In Spring Boot, implement services with `@GrpcService` extending generated `*ImplBase`, and inject client stubs with `@GrpcClient`.
- Always set **Deadlines** (`withDeadlineAfter`), implement **Cancellation checks** (`Context.current().isCancelled()`), manage cross-cutting concerns via `ServerInterceptor`/`ClientInterceptor`, and handle errors with `@GrpcAdvice`.
- To prevent traffic sticking to a single pod over persistent HTTP/2 sockets, implement **L7 load balancing** via Kubernetes Headless Services with client-side round-robin or an Envoy/Istio service mesh.

## 256. How does a service mesh (Istio/Linkerd) work with Spring Boot microservices? Explain sidecars, mTLS, traffic management, and observability.

An **API Gateway** (Q239) handles north-south traffic (client to cluster), while a **service mesh** handles east-west traffic (service to service inside the cluster). A mesh injects a **sidecar proxy** (Envoy for Istio, linkerd-proxy for Linkerd) next to every Spring Boot pod to transparently provide **mTLS encryption**, **load balancing** (fixes gRPC HTTP/2 pinning in Q255), **retries/timeouts/circuit breaking**, **canary traffic splitting**, and **uniform telemetry** (metrics/traces) without changing application code. This moves resilience and security out of libraries (Resilience4j, Q213) into infrastructure.

---

### 1. Service Mesh Architecture Basics

| Concept | Meaning | Example |
| :--- | :--- | :--- |
| **Data plane** | Sidecar proxies intercepting all pod traffic | Envoy containers in every pod |
| **Control plane** | Central config/policy distribution | Istio `istiod`, Linkerd `destination` + `identity` |
| **Sidecar injection** | Auto-add proxy via K8s mutating webhook | `kubectl label ns default istio-injection=enabled` |
| **mTLS (zero-trust)** | Every hop encrypted + identity-verified via SPIFFE certs | No plaintext inside cluster |
| **Traffic policy** | Declarative routing/resilience rules | `VirtualService`, `DestinationRule` |

```
Without mesh:  order-pod -> (direct TCP) -> payment-pod (app handles TLS, retry, LB)
With mesh:     order-pod -> localhost Envoy -> mTLS -> payment Envoy -> localhost payment-pod
```

The Spring Boot app still calls `http://payment-service:8080/api/pay` - the sidecar transparently upgrades to mTLS, load-balances, retries, and emits telemetry.

---

### 2. Istio vs Linkerd - Comparison

| Aspect | **Istio (Envoy)** | **Linkerd** |
| :--- | :--- | :--- |
| **Proxy** | Envoy (feature-rich, higher memory ~50-100MB per pod) | linkerd-proxy (Rust, ultra-light ~10MB, lower latency) |
| **Features** | Full L7 routing, Wasm plugins, rich authz, gateway + mesh unified | Focused, simple, opinionated; fewer knobs |
| **mTLS** | STRICT by default with `PeerAuthentication`; auto cert rotation | Always-on mTLS by default, zero config |
| **Traffic splitting** | `VirtualService` weight/mirror/fault-injection | `ServiceProfile` + Flagger/Argo Rollouts for progressive delivery |
| **Complexity** | Powerful but operationally heavy (istiod, CRDs) | Easiest to install/operate; great for small teams |
| **Best for** | Large platforms needing fine-grained policy | Teams wanting mTLS + observability with minimal overhead |

**Rule of thumb:** choose **Linkerd** if you want "mTLS + golden metrics with least toil". Choose **Istio** if you need advanced L7 policy, multi-cluster, or Wasm extensibility.

---

### 3. mTLS and Authorization in Practice

```yaml
# Istio: enforce STRICT mTLS mesh-wide (zero-trust, Q231/Q249)
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
---
# Allow only order-service (with valid identity) to call payment-service
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: payment-allowlist
  namespace: payments
spec:
  selector:
    matchLabels: { app: payment-service }
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/orders/sa/order-service"]
      to:
        - operation: { methods: ["POST"], paths: ["/api/pay*"] }
```

No code change in Spring Boot. The mesh issues SPIFFE identities (`spiffe://cluster.local/ns/orders/sa/order-service`), rotates certs automatically (no Vault/K8s Secret handling in app, Q243), and denies plaintext.

```yaml
# Spring Boot does not need TLS config - plain HTTP to localhost sidecar is enough
server:
  port: 8080
```

For defense-in-depth, keep Spring Security OAuth2/JWT authz (Q207/Q249) at the app layer - mesh proves *which service* called, JWT proves *which user* called.

### 4. Traffic Management - Canary, Retries, Circuit Breaking

```yaml
# Istio VirtualService: 90% stable, 10% canary (progressive delivery, Q226/Q250)
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: order-service, namespace: orders }
spec:
  hosts: ["order-service"]
  http:
    - route:
        - destination: { host: order-service, subset: stable }
          weight: 90
        - destination: { host: order-service, subset: canary }
          weight: 10
      retries:
        attempts: 3
        perTryTimeout: 2s
        retryOn: 5xx,reset,connect-failure
      timeout: 10s
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata: { name: order-service, namespace: orders }
spec:
  host: order-service
  subsets:
    - name: stable
      labels: { version: v1 }
    - name: canary
      labels: { version: v2 }
  trafficPolicy:
    loadBalancer: { simple: LEAST_REQUEST }  # fixes gRPC pinning (Q255)
    outlierDetection:                        # mesh-level circuit breaker
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
    connectionPool:
      tcp: { maxConnections: 100 }
      http: { h2UpgradePolicy: UPGRADE, maxRequestsPerConnection: 1000 }
```

This replaces scattered Resilience4j configs (Q213) with one declarative policy. Pair with Flagger/Argo Rollouts for automated canary analysis (promote on SLOs, Q230).

### 5. Observability Without Code Changes

Sidecars auto-emit **RED metrics** (Rate/Errors/Duration), **distributed traces** (W3C `traceparent` propagation, Q244), and access logs for every hop:

| Signal | What you get for free | Tool |
| :--- | :--- | :--- |
| **Metrics** | `istio_requests_total`, `istio_request_duration_milliseconds` per src/dst | Prometheus + Grafana (Q230) |
| **Traces** | Spans per hop, linked by traceId | Jaeger/Tempo (Q244) |
| **Topology** | Service graph with mTLS status + error rates | Kiali (Istio) / Linkerd viz |
| **Logs** | Envoy access logs with traceId, response flags (`UF`, `URX`) | Loki/ELK (Q214) |

Spring Boot only needs to **propagate trace headers** (`traceparent`, `b3`) on `RestTemplate`/`WebClient`/Kafka headers (Q244) - the mesh does the rest. Keep Micrometer (Q214/Q230) for business/domain metrics; let the mesh own network telemetry.

```java
// Propagate tracing headers on outbound calls - mesh picks them up
@Bean
public RestTemplate restTemplate(ObservationRegistry registry) {
    return new RestTemplateBuilder()
        .observationRegistry(registry)  // Micrometer Tracing propagates W3C headers (Q244)
        .build();
}
```

### 6. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Start with mTLS STRICT + observability** | Biggest security win with least risk; add traffic policies incrementally |
| **Keep app-level timeouts shorter than mesh** | Spring `RestTemplate` 2s timeout inside mesh 10s timeout avoids double-retry storms (Q213) |
| **Do not double-retry** | If mesh retries 3x, disable or reduce Resilience4j retries on same call to avoid amplification |
| **Right-size sidecars** | Set CPU/memory requests/limits for Envoy; Linkerd is lighter if resources are tight |
| **Use headless-friendly LB for gRPC** | Mesh L7 LB (`LEAST_REQUEST`/`round_robin` on streams) solves Q255 pinning |
| **GitOps your mesh config** | Store `VirtualService`/`AuthorizationPolicy` in GitOps repo (Q250); review like code |
| **Progressive rollout of mesh itself** | Inject per-namespace (`istio-injection=enabled` on one ns first); verify before mesh-wide STRICT |

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **mTLS conflict with app TLS** | `SSL handshake` / `connection reset` between pods | Let mesh own transport TLS; app serves plaintext to localhost sidecar, or configure `DestinationRule` TLS mode correctly |
| **Double retries (app + mesh)** | 9x upstream load on failure (3x3) | Retry in one layer only; prefer mesh for network retries, app for business fallback (Q245) |
| **Head-of-line blocking assumed fixed** | gRPC still pinned via ClusterIP | Use mesh L7 LB or headless service (Q255); verify with Kiali/topology |
| **High sidecar overhead** | Pod OOM / latency +2-5ms p99 | Tune Envoy concurrency, access-log sampling; evaluate Linkerd for lightweight needs |
| **AuthorizationPolicy too broad** | Lateral movement after one compromise | Least-privilege per workload (`principals` + `paths`); deny-all by default, allow-list explicitly |
| **Ignoring ambient/ztunnel mode** | Unexpected cost for small clusters | Consider Istio ambient (node-level proxy) to cut per-pod sidecar cost where supported |
| **No trace propagation in app** | Broken traces across hops | Propagate W3C headers in WebClient/Kafka (Q244); test with Tempo/Jaeger |
| **Mesh as excuse to skip app resilience** | No fallback when mesh ejects all endpoints | Keep bulkhead/fallback in code (Q245) - mesh handles network, app handles degradation |

### Summary

- A **service mesh** moves east-west concerns (mTLS, L7 LB, retries, canary, telemetry) from Spring Boot libraries into sidecar infrastructure, complementing the API Gateway for north-south (Q239).
- **Linkerd** is simplest for automatic mTLS + golden metrics; **Istio/Envoy** is most powerful for fine-grained routing, authz, and multi-cluster.
- Enforce **STRICT mTLS + AuthorizationPolicy** (service identity) while keeping **JWT/OAuth2** (user identity) in Spring Security (Q249) - two layers, two identities.
- Manage traffic declaratively (`VirtualService`/`DestinationRule`): weighted canary, timeouts, retries, outlier ejection; avoid double-retries with Resilience4j (Q213).
- Keep apps propagating **W3C trace headers** (Q244) and defining **business fallbacks** (Q245); let the mesh own network telemetry and GitOps-manage all mesh CRs (Q250).

## 257. How do you implement distributed locking in Spring Boot microservices? Explain Redis (Redisson, Redlock), ShedLock for scheduled tasks, database locks vs distributed locks, fencing tokens, lease renewal (watchdogs), and pitfalls.

In a single JVM, standard Java concurrency primitives (`synchronized`, `ReentrantLock`, `Semaphore`) synchronize threads sharing the same heap memory. However, in modern cloud-native architectures where Spring Boot applications scale horizontally across multiple pods or containers (Q215/Q245), local in-memory locks cannot prevent race conditions across nodes. When multiple instances concurrently attempt critical actions—such as processing the same payment, reserving limited flash-sale inventory, running scheduled batch cron jobs, or mutating shared aggregates—a **distributed lock** is required to coordinate mutual exclusion across the cluster.

---

### 1. Concurrency Control Spectrum — When to Use What

Before reaching for a distributed lock, evaluate simpler concurrency control mechanisms. Distributed locks add network latency, operational overhead, and failure modes:

| Mechanism | Scope | Latency | Contention Handling | Fault Tolerance | Best For |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **In-Memory Lock** (`ReentrantLock`) | Single JVM instance | < 1 µs | Thread blocking / queuing | Fails if JVM crashes (in-memory) | Singleton workers, local caching, thread-safe memory state |
| **DB Optimistic Lock** (`@Version`) | Multi-instance (shared DB) | Low (DB roundtrip on write) | High contention causes rollback exceptions (`OptimisticLockException`) | Relies on DB ACID guarantees | Low-to-medium contention updates (user profile updates, order edits) |
| **DB Pessimistic Lock** (`SELECT ... FOR UPDATE`) | Multi-instance (shared DB) | Medium (holds open DB connection & row lock) | Threads block on DB row; risk of DB connection pool exhaustion | Relies on DB ACID; lock released on commit/rollback | High-contention financial ledger updates, bank account balance changes (Q208) |
| **ShedLock** (DB / Redis table) | Clustered background jobs | Very Low (single check at job start) | Skips execution if lock cannot be acquired | Node crash released by `lockAtMostFor` TTL | Clustered `@Scheduled` cron jobs, periodic report generation (Q211) |
| **Distributed Lock** (Redis / Redisson) | Distributed cluster | ~1–3 ms (Redis RTT) | Fast in-memory spin/pub-sub wait | Master-replica failover hazard; Watchdog lease renewal | Flash-sale inventory reservation, distributed rate limiting, external API coordination |
| **Consensus Lock** (ZooKeeper / etcd) | Strongly consistent cluster | ~5–15 ms (Raft/ZAB consensus) | Ephemeral nodes + heartbeat watches | Strong consistency (CP in CAP, Q240), automatic cleanup on session drop | Distributed leader election, cluster metadata coordination, critical single-writer pipelines |

**Decision Rule:**
1. If the resource lives in a relational database, prefer **Optimistic Locking (`@Version`)** for low contention or **Pessimistic Locking (`SELECT FOR UPDATE`)** for high contention—it avoids introducing an external infrastructure dependency.
2. If preventing duplicate execution of clustered background tasks (`@Scheduled`), use **ShedLock**.
3. If coordinating high-throughput actions across microservices that do NOT share a single database, use **Redis with Redisson**.
4. If absolute safety is required where a split-brain or network pause could cause catastrophic data corruption, pair distributed locks with **Fencing Tokens** or use a CP consensus store (**etcd / ZooKeeper**).

### 2. Clustered Scheduled Jobs with ShedLock

In a Kubernetes deployment with multiple pod replicas, standard Spring Boot `@Scheduled` methods (Q211) execute simultaneously on **every single replica**. **ShedLock** ensures that a scheduled task executes on **at most one node at a time**.

#### How ShedLock Works
ShedLock creates a lightweight lock record in an external datastore (PostgreSQL, MySQL, Mongo, Redis). It executes an atomic `UPDATE ... WHERE locked_until <= now()` or `INSERT ... ON CONFLICT`:
- `lockAtMostFor`: Guarantees the lock is automatically released if the executing node crashes or hangs (deadlock prevention).
- `lockAtLeastFor`: Guarantees the lock is held for at least a minimum duration, preventing other nodes with slight clock skew from executing the job if the current node finishes in a few milliseconds.

#### Database Schema (PostgreSQL / MySQL)

```sql
CREATE TABLE shedlock (
    name VARCHAR(64) NOT NULL PRIMARY KEY,
    lock_until TIMESTAMP NOT NULL,
    locked_at TIMESTAMP NOT NULL,
    locked_by VARCHAR(255) NOT NULL
);
```

### 3. Redis Distributed Locks with Redisson

#### Why Naive Redis Locking Fails
A common junior anti-pattern is implementing locks with raw Spring Data Redis:
```java
// ANTI-PATTERN: Naive Redis lock
Boolean acquired = redisTemplate.opsForValue().setIfAbsent("lock:order:123", uuid, Duration.ofSeconds(10));
try {
    // Business logic...
} finally {
    redisTemplate.delete("lock:order:123"); // BUG: Deletes another thread's lock if TTL expired!
}
```
**Why this breaks in production:**
1. **Premature Expiration:** If the business logic takes 12s (due to slow DB query, thread starvation, or GC pause), the 10s TTL expires. Redis frees the key. Another node acquires the lock. Both nodes now execute concurrently!
2. **Accidental Unlock:** When the first node finally finishes, its `finally` block deletes the lock currently held by the second node!
3. **No Reentrancy:** If a thread holding `lock:order:123` calls another internal method that requests the same lock, it deadlocks itself.

#### How Redisson Solves This
**Redisson** is the de facto Redis client for distributed locks in Java:
- **Atomic Lua Scripts:** Uses Lua scripts executed atomically inside Redis to check, set, and increment lock counters.
- **Reentrant Locks:** Stores a Redis `Hash` where the field is `UUID:threadId` and the value is the reentrancy counter.
- **The Watchdog (Automatic Lease Renewal):** Solves the premature expiration problem.

```
+---------------------------------------------------------------------------------------+
|                               Redisson Watchdog Mechanism                             |
|                                                                                       |
|  Thread A                  Redisson Client                     Redis Server           |
|     |                             |                                  |                |
|     |--- lock.tryLock(10s) ------>|                                  |                |
|     |                             |--- Lua (SET lock, TTL=30s) ----->|  Lock Held     |
|     |                             |<-- Success ----------------------|  (TTL: 30s)    |
|     |                             |                                  |                |
|     |                             |-- [Watchdog timer spawned]       |                |
|     |   (Executing long task...)  |   (Fires every 10s = TTL / 3)    |                |
|     |                             |                                  |                |
|     |                             |--- Lua (EXPIRE lock, 30s) ------>|  Renewed       |
|     |                             |<-- Success ----------------------|  (TTL: 30s)    |
|     |                             |                                  |                |
|     |--- lock.unlock() ---------->|                                  |                |
|     |                             |--- [Cancel Watchdog timer]       |                |
|     |                             |--- Lua (DEL / Decr lock) ------->|  Lock Released |
|     |<-- Unlocked ----------------|<-- Success ----------------------|                |
+---------------------------------------------------------------------------------------+
```

#### The Watchdog Rules
1. If you acquire a lock **without specifying `leaseTime`** (e.g., `lock.lock()` or `lock.tryLock(5, TimeUnit.SECONDS)`), Redisson initiates the **Watchdog**.
2. The watchdog sets the initial TTL to `lockWatchdogTimeout` (default: 30,000 ms / 30 seconds).
3. Every 10 seconds (`timeout / 3`), a background timer sends a Lua script to Redis renewing the lock's expiration back to 30 seconds.
4. **CRITICAL CAVEAT:** If you call `tryLock(waitTime, leaseTime, unit)` with an explicit `leaseTime > 0` (e.g., `lock.tryLock(5, 10, TimeUnit.SECONDS)`), **the watchdog is DISABLED**. If business logic exceeds 10s, Redisson will NOT renew it, leading to concurrency leaks!

#### Production Redisson Implementation

```xml
<!-- Maven Dependency -->
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.30.0</version>
</dependency>
```

```java
@Configuration
public class RedissonConfig {

    @Value("${spring.data.redis.host:localhost}")
    private String redisHost;

    @Value("${spring.data.redis.port:6379}")
    private int redisPort;

    @Bean
    public RedissonClient redissonClient() {
        Config config = new Config();
        config.useSingleServer()
            .setAddress("redis://" + redisHost + ":" + redisPort)
            .setConnectionPoolSize(64)
            .setConnectionMinimumIdleSize(16)
            .setLockWatchdogTimeout(30_000); // 30s watchdog renewal
        return Redisson.create(config);
    }
}
```

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class InventoryReservationService {

    private final RedissonClient redissonClient;
    private final InventoryRepository inventoryRepo;

    public boolean reserveStock(String skuId, int quantity) {
        String lockKey = "lock:inventory:" + skuId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // waitTime: 3 seconds to acquire lock
            // Omit leaseTime so the Watchdog automatically extends lease during slow execution
            boolean acquired = lock.tryLock(3, TimeUnit.SECONDS);
            if (!acquired) {
                log.warn("Could not acquire lock for SKU: {}. High contention.", skuId);
                throw new InventoryLockAcquisitionException("System busy, please retry.");
            }

            // Critical Section
            return executeReservation(skuId, quantity);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new InventoryException("Thread interrupted while waiting for lock", e);
        } finally {
            // CRITICAL: Only release the lock if currently held by THIS thread!
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.debug("Lock released for SKU: {}", skuId);
            }
        }
    }

    private boolean executeReservation(String skuId, int quantity) {
        Inventory inventory = inventoryRepo.findBySkuId(skuId)
            .orElseThrow(() -> new EntityNotFoundException("SKU not found"));
        if (inventory.getAvailableStock() < quantity) {
            return false;
        }
        inventory.setAvailableStock(inventory.getAvailableStock() - quantity);
        inventoryRepo.save(inventory);
        return true;
    }
}
```

### 4. The Spring `@Transactional` Boundary Trap

A frequent, severe bug in Spring microservices occurs when combining **Distributed Locks** with `@Transactional`:

```java
// BUGGY IMPLEMENTATION - RACE CONDITION
@Service
public class OrderService {

    @Transactional // Transaction starts BEFORE lock acquired!
    public void processOrder(String orderId) {
        RLock lock = redissonClient.getLock("order:" + orderId);
        lock.lock();
        try {
            // 1. Read Order from DB
            // 2. Modify Order state
            // 3. Save Order to DB
        } finally {
            lock.unlock(); // Lock released BEFORE transaction commits!
        }
        // Spring proxy commits DB transaction HERE!
    }
}
```

#### Why This Fails:
1. **Thread 1** acquires the lock, mutates the entity, and calls `lock.unlock()`.
2. The distributed lock is now free in Redis.
3. **Thread 2** immediately acquires the lock, queries the database, and **reads the old uncommitted state** because Thread 1's database transaction has not finished committing to the database!
4. Thread 1 commits its transaction.
5. Thread 2 overwrites Thread 1's changes (Lost Update anomaly).

#### Correct Pattern: Lock Wraps Transaction
The distributed lock must **completely surround** the database transaction:

```
[Lock Acquired] ---> [Begin DB Transaction] ---> [Execute & Commit DB] ---> [Lock Released]
```

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final RedissonClient redissonClient;
    private final TransactionTemplate transactionTemplate; // Programmatic transaction boundary
    private final OrderRepository orderRepository;

    public void processOrder(String orderId) {
        String lockKey = "order:lock:" + orderId;
        RLock lock = redissonClient.getLock(lockKey);
        try {
            if (!lock.tryLock(5, TimeUnit.SECONDS)) {
                throw new OrderConcurrencyException("Could not obtain lock for order: " + orderId);
            }
            try {
                // Execute business logic INSIDE transaction, fully inside lock boundary
                transactionTemplate.execute(status -> {
                    Order order = orderRepository.findById(orderId).orElseThrow();
                    order.markAsPaid();
                    return orderRepository.save(order);
                }); // DB commits before finally block executes!
            } finally {
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock(); // Lock is released ONLY AFTER DB transaction has committed
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new OrderConcurrencyException("Interrupted while locking", e);
        }
    }
}
```

### 5. Distributed Lock Safety — Fencing Tokens & Kleppmann's Critique

Can a distributed lock guarantee **100% mutual exclusion** in an asynchronous network? The answer from distributed systems theory is **no**, unless paired with **fencing tokens**.

#### The Pause Problem (Stop-The-World GC / Network Partition)
Martin Kleppmann (author of *Designing Data-Intensive Applications*) pointed out the fundamental vulnerability of time-based distributed locks:

```
Client 1                        Redis                      Storage (DB / S3)
   |                              |                                |
   |--- Acquire lock (10s) ------>|                                |
   |<-- Lock granted -------------|                                |
   |                                                               |
   | === JVM Stop-The-World (STW) GC pause for 15 seconds ===      |
   |                                                               |
   |                    (Lock expires at 10s)                      |
   |                              |                                |
   |       Client 2               |                                |
   |          |-- Acquire lock -->|                                |
   |          |<- Lock granted ---|                                |
   |          |--- Write data (State = 2) ------------------------>| (Success)
   |                                                               |
   | === Client 1 GC finishes, wakes up unaware of time jump ===   |
   |--- Write data (State = 1) ----------------------------------->| (DATA CORRUPTED!
                                                                      Overwrote Client 2)
```

No watchdog or TTL can prevent this if the client JVM itself pauses (STW GC, hypervisor freeze, OS page fault, or network delay).

#### The Solution: Fencing Tokens
A **fencing token** is a monotonically increasing counter (1, 2, 3...) issued by the lock service with every successful lock grant. The target storage system checks the token before accepting any write:

```sql
-- Storage enforces monotonic fencing token
UPDATE accounts
SET balance = balance - 100,
    last_fencing_token = 34
WHERE account_id = 'ACC_1'
  AND last_fencing_token < 34; -- Rejects if a higher token (e.g. 35) was already applied!
```

```
Client 1 (Token = 34)                         Client 2 (Token = 35)               Storage (DB)
   |                                                    |                              |
   |-- [Paused by GC]                                   |                              |
   |                                                    |-- Write with Token 35 ------>| Accepted (DB token=35)
   |-- [Wakes up]                                       |                              |
   |-- Write with Token 34 ----------------------------------------------------------->| REJECTED! (34 < 35)
```

#### Redis Master-Replica Asynchronous Failover Risk
Standard Redis Sentinel / Redis Cluster uses **asynchronous replication**:
1. Client A acquires a lock on Redis Master.
2. The master writes the key, sends success to Client A, but crashes *before* the key is replicated to the Redis Replica.
3. Sentinel promotes the replica to new Master.
4. Client B requests the same lock. The new master does not have the key and grants the lock to Client B!
5. Client A and Client B now concurrently hold the lock.

**When to accept this risk:** For performance-oriented operations (rate limiting, non-financial deduplication, caching coordination), Redis locks are fast and pragmatic. For financial ledgers or medical safety systems, use **PostgreSQL row locks** (`SELECT FOR UPDATE`), **Consensus locks** (ZooKeeper/etcd), or **Fencing tokens**.

---

### 6. Redlock Algorithm — Quorum-Based Locking

To mitigate the single-master failover vulnerability without relying on heavy consensus engines, Salvatore Sanfilippo created the **Redlock** algorithm.

#### How Redlock Works:
1. Deploy **$N$ independent Redis master instances** (typically 5) with no replication or clustering between them.
2. The client fetches the current time in milliseconds ($T_1$).
3. The client tries to acquire the lock in all $N$ instances sequentially using the same key and random value, with a timeout much smaller than the lock TTL (e.g., 50 ms timeout for a 10s TTL).
4. The client considers the lock acquired if and only if:
   - It acquired the lock in a **majority** of nodes ($\ge rac{N}{2} + 1$, e.g., 3 out of 5).
   - The total elapsed time ($T_2 - T_1$) is strictly less than the lock validity time.
5. If the lock was acquired, the actual validity time remaining is:
   $$\text{Validity Time} = \text{TTL} - (T_2 - T_1) - \text{Clock Drift}$$
6. If the client fails to acquire the lock (could not get $\ge 3$ nodes or validity time expired), it **unlocks all instances** (even those it thought it did not acquire).

In Redisson, Redlock is available via `RedissonRedLock`, though modern consensus stores (etcd/Consul) or single-master Redis with fencing tokens are generally preferred by teams today due to Redlock's operational complexity.

### 7. Specialized Redisson Lock Types

| Lock Type | Redisson Class | Use Case |
| :--- | :--- | :--- |
| **Reentrant Lock** | `redissonClient.getLock("key")` | Standard mutual exclusion; allows same thread to re-enter without deadlock |
| **Fair Lock** | `redissonClient.getFairLock("key")` | Guarantees FIFO order of lock acquisition; avoids starvation under high contention |
| **ReadWrite Lock** | `redissonClient.getReadWriteLock("key")` | Multiple concurrent readers, single exclusive writer; ideal for read-heavy distributed caches |
| **MultiLock** | `redissonClient.getMultiLock(lock1, lock2)` | Atomically acquires multiple locks together; prevents circular wait deadlocks across resources |
| **Semaphore** | `redissonClient.getSemaphore("key")` | Distributed rate limiting or limiting concurrent access to downstream systems (e.g., max 10 concurrent requests) |

### 8. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Use Redisson Watchdog (avoid explicit leaseTime)** | Explicit lease times disable the watchdog. If business logic is delayed, the lock expires silently mid-process |
| **Surround DB transactions with the lock** | Releasing the lock before `@Transactional` commits lets other threads read stale, uncommitted data |
| **Always check `lock.isHeldByCurrentThread()` in `finally`** | Calling `unlock()` on a lock not held by the current thread throws `IllegalMonitorStateException` |
| **Use short acquisition timeouts (`tryLock(waitTime)`)** | Never use blocking `lock.lock()` without timeout in request paths; it causes HTTP thread pool starvation under traffic spikes |
| **Fine-grained lock keys** | Lock on specific entity IDs (`lock:order:1029`), never broad aggregate types (`lock:order`), to maximize concurrency |
| **Use ShedLock for scheduled jobs** | Do not reinvent cron locks with custom Redis scripts; ShedLock handles clock skew and deadlocks natively |
| **Combine locks with database unique constraints** | Defense-in-depth: a unique DB constraint (`UNIQUE(order_id, idempotency_key)`) protects against split-brain lock failures |
| **Virtual Threads compatibility** | In Java 21 / Spring Boot 3.2+ (Q241), Redisson's non-blocking Netty-based async locks prevent carrier thread pinning |

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **`unlock()` without `isHeldByCurrentThread()`** | `IllegalMonitorStateException` logged in `finally` block | Always guard unlock with `if (lock.isHeldByCurrentThread()) { lock.unlock(); }` |
| **Explicit `leaseTime` disables Watchdog** | Concurrent execution during high-load spikes or slow DB calls | Omit `leaseTime` parameter from `tryLock()` so Redisson keeps renewing the lease automatically |
| **Lock inside `@Transactional`** | Race condition; subsequent thread reads uncommitted dirty state | Put lock *outside* `@Transactional`, or use `TransactionTemplate` inside the locked block |
| **Holding lock during external REST/Payment call** | Thread exhaustion, connection pool starvation, cascading failure (Q245) | Minimize critical section; do HTTP calls before or after lock, or use asynchronous Saga patterns (Q223) |
| **ShedLock missing `lockAtLeastFor`** | Scheduled job runs multiple times across cluster nodes | Configure `lockAtLeastFor = "5m"` to prevent nodes with minor clock skew from executing the same cron |
| **Unbounded `lock.lock()` blocking indefinitely** | Tomcat / Virtual thread pool exhaustion during outages | Always use `tryLock(timeout, unit)` and handle lock acquisition failure with HTTP 429 or graceful fallback |
| **Redis master crash during failover** | Two nodes hold the lock concurrently | Acknowledge Redis AP nature; use DB constraints, optimistic locking, or fencing tokens for critical safety |
| **Clock drift between nodes** | Premature lock expiration in multi-node quorum locks | Synchronize node clocks using NTP / PTP; use DB time in ShedLock (`usingDbTime()`) |

---

### Summary

- Standard Java locks (`synchronized`, `ReentrantLock`) are strictly single-JVM; clustered Spring Boot microservices require **Distributed Locks** or database-level concurrency controls.
- **ShedLock** is the standard solution for clustered `@Scheduled` background tasks, using an atomic DB/Redis table with `lockAtMostFor` (deadlock protection) and `lockAtLeastFor` (clock skew protection).
- For distributed application logic, **Redisson** provides production-grade reentrant locks, fair locks, and read-write locks backed by Redis Lua scripts.
- The **Redisson Watchdog** automatically extends lock TTL every 10s as long as the worker thread is alive. **Specifying an explicit `leaseTime` disables the watchdog** and risks premature lock release.
- **The Transaction Boundary Trap:** A distributed lock must **completely wrap** the database transaction (`TransactionTemplate`); releasing the lock inside a `@Transactional` method lets concurrent threads read uncommitted dirty state.
- Distributed locks cannot guarantee 100% safety against long JVM Stop-The-World GC pauses or network partitions without **Fencing Tokens** verified by the storage layer. Always pair distributed locks with database unique constraints and idempotency keys (Q242).

## 258. How do you implement consumer-driven contract testing with Pact in Spring Boot microservices? Explain consumer-driven contracts, HTTP/message pacts, provider verification, Pact Broker, and CI gates.

In a microservices landscape, teams deploy independently (Q250) and evolve REST/event APIs over time (Q216/Q246). Unit tests miss integration drift; full end-to-end suites are slow and flaky. **Consumer-driven contract testing** with **Pact** sits in the middle of the pyramid: the **consumer** (e.g., Order Service, BFF/gateway — Q239) declares the exact request/response (or message) shape it needs; that contract is published; the **provider** (e.g., Payment Service) verifies it still satisfies every known consumer before shipping. Pact complements **Testcontainers** integration tests (Q210) — contracts catch API-shape breakage early; Testcontainers validate behavior against real dependencies.

---

### 1. Testing Pyramid in Microservices

| Layer | Scope | Speed | Catches | Weakness |
| :--- | :--- | :--- | :--- | :--- |
| **Unit** (Mockito, JUnit) | Single class / method | Fastest | Logic bugs, edge cases | Blind to HTTP/JSON/schema drift between services |
| **Slice / Integration** (`@WebMvcTest`, Testcontainers) | App + real DB/broker locally | Medium | Wiring, SQL, Kafka serialization | Does not prove *other* services still honor your expectations |
| **Contract (Pact)** | Consumer expectations ↔ provider implementation | Fast–medium | Breaking API/event changes across team boundaries | Does not prove full business workflows end-to-end |
| **E2E / Synthetic** | Multi-service staging or prod probes | Slowest | User journeys, env config | Flaky, expensive; too late as the only safety net |

**Rule of thumb:** keep PR feedback on unit + contract + focused Testcontainers; reserve broad E2E for merge/promote gates (Q250).

---

### 2. Consumer-Driven Contracts — Core Idea

**Provider-first** docs (OpenAPI alone) describe what the server *offers*. **Consumer-driven contracts** reverse the flow: each consumer writes a failing-expectation test against a **mock provider** spun up by Pact; on success, Pact writes a **pact file** (JSON) capturing the interaction. The provider later runs **verification**: replay those interactions against the real Spring Boot app (or a running instance) and fail the build if responses diverge.

```
Consumer CI                          Pact Broker                         Provider CI
   |                                      |                                    |
   |-- Consumer test (mock provider) ---->|                                    |
   |-- Publish pact JSON ---------------->|                                    |
   |                                      |<-- Fetch pacts for "payment-service"
   |                                      |-- Verify against @SpringBootTest -->|
   |                                      |<-- Publish verification results ----|
   |                                      |-- can-i-deploy? ------------------>| Promote / block
```

| Concept | Meaning |
| :--- | :--- |
| **Consumer** | Service that *calls* or *subscribes* (Order → Payment, BFF → Order) |
| **Provider** | Service that *implements* the HTTP API or *publishes* the message |
| **Interaction** | One request/response (or one message) in the pact |
| **Provider state** | Named fixture (`"order exists"`) the provider sets up before verifying that interaction |
| **Matcher** | Flexible assertion (`type`, `regex`, `datetime`) so UUIDs/timestamps don't flake |

OpenAPI remains valuable for **human docs and codegen**; Pact is the **executable compatibility gate** between independently released services.

---

### 3. HTTP Consumer Test (Spring / JUnit 5)

- Successful runs write `target/pacts/order-service-payment-service.json` (or `build/pacts/...`).

### 4. Provider Verification

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Provider("payment-service")
@PactBroker(url = "${pactbroker.url:http://localhost:9292}")
// Or for local/dev without broker: @PactFolder("pacts")
class PaymentProviderVerificationTest {

    @LocalServerPort
    int port;

    }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)

        context.verifyInteraction();
    }

    @State("payment can be created for order-1001")

        // Seed minimal fixtures: no conflicting order, stubs for downstream if needed.
        // Keep states idempotent and isolated per interaction.
    }

```

| Approach | When to use |
| :--- | :--- |
| **`@SpringBootTest(RANDOM_PORT)`** | Full stack verification (security filters, Jackson config, validation) — preferred for CI |
| **`@WebMvcTest` + mock services** | Faster feedback on controller contracts only; weaker for filter/security mismatches |
| **`@PactBroker`** | Team/shared contracts, `can-i-deploy`, history |
| **`@PactFolder`** | Local iteration without broker |

### 5. Message / Async Contracts (Kafka-Style Events)

HTTP pacts cover request/response. For event-driven flows (Q251/Q212/Q223), **message pacts** capture the payload a consumer expects from a topic (or that a provider publishes).

```java
@Pact(consumer = "inventory-service")

    return builder
        .expectsToReceive("an OrderCreated event")
        .withContent(new PactDslJsonBody()
            .stringType("eventType", "OrderCreated")
            .uuid("eventId")
            .stringType("orderId", "order-1001")
            .numberType("quantity", 2))
        .toPact();
}
```

Provider side verifies by producing the same message shape from the domain publisher (or serializing a domain event) and asserting it matches the pact. Choreography sagas (Q223) and idempotent consumers (Q242) depend on **stable, versioned event shapes** — message contracts catch accidental field renames before they poison the outbox/Kafka pipeline.

```
can-i-deploy asks: "Have all integrations that matter in environment X been verified successfully for these versions?"
```

Combine with API versioning (Q246) when you intentionally introduce breaking changes — add a new interaction/path rather than silently changing existing ones.

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Hard-coded mock port** | Port conflicts in parallel CI | Use `@PactTestFor(port = "0")` / dynamic ports |
| **Exact body match on timestamps/IDs** | Intermittent consumer test failures | Use `uuid()`, `datetime()`, `stringType()`, `numberType()` |

### Summary

- **Consumer-driven contracts** let each consumer declare the API/event shape it needs; the **provider verifies** those pacts against the real Spring Boot service before release — catching cross-team API drift without full E2E.

- The **Pact Broker** stores contracts + verification results; **`can-i-deploy`** is the production gate that answers whether these versions are safe to promote together (Q250).
- Pair Pact with **Testcontainers** (behavior) and **OpenAPI** (docs); keep provider states minimal, avoid brittle literals, and never use contracts as a substitute for owning third-party APIs.
- Treat breaking changes as **versioned expansions** (Q246): expand contracts first, migrate consumers, then contract-remove old interactions.

## 259. How do you handle consumer failures, retries, and dead-letter topics in Spring Kafka? Explain blocking vs non-blocking retry, `DefaultErrorHandler`, `DeadLetterPublishingRecoverer`, poison pills, and backoff.

Kafka delivery is **at-least-once** by default (Q212). A listener that throws — a database blip, a timeout, a corrupt payload — is retried, and a poison record can stall its partition while every later message waits. Spring Kafka’s error handler decides three things: **which exceptions are worth retrying**, **how long to wait**, and **where the record goes when retries are exhausted**. That pipeline only stays correct if the consumer is also **idempotent** (Q242/Q251), because every retry is another delivery.

---

### 1. Classify the Failure Before You Retry

| Kind | Examples | Retry? | Where it should land |
| :--- | :--- | :--- | :--- |
| **Transient** | DB connection reset, broker timeout, downstream 503, lock timeout | Yes, with backoff | Same topic, then DLT if it never recovers |
| **Poison / non-retryable** | Bad JSON, unknown schema, `ClassCastException`, missing required field | No | Dead-letter topic immediately |
| **Business rejection** | Insufficient funds, order already cancelled, validation rule | No | Domain outcome (`PaymentDeclined`) or a business-failure topic — Kafka retry will not change the answer |
| **Fatal infrastructure** | Broker auth failure, poisoned consumer group, disk full | No | Stop the container and alert; a DLT will not fix the process |

Retrying a business rejection burns consumer lag and can duplicate side effects. Retrying a poison pill forever freezes the partition (head-of-line blocking).

---

### 2. What Happens If You Configure Nothing

`ConcurrentKafkaListenerContainerFactory` installs a `DefaultErrorHandler` that treats most exceptions as retryable: **9 retries, no delay**, then logs and moves on. Deserialization and conversion failures are **not** retried. There is no dead-letter topic unless you attach a recoverer.

Consequences in production:

- A transient outage is retried 10 times in a tight loop and then **dropped** (logged only).
- A slow dependency plus a long in-memory backoff can exceed `max.poll.interval.ms` (default 5 minutes). The broker decides the consumer is dead, rebalances, and the same record is delivered again — often to another instance.
- Records **behind** the failed one on that partition are not processed. Ordering is preserved; throughput of the partition is not.

---

### 3. Blocking Retry + Dead Letter (`DefaultErrorHandler`)

**Blocking** retry seeks back to the failed offset and re-invokes the listener on the same thread. Order per partition is preserved. Use it when later events for the same key must not overtake a failed one (order state machine, event-sourced aggregate — Q251).

```java
@Bean
public DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, Object> template) {
    var backOff = new ExponentialBackOffWithMaxRetries(5); // 5 retries after the first failure
    backOff.setInitialInterval(500L);
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(10_000L);

    // Same partition on <topic>.DLT keeps failed-record order inspectable.
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));

    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);
    // These fail the classifier immediately and go to the recoverer.
    handler.addNotRetryableExceptions(
        IllegalArgumentException.class,
        NullPointerException.class,
        MethodArgumentNotValidException.class);
    return handler;
}

@Bean
public ConcurrentKafkaListenerContainerFactory<String, Object> kafkaListenerContainerFactory(
        ConsumerFactory<String, Object> consumerFactory,
        DefaultErrorHandler kafkaErrorHandler) {
    var factory = new ConcurrentKafkaListenerContainerFactory<String, Object>();
    factory.setConsumerFactory(consumerFactory);
    factory.setCommonErrorHandler(kafkaErrorHandler);
    return factory;
}
```

`FixedBackOff(1_000L, 3L)` is the simpler form: 1 second apart, 3 retries, then recover. `new FixedBackOff(0L, 0L)` disables retry and publishes straight to the DLT.

After the recoverer **succeeds**, the container commits the original offset (`commitRecovered` defaults to true), so the poison record is not delivered again. If the DLT publish itself fails, the offset stays uncommitted and the record is tried again — still at-least-once, never silently lost.

`DeadLetterPublishingRecoverer` copies the original key, value, and headers, and adds:

| Header (`KafkaHeaders`) | Use |
| :--- | :--- |
| `DLT_ORIGINAL_TOPIC` / `PARTITION` / `OFFSET` | Replay back to the source position |
| `DLT_EXCEPTION_FQCN` | Classifier: bug vs bad data vs dependency |
| `DLT_EXCEPTION_MESSAGE` / `STACKTRACE` | On-call context without digging through logs |
| `DLT_ORIGINAL_TIMESTAMP` | How long the record sat before it was parked |

Calling `addRetryableExceptions(...)` **flips** the classifier: only the listed types are retried, everything else goes to the recoverer. Listing one retryable type and forgetting the others is a common way to dead-letter timeouts.

---

### 4. Non-Blocking Retry (`@RetryableTopic`)

Blocking retry holds the partition for the whole backoff. A 30-second outage on one order blocks every other order on that partition. **Non-blocking retry** publishes the failed record to a retry topic, commits the main offset, and lets the partition continue. A separate listener waits until a backoff timestamp header and tries again.

```java
@RetryableTopic(
    attempts = "4",                       // 1 original delivery + 3 retries
    backoff = @Backoff(delay = 1_000, multiplier = 2.0, maxDelay = 30_000),
    autoCreateTopics = "false",           // provision partitions/replication in IaC
    topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE,
    dltTopicSuffix = "-dlt",
    exclude = {
        DeserializationException.class,
        IllegalArgumentException.class
    }
)
@KafkaListener(topics = "orders", groupId = "payment-service")
public void onOrder(OrderCreated event) {
    paymentService.charge(event);        // must be idempotent — Q242
}

@DltHandler
public void onDlt(OrderCreated event,
                  @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String reason,
                  @Header(KafkaHeaders.ORIGINAL_OFFSET) long offset) {
    meterRegistry.counter("kafka.dlt", "topic", "orders").increment();
    log.error("Parked order {} at offset {}: {}", event.orderId(), offset, reason);
}
```

With index suffixes the topics are `orders-retry-0`, `orders-retry-1`, `orders-retry-2`, then `orders-dlt`. Non-retryable exceptions skip the retry topics and go to the DLT.

| | Blocking (`DefaultErrorHandler`) | Non-blocking (`@RetryableTopic`) |
| :--- | :--- | :--- |
| **Partition progress** | Stops until retries finish | Main topic keeps moving |
| **Per-key order** | Preserved | A later event can be applied before the retried one |
| **Extra topics** | One DLT | One topic per attempt + DLT |
| **`max.poll.interval.ms`** | Backoff sum must stay under it | Backoff happens on the retry consumer, not inside the poll loop |
| **Fit** | Ordered aggregates, low failure rate | Mixed keys, flaky downstreams, high fan-in |

If the aggregate is ordered by `orderId` (Q251), non-blocking retry is only safe when the consumer tolerates reordering — a version or sequence check that rejects a stale event — or when you retry in a way that still serializes on that key.

---

### 5. Poison Pills and `ErrorHandlingDeserializer`

A deserializer that throws never reaches the listener. The container cannot commit past that offset, so the same bytes crash every restart. Wrap the real deserializer:

```properties
spring.kafka.consumer.key-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.key.delegate.class=org.apache.kafka.common.serialization.StringDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=org.springframework.kafka.support.serializer.JsonDeserializer
spring.kafka.consumer.properties.spring.json.trusted.packages=com.example.orders
spring.kafka.consumer.properties.spring.json.value.default.type=com.example.orders.OrderCreated
```

The delegate’s failure is stored on the record and rethrown as a `DeserializationException` when the listener argument is resolved. That exception is **not retryable by default** (along with `MessageConversionException`, `ConversionException`, `MethodArgumentResolutionException`, and `ClassCastException`), so the recoverer parks it on the DLT instead of looping. Pair this with a schema contract (message pacts — Q258) so producers fail in CI before they publish bytes no consumer can read.

---

### 6. Backoff, Poll Timeouts, and the Consumer Group

In-memory backoff still runs on the listener thread, between `poll()` calls.

```
total blocking time ≈ attempts × (processing + backoff)
must stay well under max.poll.interval.ms
```

| Setting | Why it matters |
| :--- | :--- |
| `max.poll.interval.ms` | Exceed it and the member is kicked out; rebalance + duplicate delivery |
| `max.poll.records` | A batch of slow records multiplies time spent before the next poll |
| `ExponentialBackOffWithMaxRetries` | Caps attempts. Plain `ExponentialBackOff` is capped by **elapsed time**, which is easy to set longer than the poll interval |
| Jitter | Stops every instance retrying a downed database on the same millisecond |

Prefer failing over to the DLT (or to non-blocking retry) once human-scale time is required. A 15-minute “retry” belongs on a retry topic or a scheduler, not inside `poll()`.

---

### 7. Transactions, Acks, and Idempotency

- **Ack mode `RECORD` / `BATCH` (default path):** let the error handler seek and commit. Do not ack the record at the start of the listener.
- **`AckMode.MANUAL`:** ack only after the side effect and the dedup row commit. Acknowledging before the database write loses the message on a crash.
- **Transactional listener** (`KafkaTransactionManager`): the DLT publish must join that transaction (the same transactional `KafkaTemplate`). A publish outside it can land on the DLT while the original offset rolls back — duplicate DLT records — or the opposite, a committed offset and a lost letter.
- **Idempotency is still mandatory.** Five retries are five deliveries. The processed-events unique key `(consumer_name, event_id)` from Q251 has to surround the side effect. The DLT is for records you have **given up** retrying automatically, not a second copy of successful work.

---

### 8. Operating the DLT

A DLT is a queue of work, not a log you ignore.

1. **Alert on depth and age**, not only on consumer lag of the main topic. A healthy main lag with a growing `orders-dlt` means you are skipping business events.
2. **Triage by `DLT_EXCEPTION_FQCN`:** bad payload → fix the producer or add a tolerant reader; `DataAccessResourceFailureException` after retries → downstream was down too long, replay; `IllegalStateException` → bug, deploy a fix before replay.
3. **Replay deliberately.** A small tool (or a one-shot listener) reads the DLT and publishes back to the original topic, preserving the key so ordering by `aggregateId` still holds. Strip or archive DLT exception headers so the next failure is diagnosable. Do not auto-replay in a loop — that recreates the poison-pill stall.
4. **Bound retention** on retry topics (hours) and keep DLT retention long enough for a human (days). Infinite retention on every retry topic is an accident.

---

### 9. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Split retryable vs fatal in code review** | Timeouts retry; validation, NPE, and deserialization do not |
| **Cap attempts and elapsed time** | Unbounded backoff becomes a stuck consumer and a rebalance storm |
| **Provision DLT/retry topics yourself** | `autoCreateTopics=true` picks the wrong partition count and replication factor |
| **Keep per-key order, or detect reordering** | Non-blocking retry lets a newer event win unless the aggregate checks a version |
| **Make the listener idempotent** | Retries and replays are normal (Q242/Q251) |
| **Use `ErrorHandlingDeserializer`** | A bad byte array must be movable, not fatal to the poll loop |
| **Page on DLT depth** | Dropped or parked events are user-visible even when the main consumer looks healthy |
| **Replay only after the cause is gone** | Replaying a poison pill immediately puts it back at the head of the partition |
| **Don’t use the DLT for expected business “no”** | Emit a domain event the rest of the system already understands (Q251) |

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Default handler, no recoverer** | Exception logged, offset committed, event gone | Attach `DeadLetterPublishingRecoverer` or `@RetryableTopic` |
| **Backoff longer than `max.poll.interval.ms`** | Rebalance loop, duplicates, rising lag | Shorten in-memory backoff; move long waits to retry topics |
| **`addRetryableExceptions` with a partial list** | Timeouts dead-lettered on the first failure | Treat that call as an allow-list; list every transient type |
| **Deserializer throws without the error-handling wrapper** | Consumer crash-loops on one offset | `ErrorHandlingDeserializer` + immediate DLT |
| **DLT template not transactional** | Duplicate or missing DLT rows around a rollback | Use the listener’s transactional `KafkaTemplate` |
| **Ack before the DB commit** | Message consumed, payment never stored | Ack after the business transaction commits |
| **Non-blocking retry on an ordered aggregate** | `OrderShipped` applied before retried `PaymentSucceeded` | Blocking retry, or reject stale sequence numbers |
| **Auto-replay of the DLT** | Same exception forever, lag never recovers | Human or gated replay after a fix |
| **Retrying a 4xx business rule** | Hot loop, duplicate charges, angry downstream | Non-retryable exception; publish a failure event |
| **Ignoring DLT headers on replay** | Next failure looks like the old one | Record exception class/message, then publish a clean payload |

---

### Summary

- A failed Kafka record is either **retried**, **parked on a dead-letter topic**, or **turned into a business event**. Swallowing it after a log line loses data; retrying it forever blocks the partition.
- **`DefaultErrorHandler`** plus **`ExponentialBackOffWithMaxRetries`** / **`FixedBackOff`** is blocking retry: order on the partition stays intact, and **`DeadLetterPublishingRecoverer`** publishes to `<topic>.DLT` with the original offset and exception headers once attempts run out.
- **`@RetryableTopic`** is non-blocking retry: the main consumer commits and moves on, retry topics delay the next attempt, and `@DltHandler` observes the give-up. Use it when one bad key must not stall the others, and only if reordering is acceptable or detectable.
- Wrap deserializers in **`ErrorHandlingDeserializer`** so poison pills are classified as non-retryable and leave the partition.
- Keep total blocking time under **`max.poll.interval.ms`**, commit offsets only after the side effect, publish DLT records inside the listener transaction, and treat every retry as a second delivery — idempotency from Q242/Q251 still applies.
- Operate the DLT: alert on depth, triage by exception class, and replay onto the original topic only after the producer bug or the downstream outage is actually fixed.

## 260. How do you publish a transactional outbox to Kafka with Debezium CDC? Explain WAL capture, the outbox event router, delivery guarantees, and how this differs from a polling publisher.

The outbox in Q251 fixes the dual-write: the business row and the event row commit in **one database transaction**, so a rollback cannot leave a Kafka message behind, and a commit cannot leave the event only in memory. Something still has to move `outbox_events` to Kafka. A polling publisher (`KafkaTemplate` + `published=true`) works at low volume and adds a second write plus a polling delay. **Change data capture** with **Debezium** tails the database log instead: it sees the outbox insert only after commit, in commit order, and turns that row into a Kafka record. Consumers stay idempotent (Q242/Q251) and still park poison messages on a dead-letter topic (Q259) — CDC does not change those rules.

---

### 1. Polling Publisher vs. Log-Based CDC

| | Polling publisher (Q251) | Debezium CDC |
| :--- | :--- | :--- |
| **How it reads** | `SELECT … WHERE published = false ORDER BY id` | Database log: PostgreSQL WAL or MySQL binlog |
| **When the event becomes visible** | Next poll (often 100 ms–a few seconds) | As soon as the transaction commits and the connector reads that LSN |
| **Extra writes** | `UPDATE outbox SET published=true` after the Kafka ack | None on the request path. The insert *is* the event |
| **Crash window** | Kafka ack succeeded, flag update did not → duplicate on the next poll | Connector produced to Kafka, offset not flushed → duplicate after restart |
| **Commit order** | Only as good as `ORDER BY` under concurrent pollers | Log order of committed transactions |
| **What you operate** | A Spring `@Scheduled` relay | Kafka Connect (or an embedded engine) and a replication slot |
| **Fit** | Modest throughput, one service, no Connect cluster | Many services, strict commit order, you already run Connect |

Both are **at-least-once**. Neither makes the consumer’s side effect exactly-once. The event id on the outbox row is the dedup key.

---

### 2. What “Committed” Means on the WAL

PostgreSQL with `wal_level=logical` records committed row changes in the write-ahead log. A replication slot is a bookmark: the server retains WAL until the slot’s confirmed LSN moves forward.

```
OrderService transaction
  INSERT order
  INSERT outbox_events
  COMMIT  ──────────────►  WAL contains both rows
                              │
                              ▼
                    Debezium reads only outbox_events
                    (table.include.list)
                              │
                              ▼
                    EventRouter → Kafka topic, key = aggregateId
```

A rolled-back transaction never reaches the log as a committed change, so Debezium cannot publish it. That is the atomicity a `KafkaTemplate.send()` *after* `commit()` cannot give you: the send is a second system.

The request thread does not call Kafka. Latency from commit to visible event is usually tens to a few hundred milliseconds, dominated by the connector’s poll of the slot — not by a `fixedDelay` poller.

---

### 3. Outbox Table Shaped for the Event Router

Debezium’s **outbox event router** (`io.debezium.transforms.outbox.EventRouter`) expects conventional columns. Unquoted PostgreSQL names are folded to lowercase; the SMT config must use those names.

```sql
CREATE TABLE outbox_events (
    id             UUID PRIMARY KEY,          -- event id (dedup key for consumers)
    aggregateid    VARCHAR(64)  NOT NULL,     -- Kafka record key
    aggregatetype  VARCHAR(128) NOT NULL,     -- routed topic, e.g. Order → Order.events
    type           VARCHAR(128) NOT NULL,     -- OrderCreated, PaymentSucceeded, …
    payload        JSONB        NOT NULL,
    traceid        VARCHAR(64),               -- Q244, copied onto a Kafka header
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

There is no `published` flag. Updates and deletes of this table are noise; the connector is configured to emit **inserts only**, and old rows are archived by a job the connector does not watch (or the table is partitioned and detached).

```java
@Entity
@Table(name = "outbox_events")
public class OutboxEvent {
    @Id
    private UUID id;
    @Column(name = "aggregateid")
    private String aggregateId;
    @Column(name = "aggregatetype")
    private String aggregateType;
    private String type;
    @JdbcTypeCode(SqlTypes.JSON)
    private String payload;
    @Column(name = "traceid")
    private String traceId;
}
```

```java
@Transactional
public Order create(CreateOrder cmd) {
    Order order = orderRepo.save(Order.from(cmd));
    outboxRepo.save(new OutboxEvent(
        UUID.randomUUID(),
        order.getId().toString(),
        "Order",
        "OrderCreated",
        mapper.writeValueAsString(OrderCreated.from(order)),
        tracer.currentTraceId()));   // same transaction as the order insert
    return order;
}
```

---

### 4. Connector and Event Router

Run Debezium as a **Kafka Connect** source connector (distributed mode), not inside the API process. One slot has one reader; Connect isolates that reader from API deploys and can use source exactly-once (below).

```json
{
  "name": "order-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/secrets/db:password}",

```

| Setting | Why |
| :--- | :--- |
| `table.include.list` | Only the outbox is an integration event. Streaming `orders` itself couples every column change to every consumer |
| `skipped.operations=u,d,t` | Archive deletes must not become a second business event |
| `snapshot.mode=no_data` | Do not republish rows that a previous poller already sent. Use an initial snapshot only when this table is the backlog you still need to drain |
| `route.topic.replacement` | `aggregatetype=Order` → topic `Order.events`. Key is `aggregateid`, so one aggregate stays on one partition (Q251 ordering) |
| `expand.json.payload` | Consumers receive a JSON object, not a string-encoded blob |
| Header placement | `eventId` feeds the processed-events unique key (Q251); `traceId` continues the trace (Q244); `eventType` is the discriminator |
| `heartbeat.interval.ms` | While the connector is up but the outbox is idle, heartbeats move the stored LSN so PostgreSQL can recycle WAL |
| `slot.drop.on.stop=false` | Stopping Connect for a deploy must not drop the slot. A dropped slot loses the bookmark; the next start either gaps or has to resnapshot |

The database user needs the `REPLICATION` attribute and `SELECT` on `outbox_events`. `wal_level=logical` is a server setting (restart). The publication created for `filtered` mode includes only the tables the connector is allowed to capture.

An **embedded Debezium engine** inside the Spring Boot process is reasonable for a single service that does not want a Connect cluster. The slot still has a single consumer, so you cannot run two API replicas both tailing it. Prefer Connect once more than one service has an outbox.

---

### 5. Delivery Guarantees

| Guarantee | What actually holds |
| :--- | :--- |
| **No event without a commit** | Rolled-back inserts are absent from the WAL |
| **No committed outbox row is skipped while the slot is healthy** | The slot retains WAL until Connect acknowledges that LSN |
| **At-least-once onto Kafka** | Default Connect commits its offset *after* the produce. A crash in between redelivers |
| **Duplicates are normal** | Same `eventId` may arrive twice. The consumer unique key `(consumer_name, event_id)` from Q251 absorbs that |
| **Per-aggregate order** | Same `aggregateid` → same Kafka partition → one consumer thread sees that key in log order |
| **Not one Kafka transaction per database transaction** | Two outbox rows in one SQL transaction become two Kafka records. A consumer can observe the first without the second. Put one fact in one event, or make the consumer tolerate a partial pair |
| **Optional connector exactly-once** | Debezium 2.3+ on **distributed** Connect, with the worker’s exactly-once source support enabled, fences duplicate source writes across a connector restart. Listener crashes and Q259 retries still redeliver to user code — keep the idempotency table |

Do not run a polling publisher **and** Debezium on the same table. Every historical row would be eligible twice.

---

### 6. Operating the Slot

The failure mode that fills a disk is a slot that stops confirming.

```sql
SELECT slot_name,
       active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS retained
FROM pg_replication_slots
WHERE slot_name = 'orders_outbox';
```

| Signal | Meaning |
| :--- | :--- |
| `active = false` and `retained` climbing | Connector is down. WAL cannot be recycled. Alert before the volume fills |
| `retained` steady at idle | Heartbeats are working |
| Connector task FAILED, slot still present | Fix the task and resume. Do not drop the slot to “clear” the error unless you accept a gap |
| Slot dropped and recreated with `no_data` | Events committed while it was gone are **not** in Kafka. That is data loss, not a clean restart |

Also alert on Connect task state, outbox table growth (inserts with no matching consumer progress), and consumer lag on `Order.events` (Q259). A healthy slot with a stuck consumer means the database is fine and the business projection is not.

Schema changes belong in Flyway/Liquibase (Q248) **before** the new payload is written. Adding a JSON field is compatible; renaming `aggregateid` breaks the router until the SMT config is deployed in the same release. Message pacts (Q258) lock the payload the consumer actually reads, which is the expanded JSON — not the JDBC row.

---

### 7. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Insert the outbox in the business transaction** | One commit, or neither side exists |
| **Let the log be the relay** | Removes `published` flag races and poll latency |
| **Route by aggregate type, key by aggregate id** | Topic ownership stays clear; per-aggregate order matches Q251 |
| **Put `eventId` in a header** | Downstream dedup does not depend on parsing the body |
| **Skip updates and deletes** | Housekeeping must not republish domain facts |
| **`snapshot.mode=no_data` when replacing a poller** | Avoids a second copy of the backlog unless you are draining it on purpose |
| **Never drop the slot on stop** | The LSN bookmark is the difference between a restart and a silent gap |
| **Heartbeat and alert on retained WAL** | An idle or dead connector otherwise retains the log until the disk is full |
| **One reader of the slot** | Connect, or one embedded engine — not every API replica |
| **Keep consumers idempotent** | At-least-once plus Q259 retries will deliver twice |

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **`KafkaTemplate` after commit, no outbox** | Order stored, `OrderCreated` never appears (or the reverse if send-then-commit fails) | Outbox insert in the same `@Transactional` method |
| **Poller and CDC together** | Duplicate events for every order | One relay |
| **`snapshot.mode=initial` on a table that still holds sent rows** | Consumers replay months of history | `no_data`, or snapshot once into an empty outbox |
| **`slot.drop.on.stop=true`** | Gap after every Connect restart | `false`, and resume the same `slot.name` |
| **No heartbeat, quiet outbox** | WAL volume grows while the API looks healthy | `heartbeat.interval.ms` and the retained-WAL alert |
| **Connector user lacks `REPLICATION`** | Task fails immediately, slot inactive | Role attribute plus `SELECT` on the outbox |
| **SMT column names don’t match folded identifiers** | Empty keys, router errors, or the whole row dumped to a raw topic | Lowercase `aggregateid`, `aggregatetype`, and the same strings in `table.field.*` |
| **`expand.json.payload=false`** | Consumer sees a JSON string and the pact (Q258) fails or double-decodes | Expand the payload, or document the string contract on both sides |
| **Two facts in one DB transaction, assumed atomic on Kafka** | Inventory reserved, payment event missing | One event per fact, or a consumer that can wait/repair |
| **Embedded engine on every pod** | Only one replica reads; the others fail the slot, or you accidentally create a second slot | Single Connect task (or a dedicated relay deployment) |
| **Renaming a payload field in place** | Green producer, consumers in DLT (Q259) | Expand/contract the JSON (Q246/Q248) and keep `eventId` stable |

---

### Summary

- The transactional outbox makes “order row + event row” one database commit (Q251). **Debezium** publishes that insert by reading the **WAL** (or binlog) after commit, so the API process never dual-writes to Kafka.
- A **polling publisher** is simpler and slower, and its `published` flag has a duplicate window. CDC removes that flag and follows **commit order**, at the cost of a replication slot and Kafka Connect.
- The **outbox event router** maps `aggregatetype` → topic, `aggregateid` → key, `payload` → value, and copies `eventId` / `eventType` / `traceId` onto headers for dedup (Q242) and tracing (Q244).
- Capture **inserts only**, do not drop the slot on shutdown, heartbeat so idle WAL can be recycled, and alert on slot lag. `snapshot.mode=no_data` when you must not republish history.
- Delivery to Kafka is **at-least-once** unless Connect’s source exactly-once support is turned on — and even then a consumer retry (Q259) can apply the event twice. Idempotent consumers stay mandatory.

## 261. How do you shut down a Spring Boot service gracefully on Kubernetes? Explain readiness, `preStop`, `server.shutdown=graceful`, Kafka consumer drain, and rolling updates.

A rolling deploy (Q250) deletes pods while other replicas are still starting. Kubernetes sends **SIGTERM**, waits `terminationGracePeriodSeconds`, then **SIGKILL**. The default Spring Boot web server treats SIGTERM as “stop now”: in-flight HTTP calls are cut, Kafka listeners lose the poll loop before they commit, and the next pod reprocesses or the client sees a 502. Graceful shutdown is the ordered drain between those two signals — stop admitting work, finish what you already took, then exit — and it only works if the grace period is long enough for that drain.

---

### 1. What Kubernetes Does on Delete

```
kubectl delete / rolling update
        │
        ▼
Pod gets deletionTimestamp  ──►  removed from Service endpoints
        │                         (propagation to kube-proxy takes seconds)
        ▼
preStop hook runs (SIGTERM is not sent yet)
        │
        ▼
SIGTERM  ──►  JVM shutdown hook  ──►  Spring context stop
        │
        ▼
grace period exhausted  ──►  SIGKILL (no finally, no offset commit)
```

`terminationGracePeriodSeconds` covers **preStop + everything after SIGTERM**. The clock starts when the delete is requested, not when the JVM notices. A 15s `preStop` sleep plus a 30s Spring drain does not fit in the default 30s grace period; the kubelet kills the process mid-request.

Pods leave the Service as soon as they are Terminating, but endpoint updates are not instantaneous. Traffic still arrives for a few seconds after delete. `preStop` exists to absorb that lag **while the process is still healthy**.

---

### 2. Spring Boot: Stop Accepting, Then Wait

```properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

# @Async and @Scheduled pools (off by default — tasks are dropped on stop)
spring.task.execution.shutdown.await-termination=true
spring.task.execution.shutdown.await-termination-period=30s
spring.task.scheduling.shutdown.await-termination=true
spring.task.scheduling.shutdown.await-termination-period=30s

# Kafka listener containers
spring.kafka.listener.shutdown-timeout=20s
```

`server.shutdown=graceful` pauses the embedded server (Tomcat connector `pause()`, or the equivalent on Jetty/Undertow/Netty). New connections are refused. Requests that already entered the server run until they complete or `spring.lifecycle.timeout-per-shutdown-phase` expires. That property is per SmartLifecycle phase, not a single budget for the whole JVM.

Default is `server.shutdown=immediate`: the connector closes as SIGTERM arrives.

On Kubernetes, Spring Boot turns on Actuator probes when it sees the cluster environment (`management.endpoint.health.probes.enabled=true`):

| Probe | Path | During drain | Include |
| :--- | :--- | :--- | :--- |
| **Readiness** | `/actuator/health/readiness` | Should go **OUT_OF_SERVICE** so the pod is not sent new traffic | `readinessState`, and hard dependencies you refuse to serve without (DB) |
| **Liveness** | `/actuator/health/liveness` | Must stay **UP** for the whole drain | `livenessState` only |

A liveness check that pings the database restarts a pod whose DB had a blip, and it will also restart a pod that is already terminating. Readiness is the traffic valve. Liveness means “the process is deadlocked, kill it.”

```yaml
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30
  periodSeconds: 2
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
```

The startup probe holds liveness off until the JVM is actually up, so a slow Spring Boot start (Q215) is not killed as a deadlock.

---

### 3. `preStop` and the Grace Period

```yaml
spec:
  terminationGracePeriodSeconds: 70
  containers:
    - name: order-service
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 15"]
```

| Slice of the 70s | What it pays for |
| :--- | :--- |
| **15s preStop** | EndpointSlice / kube-proxy / ingress catch up. The app is still serving |
| **~30s** | `spring.lifecycle.timeout-per-shutdown-phase` for HTTP and scheduler tasks |
| **~20s** | `spring.kafka.listener.shutdown-timeout`, in parallel with the web drain once the context stops |
| **Remainder** | Hikari close, JVM shutdown hook, a few seconds of slack |

If the sum of preStop and the longest drain exceeds the grace period, behavior falls off a cliff: **SIGKILL**. Offsets may be uncommitted, transactions in flight roll back, clients get a reset. Size the grace period from the drains, not from a cluster default.

`preStop` that calls `kill` or hits a custom “exit now” endpoint skips the Spring hook. Sleep, then let SIGTERM drive `SpringApplication`.

---

### 4. Kafka Consumers Leaving the Group

`ConcurrentMessageListenerContainer` is a `SmartLifecycle`. On context stop it wakes the consumer, finishes the current records (bounded by `shutdown-timeout`), commits, and sends **LeaveGroup**.

| Event | Result |
| :--- | :--- |
| Clean stop within `shutdown-timeout` | Offsets for processed records are committed. Unprocessed records in the last poll are delivered to the next owner |
| Stop longer than `max.poll.interval.ms` | The broker already decided the member was dead and rebalanced. The local commit can be rejected (`REBALANCE_IN_PROGRESS`) |
| SIGKILL during `process()` | Offset not committed. The next owner delivers again. Safe only if the listener is idempotent (Q242/Q251) |
| All replicas restart together | Every member leaves at once. A stop-the-world rebalance, lag spike, and duplicate processing |

Use a **cooperative** assignor so a deploy revokes only the partitions of the pod that left; the other pods keep consuming:

```properties
spring.kafka.consumer.properties.partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

`group.instance.id` (static membership) is a different tool: if the **same** instance id reconnects before `session.timeout.ms` **without** having left the group, the coordinator skips a rebalance. A graceful `close()` still leaves the group and still rebalances. Static membership helps a crash restart, not a rolling deploy. Do not raise `session.timeout.ms` into minutes to paper over a missing drain.

Keep `shutdown-timeout` well under `max.poll.interval.ms`, and keep both under the time left after `preStop`. One bad record must not sit in an in-memory retry longer than that window (Q259) or the deploy itself becomes the rebalance storm.

---

### 5. Rolling Update Shape

Drain one replica at a time, and do not take the Deployment below its serving count.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
---
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: order-service }
```

`maxUnavailable: 0` plus `maxSurge: 1` starts the new pod first, waits until it is **Ready**, then deletes an old one. The old one runs `preStop` and the Spring drain before it is gone. A PodDisruptionBudget blocks voluntary evictions (node drain, cluster autoscaler) from deleting the last replicas the Service needs. It does not block `kubectl delete deploy`.

Old and new code run at the same time for the whole rollout. A Flyway migration in the same release must be **expand** only (Q248): the old pod still has to read and write the schema. Contract-breaking JSON belongs in a later release, after consumers accept the new shape (Q246/Q258/Q260).

---

### 6. Work That Does Not Fit a 30s Drain

| Work | What graceful shutdown does | What you should do |
| :--- | :--- | :--- |
| Ordinary REST call | Waits until the controller returns | Bound downstream timeouts so the request finishes inside the phase timeout |
| `@Async` / `@Scheduled` | Waits only if `await-termination` is set | ShedLock `lockAtMostFor` still covers a job killed mid-run (Q257) |
| Kafka listener | Commits and leaves, up to `shutdown-timeout` | Idempotent handler; no multi-minute in-memory backoff |
| Upload, long report, SSE, WebSocket | Phase timeout fires, then the server closes | Don’t hold the request open for minutes; move the work to a job and poll, or accept a reconnect |
| Transaction still open at SIGKILL | Database rolls back | Caller or consumer retries; no “we sent 200 but the commit died” if you commit **before** the HTTP response is fully your success signal |

After the phase timeout Spring continues shutdown anyway. “Graceful” is a bounded wait, not a promise that a 10-minute export will finish.

---

### 7. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **`server.shutdown=graceful`** | In-flight HTTP finishes; new accepts stop |
| **`preStop` sleep before SIGTERM** | Covers endpoint propagation while the process still returns 200 |
| **Grace period ≥ preStop + longest drain + slack** | Otherwise the kubelet SIGKILLs the drain |
| **Readiness ≠ liveness** | Readiness removes traffic. Liveness only restarts a stuck process |
| **Startup probe** | A slow boot is not a deadlock |
| **Await termination on `@Async` and `@Scheduled`** | Those pools drop tasks on shutdown unless asked to wait |
| **Bound the Kafka stop** | Commit and LeaveGroup inside the grace period |
| **Cooperative sticky assignor** | One pod leaving does not pause every partition |
| **`maxUnavailable: 0`** | New pod is Ready before an old one is deleted |
| **Expand/contract schema** | Overlapping versions during the rollout must both work (Q248) |
| **Idempotent side effects** | SIGKILL and rebalance both redeliver (Q242/Q259) |

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Default `server.shutdown=immediate`** | 502s and truncated responses on every rollout | `graceful` plus a phase timeout |
| **`preStop` 15s inside a 30s grace period** | SIGKILL halfway through the Spring drain | Raise `terminationGracePeriodSeconds` |
| **No preStop** | Errors in the first seconds after delete, then a clean drain | Sleep (or otherwise wait) so endpoints catch up |
| **DB check on liveness** | Pod restarts when Postgres blips; restart loop during an outage | Liveness is process health only; DB belongs on readiness |
| **No startup probe** | Liveness kills the container before Tomcat is up | Startup probe with a generous `failureThreshold` |
| **`await-termination` left false** | Scheduled or async work vanishes on deploy | Enable it and budget the wait |
| **Kafka `shutdown-timeout` > remaining grace, or > `max.poll.interval.ms`** | Commit fails, duplicates, rebalance storm | Timeouts nested: poll interval > shutdown > time left after preStop |
| **Eager assignor and all pods recycled** | Lag spike on every release | `CooperativeStickyAssignor`, `maxUnavailable: 0` |
| **Breaking migration in the rolling release** | New pods write a column the old pods cannot read | Expand first, roll the app, contract later (Q248) |
| **Closing the DataSource in `@PreDestroy` ahead of listeners** | “Connection is closed” while a listener is still committing | Let `SmartLifecycle` stop consumers first; don’t close the pool yourself |
| **Treating graceful shutdown as exactly-once** | Duplicate payment after an eviction | Idempotency key / processed-events table (Q242/Q251) |

---

### Summary

- Kubernetes gives the process **SIGTERM**, then **SIGKILL** when `terminationGracePeriodSeconds` ends. Graceful shutdown is the work you finish between those signals.
- **`preStop`** burns a few seconds so Service endpoints stop sending traffic before the JVM starts draining. **`server.shutdown=graceful`** then refuses new HTTP work and waits up to `spring.lifecycle.timeout-per-shutdown-phase` for in-flight requests. `@Async` and `@Scheduled` wait only if `await-termination` is enabled.
- **Readiness** drops traffic; **liveness** only means the process is stuck. A startup probe covers a slow Spring Boot boot.
- Kafka containers stop via `spring.kafka.listener.shutdown-timeout`: commit, leave the group, and stay inside `max.poll.interval.ms`. A **cooperative sticky** assignor and **`maxUnavailable: 0`** keep a rollout from pausing every partition.
- The grace period must fit preStop plus the longest drain. Anything still running at SIGKILL is retried, so side effects stay idempotent (Q242/Q259) and schema changes stay backward compatible for the whole rollout (Q248).

## 262. How do you implement a transactional inbox so a Kafka consumer applies an event exactly once? Explain the dedup insert, `ON CONFLICT`, offset commit order, and what “exactly once” does not cover.

The producer side is settled: one database commit writes the business row and the outbox, and Debezium publishes that insert at least once (Q251/Q260). The consumer still sees duplicates — connector restarts, listener retries, dead-letter replays (Q259), and a pod killed with SIGKILL before the offset commit (Q261). A check-then-act (`exists` then `save`, as in the Q251 sketch) loses that race: two deliveries both see “not processed” and both charge the card. The **transactional inbox** makes the dedup row and the business write **one local transaction**, with the database unique key as the lock.

---

### 1. Where Duplicates Come From

| Source | What the consumer observes |
| :--- | :--- |
| Kafka at-least-once (Q212) | Same record after a rebalance or a failed offset commit |
| Debezium / Connect restart (Q260) | Same `eventId` published twice |
| Blocking or non-blocking retry (Q259) | Same record until the handler returns cleanly |
| DLT replay | A new offset, the **same** business `eventId` |
| SIGKILL mid-listener (Q261) | Processed locally, or not, and the offset was not committed |

Kafka’s “exactly once” (transactional producer, read-committed consumer) stops the **broker** from exposing a torn write. It does not stop your handler from talking to Postgres twice. The inbox is the consumer-side record of “this event id already changed our database.”

---

### 2. Why the Check and the Write Must Be One Transaction

| Order | Crash or race | Outcome |
| :--- | :--- | :--- |
| `SELECT` inbox, then later `INSERT`, two threads | Both selects miss | Side effect runs twice |
| Business commit, then inbox insert in a **second** transaction | Crash in between | Redelivery does the work again |
| Inbox commit, then business work in a **second** transaction | Crash in between | Redelivery sees the inbox row and **skips** the work. The event is lost |
| Inbox insert + business write, **one** commit | Crash before commit | Both roll back. Redelivery retries cleanly |
| Same single transaction | Crash after commit, before offset ack | Redelivery hits the unique key and does nothing |

The safe failure is always “do it again.” The unsafe failure is “remember that we did it, when we did not.”

A unique violation in PostgreSQL **aborts the transaction**. Catching `DataIntegrityViolationException` inside the same `@Transactional` method and continuing does not work: the connection stays aborted until rollback. Use an insert that does not abort when the row is already there.

---

### 3. Schema and `ON CONFLICT`

```sql
CREATE TABLE inbox (
    consumer_name  VARCHAR(100) NOT NULL,
    event_id       UUID         NOT NULL,
    processed_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, event_id)
);
```

`event_id` is the outbox id (Q260 header), not the Kafka offset. A replay onto a new partition has a new offset and the same id. `consumer_name` is required because payment-service and inventory-service both store an inbox and both must process `OrderCreated`.

```sql
INSERT INTO inbox (consumer_name, event_id, processed_at)
VALUES (:consumer, :eventId, now())
ON CONFLICT (consumer_name, event_id) DO NOTHING;
```

PostgreSQL reports `1` when this delivery won the insert and `0` when the row was already there. The statement does not abort the transaction, so the loser can return without applying the side effect and still commit.

```java
public interface InboxRepository extends JpaRepository<InboxEntry, InboxKey> {

    @Modifying
    @Query(value = """
        INSERT INTO inbox (consumer_name, event_id, processed_at)
        VALUES (:consumer, :eventId, now())
        ON CONFLICT (consumer_name, event_id) DO NOTHING
        """, nativeQuery = true)
    int insertIgnore(@Param("consumer") String consumer, @Param("eventId") UUID eventId);
}
```

```java
@Service
public class PaymentConsumer {
    private final InboxRepository inbox;
    private final PaymentService payments;

    @KafkaListener(topics = "Order.events", groupId = "payment-service")
    @Transactional
    public void onOrder(OrderCreated event, @Header("eventId") UUID eventId) {
        int inserted = inbox.insertIgnore("payment-service", eventId);
        if (inserted == 0) {
            return; // duplicate; ack and move on
        }
        payments.charge(event); // joins this transaction (REQUIRED)
    }
}
```

`payments.charge` must be another Spring bean whose transaction propagation is `REQUIRED` (the default). `REQUIRES_NEW` commits the charge on its own and brings back the “inbox and work can diverge” bug. A native `INSERT` runs immediately; if `charge` throws, the inbox row rolls back with it, and the Q259 retry is allowed to try again.

---

### 4. Offset Commit Comes After the Database Commit

Spring’s listener transaction interceptor commits the `DataSource` transaction when `onOrder` returns normally. The container then commits the Kafka offset (`enable.auto.commit` stays **false**; the listener container commits).

```
poll → begin TX → INSERT inbox → charge → commit TX → ack offset
                         │              │
                         └── one transaction ──┘
```

| Failure point | Next delivery | Inbox | Charge |
| :--- | :--- | :--- | :--- |
| Before commit | Yes | Rolled back | Rolled back, runs again |
| After commit, before ack | Yes | Row present, insert returns 0 | Skipped |
| After ack | No, unless a later replay | Row present | Skipped |

Do not ack at the start of the method (`AckMode.MANUAL` acknowledged before the commit). That is the lost-event window from Q259, and the inbox cannot repair a record Kafka will never send again.

---

### 5. What This Makes Exactly-Once — and What It Does Not

| Effect | Once? |
| :--- | :--- |
| Rows this service writes in the listener transaction (payment row, balance update, inbox) | Yes, for a given `(consumer_name, eventId)` |
| A second service’s database | No. That service has its own inbox and its own transaction |
| HTTP call to Stripe, email, or another API from inside `charge` | No. The HTTP call does not roll back. Those calls need their own idempotency key |
| Follow-on Kafka publish via `KafkaTemplate` after the fact | No, unless it is an outbox insert **in this same transaction** (Q260) |
| Two **different** event ids that both update one balance | No. The inbox dedupes an event; it does not serialize business updates. Use `UPDATE … SET balance = balance + :delta` or `@Version` |

The usual shape for a handler that must notify the outside world: local state and an outbox row in the inbox transaction; Debezium publishes the result. Call external APIs with an idempotency key equal to `eventId`, or accept that a retry of a non-transactional call needs a compensating check.

`READ COMMITTED` is enough. The unique index is the lock. `SERIALIZABLE` does not fix a handler that commits the inbox and the charge in two transactions.

---

### 6. Concurrency, Order, and How Long to Keep Rows

Kafka normally delivers one partition to one consumer, so duplicates are often **sequential**. They are not always sequential. A rebalance can hand the partition to another instance while the first transaction is still open (Q261). Both pass a naked `SELECT`. Only one `INSERT … ON CONFLICT` wins; the other gets `0` rows and must not throw. Throwing sends a successfully stored event through retries and possibly onto the DLT (Q259).

The inbox does not put events back in order. Ordering stays a property of the key (`aggregateId` → one partition, Q251/Q260) or of a version check inside `charge`. Dedup without a version still applies `OrderShipped` and a redelivered `PaymentSucceeded` in whichever order they arrive.

Keep inbox rows **longer than** the main topic retention and the dead-letter retention. A replay after you deleted the row is a second charge. Partition by month and drop partitions only past that horizon. The table does not need the payload; the key and `processed_at` are the whole record, unless you deliberately keep an audit copy.

A unique constraint on the business row (`payments.order_id`) is a second backstop for the case where a caller bypasses the listener. It is not a substitute for the inbox when one event inserts several rows.

---

### 7. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Insert the inbox and write the business rows in one transaction** | Commit means both happened, or neither did |
| **`ON CONFLICT DO NOTHING` (or the dialect’s equivalent)** | A duplicate key must not abort the transaction you still want to commit as a no-op |
| **Key by consumer and event id** | Every service processes the event; offset is the wrong identity across a replay |
| **Return normally on a conflict** | The duplicate is success. An exception invites a retry loop and a false DLT |
| **Ack only after the database commit** | The redelivery then becomes a no-op instead of a lost event |
| **`REQUIRED`, not `REQUIRES_NEW`, for the side effect** | A nested commit splits the atomic boundary |
| **Put outbound messages in an outbox in that same transaction** | The HTTP/Kafka side effect leaves the database only after commit (Q260) |
| **Retain rows past any plausible replay** | Deleting early reopens the event |
| **Treat a second event id as a new fact** | Dedup is not an optimistic lock on the aggregate |

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **`exists` then `save`** | Duplicate charges under rebalance | Single `INSERT … ON CONFLICT` |
| **Inbox committed in its own transaction first** | Consumer lag looks fine, payments missing | One transaction with the charge |
| **Charge committed first, inbox second** | Two payment rows for one `eventId` | Same transaction; inbox insert first |
| **Catch a unique violation and keep going** | `current transaction is aborted` / `UnexpectedRollbackException` | `ON CONFLICT DO NOTHING` and a row count |
| **Conflict treated as a listener failure** | Event sits on the DLT after it was applied | Return without throwing when the insert count is 0 |
| **Ack before commit** | Offset moves, transaction rolls back, event never comes back | Default container ack after the `@Transactional` method returns |
| **`REQUIRES_NEW` on `charge`** | Inbox says done, payment row absent (or the reverse) | `REQUIRED` so it joins the inbox transaction |
| **HTTP inside the transaction** | Email or capture succeeded, database rolled back, retry does it again | Outbox or a downstream idempotency key |
| **Dedup key = offset** | DLT replay or a new topic charges again | Outbox UUID forwarded in the `eventId` header (Q260) |
| **One global `event_id` primary key** | Inventory’s insert blocks payment, or payment’s success skips inventory | Primary key `(consumer_name, event_id)` |
| **Deleting inbox rows inside the topic retention window** | A rebuild or a replay double-applies | Retention longer than the log you might replay |

---

### Summary

- At-least-once delivery (Q212/Q259/Q260/Q261) means the handler runs more than once. An **inbox row keyed by `(consumer_name, event_id)`** is how this service remembers a successful apply.
- The inbox insert and the business write commit **together**. `INSERT … ON CONFLICT DO NOTHING` lets the losing delivery exit cleanly; a prior `SELECT` does not.
- Commit the database **before** the Kafka offset. A crash in between redelivers, the insert count is 0, and the charge does not run again.
- That is exactly-once for **this database transaction** only. External HTTP, other services, and a second event id need their own idempotency (Q242) or another outbox (Q260). A conflict is success, not a dead-letter, and the row must outlive any replay you still allow.

## 263. How do you make POST requests idempotent in Spring Boot with an `Idempotency-Key`? Explain the claim, request fingerprint, response replay, and concurrent retries.

A Kafka consumer can dedupe with an inbox because the broker redelivers the same `eventId` (Q262). An HTTP client has no broker. The user double-clicks, the mobile app times out and retries, or the gateway replays a `POST /payments` after it already created the payment. `POST` is not idempotent: a second call creates a second charge. The **`Idempotency-Key`** header is the client’s event id. The server stores that key with the **first response** and replays it, so every retry of one user action returns the same payment id.

---

### 1. What the Client Promises

| Rule | Why |
| :--- | :--- |
| One key per user action, generated before the first attempt | A new UUID per retry is a new payment |
| The same key on every retry of that attempt, including after a timeout | A timeout is ambiguous: the payment may already exist |
| A new key when the user asks for a new payment | The key names the action, not the endpoint |
| The same method, path, and body bytes on retry | A different body with the same key is a conflict, not a second execution |
| Keep the key until a definitive response, at least as long as the server retains it | After the server forgets the key, a retry creates a new row |

The header is `Idempotency-Key`. The value is an opaque string; require a UUID and cap the length (255 characters is the usual ceiling). Scope it to the authenticated principal (and tenant — Q253). Two clients may both send `Idempotency-Key: test-1`. The unique key is `(principal_id, idempotency_key)`.

Use it on operations that allocate something: `POST /payments`, `POST /orders`. A correct `PUT` of a full representation is already idempotent. Do not invent a key for `GET`.

---

### 2. Remember the Response, Not Only the Fact

The inbox in Q262 answers “did we apply this event?” The HTTP case also needs “**what did we tell the client?**” A retry must return the original `201`, `Location`, and payment id. Re-running the controller and hoping it returns the same JSON is how a second code path leaks a different body.

```sql
CREATE TABLE idempotency_record (
    principal_id      VARCHAR(64)  NOT NULL,
    idempotency_key   VARCHAR(255) NOT NULL,
    request_hash      CHAR(64)     NOT NULL,   -- SHA-256 of method, path, raw body
    state             VARCHAR(20)  NOT NULL,   -- IN_PROGRESS or COMPLETED
    http_status       INT,
    response_body     JSONB,
    locked_until      TIMESTAMPTZ,
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    expires_at        TIMESTAMPTZ  NOT NULL,
    PRIMARY KEY (principal_id, idempotency_key)
);
```

`request_hash` is the fingerprint. Hash the **raw** request bytes, not a Jackson re-serialization of the DTO. Key order and whitespace are part of what the client actually sent; serializing the parsed object produces a different hash and a false mismatch.

```
fingerprint = SHA-256(method + "\n" + path + "\n" + rawBody)
```

Leave the `Authorization` header out of the hash. A refreshed bearer token is still the same payment.

---

### 3. Claim First, in the Same Transaction as the Write

This is the same atomicity rule as the inbox. The winner inserts the key. The business rows and the stored response commit with it. A crash rolls all of them back, and the retry is free to become the winner.

PostgreSQL’s unique index waits: a second `INSERT … ON CONFLICT DO NOTHING` **blocks** until the first transaction commits or rolls back. If the first commits, the second inserts nothing and reads the stored response. If the first rolls back, the second insert proceeds and that request becomes the one that creates the payment.

```java
public interface IdempotencyRepository {

    @Modifying
    @Query(value = """
        INSERT INTO idempotency_record
            (principal_id, idempotency_key, request_hash, state, expires_at)
        VALUES (:principal, :key, :hash, 'IN_PROGRESS', :expires)
        ON CONFLICT (principal_id, idempotency_key) DO NOTHING
        """, nativeQuery = true)
    int claim(@Param("principal") String principal,
              @Param("key") String key,
              @Param("hash") String hash,
              @Param("expires") Instant expires);

    @Modifying
    @Query(value = """
        UPDATE idempotency_record
        SET state = 'COMPLETED', http_status = :status,
            response_body = CAST(:body AS jsonb)
        WHERE principal_id = :principal AND idempotency_key = :key
        """, nativeQuery = true)
    int complete(@Param("principal") String principal,
                 @Param("key") String key,
                 @Param("status") int status,
                 @Param("body") String body);
}
```

```java
@Service
public class PaymentService {
    private final IdempotencyRepository idempotency;
    private final PaymentRepository payments;
    private final ObjectMapper mapper;

    @Transactional
    public IdempotentResult<PaymentResponse> create(String principal, String key,
                                                    String fingerprint, CreatePayment cmd) {
        int won = idempotency.claim(principal, key, fingerprint, Instant.now().plus(Duration.ofHours(24)));
        if (won == 0) {
            return replay(principal, key, fingerprint);
        }
        Payment payment = payments.save(Payment.authorize(cmd));
        PaymentResponse body = PaymentResponse.from(payment);
        idempotency.complete(principal, key, 201, mapper.writeValueAsString(body));
        return IdempotentResult.created(body);
    }
}
```

`replay` loads the row. The same fingerprint and `COMPLETED` returns the stored status and body. A different fingerprint is `422 Unprocessable Entity` — the client reused a key for another payload. Do not run `authorize` in that branch.

While the winner is still inside the transaction, the row is invisible as a committed `IN_PROGRESS`. The loser is blocked on the unique index, then sees `COMPLETED`. Set `lock_timeout` (a couple of seconds) so a slow winner cannot pin every retried request. On lock timeout, respond **`409 Conflict`** and let the client retry with the same key. Those waiters hold pool connections until they time out (Q232); a short `lock_timeout` is what keeps a retry storm from exhausting Hikari.

---

### 4. When the Side Effect Is Not the Local Database

`charge()` that calls Stripe **inside** this transaction holds the database connection for the whole HTTP round trip and still double-calls Stripe if two app instances both get past a badly ordered check. Split that case:

1. **Commit the claim** (`IN_PROGRESS`, `locked_until = now() + 30s`) before the external call, so a concurrent retry sees the row and gets `409` immediately.
2. Call downstream with **their** idempotency key set to this same `Idempotency-Key`.
3. In a second transaction, store `COMPLETED` and the response you will replay.
4. If `locked_until` is in the past, a crash abandoned the claim. The next attempt may take the lease **and must call downstream with the same key**. Deleting the row and charging again is a second capture. The downstream key is what makes the recovery safe; the lease only decides which caller is allowed to ask.

Local writes stay on the single-transaction path in section 3. An outbox row in that same transaction (Q260) is still the better way to tell another service that the payment exists: the HTTP handler returns, and Debezium publishes after commit.

---

### 5. Which Responses to Store

| Result | Store and replay? | Retry behavior |
| :--- | :--- | :--- |
| **2xx** that created or changed state | Yes | Same status, same body, same id |
| **Deterministic 4xx** (validation, “already cancelled”) | Optional | Recomputing is safe when nothing was written. Storing is safe when the 4xx was committed with a business outcome |
| **409** while a claim is in progress | No | The client tries again later with the same key |
| **429 / 503 / 500** | No | A stored 500 would replay the failure after the bug is fixed |
| **Fingerprint mismatch** | No new row | `422`. The original key still belongs to the first body |

Throwing a `RuntimeException` rolls the transaction back, claim included, so a failed attempt does not stick. That is what you want for a transient error. It is not what you want if you already captured money outside the transaction — that path is section 4, and the downstream key has to match.

---

### 6. Reading the Body Once

The fingerprint has to be computed before the controller runs, and the controller still has to read the body. A servlet input stream does not rewind. Buffer it in a filter, but only on the routes that require the header, and refuse an unbounded body.

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 20) // after security, so the principal exists
public class IdempotencyKeyFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        if (!requiresKey(request)) {
            chain.doFilter(request, response);
            return;
        }
        String key = request.getHeader("Idempotency-Key");
        if (key == null || key.isBlank() || key.length() > 255) {
            response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Idempotency-Key required");
            return;
        }
        byte[] body = request.getInputStream().readNBytes(64 * 1024 + 1);
        if (body.length > 64 * 1024) {
            response.sendError(HttpServletResponse.SC_REQUEST_ENTITY_TOO_LARGE);
            return;
        }
        String fingerprint = sha256(request.getMethod() + "\n" + request.getRequestURI() + "\n"
                + new String(body, StandardCharsets.UTF_8));
        request.setAttribute("idempotency.key", key);
        request.setAttribute("idempotency.fingerprint", fingerprint);
        chain.doFilter(new CachedBodyRequest(request, body), response);
    }
}
```

The filter’s job stops there. Completing the record **after** `chain.doFilter` runs in a different moment from the service transaction: the payment can commit and the process can die before the filter writes `COMPLETED`. The next retry creates a second payment. `complete` belongs next to `payments.save`, inside `PaymentService.create`.

`CachedBodyRequest` is an `HttpServletRequestWrapper` whose `getInputStream()` returns the buffered bytes. Hashing `objectMapper.writeValueAsBytes(cmd)` in the service instead of the attribute is the bug the filter exists to prevent.

---

### 7. Retention

Keep rows longer than clients retry. Twenty-four hours matches common client policy and Stripe-style APIs. A scheduled delete of `expires_at < now()` (one job owner — Q257) may then drop the row. A retry after that is a **new** payment. Publish that TTL. Do not expire a key while its payment is still the one a timeout might be asking for.

The table stores response bodies. Treat it as production data: same access controls and retention class as payments, not as a debug log.

---

### 8. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Require the header on allocating POSTs** | An optional key means the dangerous call stays non-idempotent |
| **Unique on `(principal_id, idempotency_key)`** | The key is untrusted client input |
| **Fingerprint the raw body** | Parsed-and-reserialized JSON does not match the client’s bytes |
| **Claim, write, and store the 2xx in one transaction** | The retry either replays that response or becomes the single winner |
| **Replay the stored status and body** | The client must see the original id and `Location` |
| **`422` on a hash mismatch** | The key already names a different operation |
| **`409` when the claim is in progress or the lock wait times out** | The client retries; the server does not start a second charge |
| **Pass the same key downstream** | Recovery after a crash is safe only if the other system dedupes too (Q242) |
| **Do not store 5xx** | Retries have to be able to succeed once the dependency recovers |
| **Bound the body and the lock wait** | A replay storm otherwise occupies the pool (Q232) |
| **Expire on a published TTL** | Forgotten rows grow; early deletion creates a second payment |

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **New UUID on every HTTP attempt** | Duplicate payments, server logic never sees a retry | Client persists the key on the user action |
| **Global unique key, no principal** | One tenant’s retry replays another tenant’s response | Primary key `(principal_id, idempotency_key)` |
| **In-memory `Set` of keys** | Works on one pod, duplicates across the Deployment | A shared table |
| **`SELECT` then insert** | Both requests pass the check and both charge | `INSERT … ON CONFLICT DO NOTHING` as the claim |
| **Saving the response in the filter after commit** | 201 returned, process dies, retry creates another payment | `complete` in the service transaction |
| **Hash of the re-serialized DTO** | Honest retries get `422` | Hash the buffered raw body |
| **Including `Authorization` in the hash** | Token refresh looks like a different request | Method, path, and body only |
| **Storing 500 responses** | Clients replay the error after the outage | Store 2xx; let 5xx roll back |
| **Same key, different body, server runs it** | The second operation overwrites the stored meaning of the key | Compare `request_hash`, respond `422` |
| **External HTTP inside the open claim transaction** | Pool exhaustion, and a retry can call Stripe twice | Commit `IN_PROGRESS`, call with the same downstream key, then store the result |
| **Taking over an expired lease and charging again** | Two captures for one key | Downstream idempotency key equal to the client key |
| **Deleting rows inside the client retry window** | A late timeout creates a second payment | TTL at least as long as the client keeps the key |

---

### Summary

- `POST` allocates. The **`Idempotency-Key`**, scoped to the caller, is the id of one user action, and every retry of that action sends it again with the same body.
- The server **claims** `(principal_id, key)` with `INSERT … ON CONFLICT`, writes the business rows, and stores the **2xx body** in that same transaction. Concurrent duplicates wait on the unique index, then **replay** the stored response. A different body is `422`. A lock timeout or an in-progress external call is `409`.
- Do not record the outcome in a filter after the fact, do not hash a re-serialized DTO, and do not keep 5xx responses.
- A call to another system is safe to retry only if that system receives the **same** key (Q242). Local facts still belong in one transaction, with an outbox if anyone else must hear about them (Q260/Q262).
- Retain the row for the published TTL. After it is gone, the key no longer protects the client.

## 264. How do you prevent lost updates in Spring Boot? Explain `@Version`, retrying the operation, atomic SQL, and pessimistic locks.

An idempotency key stops the **same** request from running twice (Q263). An inbox stops the **same** event id from applying twice (Q262). Neither helps when two **different** actions both read a row, both change it, and both write back. The second commit replaces the first. That is a **lost update**: two credits of 10 against a balance of 100 persist as 110. `@Version` makes the write conditional on the row still matching the copy you read. A delta that the database can apply itself does not need that round trip. A hot row that conflicts on every attempt is cheaper to lock than to retry.

---

### 1. How the Update Gets Lost

Spring’s usual isolation is the database default. On PostgreSQL that is **READ COMMITTED**. Each statement sees committed rows, and nothing stops this:

```
T1  SELECT balance → 100          (version 4)
T2  SELECT balance → 100          (version 4)
T1  UPDATE balance = 110          commits, version 5
T2  UPDATE balance = 110          commits, version 5 or 6
```

T2’s write was computed from a stale 100. T1’s credit is gone. Raising the application to `REPEATABLE READ` is not the design: PostgreSQL will often abort T2 with a serialization failure (you still retry), and MySQL’s repeatable read does **not** detect a lost update that was computed in the JVM. The fix belongs on the write.

---

### 2. What `@Version` Emits

```java
@Entity
public class Account {
    @Id
    private UUID id;

    @Version
    private long version;

    private BigDecimal balance;
}
```

Hibernate stores `version` on insert and, on flush of a dirty managed entity, issues:

```sql
UPDATE account
SET balance = ?, version = version + 1
WHERE id = ? AND version = ?
```

The `?` in `version = ?` is the version this persistence context loaded. Zero rows updated means someone committed a newer version. Hibernate throws `OptimisticLockException`. Spring translates that into `ObjectOptimisticLockingFailureException` (an `OptimisticLockingFailureException`). The transaction rolls back. Nothing is half-written.

Use a number (`long` or `int`). A timestamp version collides when two commits fall in the same clock tick, and clock steps make it lie. The application does not increment the field; the persistence provider does, at flush.

`@Version` treats the **entity** as the unit of conflict. Two transactions that touch different columns of the same account still conflict. That is what you want for one aggregate. It is the wrong tool for unrelated facts that happen to share a table — split them, or the hot column will fail updates that never overlapped.

A bulk `@Modifying` query does not increment `@Version` and does not check it unless the JPQL says so. A native `UPDATE` bypasses the protection entirely.

---

### 3. Use the Version the Client Actually Read

Optimistic locking only catches a writer that committed **after this persistence context loaded the row**. This handler looks safe and is not, for a form the user opened earlier:

```java
@Transactional
public void rename(UUID id, String email) {
    Account account = repo.findById(id).orElseThrow();
    account.setEmail(email); // version is whatever is current at this GET-inside-POST
}
```

Request A loaded version 4 in the browser and edits the email. Request B loads version 4, changes the address, commits version 5. Request A then calls `rename`, which loads version **5** and writes the email. The address survives only because A did not send a stale address. If A’s form posts every field, B’s address is overwritten and the version check passes, because A’s transaction never saw version 4.

The `WHERE` clause has to carry the version from the **original read**. On the wire that is `If-Match` (or a `version` field in the JSON). A missing precondition on a write is **428 Precondition Required**. A mismatch is **412 Precondition Failed** when you are speaking HTTP validators, or **409 Conflict** when the body carries a version. Do not map it to 500. The client reloads and shows the new state.

```java
@PatchMapping("/accounts/{id}")
public AccountResponse patch(@PathVariable UUID id,
                             @RequestHeader("If-Match") String ifMatch,
                             @RequestBody PatchAccount body) {
    long expected = Long.parseLong(ifMatch.replace("\"", ""));
    return accounts.update(id, expected, body);
}

@Transactional
public AccountResponse update(UUID id, long expectedVersion, PatchAccount body) {
    Account account = repo.findById(id).orElseThrow();
    if (account.getVersion() != expectedVersion) {
        throw new ObjectOptimisticLockingFailureException(Account.class, id);
    }
    account.setEmail(body.email());
    return AccountResponse.from(account); // flush still has AND version = expectedVersion
}
```

The explicit check covers the gap between the browser and this request. The `AND version = ?` on flush still covers a commit that lands after `findById` and before the update. Return the new version (and send it as `ETag`) so the client’s next write is based on what it was just given.

---

### 4. Retry the Operation, Not the Stale Snapshot

A conflict means “read again and reapply what you were trying to do.” It does not mean “write 110 again.”

```java
@Retryable(retryFor = OptimisticLockingFailureException.class,
           maxAttempts = 5,
           backoff = @Backoff(delay = 10, multiplier = 2))
public void credit(UUID id, BigDecimal amount) {
    ledger.applyCredit(id, amount);
}

@Service
class Ledger {
    @Transactional
    public void applyCredit(UUID id, BigDecimal amount) {
        Account account = repo.findById(id).orElseThrow();
        account.setBalance(account.getBalance().add(amount));
    }
}
```

`@EnableRetry` must be on. `@Retryable` and `@Transactional` on the **same** method are the wrong shape: if the transaction advisor is outer, every retry runs inside the transaction that already aborted. Put retry on the caller and the transaction on a separate bean, so each attempt is a new transaction that re-reads the balance. Self-invocation (`this.applyCredit`) skips both proxies (Q204).

Cap the attempts. A permanently hot row under optimistic locking is a retry storm, not a fairness policy. After the last failure, return 409. The caller’s intent is still unapplied.

---

### 5. Prefer One Atomic Statement When the Database Can Express the Intent

A credit is not “set balance to the number I calculated.” It is “add this amount to whatever is there.”

```java
@Modifying(clearAutomatically = true)
@Query("""
    UPDATE Account a
    SET a.balance = a.balance + :amount,
        a.version = a.version + 1
    WHERE a.id = :id
    """)
int credit(@Param("id") UUID id, @Param("amount") BigDecimal amount);
```

One statement, no lost update, no conflict, no retry. Increment `version` in that statement so any `@Version` writer still fails if it overlaps this credit. `clearAutomatically = true` drops a managed `Account` that still holds the old balance; leaving it in the persistence context is how the next flush writes the stale number back over the SQL you just ran (Q208).

A decrement that must not go negative belongs in the `WHERE`, not in an `if` in Java:

```sql
UPDATE account
SET balance = balance - :amount, version = version + 1
WHERE id = :id AND balance >= :amount
```

`0` rows means insufficient funds. Two concurrent debits cannot both pass that predicate. A read-then-check-then-save, even with `@Version`, needs a retry to reach the same answer and burns a conflict to do it.

Use `@Version` when a human or a worker is editing a whole aggregate and must be told their copy is stale. Use the atomic update when the operation is a commutative delta or a conditional decrement (stock, balance, quota).

---

### 6. Pessimistic Locks When Retries Would Be the Common Path

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "2000"))
@Query("select a from Account a where a.id = :id")
Optional<Account> lockById(@Param("id") UUID id);
```

That is `SELECT … FOR UPDATE`. The second transaction blocks until the first commits, then reads the fresh balance. Nobody relies on a conflict. A timeout of `0` is `NOWAIT` where the dialect supports it; a positive value is how long to wait, in milliseconds. On expiry Hibernate throws `PessimisticLockException`, which Spring surfaces as a lock-acquisition failure. Map that to 409 or to a short retry, and do not hold the lock across an HTTP call to another service — the row lock occupies a pooled connection for the whole transaction (Q232).

| Mechanism | Contention | What the loser does | Use when |
| :--- | :--- | :--- | :--- |
| **`@Version`** | Low or moderate | Transaction rolls back; retry re-reads | Edits of an aggregate; overlapping writes are rare |
| **Atomic `UPDATE`** | High, if the SQL expresses the change | The statement is the change; `0` rows is a business result | Balances, counters, “decrement if enough left” |
| **`PESSIMISTIC_WRITE`** | High, and the critical section is several statements | Blocks, then continues | You must read, decide, and write several rows as one stable picture |
| **Distributed lock** (Q257) | The resource is not one database row | Waits or times out outside the database | The critical section spans services or an external API |

`FOR UPDATE SKIP LOCKED` is a queue pattern (claim a job row nobody else has). It does not protect a row you already decided to update.

`LockModeType.OPTIMISTIC_FORCE_INCREMENT` is the bridge between a parent and its children. Adding a line item often does not dirty the parent, so the parent’s `@Version` stays put and two transactions each add a child from a stale collection. Locking the parent with `OPTIMISTIC_FORCE_INCREMENT` bumps its version at flush and fails if another transaction already did. The aggregate’s version, not each child’s, is the consistency boundary. A pessimistic lock on the parent is the same idea when those conflicts are constant.

---

### 7. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **`@Version` numeric column on every aggregate you edit through the persistence context** | The lost update is invisible in logs; the row simply has the wrong balance |
| **Send that version to the client and require it back** (`If-Match` or a field) | The version loaded inside the POST is already the winner’s version |
| **409 or 412, with the current resource** | The client reloads. A 500 invites a blind retry of the stale body |
| **Retry a fresh read of the intent** | Replaying `balance = 110` restores the bug the exception just prevented |
| **Keep `@Retryable` outside `@Transactional`** | Each attempt needs a clean transaction |
| **Atomic SQL for deltas and stock checks** | One round trip, and the predicate sees concurrent commits |
| **Bump `version` in bulk updates** | Otherwise `@Version` readers never notice the bulk write |
| **`clearAutomatically` after a bulk update** | A managed instance still holds the pre-update balance |
| **Pessimistic lock only inside a short transaction** | The lock is a pooled connection you cannot spend on Stripe |
| **Force-increment the parent when the write is “add a child”** | A collection change that does not dirty the parent does not bump `@Version` |
| **Split columns that conflict for no business reason** | A last-login write should not fail a profile edit |

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **No version column** | Two credits become one, no exception | `@Version`, or an atomic `balance = balance + :amount` |
| **Version taken from `findById` inside the write** | A stale form overwrites another user’s fields and commits | `If-Match` / client version, compared before flush |
| **Client omits version and the server treats it as optional** | The check never runs | 428 when the precondition is missing |
| **Retry writes the previously computed total** | The conflict is “resolved” by losing the other update again | Re-read and add the delta |
| **`@Retryable` and `@Transactional` on one method** | `UnexpectedRollbackException`, or a single attempt | Retry facade calls a transactional bean |
| **Unbounded retry on a hot balance** | CPU and pool churn, latency spike | Atomic SQL, or a pessimistic lock; cap attempts |
| **`@Modifying` update that ignores `version`** | Optimistic writers overwrite the bulk change | Set `version = version + 1` in the JPQL |
| **Bulk update then flush a stale managed entity** | The in-memory balance wins | `clearAutomatically = true`, or refresh |
| **`PESSIMISTIC_WRITE` held across a remote call** | Pool exhaustion, lock-wait timeouts (Q232) | Commit before the call; use an idempotency key downstream (Q263) |
| **Child inserts without touching the parent version** | Two workers each add a line from the same total | `OPTIMISTIC_FORCE_INCREMENT` or lock the parent |
| **Timestamp `@Version`** | One of two same-millisecond updates silently wins | `long` version |
| **Assuming READ COMMITTED will save you** | It will not, on PostgreSQL or MySQL, for a value computed in Java | A conditional write |

---

### Summary

- A lost update is two transactions computing a new value from the same old row. **READ COMMITTED does not prevent it.** `@Version` turns the write into `UPDATE … WHERE version = :loaded` and rolls the loser back with `OptimisticLockingFailureException`.
- The version that matters is the one the **client or the worker read when it decided**, not the version a later `findById` happens to see. Require `If-Match` (412/428) or a version field.
- Retry **outside** the transaction, re-read, and reapply the intent. Do not replay a stale absolute balance.
- If the change is “add”, “subtract if enough remains”, or another predicate the database can evaluate, one **atomic `UPDATE`** is stricter and cheaper than optimistic retries. Increment `version` in that statement and clear the persistence context.
- Lock the row with **`PESSIMISTIC_WRITE`** when conflict would be the normal case and the critical section is more than one statement. Keep that transaction short. Use a distributed lock only when the resource is not a single database row (Q257).

## 265. How do you route reads to replicas and writes to the primary in Spring Boot? Explain `AbstractRoutingDataSource`, `@Transactional(readOnly)`, replica lag, and read-your-writes.

`@Version` and `SELECT … FOR UPDATE` only mean something on the database that holds the latest row (Q264). A replica is a copy applied **after** the primary commits. Scaling reads by pointing the same `DataSource` at a random host sends a lock, an idempotency claim (Q263), and a balance update at yesterday’s row. Routing is the rule for which pool a transaction borrows from: writes and “I just wrote this” reads go to the **primary**; everything else may go to a **replica**. This is not sharding (Q237). Every node has the full database. The replica is only behind.

---

### 1. What Async Replication Breaks

PostgreSQL streaming replication (and MySQL binlog apply) acknowledges the client at the primary, then ships the WAL. Until the replica applies it:

| Follow-up read | What the caller sees |
| :--- | :--- |
| `GET` immediately after `POST`, served by a replica | Missing row, or the previous balance and `@Version` |
| Inbox / idempotency check on a replica | “Not processed,” then a second apply against the primary |
| Two reads of one session, two replicas | Time going backwards: version 7, then version 6 |
| `PESSIMISTIC_WRITE` aimed at a replica | A lock on a row the next write does not see, or a rejection because the replica is read-only |

Lag is normally milliseconds and occasionally seconds. A stalled apply turns it into minutes. The application cannot treat “committed” as “visible everywhere.”

---

### 2. One Transaction Stays on One Connection

Spring binds a single JDBC connection to the transaction. `AbstractRoutingDataSource` picks the target when that connection is **first acquired**, then the transaction is stuck with it. You cannot read from a replica and write to the primary inside one `@Transactional` method. The useful split is by transaction:

| Transaction | Route |
| :--- | :--- |
| Any write, lock, or idempotency claim | Primary |
| `@Transactional(readOnly = true)` query | A replica |
| Read that must see the caller’s own commit | Primary, even though it is read-only |
| No transaction at all | Primary. A missing annotation must not silently become a stale read |

Spring Data already marks `SimpleJpaRepository.findById` as `@Transactional(readOnly = true)` and `save` as a read-write transaction. A custom query method does not get that annotation unless you add it. The route follows the transaction you actually start, not the method name.

`readOnly = true` also tells Hibernate not to dirty-check and flush (Q208). On PostgreSQL the driver can mark the transaction read-only, so an accidental `INSERT` fails instead of landing on a replica and erroring later. It does **not**, by itself, open a connection to a second host. Without a routing datasource, `readOnly` is only a flush and SQL hint.

---

### 3. The Routing Datasource Has to See the Flag

`DataSourceTransactionManager` borrows a connection at `doBegin`, and only then publishes `TransactionSynchronizationManager.setCurrentTransactionReadOnly`. A routing datasource that calls `getConnection()` during `doBegin` still sees `isCurrentTransactionReadOnly() == false` and sends every read to the primary.

Wrap the router in `LazyConnectionDataSourceProxy`. Transaction begin then receives a proxy. The real pool is touched when the first statement is created, which is **after** the read-only flag is set.

```java
public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        if (ReadRoute.pinnedToPrimary()) {
            return DataSourceType.PRIMARY;
        }
        boolean readOnly = TransactionSynchronizationManager.isActualTransactionActive()
                && TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return readOnly ? DataSourceType.REPLICA : DataSourceType.PRIMARY;
    }
}

@Bean
public DataSource dataSource(HikariDataSource primary, HikariDataSource replica) {
    var routing = new ReplicaRoutingDataSource();
    routing.setDefaultTargetDataSource(primary);
    routing.setTargetDataSources(Map.of(
            DataSourceType.PRIMARY, primary,
            DataSourceType.REPLICA, replica));
    routing.afterPropertiesSet();
    return new LazyConnectionDataSourceProxy(routing);
}
```

`afterPropertiesSet()` resolves the map. Skipping it fails on the first query. `defaultTargetDataSource` is the primary, so an unknown key fails closed onto the writer, not onto a replica.

Each target is its own Hikari pool (Q232). Four replicas times a large pool times every pod exhausts `max_connections` on engines that are supposed to be the cheap read path. Size the replica pools for read concurrency and keep the primary pool for writes, locks, and pinned reads.

A cloud “reader endpoint” can hide several replicas behind the `REPLICA` pool. If you balance in the application, round-robin **per transaction**, not per statement. The transaction already holds one connection, so it will not hop. Pin that choice for the HTTP request if you need monotonic reads: two `readOnly` transactions in one call should hit the same replica, or a slower replica can answer second with an older version.

---

### 4. Read-Your-Writes

The response of the request that wrote the row should be built from the entity just saved on the primary, not from a second query that is free to be routed elsewhere. The hole is the **next** request: the redirect `GET`, the mobile refresh, the Kafka consumer that lost the race with apply lag.

Pin to the primary when this caller might still be ahead of replication:

```java
public final class ReadRoute {
    private static final ThreadLocal<Boolean> PRIMARY = new ThreadLocal<>();

    public static boolean pinnedToPrimary() {
        return Boolean.TRUE.equals(PRIMARY.get());
    }

    public static void pinToPrimary() { PRIMARY.set(Boolean.TRUE); }

    public static void clear() { PRIMARY.remove(); }
}
```

A filter sets the pin, and a `finally` always clears it so the thread returns to the pool without a sticky flag (virtual threads and servlet pools both reuse carriers — Q241).

| Signal | Pin? |
| :--- | :--- |
| Cookie or token `primary-until`, set when a write commits, held for a published window | Yes, for that caller |
| `replay_lag` from `pg_stat_replication` still above the window you promised | Yes. A fixed 2 seconds is too short while apply is stalled and too long when it is not |
| Header from the client that just received a `201` and is following `Location` | Yes |
| Payment status, idempotency replay, lock, balance change (Q263/Q264) | Always primary, in code, not by cookie |
| Anonymous catalog browse | Replica |

The cookie is a hint about **this user’s** writes. It does not make a replica consistent. When the pinned window expires during a long stall, either extend it from measured lag or serve the read from the primary until `pg_last_wal_replay_lsn()` has caught the LSN you returned at commit time. Waiting on that LSN inside the GET couples latency to apply lag; do it only for the reads that cannot be stale.

Synchronous replication makes commit wait for a replica and shrinks the window. It does not remove routing: you still have one writer, and a replica that is merely “sync” can be the wrong node after a failover.

---

### 5. Joined Transactions and `REQUIRES_NEW`

`readOnly` is a property of the transaction that was **started**, not of the method that joined it. A `@Transactional(readOnly = true)` repository call inside a read-write service uses the connection already bound to the primary. That is what you want: the read sees the writes this transaction has not committed yet, which a replica never will.

The inverse is a smell. A read-only outer transaction that calls `REQUIRES_NEW` on a writer holds a replica connection open while another connection commits on the primary (Q232). The outer snapshot still does not contain the inner commit. Keep a use case on one node: primary if anything in it writes or must see a just-written row; replica only when the whole transaction is a query.

---

### 6. Failover

The host in the primary pool is “whoever currently accepts writes,” not a hostname you baked in at boot.

| Event | What goes wrong | What to do |
| :--- | :--- | :--- |
| Replica promoted | The pool still writes to the old primary, now read-only or gone | Point the primary pool at the new writer (a stable writer endpoint does this) and evict old connections |
| Replica down | Read transactions hang until Hikari’s connection timeout | Health-check replicas and take them out of the map; fail closed to the primary |
| Apply completely stopped | Lag grows, pinned window never ends, primary takes all reads | Alert on `replay_lag`. Routing cannot hide a dead replica |
| Split brain, two writers | Both pools commit, replication diverges | Fencing at the database (one primary). The application does not heal this with a ThreadLocal |

After failover, in-flight transactions on the old primary fail. Those writes retry with the same idempotency key (Q263) or event id (Q262). A blind retry without that key is a second payment.

---

### 7. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Route by transaction, with the primary as the default** | A missing annotation or an unknown key must not serve a stale balance or take a lock on a replica |
| **`LazyConnectionDataSourceProxy` around the router** | The read-only flag does not exist yet when `doBegin` asks for a connection |
| **`@Transactional(readOnly = true)` on real query use cases** | That is the signal the router can see. `readOnly` alone does not select a host |
| **One pool per target, sized on purpose** | Replica scale is useless if the pods open hundreds of writer connections (Q232) |
| **Pin the writer’s own next read to the primary** | Async apply will not make the redirect `GET` consistent |
| **Measure `replay_lag`** | The pin window is an SLO, not a constant |
| **Build the write response from the entity you saved** | That object came from the primary persistence context |
| **Keep locks, claims, and version checks on the primary** | A replica lock or a replica idempotency read is a false answer (Q263/Q264) |
| **Fail closed to the primary when the replica set is unhealthy** | Stale-or-error beats hanging the request |
| **Turn off Open Session in View** | `spring.jpa.open-in-view=true` holds a persistence context for the whole request and hides which transaction was supposed to run |
| **Retry a failover write with the same idempotency key** | The first attempt may have committed before the proxy returned (Q263) |

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Router reads `isCurrentTransactionReadOnly()` without a lazy connection** | Every query hits the primary; replicas sit idle | `LazyConnectionDataSourceProxy` |
| **`readOnly = true` and one `DataSource`** | No error, no scale, reads still on the writer | A routing datasource with two pools |
| **Write and “confirm” read in one read-only transaction** | Driver rejects the update, or the read never sees a commit you expected on a replica | Split transactions; pin the confirm read to the primary |
| **Assuming the replica saw the commit because the HTTP call returned** | Client `GET` shows the old balance or a 404 | Pin that caller until apply catches up |
| **Round-robin per statement across replicas** | A later read in the same request moves backward | One replica for the request |
| **`@Transactional(readOnly = true)` on a method that also saves** | Hibernate never flushes, or Postgres aborts the write. The API returns 200 and the row is unchanged | Read-write transaction on the primary |
| **Self-invocation of the read-only method** | The proxy never starts the read-only transaction; the read hits the primary or joins a write | Call through the Spring bean (Q204) |
| **Open Session in View plus an eager pool** | The request thread takes a primary connection before anyone knows the route | `open-in-view=false` and a lazy routing connection |
| **Idempotency or inbox `SELECT` on a replica** | Duplicate charge or a skipped event | Those tables are read on the primary, in the write transaction (Q262/Q263) |
| **Hardcoded primary host across a promotion** | Writes fail or, worse, land on a node that is no longer the writer | Stable writer endpoint and pool eviction |
| **Replica pool sized like the old single pool, times N** | `too many connections` on the database you added for headroom | Small pools per target, a ceiling at the server |

---

### Summary

- Replicas scale reads of a **full copy** that is behind the primary. They are not a second writer and they are not a shard (Q237). Locks, version checks, and idempotency claims stay on the primary (Q263/Q264).
- `AbstractRoutingDataSource` chooses the pool when the connection is acquired. One transaction cannot use both. `@Transactional(readOnly = true)` is the read signal, and it is visible to the router only if a **`LazyConnectionDataSourceProxy`** defers the real borrow until after Spring publishes that flag. The default target is the primary.
- Async replication makes “just committed” invisible to the next read. Return the entity you wrote, and pin that caller’s following reads to the primary for a window driven by **`replay_lag`**, not by a fixed sleep.
- Size a Hikari pool per target, drop unhealthy replicas, and follow the writer endpoint through failover. A write that fails in that window retries with the same idempotency key.

---

## 266. How do you propagate trace, tenant, and security context across HTTP, `@Async`, and Kafka in Spring Boot? Explain `ThreadLocal`, `TaskDecorator`, and virtual threads.

`ReadRoute` in Q265 is a `ThreadLocal`. So are the tenant id (Q253), SLF4J’s MDC, and Spring Security’s `SecurityContext`. They all live on the thread that set them. `@Async`, a Kafka listener, and a scheduled job run somewhere else. The task then sees an empty tenant, writes a log line with no `traceId` (Q244), or — worse — a pooled thread still holding the **previous** caller’s principal. Propagation means capturing the values at the moment of the handoff and clearing them when the task ends.

---

### 1. What Is Actually on the Thread

| Holder | ThreadLocal | Set by | Must be empty on a pooled thread |
| :--- | :--- | :--- | :--- |
| **Tenant** | Your `TenantContext` | Filter, after authentication | Yes. The next request would query another customer’s rows |
| **Security** | `SecurityContextHolder` (default `MODE_THREADLOCAL`) | Security filter chain | Yes. The next request would act as the previous user |
| **Trace** | MDC keys `traceId` / `spanId` | Micrometer tracing filter (Q244) | Yes. Support would stitch two users into one trace |
| **Replica pin** | `ReadRoute` (Q265) | Filter, from a cookie or a fresh write | Yes. A later request on that thread would skip replicas forever |

A servlet filter sets these and clears them in `finally`. That is sufficient only for work that finishes on the request thread before `chain.doFilter` returns.

```java
try {
    TenantContext.set(authenticatedTenant(request)); // claim on the principal, not a client header
    chain.doFilter(request, response);
} finally {
    TenantContext.clear();
    MDC.clear();
    ReadRoute.clear();
}
```

`SecurityContextHolder.clearContext()` belongs to the security filter; clear tenant and MDC in the same kind of `finally`. A client-supplied `X-Tenant-Id` is not context. It is input. The value you propagate is the one authentication already established (Q253).

---

### 2. `@Async` Does Not Inherit the Caller

`@Async` submits a `Runnable` to a `TaskExecutor`. With a platform pool the worker was started at boot, long before this request. `InheritableThreadLocal` and `SecurityContextHolder.MODE_INHERITABLETHREADLOCAL` copy values when a thread is **created**, not when a task is submitted. The pool worker inherited whatever was on the thread that built the pool, usually nothing. Switching the security strategy does not fix `@Async`.

`TaskDecorator.decorate` runs on the **submitting** thread. That is the moment the caller’s context still exists. The returned `Runnable` installs it on the worker and removes it even when the task throws.

```java
public final class ContextPropagatingDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable task) {
        var callerContext = SecurityContextHolder.getContext();
        var security = SecurityContextHolder.createEmptyContext();
        security.setAuthentication(callerContext.getAuthentication());
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        String tenant = TenantContext.get();
        return () -> {
            SecurityContextHolder.setContext(security);
            if (mdc != null) MDC.setContextMap(mdc); else MDC.clear();
            if (tenant != null) TenantContext.set(tenant); else TenantContext.clear();
            try {
                task.run();
            } finally {
                SecurityContextHolder.clearContext();
                MDC.clear();
                TenantContext.clear();
            }
        };
    }
}
```

```java
@Bean
public ThreadPoolTaskExecutor taskExecutor() {
    var executor = new ThreadPoolTaskExecutor();
    executor.setThreadNamePrefix("async-");
    executor.setCorePoolSize(4);
    executor.setTaskDecorator(new ContextPropagatingDecorator());
    executor.initialize();
    return executor;
}
```

Copy the authentication into a new `SecurityContext`. Do not hand the worker the same mutable object the request filter still holds. Do **not** copy `ReadRoute`: the async task’s transactions decide primary versus replica themselves (Q265). A pin captured for an HTTP redirect is the wrong policy for a background write.

Spring Framework 6.1’s `ContextPropagatingTaskDecorator` does the same capture through Micrometer’s context-propagation registry. Boot’s tracing starter registers the MDC accessor. Tenant and `ReadRoute` are yours: either a `ThreadLocalAccessor` in that registry, or the decorator above. Security has its own accessor in recent Spring Security releases; a second, hand-rolled copy of the same `SecurityContext` is harmless, two competing restorers that clear each other are not. One mechanism.

`@Async` on a method that is called through the Spring proxy starts **after** the caller’s transaction commits only if you arranged that. A direct `@Async` call races the caller’s commit. `@TransactionalEventListener(phase = AFTER_COMMIT)` is the handoff that is allowed to see the rows the request just wrote (Q204). The decorator still has to run, because “after commit” is not “on the same thread.”

---

### 3. Kafka Has No Request Thread

The producer and the consumer are different processes. Nothing in a `ThreadLocal` reaches the listener. What reaches it is a **header**, written while the producer still had the context.

For a `KafkaTemplate` send inside the request, a producer interceptor reads `TenantContext` and adds `tenantId`. For the outbox (Q260), Debezium never saw the HTTP thread. The tenant has to be a **column** on `outbox_events`, copied to a header by the event router (`tenantid:header:tenantId`), next to `traceId` and `eventId`. A trace that exists only in MDC at insert time is already gone when the connector publishes.

On the consumer, listener threads are pooled and outlive any one record. Set context per record and clear it in `afterRecord`, which runs after success and after failure. The next record on that thread must not inherit this one.

```java
public class TenantRecordInterceptor implements RecordInterceptor<String, Object> {
    @Override
    public ConsumerRecord<String, Object> intercept(ConsumerRecord<String, Object> record,
                                                    Consumer<String, Object> consumer) {
        Header header = record.headers().lastHeader("tenantId");
        if (header == null) {
            throw new IllegalStateException("missing tenantId");
        }
        TenantContext.set(new String(header.value(), StandardCharsets.UTF_8));
        return record;
    }

    @Override
    public void afterRecord(ConsumerRecord<String, Object> record, Consumer<String, Object> consumer) {
        TenantContext.clear();
        MDC.clear();
    }
}
```

Reject a missing tenant. Defaulting to “no filter” is how one bad producer reads every customer. The Hibernate filter or the repository that Q253 uses on HTTP then sees the same `TenantContext` on the listener. Trace context is separate: turn on

```properties
spring.kafka.template.observation-enabled=true
spring.kafka.listener.observation-enabled=true
```

with the Micrometer tracing bridge. The framework writes and reads W3C `traceparent` and fills MDC on the listener thread. A second homemade `traceId` header drifts out of date with that one. Business context (tenant, the read-your-writes pin you deliberately do not want here) stays an explicit header. A batch listener is a list of records that may belong to different tenants; do not set one `TenantContext` for the whole batch.

---

### 4. Virtual Threads Change the Leak, Not the Handoff

`spring.threads.virtual.enabled=true` (Boot 3.2+) serves each HTTP request on its own virtual thread. `ThreadLocal` still works. A request-scoped virtual thread dies with the request, so a forgotten `remove()` on that path is a short-lived leak rather than a permanent cross-user bug.

The pool bugs stay wherever a thread is reused:

| Executor | Created when | `InheritableThreadLocal` at submit? | What to do |
| :--- | :--- | :--- | :--- |
| Platform `ThreadPoolTaskExecutor` | Pool startup | No. The worker is not your child | `TaskDecorator` |
| `SimpleAsyncTaskExecutor` with a new virtual thread per task | Submit time, child of the caller | Yes, for inheritable values only | Decorator still required for ordinary `ThreadLocal` (MDC, default security, `TenantContext`) |
| Kafka listener container | Container start | No | Headers + `RecordInterceptor` |
| `@Scheduled` pool | Pool startup | No. There is no caller | Pass the tenant into the job. Do not read “whatever is on the thread” |

`ScopedValue` (final in Java 25, preview before that) is the JDK’s immutable version of this for structured tasks: `ScopedValue.where(TENANT, id).run(...)`, inherited by child virtual threads created inside that scope. It does not cross `@Async` onto a pool, and it does not cross Kafka. Spring Security and MDC are still `ThreadLocal`. A `ScopedValue` you introduce for tenant has to be rebound in the same decorator and the same interceptor. It is not a reason to stop clearing the others.

Virtual threads also do not make a big `ThreadLocal` free. Millions of tasks each holding a fat context is a heap leak with a different shape. Keep the captured map to ids and the authentication token, not to the `HttpServletRequest`. The request object is recycled as soon as the servlet returns; an async task that later calls `RequestContextHolder` is reading another request or a dead one.

---

### 5. WebFlux Is a Different Context

On the servlet stack the carrier is the thread. On WebFlux the carrier is the **Reactor `Context`**, and a chain hops scheduler threads under you. `SecurityContext` and MDC do not follow `publishOn` unless something copies them. Micrometer’s `Hooks.enableAutomaticContextPropagation()`, which Boot’s tracing auto-configuration turns on when the context-propagation library is present, restores registered `ThreadLocal`s at each operator. Tenant still needs a `ThreadLocalAccessor` **and** a place in the Reactor context if the value is born inside the chain. Copying the servlet `TaskDecorator` onto a `WebClient` filter does nothing useful: outbound trace propagation is an observation on the client (`RestClient` / `WebClient`), which injects `traceparent`. Outbound tenant is a header you add, the same header the Kafka producer adds.

---

### 6. Best Practices

| Practice | Rationale |
| :--- | :--- |
| **Set tenant from the authenticated principal** | A propagated header is only as trustworthy as the code that wrote it (Q253) |
| **Clear every context in `finally`** | Pooled threads outlive the request, the task, and the record |
| **`TaskDecorator` (or `ContextPropagatingTaskDecorator`) on every application executor** | `@Async` and `CompletableFuture` executors do not see the caller’s `ThreadLocal` |
| **Capture at submit time, install on the worker, copy the `SecurityContext`** | `decorate` runs on the caller. The worker must not share a mutable context with the filter |
| **Write tenant and trace onto the outbox row** | The connector publishes later, on another process (Q260/Q244) |
| **`RecordInterceptor.afterRecord` clears the listener thread** | One consumer thread handles many tenants in a row |
| **Let Micrometer own `traceparent`** | One trace format across HTTP and Kafka |
| **Do not propagate `ReadRoute`** | Routing follows the new transaction, not the HTTP pin (Q265) |
| **After-commit events for work that must see the write** | `@Async` racing the caller’s transaction reads a replica or a primary that does not have the row yet |
| **Jobs name their tenant** | A scheduler has no caller to inherit from |
| **Do not stash the servlet request in the task** | The container reuses that object |

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **`MODE_INHERITABLETHREADLOCAL` and a platform pool** | `@Async` still sees an anonymous user | `TaskDecorator`. Inheritance happens at thread construction |
| **Decorator without `finally`** | One failure, then every later task logs and queries as that user | Clear security, MDC, and tenant in `finally` |
| **Same `SecurityContext` instance on both threads** | The request filter clearing or replacing authentication mutates the async task | `createEmptyContext()` and set the `Authentication` on it |
| **MDC cleared by the filter before the decorator runs** | Async logs have no `traceId` | Decorate while the request thread still has MDC — submit from inside the request, not from a `finally` that already cleared it |
| **Tenant only in a log field** | Queries are unscoped; logs look fine | `TenantContext` drives the filter. MDC only prints it |
| **`X-Tenant-Id` copied from the client onto Kafka** | Caller picks the tenant | Write the server-resolved tenant onto the outbox |
| **Trace id invented in a second header** | The UI trace and the consumer trace never join | `observation-enabled` and W3C `traceparent` |
| **Interceptor sets tenant and never clears it** | The next order on that listener thread uses the previous tenant | `afterRecord` |
| **One context for a whole batch** | Mixed-tenant batches write one customer’s events into another schema | Per-record context, or a topic partitioned so a batch is one tenant |
| **`@Async` reads rows the caller has not committed** | Intermittent “entity not found” | `@TransactionalEventListener(AFTER_COMMIT)` |
| **Background task uses `RequestContextHolder`** | Random headers, or an exception after the response was sent | Copy the ids you need in the decorator |
| **Forgotten `ReadRoute.remove` on the servlet pool** | Unrelated requests stick to the primary (Q265) | Filter `finally`, and do not copy the pin to workers |

---

### Summary

- Tenant, security, MDC, and the replica pin are **thread-local**. A filter that sets them must clear them. That only covers the request thread.
- `@Async` runs on a worker that was not created for this request. Capture tenant, a **copy** of the `SecurityContext`, and the MDC map in a `TaskDecorator`, and clear them in `finally`. `InheritableThreadLocal` does not do this for a platform pool.
- Kafka crosses a process. Persist tenant and trace on the **outbox** (Q260), publish them as headers, and have a `RecordInterceptor` install the tenant for one record and remove it in `afterRecord`. Leave `traceparent` to Micrometer observation (Q244).
- Virtual threads and `ScopedValue` do not remove pooled listener threads, `@Scheduled` threads, or the network hop. Do not propagate `ReadRoute` (Q265), do not trust a client tenant header (Q253), and do not run async work that must see a commit before that commit exists.

## 267. How do you orchestrate a long-running saga in Spring Boot with Temporal or Camunda? Explain the workflow state machine, compensations, timeouts, and versioning.

Q223 and Q251 showed a saga as a sequence of local transactions with compensating actions. That description leaves out the hard part: **where the saga state lives**. If the orchestrator is a Spring `@Service` method, a pod restart, a deploy, or a 30-minute wait for a warehouse callback destroys it. A durable execution engine - Temporal or Camunda 8/Zeebe - persists every step as an event, so the workflow resumes on another pod, on another day, exactly where it stopped.

---

### 1. Choreography vs Orchestration

| Aspect | Choreography (events only) | Orchestration (Temporal/Camunda) |
| :--- | :--- | :--- |
| **Where the flow lives** | Implicit, spread over consumers | One explicit workflow definition |
| **Debugging a stuck order** | Reconstruct from five Kafka topics | Query the workflow by business id |
| **Adding a step** | New consumer plus new event contracts | Edit the workflow, deploy |
| **Coupling** | Services only know events (loose) | Services expose activities (orchestrator knows them) |
| **Timeout for "warehouse never answered"** | Custom scheduler and state table | `Workflow.await(timeout)` on a durable timer |
| **Compensation order** | Each consumer compensates its own step | Engine tracks the stack (or you do, via `Saga`) |
| **Risk** | Cyclic event flows, invisible state (Q251 pitfall) | Orchestrator becomes a critical dependency |

Use choreography for short, two- or three-hop reactions. Use orchestration when the flow has **waiting** (human approval, payment settlement, shipping), **many steps**, or a business-visible status ("where is my order?") that support must answer.

---

### 2. The Saga as an Explicit State Machine

```
STARTED
  |-- reserve inventory --(fail)--> CANCELLED
  |-- charge payment -----(fail)--> release inventory -> CANCELLED
  |-- await warehouse signal (timer 48h, timeout -> refund + release)  
  |-- ship
  |-- notify
  v
COMPLETED
```

Three rules make this work:

1. **Every step is an activity with its own local transaction.** The workflow never touches a database or a broker directly.
2. **Compensations are registered before their step is confirmed.** If `chargePayment` succeeds but the response is lost, the retry must not charge twice (Q263), and the saga must still know a refund may be owed.
3. **The workflow decides; activities act.** A workflow that reads `System.currentTimeMillis()`, a random number, or a database row is non-deterministic and will corrupt its replay.

---

### 3. Temporal: Workflow, Activities, Worker

```xml

    <groupId>io.temporal</groupId>
    <artifactId>temporal-spring-boot-starter</artifactId>
    <version>1.24.0</version>
</dependency>
```


```java
@WorkflowInterface
public interface OrderSagaWorkflow {
    @WorkflowMethod
    OrderResult run(OrderCommand command);

    @QueryMethod
```

The implementation is ordinary Java with two constraints: **deterministic** and **no blocking I/O**.

```java
public class OrderSagaWorkflowImpl implements OrderSagaWorkflow {

    private static final ActivityOptions OPTS = ActivityOptions.newBuilder()
            .setStartToCloseTimeout(Duration.ofSeconds(30))
            .setRetryOptions(RetryOptions.newBuilder()
                    .setInitialInterval(Duration.ofSeconds(1))
                    .setBackoffCoefficient(2.0)
                    .setMaximumAttempts(5)
                    .setDoNotRetry("com.example.NonRetryablePaymentException")
                    .build())
            .build();

    private final OrderActivities activities =
            Workflow.newActivityStub(OrderActivities.class, OPTS);

    private String trackingNumber;
    private String step = "STARTED";

    @Override
    public OrderResult run(OrderCommand cmd) {
        // Compensations are executed in reverse order of registration
        Saga saga = new Saga(new Saga.Options.Builder()
                .setParallelCompensation(false)
                .setContinueWithError(true)   // one failed refund must not hide the rest
                .build());

        try {
            step = "RESERVE";
            String reservationId = activities.reserveInventory(cmd.orderId(), cmd.items());
            saga.addCompensation(() -> activities.releaseInventory(reservationId));

            step = "CHARGE";
            String paymentId = activities.chargePayment(
                    cmd.orderId(), cmd.total(), "pay-" + cmd.orderId()); // stable key, Q263
            saga.addCompensation(() -> activities.refund(paymentId));

            step = "AWAIT_PACKING";
            // Durable timer: survives restarts, no thread is held while waiting
            boolean packed = Workflow.await(Duration.ofHours(48), () -> trackingNumber != null);
            if (!packed) {
                throw new PackingTimeoutException("Warehouse did not pack within 48h");
            }

            step = "SHIP";
            activities.notifyShipped(cmd.orderId(), trackingNumber, cmd.idempotencyKey());

            step = "COMPLETED";
            return OrderResult.completed(cmd.orderId(), trackingNumber);
        } catch (ActivityFailure | PackingTimeoutException e) {
            step = "COMPENSATING";
            saga.compensate();               // engine records each compensation
            step = "CANCELLED";
            return OrderResult.cancelled(cmd.orderId(), e.getMessage());
        }
    }

    @Override
    public void warehousePacked(String trackingNumber) { this.trackingNumber = trackingNumber; }

    @Override
    public String currentStep() { return step; }
}
```

```java
// Start it once, with the business id as workflow id: a duplicate request cannot start a second saga

        .setWorkflowIdReusePolicy(WorkflowIdReusePolicy.WORKFLOW_ID_REUSE_POLICY_REJECT_DUPLICATE)
        .setWorkflowExecutionTimeout(Duration.ofDays(7))
        .build();

OrderSagaWorkflow workflow = client.newWorkflowStub(OrderSagaWorkflow.class, options);
WorkflowClient.start(workflow::run, command);   // returns immediately; execution is durable
```


`warehousePacked` is a **signal**: the HTTP endpoint that receives the warehouse webhook just calls `workflow.warehousePacked(tracking)` and returns `202`. No thread is parked for two days; the engine stores the timer.

### 4. Camunda 8 (Zeebe): The Same Saga in BPMN

```xml
  <bpmn:compensateEventDefinition/>
</bpmn:boundaryEvent>
```

| Dimension | Temporal | Camunda 8 / Zeebe |
| :--- | :--- | :--- |
| **Definition** | Java code (DSL, testable in JUnit) | BPMN XML/YAML, modeler UI |
| **Best fit** | Engineers own the flow; complex code branches | Business-visible processes, DMN decisions, audit |
| **State** | Event history per workflow | Event stream per process instance |
| **Human tasks** | Signals plus your own UI | Native user tasks (Tasklist) |
| **Waiting** | `Workflow.await` with durable timers | Timers, message catch events |
| **Testing** | `TestWorkflowEnvironment`, `WorkflowReplayer` | `zeebe-test`, `@ZeebeSpringTest` |
| **Ceiling** | Very high throughput, code-first teams | High throughput, BPMN governance |

**Spring Statemachine is not in this category.** It is an in-process state machine: state lives in heap unless you persist it yourself, so a restart loses the saga. Use it for short-lived UI wizards, not multi-day sagas.

### 5. Determinism, Idempotency, and Compensations

| Concern | Rule |
| :--- | :--- |
| **Determinism** | No `Math.random()`, `UUID.randomUUID()`, `System.currentTimeMillis()`, or direct DB/Kafka calls in workflow code. Use `Workflow.randomUUID()`, `Workflow.currentTimeMillis()`, and activities |
| **Retries** | Activity retries are the norm; make each activity idempotent with a **stable business key** (Q263), not the attempt number |
| **Duplicate start** | `setWorkflowId("order-saga-" + orderId)` plus `REJECT_DUPLICATE` gives idempotent saga creation for free |
| **Compensation order** | Reverse order of registration. `Saga` handles it; with BPMN you attach compensation handlers |
| **Partial compensation** | `setContinueWithError(true)` so a failed refund is reported without skipping the inventory release; alert on the aggregate result |
| **Compensation is not a rollback** | It is another forward transaction. It can fail, be retried, and must be idempotent |
| **Waiting** | Use durable timers/signals, never `Thread.sleep` (blocks a worker slot and loses state on restart) |
| **Side effects outside the engine** | If an activity writes to your DB, commit that write before returning success; the engine may retry it |

---

### 6. Timeouts and Deadlines

Layered timeouts, shortest innermost:

```java
ActivityOptions.newBuilder()
    .setScheduleToCloseTimeout(Duration.ofMinutes(5))   // total budget incl. queue wait
    .setStartToCloseTimeout(Duration.ofSeconds(30))     // one attempt
    .setHeartbeatTimeout(Duration.ofSeconds(10))        // long-running activity liveness
    .build();
```

- **`setScheduleToCloseTimeout`** bounds the whole activity; without it a task queue backlog can stall a saga forever.
- **`setHeartbeatTimeout`** plus `Activity.getExecutionContext().heartbeat(...)` in a loop lets the engine detect a dead worker and retry elsewhere.
- **`WorkflowExecutionTimeout`** caps the saga; a 48-hour packing window means something like 7 days overall.
- **Business deadline != technical timeout.** "Refund if not shipped by Friday" is a `Workflow.await` on a timer; "the payment API must answer in 3 seconds" is `StartToCloseTimeout`. Model both.

```java
// Business deadline with an escalation branch instead of an exception
boolean packed = Workflow.await(Duration.ofHours(48), () -> trackingNumber != null);
if (!packed) {
    activities.notifyCustomerDelayed(orderId);   // still compensable afterwards
    throw new PackingTimeoutException("packing SLA missed");
}
```

---

### 7. Versioning a Running Saga

You will deploy while 40,000 sagas are mid-flight. Naive edits break replay.

```java
// Temporal: keep old paths for in-flight executions
int version = Workflow.getVersion("add-fraud-check", Workflow.DEFAULT_VERSION, 2);
if (version >= 2) {
    activities.fraudCheck(orderId);        // new executions take this path
}
// executions started before the deploy replay the old branch and skip the call
```

| Rule | Why |
| :--- | :--- |
| **Never change the meaning of an existing step** | In-flight histories replay the old code path |
| **Add, do not rewrite** | `getVersion` / patching keeps old branches reachable |
| **Do not remove an activity from the interface** | Workers still replaying older code may call it |
| **Drain before large refactors** | Or version the workflow type (`OrderSagaV2`) and route new orders there |
| **Test replay in CI** | `WorkflowReplayer` against captured histories catches non-determinism before prod |

```java
@Test
void histories_still_replay() throws Exception {
    WorkflowReplayer.replayWorkflowExecution(
        new File("src/test/resources/histories/order-saga-8842.json"),
        OrderSagaWorkflowImpl.class);
}
```

For BPMN, the equivalent discipline is **additive process changes with version tags** and letting old instances finish on the old definition.

### 8. Observability and Operations

| Need | Temporal | Camunda |
| :--- | :--- | :--- |
| **"Where is order 8842?"** | `client.newWorkflowStub(..., workflowId).currentStep()` (query, Q266-safe) | Operate: instance by business key |
| **Stuck workflow alerts** | `temporal_workflow_task_schedule_to_start_latency`, task queue backlog | `zeebe_job_...` metrics, incident count |
| **Tracing** | Propagate `traceparent` via `WorkflowClientInterceptor` / context propagator (Q244) | Zeebe propagates `traceparent` on job headers |
| **Logging** | Log in activities, not workflows (workflow code may run many times during replay) | Job worker logs |
| **Retention** | Namespace retention plus archival | Data retention plus exporters |

Log inside **activities**, never inside workflow code: replay executes that code repeatedly and your log volume will explode with duplicate "step 2 done" lines.

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **I/O inside the workflow** | Non-deterministic workflow task failures, stuck histories | Move all I/O to activities (or job workers) |
| **`Thread.sleep` or blocking wait** | Worker slot pinned, saga lost on restart | `Workflow.await` with a durable timer |
| **Unstable idempotency key** | Double charge after retry | Key from business id (`pay-<orderId>`), not `UUID.randomUUID()` (Q263) |
| **Compensation not registered before the step** | Orphaned reservation when the response is lost | Register compensation immediately after success, before the next call |
| **Compensation throws and stops the chain** | Inventory never released after refund failure | `setContinueWithError(true)` and alert on partial compensation |
| **No `WorkflowExecutionTimeout`** | Zombie sagas accumulate for months | Set an overall cap plus business timers |
| **Workflow id from a random UUID** | Duplicate sagas for one order | Workflow id = business id, with `REJECT_DUPLICATE` |
| **Editing workflow code during rollout** | `NonDeterministicWorkflowTask` errors | `getVersion`, or a new workflow type per breaking change |
| **Treating Spring Statemachine as durable** | Saga state vanishes on pod restart | Persist state yourself, or use Temporal/Camunda |
| **Orchestrator as a shared database of truth** | Services query workflow history for business data | Keep business state in your service DB; the workflow is a coordinator |
| **Blocking HTTP webhook waiting for saga end** | Client times out after 30s on a 2-day saga | Return `202` with a status URL/poll or an SSE/WebSocket update (Q228) |

### Summary

- Choreography hides the flow in events; **orchestration makes it one durable, queryable state machine**. Pick orchestration when the saga waits on humans, money, or shipping.
- **Temporal** = code-first workflow plus activities with retries and durable timers. **Camunda 8** = BPMN plus job workers when the process must be readable by the business. **Spring Statemachine is in-process only** and does not survive a restart.
- Keep workflows **deterministic**: no I/O, no clocks, no random values. All side effects live in idempotent activities keyed by business id (Q263).
- Model **both** timeouts: technical (`StartToClose`, `ScheduleToClose`, heartbeat) and business delays (durable `Workflow.await` timers). Register compensations in reverse, and let one failure not skip the rest.
- Ship safely: **version with `getVersion`** (or a new workflow type), replay captured histories in CI, query step state for support, and trace via propagated `traceparent` (Q244/Q266).

## 268. How do you run a multi-region active-active Spring Boot system? Explain write affinity, conflict resolution, read-your-writes, and failover.

A single-region deployment has one writer and one clock. **Active-active** runs the same service in two or more regions, each accepting writes. That buys latency (users write to their nearest region), availability (one region can die), and data-residency compliance - and costs you the two guarantees you used to get for free: **one order of events** and **one winner per row**. CAP (Q240) says you cannot have both consistency and availability across a partition, so the architecture decision is really "which conflicts am I willing to resolve, and how".

---

### 1. Choose the Topology Before the Database

| Topology | Writes | Reads | Typical use |
| :--- | :--- | :--- | :--- |
| **Active-passive (warm standby)** | One region | One region | Simplest. Failover in minutes, RPO measured in seconds |
| **Active-active, partitioned writes** | Each key has exactly **one home region** | Anywhere (may be stale) | Most SaaS. No write-write conflict by construction |
| **Active-active, multi-writer** | Any region can write any key | Anywhere | Only with CRDTs or business merge rules. Rare and expensive |
| **Active-active, read-local/write-global** | Single global writer | Local replicas | Read-heavy catalogues, dashboards |

**Default recommendation:** partitioned writes. Assign every customer/tenant/order to a **home region** and route all mutations for that key there. You keep local write latency, avoid most conflicts, and still serve reads globally.

```java
public record Region(String id, boolean healthy) {}

@Component
public class HomeRegionRouter {

    // Home region is stable data, not a runtime choice: it lives with the tenant record (Q253)
    public Region homeRegionFor(Tenant tenant) {
        return tenant.homeRegion();
    }

    public boolean canWriteLocally(Tenant tenant, Region self) {
        return tenant.homeRegion().id().equals(self.id());
    }
}
```

```java
@PostMapping("/orders")
public ResponseEntity<?> create(@RequestBody CreateOrder cmd, @AuthenticationPrincipal Jwt jwt) {
    Tenant tenant = tenantService.byId(jwt.getClaimAsString("tenant_id"));
    if (!router.canWriteLocally(tenant, selfRegion)) {
        // 307 keeps the method and body; the client re-sends to the owner region
        return ResponseEntity.status(HttpStatus.TEMPORARY_REDIRECT)
                .location(URI.create(tenant.homeRegion().publicBaseUrl() + "/orders"))
                .build();
    }
    return ResponseEntity.ok(orderService.create(cmd)); // local transaction, Q223
}
```

Redirect at the edge (Route53/Cloudflare/API gateway, Q239) is better than redirecting in application code; the router above is the fallback when the gateway cannot see the tenant claim.

---

### 2. The Three Conflict Families

| Conflict | Example | Mechanism |
| :--- | :--- | :--- |
| **Write-write on one row** | Two regions set `status = SHIPPED` and `CANCELLED` | Single-writer-per-key, version check (Q264), or LWW with a total order |
| **Concurrent increments** | Stock decremented in both regions | CRDT counter, or reserve-per-region quotas |
| **Ordering across events** | `OrderShipped` reaches region B before `OrderCreated` | Per-aggregate partition key (Q212) plus causal delivery, or reconciliation job |

Only the first family is cheap to solve. That is why **partitioned writes dominate**: eliminate the conflict instead of resolving it.

---

### 3. Resolution Strategies That Actually Work

**a) Last-write-wins with a hybrid logical clock.** Simple, lossy, and acceptable only for independent fields (profile name, preference flags) - never for money or stock.

```java
public record Hlc(long physicalMillis, int counter, String regionId) implements Comparable<Hlc> {
    @Override
    public int compareTo(Hlc o) {
        int byTime = Long.compare(physicalMillis, o.physicalMillis);
        if (byTime != 0) return byTime;
        int byCounter = Integer.compare(counter, o.counter);
        return byCounter != 0 ? byCounter : regionId.compareTo(o.regionId); // deterministic tiebreak
    }
}

public final class LwwRegister<T> {
    private T value;
    private Hlc stamp;

    public synchronized boolean merge(T incoming, Hlc incomingStamp) {
        if (stamp == null || incomingStamp.compareTo(stamp) > 0) {
            value = incoming; stamp = incomingStamp; return true;
        }
        return false; // older or equal: drop, do not apply
    }
}
```

The region id in the tiebreak is what makes two regions converge on the **same** winner. Without it, A and B each keep their own value and never reconcile.

**b) CRDTs for counters and sets.** A grow-only counter is a vector of per-region counts; the value is the sum, and merges are order-independent.

```java
public final class GCounter {
    private final Map<String, Long> perRegion = new ConcurrentHashMap<>();

    public void increment(String regionId, long delta) {
        perRegion.merge(regionId, delta, Long::sum);
    }

    public void merge(GCounter other) {
        other.perRegion.forEach((region, count) -> perRegion.merge(region, count, Math::max));
    }

    public long value() { return perRegion.values().stream().mapToLong(Long::longValue).sum(); }
}
```

This works for "views", "likes", "bytes uploaded". It does **not** work for inventory, where you need a decrement that cannot go below zero - use per-region reservations with a global reconciliation job instead.

**c) Business merge plus a conflict log.** For domain rules a machine cannot decide (two refunds approved by two agents), persist both versions and surface them.

```sql
CREATE TABLE conflict_log (
  id            BIGSERIAL PRIMARY KEY,
  entity_type   TEXT NOT NULL,
  entity_id     TEXT NOT NULL,
  region_a      TEXT NOT NULL,
  region_b      TEXT NOT NULL,
  payload_a     JSONB NOT NULL,
  payload_b     JSONB NOT NULL,
  detected_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  resolved_at   TIMESTAMPTZ,
  resolved_by   TEXT,
  resolution    TEXT
);
```

An unresolved conflict older than N minutes is an **alert** (Q230), not a silent row.

---

### 4. IDs, Time, and Ordering

| Rule | Why |
| :--- | :--- |
| **No auto-increment across regions** | Two regions allocate the same id. Use UUIDv7/ULID (time-ordered, index-friendly) or a region-prefixed snowflake |
| **Never order by wall-clock timestamps from different regions** | Clocks drift. Use HLC or the database commit order per region |
| **Keep a region code in the id when debugging** | `01H...` prefixed with region makes cross-region tracing obvious (Q244) |
| **`created_at` is data, not ordering** | Order by aggregate version (Q264), not `created_at` |
| **Sequence per aggregate, not per table** | Version column increments only for that aggregate, so gaps are expected and harmless |

---

### 5. Read-Your-Writes Across Regions

Replication lag means a user who just wrote may read an older value from the local replica.

```java
// Return a session token that encodes the write position, then require the read to reach it
public record SessionToken(String regionId, long commitLsn) {}

@GetMapping("/orders/{id}")
public OrderDto get(@PathVariable String id,
                    @RequestHeader(value = "X-Session-Token", required = false) String token) {

    SessionToken required = token == null ? null : SessionTokenCodec.decode(token);

    if (required != null && !replica.hasReached(required)) {
        // Local replica is behind the write this user just made: read the owner region
        return ownerClient.get(id, required);
    }
    return replica.get(id);  // local, fast, possibly slightly stale for other users
}
```

Options, cheapest first:

1. **Sticky reads for the session** - route the user's reads to the home region for a short window (e.g., 30s) after a write.
2. **Session token / LSN check** - read locally only if the replica has caught up to the token; otherwise read the owner.
3. **Monotonic reads via version check** - the client sends the last version it saw; if the replica is older, wait or redirect.

Do not solve this with "read from primary always": that discards the entire latency benefit of the second region.

---

### 6. Replication and Cross-Region Events

Replicate with the database's native mechanism (Postgres logical replication, Aurora Global Database, CockroachDB/Spanner multi-region) or with CDC (Debezium, Q260) into Kafka per region.

Rules that prevent the classic failures:

- **Replicate the outbox, not the domain tables** for downstream services (Q260). One ordered stream per aggregate, keyed by aggregate id (Q212).
- **Consumers are idempotent across regions** - a replayed event after failover is normal, not an error (Q262/Q263).
- **Do not dual-write to two regions from one transaction.** Two-phase commit across regions is a latency and availability trap (Q223). Write locally, replicate, reconcile.
- **Never let a replica apply a write for a key it does not own** - reject or forward, so split brain cannot create two histories.
- **Track replication lag as an SLI** (Q230). Cross-region lag is the number that decides whether a failover is safe.

```yaml
# Alert when cross-region replication lag threatens the RPO
- alert: CrossRegionLagHigh
  expr: pg_replication_lag_seconds{region!="primary"} > 30
  for: 5m
  labels: { severity: page }
  annotations:
    summary: "Replication lag exceeds RPO; failover would lose writes"
```

---

### 7. Failover and Failback

| Phase | What must be true |
| :--- | :--- |
| **Detect** | Regional health from outside the region (synthetic probes, Q250), not from a pod inside it |
| **Fence** | The failed region must not come back and accept writes with stale data. Revoke its credentials or flip its routing to read-only (Q243/Q265) |
| **Promote** | Promote the replica with the highest LSN; record the divergence window |
| **Redirect** | DNS/anycast plus gateway rules; keep TTLs low enough to matter (30-60s) |
| **Reconcile** | Replay the divergence window from the outbox; resolve conflicts through the rules above |
| **Fail back** | Only after the old region is rebuilt from the new primary, never by "just pointing DNS back" |

Failback is where most incidents get worse. Treat it as a **planned migration with a freeze**, not a revert.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **True multi-writer without a merge rule** | Two regions both "win"; data diverges permanently | Partition writes by home region, or adopt CRDTs/LWW with deterministic tiebreak |
| **LWW on money or stock** | Silently lost decrement, oversold inventory | Single-writer per key or reservations plus reconciliation; never LWW for quantities |
| **Dual-write to both regions in one request** | One write succeeds, one fails, no rollback | Write locally + replicate (outbox/CDC), Q260 |
| **Trusting `created_at` for ordering** | Out-of-order processing after failover | Aggregate version or per-partition sequence (Q264) |
| **No fencing on failover** | Old region returns and accepts writes; split brain | Revoke credentials / force read-only before promotion |
| **Auto-increment ids** | Duplicate primary keys after merge | UUIDv7/ULID or region-prefixed ids |
| **Reading local replica right after a write** | User sees their own change disappear | Session token, sticky reads, or read-owner fallback |
| **Cross-region 2PC for consistency** | Latency spikes, blocked transactions when a region is slow | Sagas and idempotent reconciliation (Q223/Q267) |
| **Data residency ignored** | EU tenant data replicated to US | Region-pinned tenants plus replication filters; verify at the storage layer, not just routing (Q253) |
| **Failover never rehearsed** | First real failover is the first test | Game days with fencing, promotion, and reconciliation in staging |
| **Lag not monitored** | Failover loses hours of writes silently | Lag SLI with page-level alert tied to RPO/RTO (Q230) |

### Summary

- **Partition writes by home region** by default. Eliminating conflicts is cheaper and safer than resolving them; only use multi-writer when the data model is genuinely conflict-free (CRDTs) or the business can merge.
- **Resolve with a deterministic rule**: HLC + region-id tiebreak for LWW on independent fields, CRDTs for counters/sets, and a **conflict log with an alert** for anything a machine must not guess.
- **IDs and ordering**: UUIDv7/ULID, per-aggregate version columns, never cross-region wall-clock ordering, never auto-increment.
- **Read-your-writes** via session tokens, sticky reads, or read-owner fallback - not by always reading the primary.
- **Failover is a four-part operation**: detect from outside, **fence the old region**, promote the highest-LSN replica, then reconcile from the outbox. `git revert` has no equivalent here, so rehearse it and monitor replication lag as an SLI.

## 269. How do you implement audit trails and GDPR-compliant erasure in Spring Boot? Explain append-only logs, Hibernate Envers, and crypto-shredding.

Two requirements get conflated and then implemented badly. An **audit trail** answers "who changed what, when, from where" and must be **immutable and retained**. An **erasure request** (GDPR Art. 17, CCPA) says personal data must be **gone**, and "gone" includes replicas, backups, caches, search indexes, and event logs. Keeping a permanent audit log and honouring deletion at the same time is only possible if the audit log stores a **pseudonymous subject key** rather than the personal data itself, and if the personal data is encrypted with a **per-subject key you can destroy**.

---

### 1. Two Problems, Two Designs

| | Audit trail | Erasure |
| :--- | :--- | :--- |
| **Goal** | Prove what happened | Remove personal data |
| **Lifetime** | Years, often immutable/WORM | Until the request, then gone |
| **Mutability** | Append-only, tamper-evident | Destructive by design |
| **Contains PII?** | Ideally no. Actor id, subject pseudonym, action, diff of non-PII fields | Was PII, must stop being readable |
| **Failure mode** | Missing or editable entries | Data still readable somewhere (backups, logs, index) |

The bridge between them: the audit row references `subject_id`, and `subject_id` is an internal identifier whose mapping to a human is deletable. After erasure the audit trail still reads "user 8f3c... cancelled order 8842" - useful, and no longer personal data.

---

### 2. Audit Trail: What to Store

```java
@Entity
@Table(name = "audit_event", indexes = {
        @Index(name = "ix_audit_subject", columnList = "subject_id, occurred_at"),
        @Index(name = "ix_audit_actor", columnList = "actor_id, occurred_at")
})
public class AuditEvent {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String eventType;        // ORDER_CANCELLED, ROLE_GRANTED, DATA_EXPORTED
    private String actorId;          // authenticated principal, not an email
    private String actorType;        // USER, SERVICE, SYSTEM
    private String subjectId;        // pseudonymous internal id; the erased-then-audit bridge
    private String resourceType;     // ORDER
    private String resourceId;       // 8842
    private String outcome;          // SUCCESS, DENIED

    @Column(columnDefinition = "jsonb")
    private String changes;          // {"status": ["PAID","CANCELLED"]} - field-level diff

    private String requestId;        // correlates with the access log (Q244)
    private String ipHash;           // salted hash, not the raw IP
    private Instant occurredAt;

    private String prevHash;         // hash chain
    private String entryHash;
}
```

```java
@Service
public class AuditWriter {

    private final AuditRepository repo;
    private final ObjectMapper mapper;

    @Transactional(propagation = Propagation.REQUIRES_NEW)  // audit survives a rolled-back business TX
    public void append(AuditEvent event) {
        AuditEvent previous = repo.findTopByOrderByIdDesc();   // single writer, or a DB sequence
        event.setPrevHash(previous == null ? GENESIS : previous.getEntryHash());
        event.setOccurredAt(Instant.now());
        event.setEntryHash(sha256(event.getPrevHash() + canonicalJson(event, mapper)));
        repo.save(event);
    }
}
```

Why the hash chain matters: an attacker with SQL access can edit a row, but cannot recompute every subsequent `entryHash` without also rewriting the chain - and if the head hash is periodically published (object storage with WORM/Object Lock, or a separate log service), tampering becomes detectable.

| Audit rule | Reason |
| :--- | :--- |
| **Write in `REQUIRES_NEW`** | A failed business transaction must still leave "attempt denied" evidence |
| **Never update or delete** | Revoke `UPDATE`/`DELETE` grants on the table for the app user |
| **Store diffs, not snapshots** | A full row snapshot leaks PII and bloats storage; store changed fields only |
| **No free-text PII** | No emails, names, card numbers, or request bodies in `changes` |
| **Audit reads too** | "Who viewed this record" matters for health/finance domains |
| **Emit for security events** | Login failures, role changes, export/download, admin impersonation (Q249) |

Ship the audit row in the **same local transaction** as the mutation when possible, or via the outbox (Q260) when the audit sink is remote - never a best-effort `@Async` call that can be lost.

---

### 3. Hibernate Envers vs a Hand-Rolled Table

| Aspect | Envers (`@Audited`) | Custom audit table |
| :--- | :--- | :--- |
| **Effort** | Minutes: annotate entities, add `_AUD` tables | You design schema, writer, and diffing |
| **Coverage** | Field-level history of audited entities, automatic | Only what you explicitly write |
| **Includes business intent** | No. Knows "column changed", not "user cancelled order" | Yes: `eventType`, outcome, actor |
| **PII risk** | Copies every field, including PII, into history tables | You control exactly what is stored |
| **Queries** | `AuditReader` for revisions, `forRevisionsOfEntity` | Plain SQL, easy to join |
| **Retention/erasure** | Hard: history rows must be scrubbed too | Crypto-shredding works if PII columns are encrypted |

Envers is the right choice for **internal compliance history of master data** (who edited this price list), and a poor fit for **personal data** unless the audited PII columns are encrypted per subject - otherwise every revision pins a copy of the data forever.

```java
@Entity
@Audited                                  // creates order_aud with REV/REVTYPE columns
public class Order {
    @Id private Long id;
    @NotAudited private String internalNote;
    private String status;                // audited: safe, non-PII
}
```

```yaml
spring:
  jpa:
    properties:
      org.hibernate.envers.audit_table_suffix: _aud
      org.hibernate.envers.store_data_at_delete: true
      org.hibernate.envers.revision_on_collection_change: false
```

```java
// Read history
AuditReader reader = AuditReaderFactory.get(entityManager);
List<Number> revisions = reader.getRevisions(Order.class, 8842L);
Order old = reader.find(Order.class, 8842L, revisions.get(0));
```

Use **Envers for non-PII state history**, and a **custom event log for business/security events**. Most mature systems end up with both.

---

### 4. Classify PII Before You Store It

| Class | Examples | Handling |
| :--- | :--- | :--- |
| **Direct identifier** | Name, email, phone, national id, card PAN | Encrypt per subject; never in logs or audit |
| **Quasi-identifier** | Birth date, postcode, IP | Hash or truncate where the exact value is not needed |
| **Sensitive** | Health, biometrics, religion | Encrypt, restrict by role, separate key |
| **Derived** | `age_bucket`, `country` | Prefer over raw values; analytics rarely needs raw |
| **Operational** | `order_id`, `tenant_id` | Safe to keep; these are what the audit trail needs |

Rules that prevent most incidents:

- **Do not log PII.** Scrub request bodies and mask fields in a Logback converter (Q214); a stack trace containing an email is a reportable leak.
- **Do not put PII in URLs** (path, query, referrer) - it lands in access logs and browser history.
- **Do not put PII in Kafka keys or headers** (Q212) - headers are not encrypted by default and keys are visible in tooling.
- **Tokenise where a surrogate works**: store `payment_token` from the PSP instead of the PAN; you inherit their compliance scope instead of building it.

---

### 5. Erasure: Three Options

| Option | Mechanism | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Hard delete** | `DELETE FROM customer WHERE id = ?` and cascade | Simple, truly gone in the primary | Cannot reach immutable backups; breaks referential history; audit trail loses its subject |
| **Pseudonymisation** | Overwrite PII columns with `ERASED-<uuid>`, keep the row | Keeps FK integrity and analytics counts | Data may still exist in backups, replicas, and history tables |
| **Crypto-shredding** | Encrypt PII with a **per-subject key**; delete the key | Instant, works on replicas and backups, no rewrite of millions of rows | Requires envelope encryption and key custody; irreversible by design |

Crypto-shredding is the only option that satisfies erasure across **immutable** copies (backups, snapshots, WORM archives), because the ciphertext may remain but becomes undecryptable once the key is destroyed.

---

### 6. Crypto-Shredding in Practice

Envelope encryption: a **key encryption key (KEK)** in KMS/Vault (Q243) wraps a **data encryption key (DEK)** per subject. Ciphertext stored in the database is AES-GCM with that DEK.

```java
@Component
public class SubjectKeyService {

    private final KmsClient kms;          // AWS KMS, GCP KMS, or Vault Transit
    private final SubjectKeyRepository keys;

    // One DEK per subject; cached briefly, never logged
    public SecretKey dataKeyFor(String subjectId) {
        SubjectKey record = keys.findActive(subjectId)
                .orElseGet(() -> createKey(subjectId));
        byte[] wrapped = kms.decrypt(record.getWrappedDek(), record.getKeyContext());
        return new SecretKeySpec(wrapped, "AES");
    }

    public void shred(String subjectId) {
        keys.findActive(subjectId).ifPresent(record -> {
            kms.scheduleKeyDestruction(record.getKekId(), record.getKeyContext()); // 7-day window
            keys.markDestroyed(subjectId, Instant.now());   // keep the row, lose the material
        });
    }

    private SubjectKey createKey(String subjectId) {
        KmsDataKey dek = kms.generateDataKey("alias/pii-subject");
        return keys.save(new SubjectKey(subjectId, dek.getCiphertextBlob(), dek.getKeyContext()));
    }
}
```

```java
@Service
public class CustomerPiiService {

    private final SubjectKeyService keys;
    private final AesGcmCipher cipher;   // AES/GCM/NoPadding, random 12-byte IV per value

    public String storeEmail(String subjectId, String email) {
        return cipher.encrypt(keys.dataKeyFor(subjectId), email);  // base64(iv || ciphertext)
    }

    public String readEmail(String subjectId, String stored) {
        try {
            return cipher.decrypt(keys.dataKeyFor(subjectId), stored);
        } catch (KeyDestroyedException e) {
            return null;   // erased by design, not an error
        }
    }
}
```

Key custody rules:

- **KEK never leaves KMS.** The app only handles wrapped DEKs.
- **Key context/AAD binds the ciphertext** to `subjectId`, so a copied blob cannot be decrypted under another subject.
- **Destruction is scheduled, not instant** (KMS minimum is typically 7 days) - your SLA must account for it, and legal hold must be checked **before** scheduling.
- **`markDestroyed` is the audit record.** Never delete the `subject_key` row; "key existed and was destroyed at T" is the evidence.
- **Rotation is not shredding.** Rotating a DEK means re-encrypting; destroying the old key without re-encrypting is data loss.

---

### 7. Erasure Reaches Everywhere

Deleting the row in the primary is the easy 10%. The remaining 90%:

| Store | What to do |
| :--- | :--- |
| **Primary DB** | Overwrite PII columns, or delete the row; keep non-PII history |
| **Read replicas** (Q265) | Follow the primary; verify after replication lag |
| **Backups / snapshots** | Key destruction covers them; otherwise document the retention window as the residual risk |
| **Caches** (Q229) | Evict keys by subject prefix; a Redis entry can outlive the DB row |
| **Search index** (Q225) | Delete/reindex the document; ES `_delete_by_query` plus refresh |
| **Object storage** | Delete objects and non-current versions (S3 versioning keeps old copies) |
| **Logs** (Q214) | Redact at write time; retroactive log scrubbing is expensive and often incomplete |
| **Kafka / event log** (Q212) | Tombstone keyed by subject; compacted topics eventually drop it - consumers must handle tombstones |
| **Outbox** (Q260) | Erase or encrypt payloads; pending events may still carry PII |
| **Data warehouse / analytics** | Delete by subject id in the ELT pipeline; re-run affected aggregates |
| **ML feature store / exports** | Feature rows and CSV exports are the most commonly forgotten copies |
| **Audit log** | Keep it, but only the pseudonym; the mapping row is what gets erased |

Track this as an **erasure runbook with a checklist and an SLA** (e.g., 30 days), and record per-store completion so you can prove it.

```java
@Service
public class ErasureService {

    @Transactional
    public ErasureReceipt erase(String subjectId, String requestId) {
        if (legalHoldService.isOnHold(subjectId)) {
            throw new ErasureBlockedException("Legal hold active");
        }

        customerRepository.pseudonymise(subjectId, "ERASED-" + requestId);
        cacheEvictor.evictByPrefix("customer:" + subjectId);
        searchIndexer.deleteBySubject(subjectId);
        outboxWriter.append(new SubjectErased(subjectId, requestId));  // Q260
        keyService.shred(subjectId);                                   // only after the above commit

        auditWriter.append(AuditEvent.erasure(subjectId, requestId));
        return new ErasureReceipt(requestId, Instant.now(), "SCHEDULED_KEY_DESTRUCTION");
    }
}
```

Shred the key **last**: if the shred succeeds and a later step fails, you cannot retry the earlier steps against readable data.

---

### 8. Access Requests, Retention, and Legal Hold

- **Right of access / portability**: assemble an export from every store in the same checklist, deliver it out-of-band with an expiring link, and audit the export itself (`DATA_EXPORTED`).
- **Retention schedule**: define per-entity TTLs (orders 10 years for tax, marketing leads 24 months). Automate deletion jobs; do not rely on "we'll clean it later".
- **Legal hold** overrides erasure and retention. Check it in one place (`legalHoldService`) and audit the block.
- **Consent vs contract basis**: store the lawful basis and its timestamp; deleting data you were legally required to keep is its own violation.
- **Minimisation beats deletion tooling**: the cheapest erasure is the field you never collected.

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Audit row in the business transaction** | Denied/failed attempts leave no trace | `REQUIRES_NEW` or outbox-driven append |
| **PII copied into `changes` JSON** | Audit log becomes an un-erasable PII store | Store field names and non-PII values; hash identifiers |
| **Envers on PII entities** | Every revision pins a copy forever | Encrypt audited PII columns per subject, or `@NotAudited` them |
| **Deleting the DEK row** | No evidence the key ever existed | Keep the row with `destroyed_at`; destroy only the KMS material |
| **Shredding before dependent steps** | Cannot retry the remaining stores | Shred last, after the erasure job commits |
| **Forgetting S3 object versions** | "Deleted" file still downloadable | Delete non-current versions, or rely on key destruction |
| **PII in URLs, headers, or logs** | Data persists outside any store you can erase | Redact at write time; log fields, not bodies |
| **Kafka compacted topic holds PII** | Event replay resurfaces the erased subject | Tombstone the key; consumers must handle tombstones (Q212) |
| **Legal hold ignored** | Data deleted during litigation | Single `legalHoldService` check before any erasure |
| **Assuming key destruction is instant** | Erasure SLA missed by the KMS window | Publish the real timeline; use a shorter window where policy allows |
| **No per-subject key** | Crypto-shredding impossible without a full re-encrypt | Design envelope encryption before the first PII row |
| **Audit table writable by the app** | Tampering undetectable | Revoke `UPDATE`/`DELETE`, add hash chain plus WORM export |

### Summary

- **Audit and erasure are different systems.** The audit trail stores `actor`, `subject_id`, `eventType`, and a non-PII diff, append-only and tamper-evident (hash chain plus WORM export); personal data stays out of it.
- **Envers** gives field-level history cheaply for non-PII master data; a **custom event log** carries business and security intent. Mixing them is normal.
- **Crypto-shredding** (envelope encryption with a per-subject DEK, KEK held in KMS/Vault) is the only erasure that reaches backups, snapshots, and replicas; destroy the key **last**, keep the `subject_key` row as evidence, and check **legal hold** first.
- **Erasure is a checklist, not a `DELETE`**: primary, replicas, caches, search, object versions, logs, Kafka, outbox, warehouse, feature store, exports. Track completion per store and publish an SLA that respects the KMS destruction window.
- **Minimise and redact at write time.** Every email never logged and every field never collected is a store you do not have to erase, and an incident you do not have to report.
