# Java Interview Questions (Advanced Level)

## 176. How does `CopyOnWriteArrayList` work internally? Explain copy-on-write semantics, why reads need no locking, the writer's `ReentrantLock`, snapshot iterators, and when to use it vs `ConcurrentLinkedQueue` or a synchronized `ArrayList`.

`CopyOnWriteArrayList` is a thread-safe `List` whose name describes its strategy exactly: **every mutating operation copies the entire backing array** before modifying it, and publishes the new array. This makes reads completely lock-free and never blocking, at the cost of making writes expensive â€” `O(n)` copy plus an array allocation on every add/remove/set.

---

### 1. The Core Data Structure: A `volatile Object[]`

The list holds its elements in a single array field that is declared `volatile`:

```java
public class CopyOnWriteArrayList<E> implements List<E> {
    private transient volatile Object[] array;
}
```

The entire thread-safety of the *read* path rests on that one `volatile` reference:

- **Reads** load `array` once and index into it â€” they never take a lock.
- **Writes** work on a **fresh copy** of the array, and then publish it with a single `volatile` write (`setArray(newArray)`).
- Because a reader either sees the old array or the new array (never a partially-updated one), reads are always consistent.

```java
// The whole read path â€” no lock, no CAS:
@SuppressWarnings("unchecked")
private E get(Object[] a, int index) {
    return (E) a[index];
}

public E get(int index) {
    return get(getArray(), index);   // volatile read of the array ref
}
```

---

### 2. The Write Path: Copy â†’ Modify â†’ Publish

All writes are guarded by a single **`ReentrantLock`** (so that two concurrent writers cannot copy-then-publish out of order) and follow the same three steps:

```java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // 1. copy
        newElements[len] = e;                                     // 2. modify
        setArray(newElements);                                    // 3. publish (volatile write)
        return true;
    } finally {
        lock.unlock();
    }
}
```

`remove` follows the same pattern but uses `System.arraycopy` to skip the removed element. The cost profile:

| Operation | Cost | Why |
| :--- | :--- | :--- |
| `get(i)`, `iterator()` | `O(1)` | Just indexes / wraps the current array â€” no lock. |
| `add(e)`, `add(i, e)`, `remove(i)` | `O(n)` | Copies the whole array, allocates a new one. |
| `set(i, e)` | `O(n)` | Still copies; there is no in-place element write. |
| `size()` | `O(1)` | Reads `array.length`. |

Every single write allocates a new array â€” which is also why `CopyOnWriteArrayList` puts pressure on the young generation of the GC when written frequently.

---

### 3. Snapshot Iterators (Weakly Consistent, Never Fail-Fast)

The `iterator()` (and `listIterator()`) returned by `CopyOnWriteArrayList` hold a **snapshot** of the array captured at creation:

```java
public Iterator<E> iterator() {
    return new COWIterator<E>(getArray(), 0);   // freezes the current array
}
```

Consequences:

- The iterator **never throws `ConcurrentModificationException`**, even if the list is modified while iterating.
- It sees a **consistent point-in-time view** â€” modifications made after the iterator was created are invisible to that iterator.
- The iterator does **not** support `remove()` (throws `UnsupportedOperationException`), because removing from a snapshot would be meaningless.

This is the opposite of `ArrayList`'s fail-fast behavior, and it makes copy-on-write iterators safe to hold across concurrent writes â€” at the cost of the snapshot being stale by design.

---

### 4. Mutations During Iteration: What Actually Happens

Consider two threads: T1 iterating, T2 calling `add(e)`.

1. T2 copies the array, appends `e`, and publishes the new array (volatile write).
2. T1's iterator keeps its reference to the **old** array, so it keeps iterating the old snapshot.
3. T1 is never interrupted and never sees inconsistent data â€” it simply does not see `e`.

This is the fundamental trade-off: **iteration is stable but may miss concurrent updates**, and elements added/removed mid-iteration may not appear (a copy-on-write list is not a live view).

---

### 5. Comparison With Alternatives

| Use case | `CopyOnWriteArrayList` | `Collections.synchronizedList(new ArrayList<>())` | `ConcurrentLinkedQueue` |
| :--- | :--- | :--- | :--- |
| **Reads** | Lock-free `O(1)` | Contended synchronized `get` | Volatile-free traversal |
| **Writes** | `O(n)` array copy + allocation | `O(1)` amortized (locked) | `O(1)` lock-free CAS |
| **Iteration** | Snapshot (never CME) | Fail-fast (CME possible) | Weakly consistent, no CME |
| **Index access** | Yes (`get(i)`) | Yes | No (queue, head-only ops) |
| **Best when** | Read-dominated, iteration-heavy, rare writes (e.g., listener/callback lists) | Simple correctness under modest contention | Producer-consumer hand-offs |

**The rule of thumb:** `CopyOnWriteArrayList` wins when *reads and traversals vastly outnumber writes* â€” classic examples are listener/observer registries in frameworks (each event iterates the whole list; listeners are added rarely). If you write frequently, the array copying dominates and a synchronized or concurrent alternative is better.

---

### 6. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Treating it as a general-purpose thread-safe `ArrayList` | Write-heavy code runs slower than expected | Use a `ConcurrentHashMap` or synchronized list |
| Using stale iterators to read "current" state | Missing recently-added elements | Re-acquire an iterator (or `get(i)`) for fresh data |
| Calling `listIterator.remove()` | `UnsupportedOperationException` | Remove via the list, not the iterator |
| Assuming `addIfAbsent`/`addAllAbsent` are cheap | Unexpected allocation spikes | These also copy on every call |

### Summary

- `CopyOnWriteArrayList` keeps a **`volatile Object[]`**; reads index into it with **no lock at all**.
- **Writes copy the whole array, mutate the copy, and publish it** with one volatile write â€” `O(n)` per mutation, guarded by a single `ReentrantLock`.
- Iterators are **snapshot-based**: weakly consistent, never fail-fast, but invisible to later writes and do not support `remove()`.
- It is the right choice for **read- and iteration-heavy, write-rare** structures (listeners, subscriptions), not for write-hot data.

## 177. How does `ConcurrentLinkedQueue` work internally? Explain the Michael-Scott lock-free queue algorithm, CAS-based `offer`/`poll` with hop-lazy deletion, the ABA problem and its avoidance, and how it differs from `LinkedBlockingQueue`.

`ConcurrentLinkedQueue` is an **unbounded, thread-safe, lock-free FIFO queue** in `java.util.concurrent`. It implements the famous **Michael-Scott queue algorithm** (1996) using **CAS (Compare-And-Swap)** and **volatile fields**, with no locks and no blocking. Its producers and consumers can operate concurrently at full speed, at the cost of slightly relaxed ordering guarantees (`size()` is `O(n)` and approximate).

---

### 1. The Node Structure

Each queue entry is a node with a `volatile` item and a `volatile` next pointer:

```java
private static class Node<E> {
    volatile E item;      // null => node is logically removed
    volatile Node<E> next; // next node in the queue
}
```

The queue itself holds `volatile Node<E> head` and `volatile Node<E> tail`, and performs all mutations via `sun.misc.Unsafe`/`VarHandle`-style `casNext`/`casItem` operations.

---

### 2. `offer(E)` â€” Enqueue at the Tail (CAS Loop)

Enqueueing uses a **CAS loop** on `tail`:

```java
public boolean offer(E e) {
    final Node<E> newNode = new Node<E>(e);
    for (Node<E> t = tail, p = t;;) {
        Node<E> q = p.next;
        if (q == null) {
            // p is the true last node; try to link newNode after it.
            if (p.casNext(null, newNode)) {
                // CAS succeeded. If p was not the tail field's target,
                // move tail forward opportunistically (hop / lazy update).
                if (p != t)
                    casTail(t, newNode);
                return true;
            }
            // CAS lost to another producer -> retry
        }
        else if (p == q)
            // Sentinel: p is a self-link left by a removed node;
            // re-locate the real tail.
            p = (t != (t = tail)) ? t : head;
        else
            // Advance p one step toward the true tail.
            p = (p != t && t != (t = tail)) ? t : q;
    }
}
```

Key design decisions:

- **Multiple producers** race to `casNext(null, newNode)`; exactly one wins each round, others retry â€” **no lock, no blocking**.
- **Lazy tail update**: `tail` is *not* updated on every enqueue; it lags behind. Producers instead walk from `tail` to the true last node. This "hop" policy reduces CAS contention on the single `tail` field (Michael & Scott's `dist` threshold, set to 2 hops).
- A node whose `next` points to itself (`p == q`) is a **sentinel** left behind when a node was removed by `poll`; the algorithm detects it and re-anchors to `head`.

---

### 3. `poll()` â€” Dequeue From the Head (CAS on Item)

Dequeueing CASes the **item field** of the head node to `null` (a logical delete) rather than unlinking nodes:

```java
public E poll() {
    restartFromHead:
    for (;;) {
        for (Node<E> h = head, p = h, q;;) {
            E item = p.item;
            if (item != null && p.casItem(item, null)) {
                // CAS succeeded: this node is dequeued.
                if (p != h)   // hop â€” skip over empty nodes
                    updateHead(h, ((q = p.next) != null) ? q : p);
                return item;
            }
            else if ((q = p.next) == null) {
                updateHead(h, p);   // queue is empty
                return null;
            }
            else if (p == q)
                continue restartFromHead;  // self-link -> restart
            else
                p = q;                     // skip deleted node
        }
    }
}
```

The item-CAS is what makes `poll` safe: only one consumer can flip a given node's `item` from non-null to null, so each element is returned **exactly once** even with many concurrent consumers.

---

### 4. Logical Deletion vs Physical Unlinking

`ConcurrentLinkedQueue` deliberately does **not** physically remove the head node on dequeue:

- `poll` nulls the `item` (logical removal) and later hops `head` past it.
- Nodes are only physically unlinked when `head` moves forward past them; the removed node's `next` is set to itself (`p == q`) â€” the **self-link sentinel** â€” which the enqueue/dequeue loops recognize to re-anchor.

This avoids the otherwise-fatal race where a consumer nulls `item` while a producer still holds a stale reference to `next`, keeping the algorithm linearizable without heavy locking.

---

### 5. The ABA Problem and How It Is Avoided

The **ABA problem** is the classic hazard of CAS-based structures: a thread reads a location as value `A`, another thread changes it `A â†’ B â†’ A`, and the first thread's CAS then succeeds against the *wrong* state.

Michael-Scott-style queues avoid ABA by CASing **immutable `Node` references**, not mutable value fields:

- Each node is created once, and its `next` reference is set **exactly once** (from `null` to the new node). A node reference can never be "reused" for a different purpose.
- The ABA problem requires the same address to be recycled through two different states. Because nodes are never reused (they are GC-managed and never recycled into a free-list), the reference itself is a stable identity â€” the CAS compare-and-swap on `next` is immune to ABA.
- HotSpot additionally relies on `item == null` as a separate linearization point for dequeue, so a consumer never CASes a `null` item onto a non-null one.

The explicit note in the JDK source is that "the main part of this algorithm is to make sure that a node cannot be reused by another thread" â€” GC gives it this property for free (unlike C++, which would need epoch-based reclamation or hazard pointers).

---

### 6. `ConcurrentLinkedQueue` vs `LinkedBlockingQueue`

| Feature | `ConcurrentLinkedQueue` | `LinkedBlockingQueue` |
| :--- | :--- | :--- |
| **Blocking** | Never blocks | `put()`/`take()` block on capacity/emptiness |
| **Locking** | Lock-free (CAS only) | Two `ReentrantLock`s (put lock + take lock) |
| **Capacity** | Unbounded | Optional bounded (default `Integer.MAX_VALUE`) |
| **Backpressure** | None (unbounded memory growth risk) | Yes (bounded capacity) |
| **`size()`** | `O(n)` walk, approximate | `O(1)` via atomic counter |
| **Best for** | Low-contention pipelines, lock-free hand-off | Producer-consumer with capacity limits / backpressure |

**Summary of the comparison:** if you need backpressure or blocking semantics, use `LinkedBlockingQueue` (used by `ThreadPoolExecutor`); if you want a purely lock-free, non-blocking FIFO and accept unbounded growth and an `O(n)` `size()`, use `ConcurrentLinkedQueue`.

---

### 7. Weakly Consistent Iterators

Like most concurrent collections, the iterator is **weakly consistent**:

- It never throws `ConcurrentModificationException`.
- It reflects the queue state at some point during iteration; elements removed concurrently may or may not be visited.
- `iterator().remove()` is supported (it nulls the item via CAS) but the element may already have been removed.

### Summary

- `ConcurrentLinkedQueue` is an **unbounded, lock-free FIFO** based on the **Michael-Scott algorithm**: producers CAS onto `tail`, consumers CAS the head's `item` to `null`.
- `tail`/`head` are **updated lazily** (hop-by-hop) to reduce CAS contention on the shared refs.
- Deletion is **logical first** (`item = null`), with self-link sentinels and `head`-hopping handling physical cleanup.
- The **ABA problem is avoided** by CASing immutable, never-recycled `Node` references (GC-managed), so an address is never reused across two states.
- Unlike `LinkedBlockingQueue`, it is **non-blocking and unbounded** â€” no capacity, no blocking `put`/`take`, but an `O(n)` approximate `size()`.

---

## 178. How does `Phaser` work internally, and how is it more flexible than `CyclicBarrier` and `CountDownLatch`? Explain its phase-based state, party registration (`register`/`bulkRegister`), the `arrive`/`awaitAdvance` protocol, phase numbers, and how `Phaser` supports dynamic participation and a `Phaser` tree.

`Phaser` (`java.util.concurrent`) is a **reusable synchronization barrier** that generalizes both `CyclicBarrier` and `CountDownLatch`. Its central abstraction is a **phase**: a round of work that completes when a countable set of **parties** have each arrived. Unlike the fixed-party `CyclicBarrier` or the one-shot `CountDownLatch`, a `Phaser` lets parties **register and deregister dynamically**, supports a variable barrier count per phase, and can even be arranged into a `Phaser` **tree** for scalability.

---

### 1. The Core State: One `volatile long` Phases Everything

Like many `JUC` synchronization primitives, `Phaser` packs its entire state into a single **`volatile long state`** and mutates it atomically via CAS:

```
state (64-bit long) packed fields:
+-----------+----------+------------------+----------+
|  phase   |  counts  |  unarrived      |  parties |
| (bits 32-62)| (16-31) | (16 bits)       | (16 bits)|
+-----------+----------+------------------+----------+
```

- **`phase`** (upper 32 bits): the current phase number. Increments each time the barrier trips.
- **`parties`** (low 16 bits): the *total* registered parties.
- **`unarrived`** (next 16 bits): how many parties have not yet arrived this phase.
- **`counts`** (16â€“31): derived number of parties that can arrived (used to know when to trip).

A single CAS is used to update `unarrived`, `parties`, and `phase` atomically, so phaser transitionsâ€”"a party arrived", "all parties arrived, bump the phase"â€”are race-free without locks.

---

### 2. Parties Are Dynamic: `register()` / `bulkRegister(int)`

Unlike `CyclicBarrier` (fixed party count at construction), a `Phaser` allows parties to **join or leave over time**:

```java
Phaser phaser = new Phaser();         // initial parties = 0

// A thread joins dynamically:
phaser.register();                    // parties += 1
// Several at once:
phaser.bulkRegister(3);               // parties += 3
```

- `register()` increments the party count for the **next phase** on the current thread.
- `arriveAndDeregister()` decrements it, so the barrier can shrink.
- This dynamic participation is what makes `Phaser` suitable for **fork/join** style work where the "member count" isn't known until runtime.

Because the count can change, the number of `arrive` calls required to trip a phase can **grow or shrink between phases** - the flexibility of `Phaser` that `CyclicBarrier` lacks.

---

### 3. The `arrive` / `awaitAdvance` Protocol

The barrier is driven by two families of methods:

| Method | Effect |
| :--- | :--- |
| `arrive()` | Marks the current thread as arrived, without blocking. Returns the phase number. |
| `arriveAndAwaitAdvance()` | Arrives, then **blocks until the barrier trips**. The standard "join + wait" call. |
| `arriveAndDeregister()` | Arrives and permanently removes this party from the count. |
| `awaitAdvance(phase)` | Blocks (without arriving) until the given `phase` advances. |
| `getPhase()` | Returns the current phase number. |

The central algorithm idea:

```java
// arrive + determine whether this was the last arriving party:
int arrive() {
    // atomically decrement unarrived
    if (cas current -> unarrived-1) {
        if (unarrived == 0) {
            // LAST party arrived => trigger the phase barrier:
            // 1. run any onAdvance(phase, parties) barrier action
            // 2. bump phase (state changed)
            // 3. wake all waiters
        }
        return phase;
    }
}
```

The key behavior of a `Phaser` barrier trip:

1. The **last party to arrive** in a phase trips the barrier.
2. Unlike `CyclicBarrier`, arriving threads **don't block at the barrier point** (unless they call `awaitAdvance`). An `arrive()` is fire-and-forget; only threads that explicitly wait block.
3. When the phase completes, the phase number increments, and **all pending `awaitAdvance` callers unblock**.

#### How `awaitAdvance` works:

```java
public int awaitAdvance(int phase) {
    for (;;) {
        int p = this.phase;      // read current phase
        if (p != phase)          // phase already moved past the one we waited for
            return p;            // done â€” return the new phase
        // else park until the phase changes or a timeout occurs
    }
}
```

This is why `awaitAdvance(phase)` is often the right primitive for **late-arriving** threads (a thread might not be ready to `arrive()` yet; it can still wait for a given phase using the stamp).

---

### 4. CyclicBarrier / CountDownLatch / Phaser Comparison

| Feature | `CountDownLatch` | `CyclicBarrier` | `Phaser` |
| :--- | :--- | :--- | :--- |
| **Reusable** | No (one-shot) | Yes | Yes |
| **Dynamic parties** | No (fixed at construction) | No (fixed) | **Yes** â€” `register`/`deregister` |
| **Blocking model** | `await()` blocks until count 0 | All parties block until all arrive | Arrive is fire-and-forget; only `awaitAdvance` blocks |
| **Advanced features** | â€” | Barrier action (`Runnable`) | **Barrier action**, **tree**, **phase-based** |
| **Work split** | Not reusable after count 0 | Fixed size rounds | Varies across phases |

---

### 5. `Phaser` Tree (Scalability)

Because a single `Phaser` uses one contended `long`, very large party counts cause CAS contention. `Phaser` supports **phase trees**: a parent phaser whose children merge their completed phases into it.

```java
Phaser root = new Phaser();
Phaser child1 = new Phaser(root, 5); // 5 parties in subtree 1
Phaser child2 = new Phaser(root, 5); // 5 parties in subtree 2
```

- When all parties in a child phase arrive, the child forwards a single arrival to its parent.
- This reduces contention: chief contention is spread across subtree phasers, each doing a couple of CASes, rather than all N parties hammering one `long`.
- Used in `ForkJoinPool` internally for its work-stealing dispatch.

---

### 6. Common Uses and Gotchas

**Uses:**
- **Dynamic parallel frameworks** (ForkJoinPool-like slicing), where party count is known only at runtime.
- **Multi-stage/multi-wave processing** â€” a reusable barrier for each wave of work.
- **Larger-scale concurrency** where `CyclicBarrier` at fixed size is too limiting.

**Gotchas:**
- Trivial `arrive()` and a last-party trip means the **guest phase only advances when the final party arrives**; if you `arrive()` without registering correctly, `Phaser.PARTIES_MISMATCH` can be thrown.
- Arrive is **not a blocking wait**: the typical mistake is to `arrive()` and then immediately check state that isn't ready. Use `awaitAdvance` when you need to wait.
- `register()` affects *next* phase, so reading `getRegisteredParties()` mid-cycle can be misleading.

### Summary

- `Phaser` generalizes `CyclicBarrier` and `CountDownLatch` with **reusable, dynamic party registration**.
- State is one `volatile long` packing **phase** (32-bit), **parties** (16-bit), and **unarrived** (16-bit), mutated with CAS.
- The protocol is **`arrive()` (fire-and-forget) + `awaitAdvance(phase)` (wait)**, plus `arriveAndAwaitAdvance()` to both arrive and wait.
- The **last arriver in a phase trips the barrier** and bumps the phase; `arriveAndDeregister` can shrink the count.
- `Phaser` trees (`new Phaser(parent, parties)`) spread CAS contention for very large party counts.

## 179. How does `LockSupport` work, and why is it the foundation for all JUC blocking? Explain `park()`/`unpark(thread)` vs `Object.wait()`/`notify()`, the permit-based model, `parkNanos`/`parkUntil` timeouts, and spurious wakeup handling in `LockSupport.park`.

`LockSupport` (`java.util.concurrent.locks`) provides **thread blocking primitives** — `park()` (block the current thread) and `unpark(Thread)` (resume a specific thread) — that form the low-level foundation for every `JUC` synchronizer. `AQS`, `ReentrantLock`, `Semaphore`, `CountDownLatch`, `Condition`, and `ForkJoinPool` all block threads via `LockSupport`, not via `Object.wait()`. Its core idea is a **per-thread permit**.

---

### 1. The Permit Model (A Tiny Semaphore per Thread)

Every thread has an implicit, internal **permit** (a `count` — 0 or 1) that `park` and `unpark` manipulate:

| Operation | Effect on the permit |
| :--- | :--- |
| `unpark(thread)` | If the thread's permit is 0, **set it to 1** (permit is consumed on next park). If already 1, **no-op** (permits do not accumulate above 1). |
| `park()` | **Consumes** the permit if it is 1 (returns immediately). Otherwise **blocks** until a permit is granted. |

This is fundamentally different from a mutex: a permit has **no ownership**. Any thread may call `unpark(anyOtherThread)`, and permits do not need to be "released" by the same thread that "acquired" them.

```java
// unblocking a parked thread from another thread:
LockSupport.unpark(workerThread);   // grants a permit
```

The "permit pre-grant" property is the crucial difference from `wait/notify`: **`unpark` before `park` is not lost** — the parked thread will return immediately from its next `park` because the permit is already held. With `wait/notify`, a `notify` that happens before `wait` is lost and the waiter blocks forever.

---

### 2. `park()` vs `Object.wait()` — the Key Differences

| Feature | `Object.wait()` | `LockSupport.park()` |
| :--- | :--- | :--- |
| **Monitors** | Requires `synchronized` (a monitor lock must be held) | No monitor — usable anywhere |
| **Target** | Wakes *all* (or one of) the threads waiting on the monitor | Wakes an *exact* named thread (`unpark(thread)`) |
| **Lost wakeup** | `notify` before `wait` is lost | `unpark` before `park` persists (permit) |
| **Interruption** | Throws `InterruptedException` (clears flag) | Sets the interrupted flag, `park` returns, **no exception** |
| **Timeouts** | `wait(millis)` | `parkNanos`, `parkUntil` |
| **Used by** | `synchronized`/legacy code | All of `java.util.concurrent` |

Because `park` doesn't throw `InterruptedException` and doesn't require a monitor, it's the ideal primitive for writing lock-free synchronizers.

---

### 3. `park()` Implementation Details (HotSpot)

`LockSupport.park()` is backed by a native method that ultimately parks the OS thread:

```
LockSupport.park()
  -> UNSAFE.park(false, 0L)           // a "safe point" blocking call
  -> (HotSpot) parks the thread via platform primitives
       (futex on Linux, WaitOnAddress/SleepConditionVariable on Windows)
```

On Linux, `park` uses the **`futex`** system call; on Windows it uses the thread-park emulation. The important point: **parking does not burn CPU** — the OS deschedules the thread until `unpark` (or a timeout) resumes it.

---

### 4. Timeout Variants

```java
// Block until unparked, but no longer than 100ms:
LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(100));

// Block until a deadline (millis since epoch, or nanos since epoch):
LockSupport.parkUntil(System.currentTimeMillis() + 5_000);   // 5s from now
```

- `parkNanos(long nanos)`: relative timeout, granularity is nanos (subject to OS timer resolution).
- `parkUntil(long deadline)`: absolute deadline in millis since epoch.
- These are used extensively by `AQS` (`tryAcquireNanos`, condition `awaitNanos`) and by `ThreadPoolExecutor.getTask()`'s `keepAliveTime` polling.

Note the per-thread permit model means a `parkNanos` that times out simply returns; no exception, no cleanup needed.

---

### 5. The Critical Safety Rule: Park Must Be Guarded by a Condition Loop

`park` has **spurious wakeups** (a thread can return from `park` without any `unpark` — permitted by the JMM). Therefore, correct code **never calls `park` in a bare if**. It must loop while the condition it's waiting for is not yet satisfied:

```java
// WRONG: lost wakeup / spurious wakeup bug
if (!ready) {
    LockSupport.park();   // might wake spuriously, might miss the unperm...
}

// CORRECT:
while (!ready) {
    LockSupport.park();   // re-checks the condition after every wake
}
```

This mirrors the mandatory `while` loop with `Object.wait()`. AQS, `Condition.await`, and all JUC primitives follow this discipline internally.

The associated gotcha: because `park` doesn't throw `InterruptedException`, interrupted waiters rely on **re-checking** the interrupt flag — JUC code typically calls `Thread.interrupted()` in the loop to respond to interrupts.

---

### 6. Practical Example — A Minimal Waiter

```java
import java.util.concurrent.locks.LockSupport;

public class Blocker {
    private volatile boolean ready = false;

    public void waitForReady() {
        while (!ready) {          // guard against spurious + lost wakeup
            LockSupport.park();
        }
    }

    public void signal() {
        ready = true;
        LockSupport.unpark(Thread.currentThread()); // wake the *specific* waiter
    }
}
```

---

### 7. LockSupport vs synchronized Park (Summary Table)

| Need | Use |
| :--- | :--- |
| Block a thread without a monitor, exact-target wake, no lost wakeup | `LockSupport.park/unpark` |
| Legacy monitor-based blocking, multiple conditions via monitor | `Object.wait/notify` |
| High-level reusable barrier / latch | `Phaser`, `CountDownLatch`, `CyclicBarrier` (built on AQS → `LockSupport`) |
| Cooperative CPU yielding, no blocking | `Thread.yield()` |

### Summary

- `LockSupport` provides **permit-based blocking** (`park` consumes, `unpark` grants) with no monitor requirement and no `InterruptedException`.
- The permit is **not owned**, and an `unpark` before a `park` is **not lost** — the exact opposite of `notify`-before-`wait`.
- `parkNanos`/`parkUntil` add timeouts; the OS parks the thread (e.g., `futex` on Linux), so parked threads cost no CPU.
- **Always guard `park` with a condition loop** — spurious wakeups are legal, so a bare `if (!cond) park()` is a bug.
- It is the hidden engine beneath `AQS`, `ReentrantLock`, `Semaphore`, `CountDownLatch`, `Phaser`, `Condition`, and `ForkJoinPool`.

## 180. How do `DelayQueue` and `ScheduledThreadPoolExecutor` implement delayed/timed execution internally? Explain the priority-queue core, the delay leader-wait pattern, the `ScheduledFutureTask` time fields, and why delayed tasks are not removed by a dedicated timer thread.

Both `DelayQueue` and `ScheduledThreadPoolExecutor` implement **timed/delayed execution** using a **priority queue** ordered by deadline, plus a clever **leader-waiter** pattern that avoids waking a thread for every delay tick. Understanding these internals explains why scheduling in Java does not rely on per-task timer threads and how `scheduleAtFixedRate` vs `scheduleWithFixedDelay` really differ.

---

### 1. The Common Core: A Delay-Ordered Priority Queue

Both classes are built on `PriorityQueue` (for `DelayQueue`) or `DelayedWorkQueue` (a private delay-ordered priority queue inside `ScheduledThreadPoolExecutor`). The queue holds tasks implementing `Delayed`:

```java
public interface Delayed extends Comparable<Delayed> {
    long getDelay(TimeUnit unit);   // remaining delay; <= 0 means "expired"
}
```

The queue orders tasks by their **scheduled execution time** (`scheduledFireTime` in `ScheduledFutureTask`), so the **head of the queue is always the next task to run**. `DelayQueue.poll()` blocks until the head's delay expires; `ScheduledThreadPoolExecutor` uses the same structure internally with worker threads.

---

### 2. `DelayQueue` — How It Blocks Until Something Is Due

```java
public E take() throws InterruptedException {
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        for (;;) {
            E first = q.peek();
            if (first == null)
                available.await();          // queue empty: block
            else {
                long delay = first.getDelay(NANOSECONDS);
                if (delay <= 0)
                    return q.poll();        // head is due: return it
                first = null;               // don't retain ref while parked
                if (leader != null)
                    available.await();      // another thread is the leader
                else {
                    Thread thisThread = Thread.currentThread();
                    leader = thisThread;
                    try {
                        available.awaitNanos(delay);  // sleep ONLY until head is due
                    } finally {
                        if (leader == thisThread)
                            leader = null;
                    }
                }
            }
        }
    } finally {
        if (leader == null && q.peek() != null)
            available.signal();             // promote a new leader
        lock.unlock();
    }
}
```

Key points:

- It uses a single `ReentrantLock` + a `Condition available`.
- It **sleeps exactly until the head's delay** (`awaitNanos(delay)`), not a fixed polling interval — so the JVM parks the thread until the deadline via `LockSupport.parkNanos` under the hood.
- The **leader** is the one thread currently sleeping for the head task; all other waiting threads park indefinitely. When the leader wakes and takes the task, it signals to promote a new leader.

---

### 3. The Leader-Waiter Pattern (Avoiding "thundering herd")

Without a leader, **every** waiting thread would time out near-simultaneously when a task becomes due, wake up, and all fight to take the same head — a thundering herd.

The leader pattern fixes it:

1. **Leader** — the single thread that sleeps *exactly* until the head's deadline (`awaitNanos(delay)`).
2. **Waiters** — all other threads park with **no timeout** (`available.await()`); they rely on being signaled.
3. When the leader wakes, takes the head, and it's still the leader, it calls `available.signal()` to promote a new leader.

Result: at most **one thread** wakes at a deadline, so timed wakes scale to many delayed tasks without wakeup storms. (This is the same pattern used in `SynchronousQueue`.)

---

### 4. `ScheduledThreadPoolExecutor` — Tasks on a Worker Thread

`ScheduledThreadPoolExecutor` is a `ThreadPoolExecutor` whose `workQueue` is a `DelayedWorkQueue`, and whose tasks are **`ScheduledFutureTask`** objects:

```
ScheduledFutureTask
  + long sequenceNumber       (FIFO tie-break when deadlines are equal)
  + long time                 (the scheduled execution time, in nanos)
  + long period               (0 => one-shot; >0 => fixed-rate; <0 => fixed-delay)
  + RunnableScheduledFuture<V> outerTask
```

- `submit`/`schedule` enqueue a `ScheduledFutureTask` ordered by `time`.
- Worker threads call `getTask()`, which uses `DelayQueue.take()` semantics: **the worker sleeps until the head task's deadline**, then runs it.
- Because the worker pool threads execute the delayed tasks themselves, **no dedicated timer thread** is needed.

```java
// schedule a one-shot task:
ScheduledFuture<?> f = executor.schedule(
    () -> System.out.println("run after 1s"), 1, TimeUnit.SECONDS);

// schedule a fixed-rate task (runs at t, t+p, t+2p, ...):
executor.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);

// schedule a fixed-delay task (runs delay after each completion):
executor.scheduleWithFixedDelay(task, 0, 1, TimeUnit.SECONDS);
```

---

### 5. Fixed-Rate vs Fixed-Delay (the `period` field)

The `period` field decides what happens after a task finishes:

| Method | `period` | Re-queue behavior |
| :--- | :--- | :--- |
| `schedule` | `0` | One-shot — task not re-queued. |
| `scheduleAtFixedRate` | `> 0` | Re-queue with `time = lastTime + period`. **Runs on a fixed cadence**, ignoring how long the task took; consecutive executions never overlap. |
| `scheduleWithFixedDelay` | `< 0` | Re-queue with `time = now + |period|`. **Runs `delay` after the previous run completes**. |

**Fixed-rate** semantics: the *start* times are spaced `period` apart. If a run is slow, the next run fires as soon as possible after completion (never overlapping), and the schedule drifts but never catches up.

**Fixed-delay** semantics: the gap is measured *between completions* and next start.

`ScheduledFutureTask.run()` checks the `period` and calls `setNextRunTime()` to compute the re-queue time, then returns it to the pool which re-enqueues it.

---

### 6. `scheduleAtFixedRate` vs `scheduleWithFixedDelay` — Comparison

| Aspect | `scheduleAtFixedRate` | `scheduleWithFixedDelay` |
| :--- | :--- | :--- |
| **Next run time** | `previousStart + period` | `completionTime + period` |
| **If task runs long** | Next run fires immediately after completion (no overlap, catches up only partially) | Next run always starts `period` after the last one ended |
| **Cadence** | Drifts when work overruns | Fixed gap between runs |
| **Use for** | Heartbeats, polling metrics | Chained jobs where each run's delay matters |

---

### 7. Why No Dedicated Timer Thread?

A naive design uses one thread per delayed task or one global timer thread that wakes every tick and scans all tasks. `ScheduledThreadPoolExecutor` instead:

1. Uses the delay-ordered priority queue — **only the head's deadline matters**.
2. Uses the **leader-waiter** pattern — only one worker sleeps until a deadline.
3. Reuses the pool's worker threads — the same threads also execute non-delayed tasks, so no per-task thread is spawned.

This gives `O(log n)` enqueue (priority queue) and `O(1)`-ish wakeup behavior, scaling far better than per-task timers.

### Summary

- `DelayQueue` and `ScheduledThreadPoolExecutor` are built on **deadline-ordered priority queues** of `Delayed` tasks.
- `take()` sleeps **exactly until the head's delay** via `awaitNanos(delay)`, using the **leader-waiter** pattern to keep only one thread parked to a deadline.
- `ScheduledFutureTask` stores **`time`** (execution deadline) and **`period`** (`0` one-shot, `>0` fixed-rate, `<0` fixed-delay).
- **Fixed-rate** schedules by start-to-start cadence; **fixed-delay** schedules completion-to-start.
- No dedicated timer thread exists: worker threads self-block on the queue until the next deadline, making it scalable and `O(log n)` per schedule.

## 181. How does `ThreadLocal` work internally? Explain the per-thread `ThreadLocalMap`, the `ThreadLocalMap.Entry` with its weak key, how `set`/`get` compute thread-local index and handle hash collisions via linear probing, and how `ThreadLocal` leaks occur in thread pools.

`ThreadLocal` provides **per-thread variables**: each thread that touches a `ThreadLocal` gets its own independent value. Under the hood there is **no map keyed by thread** inside the `ThreadLocal` — instead, **each `Thread` object owns a `ThreadLocalMap`** that maps the `ThreadLocal` instance (a weak key) to the value. Understanding this inverted structure explains both the elegance and the classic memory-leak pitfalls.

---

### 1. The Inverted Ownership: Each `Thread` Has Its Own Map

The value lives in the thread, not in the `ThreadLocal` object:

```
ThreadLocal<T> (the "key", shared)
      |
      v
Thread 1 ──── ThreadLocalMap { [weak ref to ThreadLocal] -> value1 }
Thread 2 ──── ThreadLocalMap { [weak ref to ThreadLocal] -> value2 }
```

```java
public class Thread implements Runnable {
    ThreadLocal.ThreadLocalMap threadLocals = null;   // per-thread map
    ThreadLocal.ThreadLocalMap inheritableThreadLocals = null;
}
```

- `ThreadLocal.set(v)` fetches the **current thread's** `threadLocals` map and puts the value under this `ThreadLocal` key.
- `ThreadLocal.get()` fetches the current thread's map and looks up this key.
- If the map does not exist yet, `ThreadLocal` lazily creates it (in `createMap`).

---

### 2. The Map Itself: Open-Addressing With Linear Probing

`ThreadLocalMap` is **not** a `HashMap`. It is a custom **open-addressed hash table** using **linear probing**, with the `ThreadLocal` instance as key and the value as the stored object:

```java
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;               // the actual value held strongly
        Entry(ThreadLocal<?> k, Object v) {
            super(k);               // super = WeakReference to the ThreadLocal key
            value = v;
        }
    }
    private Entry[] table;          // like HashMap's buckets
    private int size;
    private int threshold;
}
```

- `table` is a power-of-two-sized array of `Entry`s (initial capacity 16, default load factor 2/3).
- The slot index is computed from the key's `threadLocalHashCode` (an incrementing `AtomicInteger` hash assigned per `ThreadLocal` instance) masked with `(table.length - 1)`.
- Because `Entry` extends `WeakReference<ThreadLocal<?>>`, the **key is held weakly** while the **value is held strongly** — this asymmetry is the source of the famous leak.

`get()` follows the hash chain using linear probing (step to the next slot until a matching key or a null slot):

```java
private Entry getEntry(ThreadLocal<?> key) {
    int i = key.threadLocalHashCode & (table.length - 1);
    Entry e = table[i];
    if (e != null && e.get() == key)
        return e;                       // fast path: found at the hash slot
    else
        return getEntryAfterMiss(key, i, e);  // probe further for the key
}
```

---

### 3. Collisions and Cleanup — `getEntryAfterMiss` and `expungeStaleEntry`

When the key is not at its hash slot, `getEntryAfterMiss` linear-probes forward; when it hits an entry whose `get()` (the weak reference) returns `null` — a **stale entry** whose `ThreadLocal` was GC'd — it calls `expungeStaleEntry` to clear both the entry and its strongly-held `value`:

```java
private int expungeStaleEntry(int staleSlot) {
    Entry[] tab = table;
    int len = tab.length;
    tab[staleSlot].value = null;   // drop the strong ref to the value
    tab[staleSlot] = null;         // free the slot
    // ... rehash subsequent entries to keep probing consistent ...
    return nextStaleSlot;
}
```

So the **only** mechanism that cleans up a dead `ThreadLocal`'s value is hitting a stale entry during `get`/`set` on the *same* thread's map. If a thread never touches the map again, the stale value stays put.

---

### 4. `set`, `get`, `remove` — The Three Core Operations

| Method | What it does |
| :--- | :--- |
| `set(value)` | Get current thread's map; create if absent; put (replace) the entry; call `expungeStaleEntries` when probing. |
| `get()` | Get map; if absent, run `initialValue()` (or the `Supplier` for `withInitial`) and store it. |
| `remove()` | Remove this `ThreadLocal`'s entry and expunge stale entries — the *correct* cleanup call. |

`initialValue()` is invoked once per thread on first `get()` (or via `withInitial(Supplier)`).

---

### 5. The Thread-Pool Leak: Weak Key + Strong Value

The classic leak happens in a **thread pool** where threads live long:

1. A task sets a `ThreadLocal` value (say a large `byte[]` or a `UserContext`).
2. The `ThreadLocal` object becomes unreachable after the task (e.g., a static field was removed, or it was local).
3. The map entry's **key** is weak → GC clears it → `entry.get()` becomes `null`.
4. But the entry's **`value`** is still a strong reference → it keeps the large object alive.
5. The worker thread never calls `remove()` and never performs another `get/set` that would trigger `expungeStaleEntry`.
6. Result: **the value leaks for as long as the thread lives** — in Tomcat/thread-pool apps this is a slow, invisible memory growth.

Reference chain: `Thread (GC Root)` → `ThreadLocalMap` → `Entry.value` → **leaked object**.

**The fix:** always call `ThreadLocal.remove()` in a `finally` block when the thread is reused:

```java
private static final ThreadLocal<RequestContext> ctx = new ThreadLocal<>();
try {
    ctx.set(parse(request));
    handle();
} finally {
    ctx.remove();     // mandatory in pooled-thread environments
}
```

Alternatively, avoid thread pools for request-scoped data, or use `InheritableThreadLocal`/scoped values where appropriate.

---

### 6. `InheritableThreadLocal` and Inheritance

`InheritableThreadLocal` overrides `childValue(parentValue)` so a **child thread created via `new Thread()`** inherits the parent's values at construction time (stored in `Thread.inheritableThreadLocals`). It does **not** propagate automatically to virtual threads or thread-pool workers — which is why request-scoped values across async boundaries typically need explicit passing or `ScopedValue` (Q127).

---

### 7. Comparison: `ThreadLocal` vs `ScopedValue` vs Plain Map

| Mechanism | Storage | Cleanup | Use |
| :--- | :--- | :--- | :--- |
| `ThreadLocal` | Per-thread `ThreadLocalMap` (weak key, strong value) | Manual `remove()` or stale-expunge | Thread-bound request context, pooling-safe with care |
| `ScopedValue` (Java 22+) | Per-thread, **bound for a scope**, immutable | **Automatic** when scope exits | Virtual-thread-friendly request context |
| `ConcurrentHashMap<Thread,...>` | External map keyed by thread | Manual removal | Rarely needed; awkward GC root retention |

### Summary

- `ThreadLocal` stores values in a **per-thread `ThreadLocalMap`** — the key is the `ThreadLocal` (a **weak reference**), the value is held **strongly**.
- The map is an **open-addressed table with linear probing**, indexed by each `ThreadLocal`'s `threadLocalHashCode`.
- `expungeStaleEntry` (triggered by later `get`/`set` on the same thread) is the only cleanup of dead keys — and it releases the strong value reference.
- **Thread-pool leaks** arise because pooled threads outlive the `ThreadLocal` key: the strong `value` survives while the weak key is gone, so `remove()` in a `finally` is mandatory.
- `InheritableThreadLocal` copies values to `new Thread()` children at creation; `ScopedValue` is the modern, scope-bounded replacement.

---

## 182. How do the `java.util.concurrent.atomic` classes work? Explain `AtomicInteger`'s `volatile int` + CAS (`Unsafe.compareAndSwapInt`), the spin-loop retry pattern, and how `LongAdder`/`LongAccumulator` scale better under high contention than a single `AtomicLong`.

The `java.util.concurrent.atomic` package provides **lock-free, thread-safe scalar types** (and array/field/ref variants). Instead of `synchronized`, they rely on **compare-and-swap (CAS)** — an atomic hardware primitive — combined with a `volatile` value. Understanding how `AtomicInteger`, `AtomicLong`, `AtomicReference`, and the striped accumulators (`LongAdder`, `DoubleAdder`) work explains most lock-free programming in the JDK.

---

### 1. `AtomicInteger` — A `volatile int` + CAS

The core is a single `volatile int value` manipulated through CAS helpers. The `value` is declared `volatile` so plain reads/writes are always visible:

```java
public class AtomicInteger extends Number {
    private static final Unsafe U = Unsafe.getUnsafe();
    private static final long VALUE = U.objectFieldOffset(AtomicInteger.class, "value");
    private volatile int value;          // the single atomic state

    public AtomicInteger(int initialValue) {
        value = initialValue;
    }
}
```

- **Read** (`get()`): just returns `value` — a `volatile` read, no lock.
- **Write** (`set(int)`): a plain `volatile` write (`putIntVolatile`). Note: no CAS involved.
- **Atomic update** (`compareAndSet(expected, new)`): translated into the native `compareAndSwapInt`, which the JIT compiles into a hardware atomic instruction.

---

### 2. CAS and the Hardware Instruction

`compareAndSet(expected, newValue)` has the semantics:

> "If the current value equals `expected`, set it to `newValue` and return `true`; otherwise leave it unchanged and return `false`." — **atomically**, with no way to observe an intermediate state.

Under the hood:

```
AtomicInteger.compareAndSet(exp, upd)
  -> U.compareAndSwapInt(this, VALUE, exp, upd)     // native
       -> on x86:  lock cmpxchg dword ptr [r]; seta al
       -> on ARM : LDXR ... STXR (exclusive load/store pair)
       -> on RISC-V: AMOCAS.W
```

- On x86 the atomicity comes from the **`lock` prefix** (which pins the cache line / assert bus lock); on ARM/RISC-V from **load-linked/store-conditional** primitives.
- Because `VALUE` is the field **offset**, the native CAS writes directly into the object's memory — the JIT for `AtomicInteger` calls are often **inlined** as a single instruction, so lock-free operations are extremely fast.

---

### 3. The Spin-Loop Pattern (getAndIncrement, addAndGet, etc.)

Most operations are built on a **read-modify-CAS loop**:

```java
public final int getAndIncrement() {
    return U.getAndAddInt(this, VALUE, 1);   // Unsafe helper does the loop
}

// Unsafe.getAndAddInt — the canonical CAS retry loop:
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);      // 1. read current (volatile)
    } while (!compareAndSwapInt(o, offset, v, v + delta));  // 2. CAS; retry on failure
    return v;
}
```

So `getAndIncrement()` is:

1. Volatile-read the current value `v`.
2. CAS `v -> v+1`.
3. If the CAS fails (someone else raced), loop back and re-read.

This is **optimistic with retry**: it never blocks; under low contention it succeeds on the first attempt; under heavy contention threads spin retrying (which is why ultra-high contention favors `LongAdder`).

---

### 4. `AtomicReference<V>` and the More Complex Variants

The package generalizes the same pattern:

| Class | Uses |
| :--- | :--- |
| `AtomicBoolean` / `AtomicInteger` / `AtomicLong` | BOOLEAN (int backed), numeric scalars |
| `AtomicReference<V>` | Any object reference (identity-compare CAS) |
| `AtomicIntegerArray`/`AtomicLongArray`/`AtomicReferenceArray` | CAS on array elements |
| `AtomicIntegerFieldUpdater`/`AtomicLongFieldUpdater` | CAS on a `volatile` field of an existing object without a wrapper |
| `AtomicMarkableReference` / `AtomicStampedReference` | (value, mark) and (value, version) pairs — **solves the ABA problem** |

`AtomicStampedReference` is the canonical ABA solver: it packs a version stamp with the reference, so a change `A -> B -> A` is *not* seen as unchanged because the **stamp incremented**.

---

### 5. The ABA Problem (Recap in Atomic Context)

| Scenario | Problem |
| :--- | :--- |
| Thread T1 reads `A`. | — |
| T2 changes `A -> B` then `B -> A`. | Now the value is again `A`. |
| T1's CAS `A -> C` **succeeds**, even though the state "changed" in between. | If the intermediate `B` mattered (e.g., a reused pointer, a linked-list node), the algorithm is subtly corrupt. |

For **references**, ABA is the classic hazard. `AtomicStampedReference` and `AtomicMarkableReference` add a version token specifically to detect this.

---

### 6. `LongAdder` / `LongAccumulator` — Scaling By Striping

Under **extreme write contention**, a single `AtomicLong` becomes a bottleneck: every increment is a CAS retry against one cache line, and the hardware serializes them.

**`LongAdder`** solves this with **striped counters** (the same pattern `ConcurrentHashMap` uses for `map.size()`):

```
LongAdder
  + base (long)                       // used when count is small / uncontended
  + Cell[] cells                      // striped buckets for contending threads
      Cell0, Cell1, ... CellN         // each a padded (cache-line-aligned) long
```

- **`increment()`**: tries CAS on `base`. If the CAS fails (contention detected), it selects a **`Cell`** based on the current thread's hash (`ThreadLocalRandom.current().probe()`), and CASes that cell instead.
- **`sum()`**: returns `base + Σ cells[i]` — a cheap snapshot (may be slightly stale, which is fine for counters).
- **`reset()`**: zeros `base` and all cells.
- Each `Cell` is **padded** so multiple workers writing different cells never share a cache line (avoiding **false sharing**), letting different cores update in parallel.

So at low contention `LongAdder ≈ AtomicLong` (just `base`); at high contention one thread per cell updates a private cache line with almost no CAS retries — near-linear scalability.

**`LongAccumulator`**: the same striping mechanics, but with an arbitrary binary accumulator function (`LongBinaryOperator`), so you can build striped `max`, `min`, `sum`, `product` aggregate functions.

---

### 7. `AtomicLong` vs `LongAdder` — When to Prefer Each

| Aspect | `AtomicLong` | `LongAdder` |
| :--- | :--- | :--- |
| **Read of current value** | `get()` stays exactly accurate | `sum()` is a **snapshot**, may be slightly stale |
| **Write contention** | Single CAS on one cache line → retries | Striped cells → near-linear |
| **Read-write mix** | Best when reads are frequent & writes rare | Best when **writes dominate** (metrics counters, load gauges) |
| **If you need monotonic exact value** | Use it | Not suitable (snapshot semantics) |
| **Example use** | Sequence generators, id counters | ConcurrentHashMap size counters, stats aggregations |

### Summary

- Atomics = **`volatile` storage + hardware CAS** (`lock cmpxchg` on x86, `LDXR/STXR` on ARM), giving lock-free scalar updates.
- Higher-level ops (`getAndIncrement`, `addAndGet`) use the **read-CAS-retry spin loop**.
- **ABA** is handled by `AtomicStampedReference` / `AtomicMarkableReference` (version-tagged).
- **`LongAdder` / `LongAccumulator`** shard a single counter into cache-line-padded **`Cell`s**, avoiding contention and scaling to many writers — ideal for write-heavy statistics, at the cost of a slightly stale `sum()`.

## 183. How do `Exchanger` and `SynchronousQueue` enable direct thread-to-thread hand-offs? Explain the two-party rendezvous (`exchanger.exchange(x)`), the slot-based approach with the `Node` arena, and how `SynchronousQueue`'s transfer stack/queue give a "no buffering" blocking channel.

Both `Exchanger` and `SynchronousQueue` implement a **rendezvous**: a point where two threads meet and hand data directly to each other with **zero buffering**. They are the primitives behind "no capacity" queues (`Executors.newCachedThreadPool()` uses a `SynchronousQueue`), and they illustrate how the JDK packs a lot of concurrency sophistication into a small API.

---

### 1. `Exchanger` — A Two-Party Rendezvous

`Exchanger<V>` lets **exactly two threads** swap objects:

```java
Exchanger<Message> exchanger = new Exchanger<>();

// Thread A:
Message aOut = new Message("from-A");
Message aIn = exchanger.exchange(aOut);     // blocks until Thread B also calls exchange

// Thread B:
Message bOut = new Message("from-B");
Message bIn = exchanger.exchange(bOut);
```

- Both threads block until **both** have arrived.
- Each `exchange(x)` returns the value **provided by the other thread**.
- There is no queue and no storage: the two objects are swapped directly.
- `exchange(x, timeout, unit)` adds a timeout so a partner that never arrives doesn't block forever.

The classic use case: a "genetic algorithm worker" or pipeline stage where each round, two threads swap their current best result.

---

### 2. `Exchanger` Internals — From Single Slot to an Arena

The implementation has evolved (Java 5 → Java 8) from a **single-slot** design to an **arena** of slots for high-contention scenarios:

#### A. Single-Slot Version (Simple)

- A single `Slot` reference holds one waiting thread's data.
- Thread A CASes its data into the slot; Thread B reads it, swaps in its own data, and wakes A.
- If no partner has arrived, the arriving thread **spins briefly, then parks** (via `LockSupport`) until the partner shows up.

#### B. Arena Version (Java 8+)

- For many threads contending on the same `Exchanger`, a single slot causes CAS storms.
- The `Exchanger` maintains an **`Node[] arena`** of slots. Each thread picks a slot based on its `ThreadLocalRandom` probe, reducing contention.
- `exchange(x)` now walks: try a slot → on failure, expand the arena → retry with a different slot → eventually park.

```java
// Conceptual arena slot:
class Node {
    Object item;             // the value being exchanged
    volatile Node match;     // the matched partner's node
    volatile Thread waiter;  // parked thread
    int index;               // arena index
    int bound;               // contention threshold
    int collision;           // CAS-failure counter
}
```

- Nodes in the arena use the "ticket" / `match` handshake: the exchanging thread posts its item into a `Node`, then **spins or parks until `node.match != null`** — i.e., until the partner has swapped.
- The arena amortizes contention: the more threads contend, the larger the arena grows (up to the number of CPUs), so each pair of threads tends to rendezvous on its own slot.

---

### 3. `SynchronousQueue` — A Blocking Channel With Zero Capacity

`SynchronousQueue<E>` is a `BlockingQueue` that **buffers nothing**. `put(e)` **blocks until a consumer `take()`s the element**, and `take()` blocks until a producer `put`s one. It is the queue used by `Executors.newCachedThreadPool()`.

```java
SynchronousQueue<Runnable> handoff = new SynchronousQueue<>();

// Producer:
handoff.put(task);              // blocks until a consumer takes it

// Consumer:
Runnable r = handoff.take();    // blocks until a producer provides one
```

"Zero capacity" means: at any moment the queue holds at most the one element currently being handed off — no backlog, no latency buildup, and the hand-off is a **direct rendezvous between the producer's thread and the consumer's thread**.

---

### 4. Two Modes: The Stack (LIFO) and the Queue (FIFO)

`SynchronousQueue` has two implementations chosen at construction:

| Constructor | Mode | Behavior |
| :--- | :--- | :--- |
| `new SynchronousQueue<>()` | **Stack** (default, `TransferStack`) | LIFO — favors throughput; hand-offs may starve the "other end" under mismatched rates. |
| `new SynchronousQueue<>(true)` | **Queue** (`TransferQueue`) | FIFO — fairer; guarantees the longest-waiting thread matches first. |

Both modes work on the same `transfer` principle:

```java
// TransferStack mode, simplified:
abstract static class TransferStack<E> extends Transferer<E> {
    static final int REQUEST = 0;    // consumer waiting for an item
    static final int DATA    = 1;    // producer offering an item
    static final int FULFILLING = 2; // a thread completing a match

    volatile SNode head;             // the stack of waiting threads

    E transfer(E e, boolean timed, long nanos) {
        SNode s = null;
        // 1. If the head is a matching mode (REQUEST vs DATA), try to FULFILL it:
        //    CAS the head into FULFILLING, swap items, wake the parked thread.
        // 2. Otherwise, push a new node (REQUEST or DATA) onto the stack
        //    and park until a partner fulfills it (or timeout).
    }
}
```

The **"FULFILLING"** trick is what makes the rendezvous atomic without a lock: when a producer finds a waiting consumer at the head, it CASes the head to `FULFILLING`, exchanges the item, and unparks the partner — a single linearization point so both `put` and `take` are guaranteed to match exactly one partner.

---

### 5. `SynchronousQueue` vs `Exchanger` — Key Differences

| Feature | `SynchronousQueue` | `Exchanger` |
| :--- | :--- | :--- |
| **Parties** | Any number of producers/consumers | Exactly two threads per rendezvous |
| **Direction** | One-way (producer → consumer) | Two-way swap |
| **API** | `put`/`take`/`offer`/`poll` | `exchange(x)` |
| **Capacity** | Zero (direct hand-off) | Zero (direct hand-off) |
| **Fairness option** | FIFO via `TransferQueue` | Arena (no explicit fairness) |
| **Use case** | Thread-pool hand-off, actor mailboxes | Pair-wise exchange of data between two peers |

### Summary

- `Exchanger` is a **two-party rendezvous**: `exchange(x)` blocks until the other thread arrives, then swaps values — implemented with a single slot and an **arena of slots** under contention, with spin-then-park waiting.
- `SynchronousQueue` is a **zero-capacity blocking channel**: `put` and `take` rendezvous directly, implemented with a `TransferStack` (LIFO, default) or `TransferQueue` (FIFO, fair).
- Both use **CAS + parking** (via `LockSupport`) and a `FULFILLING`/`match` handshake for atomic, lock-free rendezvous.
- `SynchronousQueue` is what `newCachedThreadPool()` uses to hand tasks directly to newly-spawned threads with no buffering.

## 184. What is False Sharing, and how do Java developers avoid it? Explain CPU cache lines, the MESI coherence protocol, `@Contended` / cache-line padding, why `LongAdder.Cell` and the LMAX Disruptor pad their fields, and how to measure it.

**False sharing** is a silent performance killer in concurrent Java code. Two threads accessing *different* variables that happen to share the same CPU **cache line** appear to contend, even though they never touch the same data. Understanding cache lines and the coherence protocol explains why fields like `LongAdder.Cell` and Disruptor's ring-buffer slots are explicitly padded.

---

### 1. CPU Cache Lines: The Unit of Transfer

Modern CPUs do **not** transfer memory one byte at a time. The smallest unit of transfer between main memory and the L1/L2/L3 caches is a **cache line** — typically **64 bytes** on x86 (and 64 or 128 bytes on some ARM cores).

```
main memory byte stream (64-byte cache lines):
[ line0: bytes 0..63 ] [ line1: bytes 64..127 ] [ line2: ... ]
```

When a thread reads *any* byte in a line, the whole line is fetched into the cache. When it writes *any* byte in a line, the **whole line** must be owned exclusively.

---

### 2. MESI Coherence: Why a Shared Line Serializes Writers

The **MESI protocol** (Modified, Exclusive, Shared, Invalid) keeps all cores' caches consistent. The states that matter for false sharing:

| State | Meaning | Writer behavior |
| :--- | :--- | :--- |
| **Modified (M)** | This core owns the line, dirty (not yet in RAM) | Write is local (fast). |
| **Exclusive (E)** | This core owns the line, clean | Write upgrades to M locally. |
| **Shared (S)** | Multiple cores have the line | Write requires an **invalidation broadcast** — all other cores drop the line. |
| **Invalid (I)** | Line not valid in this cache | Next read triggers a cache miss / fetch. |

The key consequence: **any write to a line held in `Shared` state forces an invalidation** of that line in every other core's cache — and the writer must wait for the others to acknowledge. When the other core next touches *any* byte of that line, it takes a cache miss.

---

### 3. The False-Sharing Scenario

Consider two counters placed adjacently in the same cache line:

```java
class BadCounters {
    long counterA;   // bytes 0..7
    long counterB;   // bytes 8..15   (same 64-byte line as counterA)
}
```

- Thread 1 increments `counterA` in a hot loop.
- Thread 2 increments `counterB` in a hot loop.
- They never access the same field — yet they contend on the **same cache line**.

The result per iteration: Thread 1's write to `counterA` invalidates the line in Thread 2's cache; Thread 2's next read of `counterB` misses and refetches the whole line, then its write invalidates the line back in Thread 1's cache. The cores ping-pong the line, and the loop can run **100–1000× slower** than if the counters were on separate lines.

```
Thread 1 (core 0)                  Thread 2 (core 1)
  write counterA                        write counterB
  invalidate line in core1  <------->   invalidate line in core0
  refetch whole line after miss         refetch whole line after miss
```

This is "false" sharing because the threads share a line **without sharing data**.

---

### 4. The Fixes: Padding and `@Contended`

#### A. Manual Cache-Line Padding (Classic)

Insert dummy fields so each hot field lives on its own line:

```java
class PaddedCounters {
    long counterA;
    long p1, p2, p3, p4, p5, p6, p7;   // pad counterA to its own 64-byte line
    long counterB;
    long q1, q2, q3, q4, q5, q6, q7;   // pad counterB to its own 64-byte line
}
```

Because `counterA` and `counterB` now sit ≥ 64 bytes apart, they cannot share a line, and the two hot loops stop invalidating each other.

#### B. `@Contended` Annotation (JDK 8+)

The JDK provides `jdk.internal.vm.annotation.Contended` (and `sun.misc.Contended` in `--add-exports`/`--add-opens` setups). HotSpot's JIT honors it by **inserting padding around the field** automatically:

```java
import jdk.internal.vm.annotation.Contended;

class LongAdderLike {
    @Contended
    volatile long cellValue;
}
```

- You must pass `-XX:-RestrictContended` to use it in your own (non-JDK) classes on some JDKs, or access it via the JDK's internal API.
- This is exactly how `LongAdder.Cell` and `ThreadLocalRandom` are padded internally.

#### C. `VarHandle` / `Unsafe` Padding

Frameworks like the **LMAX Disruptor** allocate `RingBuffer` slots as arrays of padded `Sequence` objects, ensuring consecutive slots never share a line with the producer/consumer sequence counters.

---

### 5. Where the JDK Already Pads

| Class | Padding reason |
| :--- | :--- |
| `LongAdder.Cell` | Each cell is its own padded `long` so different threads incrementing different cells never invalidate each other's lines. |
| `ThreadLocalRandom` / probe fields | Hot counters shared by many threads. |
| `AtomicLong` subclasses, `Exchanger.Node` | Arena slots / hot state kept on separate lines. |
| LMAX Disruptor `Sequence` | Producer/consumer cursors are padded so they don't false-share with the ring buffer contents. |

---

### 6. How to Detect / Measure False Sharing

1. **Profile with a hardware-performance-counter tool** (`perf stat` on Linux, `VTune`, `AMD uProf`): look for a high **cache-miss rate** combined with high **`lock cmpxchg` retries**.
2. **JMH test** (Q162): benchmark the "bad" vs "padded" layout — the padded version typically shows a dramatic win when more than one thread runs.
3. **`jcmd` / JMH `-prof perfnorm`** can expose `l1d_cache_miss`, `l2_request`, and `cacheline_contention` events.
4. A simple heuristic: if a multi-threaded counter benchmark doesn't scale at all (throughput flat with more cores), suspect false sharing before suspecting the lock.

---

### 7. Costs and Caveats

| Consideration | Detail |
| :--- | :--- |
| **Memory overhead** | Padding wastes heap (7 longs per field = ~56 bytes each). Only pad genuinely hot fields. |
| **Layout dependency** | Object field order can be changed by `-XX:FieldsAllocationStyle`; prefer `@Contended` or a dedicated array of padded objects. |
| **Not a lock** | Padding doesn't fix true contention on the *same* variable; it only removes spurious line contention. |
| **Machine dependent** | Line size varies (64 vs 128 bytes); over-padding is safer than under-padding. |

### Summary

- A **cache line** (64 bytes typical) is the transfer unit between memory and CPU caches; the **MESI** protocol invalidates the whole line on any write to a shared line.
- **False sharing** occurs when distinct variables on the same line are written by different cores — they ping-pong the line even though no data is shared.
- Fixes: **manual padding** (dummy fields) or the **`@Contended`** annotation; the JDK pads `LongAdder.Cell`, `ThreadLocalRandom`, and Disruptor sequences for exactly this reason.
- Detect it via **perf counters / JMH profiles**; the classic symptom is a counter that fails to scale with cores.

---

## 185. How do `Condition` objects work internally? Explain `await()`/`signal()`/`signalAll()`, the separate condition queue (`ConditionObject`), how a thread is moved between the AQS lock queue and the condition queue, and the differences from `Object.wait()`/`notify()`.

A `Condition` (created via `ReentrantLock.newCondition()`) is the modern replacement for `Object.wait()`/`notify()` — but designed to work with a `Lock` instead of `synchronized`. Its implementation, `AbstractQueuedSynchronizer.ConditionObject`, uses a **separate FIFO wait queue** per condition, which is what enables **multiple wait-sets per lock** and interruptible, timed waits.

---

### 1. The Mental Model: Two Queues Per Lock

Every `ReentrantLock` has **one AQS lock queue** (for threads waiting to acquire the lock) and can have **several condition queues** (one per `Condition` created on that lock).

```
            ReentrantLock
   lock queue (AQS)         Condition A queue        Condition B queue
   [T2 -> T3 -> T4]         [T5 -> T6]               [T7]
      waiters on lock          threads awaiting cond A    threads awaiting cond B
```

- **Lock queue**: threads blocked in `lock()` / `tryLock()`.
- **Condition queue**: threads that called `condition.await()` while holding the lock; they are parked on that condition's queue.

The two queues never merge physically — a thread moves from one to the other only through explicit `signal()`/`await()` transitions.

---

### 2. `ConditionObject` — A Single-FIFO Queue Per Condition

```java
public class ConditionObject implements Condition {
    private transient Node firstWaiter;   // head of the condition queue
    private transient Node lastWaiter;    // tail of the condition queue
}
```

The queue is just a linked list of **AQS `Node`s**, where each node holds a parked thread. It's FIFO — `signal()` wakes the **oldest waiter** (`firstWaiter`), which makes `signal()` fair with respect to arrival order (unlike `notify()`, which is unspecified).

---

### 3. `await()` — Release Lock, Park, Re-Acquire

`await()` performs three distinct steps:

```java
public final void await() throws InterruptedException {
    // 1. Enqueue the current thread onto the condition queue:
    Node node = addConditionWaiter();
    // 2. Fully release the lock (including reentrant holds!):
    int savedState = fullyRelease(node);
    int interruptMode = 0;
    // 3. Park until signaled (and no longer in the lock queue):
    while (!isOnSyncQueue(node)) {
        LockSupport.park(this);
        if ((interruptMode = checkInterruptWhileWaiting(node)) != 0)
            break;
    }
    // 4. After being signaled, re-acquire the lock through the normal AQS path:
    if (acquireQueued(node, savedState) && interruptMode != THROW_IE)
        interruptMode = REINTERRUPT;
    // 5. Cleanup + handle interrupt (throw vs re-interrupt).
}
```

The critical details:

- **`fullyRelease`** releases the lock **down to zero** — including any reentrant holds — and saves how many times the lock was held so it can be restored.
- **`isOnSyncQueue(node)`**: after `signal()` the thread is moved back onto the AQS lock queue; `await()` loops parking until that happens (spurious wakeups are handled by re-checking).
- **Re-acquisition** is the normal `acquireQueued` — so the waiting thread competes **fairly** (or unfairly, per lock policy) for the lock again.
- **Interrupts**: `await()` is interruptible; on interrupt during wait it either throws `InterruptedException` (`THROW_IE`) or just sets the interrupt flag (`REINTERRUPT`) depending on whether the thread had already been signaled.

---

### 4. `signal()` — Move One Waiter Back to the Lock Queue

```java
public final void signal() {
    if (!isHeldExclusively())           // must hold the lock
        throw new IllegalMonitorStateException();
    Node first = firstWaiter;
    if (first != null)
        doSignal(first);                // transfer firstWaiter to the sync queue
}
```

- `signal()` requires **holding the lock** (like `notify()` requires the monitor).
- It takes the **oldest** waiter (`firstWaiter`), unlinks it from the condition queue, and calls `transferForSignal`:

```java
final boolean transferForSignal(Node node) {
    // 1. clear the CONDITION status (no longer in the condition queue)
    if (!node.compareAndSetWaitStatus(Node.CONDITION, 0))
        return false;                   // already cancelled
    // 2. enqueue onto the AQS lock queue (FIFO tail):
    Node p = enq(node);
    // 3. if the new predecessor is cancelled, or park failed, unpark now
    if (p.waitStatus > 0 || !compareAndSetWaitStatus(p, Node.SIGNAL))
        LockSupport.unpark(node.thread);
    return true;
}
```

So `signal()` does **not** immediately wake the thread — it moves the node to the *lock* queue, and the thread wakes naturally when it wins the lock (or is unparked early if the predecessor is cancelled). `signalAll()` simply loops `doSignal` until the condition queue is empty.

---

### 5. The Key Difference: `await()` vs `Object.wait()`

| Feature | `Object.wait()` | `Condition.await()` |
| :--- | :--- | :--- |
| **Locking model** | Requires `synchronized` (monitor) | Works with any `Lock` (AQS) |
| **Multiple wait-sets** | One monitor per object | **Many** conditions per lock |
| **Reentrancy** | Monitor is fully released on wait | **Reentrant holds fully released** and restored (via `savedState`) |
| **Wake-up target** | `notify()` picks an unspecified thread | `signal()` wakes the **oldest** waiter (FIFO) |
| **Timed wait** | `wait(timeout)` | `awaitNanos`, `await(time, unit)`, `awaitUntil` |
| **Interrupts** | Throws `InterruptedException`, clears flag | Configurable throw/re-interrupt |
| **Spurious wakeups** | Can happen; must loop | Can happen; `await` re-checks internally |

**Why multiple conditions matter:** with one monitor, you cannot wait on "queue full" and "queue empty" simultaneously with different predicates — you must `notifyAll()` and re-check. With `Condition`, you get `notFull` and `notEmpty` as separate wait-sets, so `ArrayBlockingQueue` can wake only the threads that matter (`notEmpty.signal()` on `put`).

---

### 6. Practical Example — `ArrayBlockingQueue`-Style

```java
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull = lock.newCondition();
private final Condition notEmpty = lock.newCondition();

void put(E e) throws InterruptedException {
    lock.lock();
    try {
        while (count == capacity) notFull.await();   // wait for space
        // ... enqueue ...
        notEmpty.signal();                           // wake one consumer
    } finally { lock.unlock(); }
}

E take() throws InterruptedException {
    lock.lock();
    try {
        while (count == 0) notEmpty.await();         // wait for data
        // ... dequeue ...
        notFull.signal();                            // wake one producer
    } finally { lock.unlock(); }
}
```

Note the **`while` loop guard**: like `wait()`, `await()` may return spuriously, so the predicate must be re-checked in a loop.

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Calling `signal()` without holding the lock | `IllegalMonitorStateException` | Acquire the lock first |
| Using a bare `if` after `await()` | Lost/spurious wakeups corrupt logic | Loop while the predicate is false |
| Creating a new `Condition` per task instead of per resource | Broken wakeup targeting | One `Condition` per distinct predicate/resource |
| Forgetting to restore `savedState` semantics | Reentrant count mismatch | Rely on `ConditionObject` — it handles it; don't roll your own |

### Summary

- `Condition` (`ConditionObject`) maintains a **separate FIFO wait queue** per condition, using AQS `Node`s.
- `await()` enqueues the thread, **fully releases the lock** (incl. reentrant holds), parks, then **re-acquires** through the normal AQS path.
- `signal()` moves the **oldest waiter** from the condition queue to the AQS lock queue (FIFO); `signalAll()` drains the queue.
- It generalizes `wait/notify` with **multiple wait-sets per lock**, FIFO wake-up, timed/interruptible waits, and is used internally by `ArrayBlockingQueue`, `ReentrantLock`-based pools, and most bounded structures.

---

## 186. How does `ReentrantReadWriteLock` work internally? Explain how the single 32-bit AQS state is partitioned into two 16-bit counts, how read/write locks are acquired and released, the mechanics of lock downgrading vs. upgrading, write-starvation avoidance, and the role of `ThreadLocalHoldCounter`.

`ReentrantReadWriteLock` (RRWL) allows multiple concurrent readers but only a single exclusive writer. Under the hood, it is implemented using a custom **AbstractQueuedSynchronizer (AQS)** helper class (`Sync`). Because AQS manages lock state via a single 32-bit integer (`state`), RRWL's primary engineering challenge is representing both **read lock holds (shared)** and **write lock holds (exclusive)** within that single 32-bit value.

---

### 1. The 32-bit State Split

To track both reader and writer counts in one variable, RRWL partitions the 32-bit AQS `state` into two 16-bit halves:

```
               32-bit AQS State
+-------------------------------+-------------------------------+
|  Shared (Read) Count: 16 bits | Exclusive (Write) Count: 16-bit |
+-------------------------------+-------------------------------+
 31                           16 15                            0
```

- **High 16 bits (bits 16–31)**: Shared (Read) lock count. It represents the total number of shared locks held across all threads (including reentrant reads).
- **Low 16 bits (bits 0–15)**: Exclusive (Write) lock count. It represents the write lock hold count (which is always held by a single thread, representing reentrant write holds).

In the source code, this split is managed using bit shifts and bitwise AND masking:

```java
abstract static class Sync extends AbstractQueuedSynchronizer {
    static final int SHARED_SHIFT   = 16;
    static final int SHARED_UNIT    = (1 << SHARED_SHIFT); // 65536
    static final int MAX_COUNT      = (1 << SHARED_SHIFT) - 1; // 65535
    static final int EXCLUSIVE_MASK = (1 << SHARED_SHIFT) - 1; // 65535

    /** Returns the shared (read) lock count */
    static int sharedCount(int c)    { return c >>> SHARED_SHIFT; }
    
    /** Returns the exclusive (write) lock count */
    static int exclusiveCount(int c) { return c & EXCLUSIVE_MASK; }
}
```

Since each half is 16 bits, the maximum number of reentrant read or write locks that can be held is **65,535** (`MAX_COUNT`). Exceeding this limit causes an `Error("Maximum lock count exceeded")`.

---

### 2. Write Lock Acquisition (`tryAcquire`)

The write lock is an exclusive (write) lock. Its acquisition logic (`tryAcquire`) executes the following steps:

```java
protected boolean tryAcquire(int acquires) {
    Thread current = Thread.currentThread();
    int c = getState();
    int w = exclusiveCount(c);
    
    if (c != 0) {
        // 1. If there is a read lock (w == 0 means read count > 0) 
        //    OR the write lock is held by a different thread: fail.
        if (w == 0 || current != getExclusiveOwnerThread())
            return false;
            
        // 2. Check low 16-bit overflow
        if (w + exclusiveCount(acquires) > MAX_COUNT)
            throw new Error("Maximum lock count exceeded");
            
        // Reentrant write acquisition: update state
        setState(c + acquires);
        return true;
    }
    
    // 3. If state is 0, check if the thread should block based on fairness policy.
    //    If writer should block, or CAS to acquire fails, return false.
    if (writerShouldBlock() || !compareAndSetState(c, c + acquires))
        return false;
        
    setExclusiveOwnerThread(current);
    return true;
}
```

- **Read blocks write**: A writer cannot acquire the lock if there are any active readers (`c != 0 && w == 0`).
- **Exclusive ownership**: If a write lock is already held, only the thread holding the write lock can acquire it again (reentrancy).

---

### 3. Read Lock Acquisition (`tryAcquireShared`)

The read lock is a shared lock. Its acquisition logic (`tryAcquireShared`) executes the following steps:

```java
protected int tryAcquireShared(int unused) {
    Thread current = Thread.currentThread();
    int c = getState();
    
    // 1. If write lock is held by another thread, fail immediately.
    if (exclusiveCount(c) != 0 && getExclusiveOwnerThread() != current)
        return -1;
        
    int r = sharedCount(c);
    
    // 2. Check if reader should block according to policy, and if r < MAX_COUNT,
    //    and attempt to CAS the shared count up by SHARED_UNIT.
    if (!readerShouldBlock() && r < MAX_COUNT &&
        compareAndSetState(c, c + SHARED_UNIT)) {
        
        // 3. Record local read hold count for debugging and reentrancy tracking
        if (r == 0) {
            firstReader = current;
            firstReaderHoldCount = 1;
        } else if (firstReader == current) {
            firstReaderHoldCount++;
        } else {
            HoldCounter rh = cachedHoldCounter;
            if (rh == null || rh.tid != LockSupport.getThreadId(current))
                cachedHoldCounter = rh = readHolds.get();
            else if (rh.count == 0)
                readHolds.set(rh);
            rh.count++;
        }
        return 1;
    }
    
    // 4. Fallback to full spin-loop if CAS fails or thread needs to block/queue
    return fullTryAcquireShared(current);
}
```

- **Write blocks read**: A reader cannot acquire the lock if another thread holds the write lock. However, if the *current* thread holds the write lock, it *can* acquire the read lock (supporting lock downgrading).
- **CAS Step**: The read lock acquisition increments the state by `SHARED_UNIT` (`1 << 16` or `65536`), which changes only the high 16 bits of the state.

---

### 4. Tracking Reentrant Read Holds: `ThreadLocalHoldCounter` and Caching

While the AQS `state` tracks the *total* number of read locks held globally across all threads, it does not record *which* individual threads hold the read lock, nor how many times they have reentrantly acquired it. This mapping is needed to:
- Enforce reentrant read acquisitions.
- Know when a thread's read hold count drops to zero to clean up its state on `unlock()`.

To track per-thread read hold counts, RRWL uses:
1. **`readHolds`**: A subclass of `ThreadLocal<HoldCounter>`. Each thread gets a unique `HoldCounter` containing its count and thread ID.
2. **Performance Optimizations (Caching)**:
   - `ThreadLocal` lookups require map lookups, which degrade read performance.
   - **`firstReader` and `firstReaderHoldCount`**: Fields that store the first thread that acquired the read lock when the read count transitioned from 0 to 1. If only a single thread uses the read lock, this avoids the `ThreadLocal` lookup entirely.
   - **`cachedHoldCounter`**: A field that caches the `HoldCounter` of the *last* thread to successfully acquire the read lock. In cases where the same thread repeatedly acquires/releases the read lock, this cached lookup avoids the `ThreadLocal` access.

---

### 5. Lock Downgrading vs. Upgrading

Lock downgrading allows a thread holding the write lock to acquire the read lock and then release the write lock, keeping the resource locked for reading without a gap.

```
Write Lock Held  -->  Read Lock Acquired  -->  Write Lock Released
(State: Exclusive)     (State: Both Held)       (State: Shared Only)
```

- **Lock Downgrading (Supported)**:
  1. Current thread holds the write lock.
  2. Thread calls `readLock().lock()`. In `tryAcquireShared`, the check `exclusiveCount(c) != 0 && getExclusiveOwnerThread() != current` passes because the owner *is* the current thread. The read lock is successfully acquired.
  3. Thread calls `writeLock().unlock()`. The write count goes to 0, leaving only the read lock active.
  4. **Why this matters**: It prevents race conditions. If you released the write lock *before* acquiring the read lock, another writer could sneak in and modify the state in the middle. Downgrading ensures continuous, atomic locking.

- **Lock Upgrading (Not Supported / Deadlock)**:
  1. Thread holds the read lock and calls `writeLock().lock()`.
  2. In `tryAcquire`, the check `w == 0` (which implies read count > 0) evaluates to true because the current thread itself is holding a read lock.
  3. The thread blocks waiting for all readers to release their locks.
  4. Since the current thread is blocked, it will never release its read lock.
  5. Result: **Permanent deadlock**. To upgrade, the thread must manually release its read lock first, then acquire the write lock (which introduces a race condition).

---

### 6. Write Starvation Avoidance

In the unfair implementation of `ReentrantReadWriteLock` (`NonfairSync`), a reader trying to acquire the lock could easily starve waiting writers if there is a constant stream of concurrent readers.

To prevent this, `NonfairSync` implements the following write-starvation avoidance mechanism:

```java
static final class NonfairSync extends Sync {
    final boolean writerShouldBlock() {
        return false; // Writers can always barge/try CAS
    }
    final boolean readerShouldBlock() {
        // Starvation avoidance: block reader if the first queued thread is a writer
        return apparentlyFirstQueuedIsExclusive();
    }
}
```

- If `apparentlyFirstQueuedIsExclusive()` returns true (meaning the thread at the head of the AQS wait queue is waiting in exclusive mode for a write lock), `readerShouldBlock()` returns true.
- Any incoming reader will bypass the fast-path acquisition in `tryAcquireShared` and be forced to enqueue behind the waiting writer, even in an unfair lock.

---

### 7. Comparison: Read Lock vs. Write Lock

| Feature | Read Lock (Shared) | Write Lock (Exclusive) |
| :--- | :--- | :--- |
| **AQS state mutation** | Adds `SHARED_UNIT` (`1 << 16`) to state | Adds `1` to state |
| **Wait queue behavior** | Propagates unparks to subsequent readers | Unparks only the next direct waiter |
| **Reentrancy tracking** | `firstReader` field + `ThreadLocalHoldCounter` | `state` low 16 bits |
| **Condition support** | Not supported (throws `UnsupportedOperationException`) | Fully supported via `newCondition()` |
| **Interruptibility** | Optional (standard `lock()` blocks uninterruptibly) | Optional (standard `lock()` blocks uninterruptibly) |

### Summary

- **State Partition**: RRWL splits the 32-bit AQS state into two 16-bit halves: the high 16 bits track the read lock count, and the low 16 bits track the write lock count.
- **Acquisition Guards**: A read lock cannot be acquired if another thread holds the write lock. A write lock cannot be acquired if there are *any* active read locks or another writer.
- **Lock Downgrading**: A writer can acquire a read lock and release its write lock. Lock upgrading (read -> write) is prohibited and deadlocks.
- **Hold Count Cache**: Because `ThreadLocal` lookups are slow, RRWL optimizes read performance by caching the first reader thread and the last reader's hold counter in thread-local cache fields.
- **Starvation Avoidance**: In unfair mode, readers will block (`readerShouldBlock()`) if the first thread queued in AQS is waiting for a write lock.

---

## 187. How does `StampedLock` work internally, and when should you use it instead of `ReentrantReadWriteLock`? Explain optimistic read stamps, the `state` bit layout (write bit + read count), `tryOptimisticRead`/`validate`, and lock upgrading with the `readLock`/`writeLock` conversion.

`StampedLock` (`java.util.concurrent.locks`) is a **performance-oriented read-write lock** that adds a third, lock-free mode: **optimistic reading**. Unlike `ReentrantReadWriteLock` (RRWL), it is **not reentrant** and **cannot be used with `Condition`** — but for read-dominated workloads with short critical sections, its optimistic path can be dramatically faster because it **never blocks and never writes to shared state** while a reader merely validates.

---

### 1. The Core State: One `long` With a Write Bit

`StampedLock` packs its entire state into a single **`volatile long state`** (updated with CAS), laid out as:

```
state (64-bit long):
+----------------------------------------------------+
| unused (16 bits) | read count (48 bits) | write bit |
+----------------------------------------------------+
   63              48                   1           0
```

- **Write bit (bit 0)**: `1` means a writer holds the lock (exclusive); `0` means unlocked or readers only.
- **Read count (bits 1–48)**: the number of active readers. Incremented/decremented by `2` (because bit 0 is reserved), so each read lock adds `RUNIT = 1L << 1`.
- The **stamp** returned by every acquisition method is just a snapshot of this `state`. The stamp is the *entire handshake*: you hold it and you must hand it back on release.

```java
public class StampedLock implements java.io.Serializable {
    private volatile long state;
    private static final int  LG_READERS = 7;           // spin threshold
    private static final long RUNIT     = 1L << 1;      // +1 reader
    private static final long WBIT      = 1L;           // write bit
    // ... reader/writer wait queues (WNode) ...
}
```

---

### 2. The Three Modes

| Mode | Method | Blocks? | Reentrant? | Returns |
| :--- | :--- | :--- | :--- | :--- |
| **Writing** | `writeLock()` / `tryWriteLock()` | Yes | No | A stamp; writing requires `state`'s write bit clear, then sets it |
| **Reading** | `readLock()` / `tryReadLock()` | Yes (if writer holds it) | No | A stamp; adds `RUNIT` to the read count |
| **Optimistic read** | `tryOptimisticRead()` | **Never** | N/A | A stamp that is **not a lock** — just a state snapshot |

The optimistic "stamp" is the key novelty: `tryOptimisticRead()` merely **reads `state`** (a volatile read) and returns it. It acquires nothing, blocks nothing, and takes **no lock at all**:

```java
public long tryOptimisticRead() {
    long s;
    return (((s = state) & WBIT) == 0L) ? s : 0L;   // 0 => a writer owns it
}
```

A return of `0` means a writer currently holds the lock. A non-zero stamp means "the state looked like this at the moment I read it" — it is your proof-of-snapshot, to be verified later.

---

### 3. The Optimistic-Read Pattern: Read → Validate → Retry

The canonical usage reads shared data, then **validates** that no writer intervened *while* the read happened:

```java
long stamp = lock.tryOptimisticRead();          // 1. snapshot state (no blocking)
double x = px;                                  // 2. read the fields (no lock held!)
double y = py;
if (!lock.validate(stamp)) {                    // 3. did a writer change state since?
    stamp = lock.readLock();                    //    yes -> upgrade to a real read lock
    try {
        x = px;                                 //    re-read under the lock
        y = py;
    } finally {
        lock.unlockRead(stamp);
    }
}
```

`validate(stamp)` compares the passed stamp to the **current `state`**:

```java
public boolean validate(long stamp) {
    return (stamp & WBIT) == 0L
        && (stamp & ~WBIT) == (state & ~WBIT);  // same read count & no write bit
}
```

The correctness argument (a form of **data-race detection via version numbers**):

- The fields being read must be `volatile` (or otherwise read/written with release/acquire semantics), so the initial reads and the writer's writes are ordered.
- If **no writer** bumped the write bit between the stamp snapshot and `validate`, then the values read are consistent — the whole read happened during a window with no writer.
- If a writer **did** interleave, the write bit differs (or the read count moved), `validate` returns `false`, and you must fall back to a real read lock and re-read.

**This is the crucial advantage:** in the uncontended case the optimistic path does exactly one volatile read plus a comparison — **no CAS, no parking, no cache-line ownership transfer**. RRWL readers always acquire and release shared locks (each a CAS), so `StampedLock` optimistic reads win decisively when the read side dominates and writes are rare.

---

### 4. Write Lock and Upgrade / Downgrade Mechanics

**Write acquisition** flips the write bit atomically:

```java
public long writeLock() {
    long s, next;
    return ((next = ((s = state) + WBIT)) == 0L
            ? acquireWrite(false, 0L)     // overflow -> full blocking path
            : casState(s, next))          // normal path: just set bit 0
        ? next : acquireWrite(false, 0L);
}
```

**Lock upgrading (read → write)** is supported via `tryConvertToWriteLock(stamp)`:

```java
long stamp = lock.readLock();
// ... read phase ...
long wstamp = lock.tryConvertToWriteLock(stamp);   // atomically convert if possible
if (wstamp != 0L) {
    stamp = wstamp;                                // upgraded without releasing
} else {
    lock.unlockRead(stamp);                        // contention: release and retry
    stamp = lock.writeLock();
}
```

- **No deadlock, unlike RRWL**: the current thread already holds the read lock, so the conversion CASes the read count down and the write bit up **atomically** — it never waits for itself. If another writer is active, the CAS fails and `0` is returned (you must release and re-acquire).
- **Downgrading (write → read)** works similarly with `tryConvertToReadLock(stamp)`, and **conversion to optimistic** is `tryConvertToOptimisticRead(stamp)` — e.g., downgrade to a read lock then to optimistic as the write phase finishes.

---

### 5. `StampedLock` vs `ReentrantReadWriteLock`

| Feature | `ReentrantReadWriteLock` | `StampedLock` |
| :--- | :--- | :--- |
| **Optimistic reads** | No | **Yes** — `tryOptimisticRead`/`validate` |
| **Reentrancy** | Yes (both read and write) | **No** — every acquisition must be released |
| **`Condition` support** | Yes (on the write lock) | **No** — throws `UnsupportedOperationException` |
| **Read-mode cost** | CAS acquire/release every time | Uncontended reads are **lock-free** (validate only) |
| **Fairness option** | Fair/unfair constructors | No fairness flag (waiters use a CLH-style queue) |
| **Best for** | General-purpose, need reentrancy or conditions | Read-mostly, write-rare, short critical sections |
| **Upgrade read → write** | Deadlocks | `tryConvertToWriteLock` — safe, atomic |

---

### 6. Pitfalls and Warnings

| Pitfall | Why it hurts |
| :--- | :--- |
| Optimistic reads with **non-volatile** fields | `validate` cannot prove consistency; you must ensure the fields you read during the optimistic window are `volatile` (or use safe publication) |
| Holding a lock and then calling `tryConvert...` on the wrong stamp | Every conversion validates the stamp; a wrong/expired stamp returns `0` and you must handle the retry path |
| Forgetting reentrancy is unsupported | A second `writeLock()` on the same thread blocks forever — RRWL users trip on this |
| Using it where readers block long | The spin-based waiting (`LG_READERS`) burns CPU under heavy contention; a `ReentrantReadWriteLock` with blocking queues scales better there |
| Validating after the object is mutated through a non-stamped path | `validate` only detects changes made *through this lock* — external unsynchronized writes corrupt the data before the lock can help |

### Summary

- `StampedLock` tracks state in a single `long`: **write bit 0** + **48-bit read count**, mutated with CAS, with every acquisition returning a **stamp**.
- `tryOptimisticRead()` is **lock-free**: it snapshots `state`, you read `volatile` fields, then `validate(stamp)` proves no writer interleaved — else you fall back to a real read lock and retry.
- `tryConvertToWriteLock` / `tryConvertToReadLock` / `tryConvertToOptimisticRead` give **atomic mode conversions** — including a safe read→write upgrade that RRWL cannot offer.
- It is **not reentrant** and has **no `Condition`**, so prefer `ReentrantReadWriteLock` when those are required; prefer `StampedLock` for read-dominated workloads with short, hot critical sections where uncontended reads must be as cheap as a volatile read.

---

## 188. How does `ForkJoinPool` work internally? Explain work-stealing, the double-ended `ForkJoinTask` work queue, `ForkJoinWorkerThread` and the common pool, the `submit`/`invoke`/`fork`/`join` protocol, and the relation to `ThreadPoolExecutor` and the managed blocker mechanism.

`ForkJoinPool` (`java.util.concurrent`) is a **specialized executor built for divide-and-conquer and fork/join parallelism**. Its core trick is **work stealing**: idle worker threads steal tasks from the tails of other workers' queues, which keeps all CPUs busy even when individual subtasks are tiny. It is what powers `parallelStream()`, `CompletableFuture`'s common pool, and `Arrays.parallelSort`.

---

### 1. Work Stealing: The Core Idea

A classic thread pool has one shared task queue; every worker contends on it. `ForkJoinPool` instead gives **each worker thread its own double-ended queue (`WorkQueue`)**, and adds stealing:

```
Worker 1 (busy)      Worker 2 (idle)      Worker 3 (idle)
  queue: [t1,t2,t3]    queue: [..]          queue: [t4,t5]
              ^ LIFO        ^ steals from      ^ steals from
              own tasks     tail of others     tail of others
```

- **Push / pop**: a worker pushes subtasks (from `fork()`) onto the **bottom (tail)** of its own queue and pops them LIFO.
- **Steal**: an **idle** worker takes a task from the **head/tail** of a *random* victim's queue.
- **Why it works**: because a worker pops its *own* tasks LIFO (most recent = most likely to be the still-unexplored subproblem, maximizing cache locality), while stealers take from the *other end*. The queues are accessed by exactly one owner (the worker) plus many potential stealers, so the design only needs cheap, contention-light coordination.

```java
// Worker's own queue:
final ForkJoinTask<?>[] queue;    // task array (ring buffer)
int top;                          // stack top for the owner
volatile int base;                // index for stealers (volatile!)
```

The asymmetry — owner writes `top` with no CAS, stealers CAS `base` — is what makes work stealing so cheap for the common (non-contended) case.

---

### 2. The Double-Ended Queue (Deque) and Its Protocol

Each `WorkQueue` is a **bounded ring buffer of `ForkJoinTask` references** with two indices:

| Index | Written by | Semantics |
| :--- | :--- | :--- |
| `top` | Owner only | Pushes/pops at the tail (LIFO for the owner) |
| `base` | Stealers (`volatile`, CAS) | Stealers take from the head |

The invariant that keeps it simple:

- The **owner** runs `push` (tail) and `pop` (tail) without any synchronization — only it touches `top`.
- **Stealers** use a CAS on `base` to grab the task at the head and claim it, moving `base` forward.
- If a queue becomes empty, stealers mark it inactive; if the owner's pop races with a steal at the boundary, the owner falls back to a CAS-safe path.

This "one thread owns the queue, others only steal from the head" design gives near-zero overhead for the 99% case (no stealing happening) and clean correctness when stealing happens.

---

### 3. `fork` / `join` / `invoke` — The Task Protocol

- **`fork()`** = push a new subtask onto the **current worker's own queue**:

```java
public final ForkJoinTask<V> fork() {
    Thread t;
    if ((t = Thread.currentThread()) instanceof ForkJoinWorkerThread)
        ((ForkJoinWorkerThread)t).workQueue.push(this);   // fast path: own queue
    else
        ForkJoinPool.common.externalPush(this);           // external thread path
    return this;
}
```

- **`join()`** = wait for the task's result. For the *owner*, if the task is still in its own queue it may **help complete it by popping** it (cheap). Otherwise the worker **parks** (via the pool's idle mechanism) and/or **steals** other work while waiting, so the wait does not waste a CPU.

- **`invoke(task)`** = `fork()` + `join()`: start the task and block for its result. If a `ForkJoinWorkerThread` calls it, the worker performs **task merging** locally (running subtasks without leaving the pool). The key guarantee: a blocked `join()` on one worker lets the worker continue doing *other* pool work (stealing), unlike a normal executor where a blocked task wastes its thread.

The `ForkJoinTask` class comes in three flavors:

| Class | When to use |
| :--- | :--- |
| `RecursiveAction` | Task returns no result (e.g., sort a subrange) |
| `RecursiveTask<V>` | Task returns a result (e.g., sum, search) |
| `CountedCompleter` | Fine-grained completion callbacks / dependent tasks |

---

### 4. The Common Pool and Worker Threads

- **`ForkJoinPool.commonPool()`** is a process-wide static pool lazily created on first use, sized at `parallelism = Runtime.getRuntime().availableProcessors() - 1` (configurable via `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N`).
- `parallelStream()` and `CompletableFuture` (default executor) use this common pool — so a blocking `parallelStream()` task can starve the whole process's async pipeline.
- **`ForkJoinWorkerThread`** is a thin `Thread` subclass holding a reference to its `WorkQueue`; it runs `runWorker()` which loops: execute a task from own queue → steal from others → park when nothing is available.

---

### 5. Managed Blockers: Handling Blocking Inside Fork/Join

The fork/join model assumes tasks are **CPU-bound and non-blocking**. If a task blocks (I/O, `Thread.sleep`, waiting on a lock), the occupying worker can no longer steal, defeating the design. `ManagedBlocker` lets a task tell the pool "I'm about to block, please add a compensation thread":

```java
ForkJoinPool.managedBlock(new ForkJoinPool.ManagedBlocker() {
    public boolean block() {
        return latch.await();            // the real blocking operation
    }
    public boolean isReleasable() {
        return latch.getCount() == 0;
    }
});
```

`managedBlock` checks whether the pool is at target parallelism and, if so, **spawns a temporary compensation worker** so overall throughput doesn't collapse while the original worker is blocked. This is exactly how `Phaser`, `CountDownLatch`, and `CompletableFuture`'s internal waits cooperate with `ForkJoinPool`.

---

### 6. `ForkJoinPool` vs `ThreadPoolExecutor`

| Aspect | `ThreadPoolExecutor` | `ForkJoinPool` |
| :--- | :--- | :--- |
| **Queue** | One shared `BlockingQueue` (all threads contend) | Per-worker **double-ended queues** + stealing |
| **Concurrency model** | Tasks are independent; a blocked task wastes its thread | Tasks may split; a blocked `join()` lets the worker do other work |
| **Idle threads** | Park on the shared queue | Steal from random victims, then park |
| **Suitability** | I/O-bound, independent tasks | CPU-bound, recursively splittable tasks |
| **Backpressure** | Bounded queue / saturation policies | No queue bound; relies on task granularity (pools can exhaust memory if subtasks are oversized) |
| **Common use** | Web servers, task pipelines | `parallelStream()`, `CompletableFuture` common pool, `Arrays.parallelSort` |

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Doing blocking I/O in a `parallelStream()` task | Common pool starves the whole JVM | Use `managedBlock` or a dedicated `ThreadPoolExecutor` |
| Forking too-fine subtasks | Huge task allocation + stealing overhead | Set a **threshold** (e.g., split until `size < 10_000`), don't fork every element |
| Sharing mutable state between subtasks | Race conditions | Each subtask must work on its own slice |
| Joining without checking for cancellation/exceptions | Results silently wrong or swallowed | Handle `ForkJoinTask` exceptions (`getException`) |

### Summary

- `ForkJoinPool` is a **work-stealing executor**: each worker owns a **deque**, pushes/forks to its tail, pops its own tasks LIFO, and idle workers **steal from the head of random victims' queues**.
- The protocol is **`fork()`** (push to own queue) → **`join()`** (park/steal while waiting) → `invoke()` (`fork`+`join`), with `RecursiveAction`/`RecursiveTask`/`CountedCompleter` task types.
- The **common pool** backs `parallelStream()` and `CompletableFuture`; worker threads loop execute → steal → park.
- **`ManagedBlocker`** compensates for blocking tasks by adding temporary worker threads so a blocked `join` doesn't idle a CPU.
- Prefer `ForkJoinPool` for **CPU-bound, recursively splittable** work; prefer `ThreadPoolExecutor` for **I/O-bound, independent** tasks.

---

## 189. How does `ConcurrentHashMap` work internally in Java 8+? Explain the `Node[]` table with `synchronized` bins (lock striping per bucket), CAS on `binCount`/`sizeCtl` for `put`, the migration/`ForwardingNode` mechanism during resize, `treeifyBin` to `TreeNode` for long chains, and how `size()`/`mappingCount()` sum via `CounterCell`s.

`ConcurrentHashMap` is Java's workhorse concurrent map. Since Java 8 its design changed fundamentally from the old segment-based one (Java 7): instead of locking a few large segments, it now uses a single **`Node[]` table** where **each bin (bucket) is individually synchronized** — a fine-grained, adaptive lock-striping scheme. This gives much higher concurrency: concurrent `put`s on *different* bins proceed fully in parallel, while long bins are upgraded to balanced red-black trees.

---

### 1. The Table and the Node

```java
public class ConcurrentHashMap<K,V> extends AbstractMap<K,V>
        implements ConcurrentMap<K,V>, Serializable {
    transient volatile Node<K,V>[] table;   // the bucket array
    private transient volatile Node<K,V>[] nextTable;  // used during resize
    private transient volatile long baseCount;         // size when uncontended
    private transient volatile int sizeCtl;            // resize control / threshold
}
```

- `table` is a `volatile Node[]` — bins are accessed via `(n - 1) & hash`.
- `Node` is the same linked-list node type as in `HashMap`, but with **`volatile` fields** (`hash`, `key`, `val`, `next`):

```java
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    volatile V val;          // visible to readers without a lock
    volatile Node<K,V> next;
}
```

- **Reads (`get`) are lock-free**: they walk the bin using `volatile` reads; correctness comes from `happens-before` edges established by the `volatile` writes of concurrent `put`s.

---

### 2. `put` — CAS the Bin, Then Synchronize on It

`putVal` uses a **CAS loop**: repeatedly find the target bin, and take one of three actions depending on its state:

```java
final V putVal(K key, V value, boolean onlyIfAbsent) {
    ...
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                          // lazy init
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            // 1. Bin is EMPTY: CAS the first node in — no lock needed.
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;                                  // fast path
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);                 // 2. bin is a ForwardingNode → help resize
        else {
            // 3. Bin is OCCUPIED: synchronize on that single bin (lock striping).
            synchronized (f) {
                // re-check under the lock, then walk/insert the list,
                // increment binCount; maybe treeify; if needed resize.
            }
        }
    }
    addCount(1L, binCount);                             // update size counters
}
```

Key design points:

- **Empty bin fast path**: `casTabAt` inserts the first node with a single CAS — no lock at all. This is why `ConcurrentHashMap` excels at *insert-only* workloads.
- **Occupied bin slow path**: `synchronized (f)` locks *the head node of the bin*, not the whole table. Different bins = different head nodes = different monitors → full parallelism across buckets. This is lock striping reduced to its finest grain (one lock per bucket).
- **`MOVED` bins**: during a resize the old bins are replaced by `ForwardingNode`s; a `put` that finds one helps the resize (`helpTransfer`) instead of waiting.

---

### 3. `sizeCtl` and the CAS-Based `addCount` Path

`sizeCtl` is a multi-purpose control field (default 0, `-1` while initializing, `-(1 + resizeThreads)` while resizing, else the next resize threshold):

| `sizeCtl` value | Meaning |
| :--- | :--- |
| `0` | Default / not initialized |
| `-1` | A thread is initializing the table |
| `< -1` | Resize in progress; `-(1 + n)` encodes how many threads are helping |
| `> 0` | The next resize threshold (`table.length * 0.75`) |

`addCount` increments the size in a **CAS loop on `baseCount`**; on CAS failure (contention), it bumps a random **`CounterCell`** instead — the same striping trick as `LongAdder` (Q182). `size()`/`mappingCount()` then sum `baseCount + Σ cells`.

---

### 4. Resizing: The `ForwardingNode` Migration Protocol

Resizing is cooperative and lock-free to read. When a bin is migrated, its slot in the old table is replaced by a **`ForwardingNode`** (whose `nextTable` field points at the new array):

```java
static final class ForwardingNode<K,V> extends Node<K,V> {
    final Node<K,V>[] nextTable;
    ForwardingNode(Node<K,V>[] tab) { super(MOVED, null, null, null); nextTable = tab; }
}
```

- A reader that encounters a `ForwardingNode` simply **redirects its lookup into `nextTable`** (`find` is overridden) — reads never block during a resize.
- A writer that encounters one **joins the migration** (`helpTransfer` / `transfer`): it moves bins from old → new table, marks each moved bin's old slot with a new `ForwardingNode`, and each participating thread CASes `sizeCtl` to register itself.
- The new table is **double the size** (`n << 1`), and each bin's entries are split between two new bins based on a bit of the hash — so a single old bin maps to exactly two new bins, preserving ordering within each half.
- **Resize is incremental**: `transfer` moves bins one at a time (`stride`), so the map stays usable — and lock-free to readers — throughout.

---

### 5. `treeifyBin` — Upgrading Long Bins to Red-Black Trees

If a bin's list grows past `TREEIFY_THRESHOLD` (8) **and** the table is at least 64 bins (`MIN_TREEIFY_CAPACITY`), the bin is converted to a balanced red-black tree of `TreeNode`s:

- **Why**: `get`/`put` on a long linked list is `O(n)`; a red-black tree keeps it `O(log n)` even for adversarial hash collisions.
- `TreeBin` is a special node holding the tree's root; it also maintains a **read-lock-free structure** — writers synchronize on the bin, while concurrent readers can still traverse (readers see a mostly-immutable tree thanks to careful `volatile`/`next` wiring and lock-free `find`).
- If the table is still small (< 64 bins), `treeifyBin` instead **resizes the table** to spread the colliding keys first.

---

### 6. `size()` / `mappingCount()` — Summing With `CounterCell`s

Size tracking uses **stripped counters** (like `LongAdder`):

- Uncontended increments go to `baseCount` via CAS.
- On CAS failure, a per-thread `CounterCell` (a padded `volatile long`) is bumped.
- `size()` = `baseCount + Σ counterCells`. It is **approximate under concurrent writes** — but `mappingCount()` returns the same value as a `long` and is the recommended API.

This avoids a single contended counter line and mirrors `LongAdder`'s scaling logic (Q182).

---

### 7. `ConcurrentHashMap` vs `Hashtable` vs `HashMap`

| Feature | `HashMap` | `Hashtable` | `ConcurrentHashMap` |
| :--- | :--- | :--- | :--- |
| **Thread-safe** | No | Yes | Yes |
| **Locking** | None | Global lock (`synchronized` on whole map) | **Per-bin** `synchronized` + CAS for empty bins |
| **Null keys/values** | Allowed | Not allowed | **Not allowed** |
| **Read concurrency** | Not safe | Blocked by writers | **Lock-free** (`volatile` reads) |
| **Write concurrency** | Not safe | Serialized | Parallel across different bins |
| **Iteration** | Fail-fast | Fail-fast | **Weakly consistent** (no `ConcurrentModificationException`) |

---

### 8. Common Pitfalls

| Pitfall | Why it hurts |
| :--- | :--- |
| **Using `null` keys/values** | Throws `NullPointerException` — `ConcurrentHashMap` forbids nulls |
| **Long-running atomic ops on the map's own key/value** | No built-in CAS on `Map.Entry`; use `compute`, `merge`, `computeIfAbsent` for atomic updates |
| **Assuming `size()` is exact under writes** | It is an approximation; `mappingCount()` still approximates but returns `long` |
| **Heavy write contention on a few keys** | Bin-level locking serializes them; consider sharding the keys |
| **Not handling `computeIfAbsent` reentrancy** | Recursively calling the map from within the mapping function can deadlock or throw |

### Summary

- Java 8+ `ConcurrentHashMap` uses **one `Node[]` table with per-bin `synchronized` locks** — CAS for empty bins, monitor on the bin head for occupied ones → write parallelism across buckets.
- `sizeCtl` encodes init/resize/threshold state; `addCount` uses `baseCount` + striped `CounterCell`s (`LongAdder` style) for scalable size tracking.
- Resize uses **`ForwardingNode`s** so readers redirect seamlessly and writers help migrate incrementally — reads never block during growth.
- Long bins become red-black **`TreeNode`** trees past threshold 8 (with a 64-bin minimum) to keep `O(log n)` lookups under hash collisions.
- It forbids `null` keys/values, iterates **weakly consistent**, and beats `Hashtable` (global lock) and `HashMap` (unsafe) on every axis.

---

## 190. How does `ThreadPoolExecutor` work internally? Explain the single `ctl` state (`workerCount` + `runState`), the worker lifecycle (`addWorker`/`Worker.run`/`getTask`), keep-alive timing, and how the four saturation policies (`AbortPolicy`, `CallerRunsPolicy`, `DiscardPolicy`, `DiscardOldestPolicy`) interact with the queue.

`ThreadPoolExecutor` is the production thread pool that `Executors.newFixedThreadPool()`, `newCachedThreadPool()`, and `ScheduledThreadPoolExecutor` all build on. Its internal design packs **two pieces of state into one `AtomicInteger` (`ctl`)** — the number of worker threads and the pool's lifecycle state — so every transition can be validated with one CAS. Understanding `ctl`, the worker loop, and the saturation policies explains most interview questions about Java thread pools.

---

### 1. The Single `ctl` Field: `workerCount` + `runState`

```java
public class ThreadPoolExecutor extends AbstractExecutorService {
    private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
    private static final int COUNT_BITS = Integer.SIZE - 3;   // 29
    private static final int CAPACITY   = (1 << COUNT_BITS) - 1;

    // runState stored in the HIGH 3 bits
    private static final int RUNNING    = -1 << COUNT_BITS;
    private static final int SHUTDOWN   =  0 << COUNT_BITS;
    private static final int STOP       =  1 << COUNT_BITS;
    private static final int TIDYING    =  2 << COUNT_BITS;
    private static final int TERMINATED =  3 << COUNT_BITS;

    private static int runStateOf(int c)     { return c & ~CAPACITY; }
    private static int workerCountOf(int c)  { return c & CAPACITY; }
    private static int ctlOf(int rs, int wc) { return rs | wc; }
}
```

- **Low 29 bits**: the **worker count** (how many worker threads exist).
- **High 3 bits**: the **run state** — one of `RUNNING`, `SHUTDOWN`, `STOP`, `TIDYING`, `TERMINATED`.
- Using a single `AtomicInteger` means `addWorker()` and `shutdown()` can be atomic: e.g., `compareAndSet(ctlOf(rs, wc), ctlOf(rs, wc + 1))` either adds exactly one worker *and* keeps the run state consistent, or fails atomically.

The 5 lifecycle states:

| State | Meaning | Executes queued tasks? | Accepts new tasks? |
| :--- | :--- | :--- | :--- |
| `RUNNING` | Normal operation | Yes | Yes |
| `SHUTDOWN` | `shutdown()` called | Yes (drains queue) | **No** |
| `STOP` | `shutdownNow()` called | **No** (interrupts workers) | **No** |
| `TIDYING` | All tasks done, workers terminated | — | — |
| `TERMINATED` | `terminated()` hook ran | — | — |

---

### 2. The Worker Lifecycle: `execute` → `addWorker` → `runWorker` → `getTask`

The entry point is `execute(runnable)`, which follows four steps:

```java
public void execute(Runnable command) {
    int c = ctl.get();
    // 1. If fewer than corePoolSize workers, start a new worker.
    if (workerCountOf(c) < corePoolSize)
        if (addWorker(command, true)) return;
    // 2. Else try to enqueue the task.
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        if (! isRunning(recheck) && remove(command))
            reject(command);                  // double-check shutdown races
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);           // ensure at least one worker
    }
    // 3. If either earlier step failed, try a non-core worker.
    else if (!addWorker(command, false))
        reject(command);                      // 4. Saturation policy
}
```

The `Worker` is both a `Runnable` and a holder of the thread plus a lock state (so workers can be interrupted on shutdown). Its `run()` calls `runWorker(worker)`, an infinite loop:

```java
final void runWorker(Worker w) {
    Runnable task = w.firstTask;
    while (task != null || (task = getTask()) != null) {
        // ... lock the worker, update its last task timestamp,
        // run the task, reset interrupt status, count completed tasks ...
        task.run();
        task = null;
    }
    processWorkerExit(w, completedAbruptly);
}
```

And the critical **`getTask()`** — how a worker decides whether to keep living:

```java
private Runnable getTask() {
    boolean timed = allowCoreThreadTimeOut || workerCountOf(c) > corePoolSize;
    for (;;) {
        int c = ctl.get();
        // ... handle shutdown/stop conditions (return null → worker exits) ...
        if (workerCountOf(c) >= (timed ? maximumPoolSize : corePoolSize) || !timed)
            poll = false;
        // Core workers: block indefinitely on take().
        // Non-core workers: poll(queue, keepAliveTime, NANOSECONDS) → null on timeout.
        Runnable r = timed ?
            workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
            workQueue.take();
        if (r != null)
            return r;
        if (workerCountOf(c) >= maximumPoolSize ...) return null;   // worker exits
        timed = false;   // lost a race; don't kill this worker
    }
}
```

**Key consequences of this design:**

- **Core workers never die** (unless `allowCoreThreadTimeOut(true)`): they block in `workQueue.take()`.
- **Non-core workers die after `keepAliveTime` idle**: they use `poll(timeout)` and exit on `null`.
- **Idle workers still consume a thread/stack** — that's why pools of many core threads are not "free".
- A **new task goes to the queue, not to a fresh thread**, once `corePoolSize` is reached — even if all core workers are busy.

---

### 3. Core vs Maximum: Queueing Order and the "Wrong" Assumption

Many developers assume "pool grows to `maximumPoolSize` when full", but the actual order is:

```
1. Fill up to corePoolSize with new threads.
2. Enqueue excess tasks into the workQueue.
3. Only when the queue is FULL, grow threads toward maximumPoolSize.
4. If the queue is still full at maximumPoolSize → saturation policy.
```

So if you create a pool with `new ThreadPoolExecutor(2, 100, 60s, new ArrayBlockingQueue<>(1000))`, it will **never** reach 100 threads unless the queue itself overflows. To get "grow threads first", you'd need an **unbounded synchronous queue** (`SynchronousQueue`, used by `newCachedThreadPool`) where there is no buffer at all.

---

### 4. Saturation Policies (When the Queue Is Full)

When a task cannot be run or queued, `execute` calls the configured `RejectedExecutionHandler`:

| Policy | Behavior | Risk |
| :--- | :--- | :--- |
| **`AbortPolicy`** (default) | Throws `RejectedExecutionException` | Caller must handle; best for fail-fast |
| **`CallerRunsPolicy`** | Runs the rejected task **on the submitting thread** | Natural backpressure (submitter slows down), but can block your request thread |
| **`DiscardPolicy`** | Silently drops the task | Silent data loss |
| **`DiscardOldestPolicy`** | Drops the **oldest unstarted** queued task and retries `execute` | May starve a long-running pending task |

The default (`AbortPolicy`) is why an unbounded-queue pool like `newFixedThreadPool` normally never rejects — the queue never fills — while `newCachedThreadPool` (no buffer) can reject under a surge of submissions.

---

### 5. The Factory Methods Compared

| `Executors` method | `corePoolSize` | `maximumPoolSize` | Queue | Idle timeout |
| :--- | :--- | :--- | :--- | :--- |
| `newFixedThreadPool(n)` | n | n | **Unbounded** `LinkedBlockingQueue` | ∞ |
| `newCachedThreadPool()` | 0 | `MAX_VALUE` | `SynchronousQueue` (no buffer) | 60 s |
| `newSingleThreadExecutor()` | 1 | 1 | **Unbounded** `LinkedBlockingQueue` | ∞ |
| `newScheduledThreadPool(n)` | n | `MAX_VALUE` | `DelayedWorkQueue` | 0 |

**Warnings:** the unbounded-queue factories can exhaust memory under a burst; `newCachedThreadPool` can spawn unbounded threads under a burst (each has its own stack → OOM). For production, prefer explicitly constructed pools with bounded queues and a defined saturation policy (`new ThreadPoolExecutor(...)`).

---

### 6. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Assuming pool grows before queueing | Threads never reach `maximumPoolSize` | Understand the core→queue→max→reject order |
| Using unbounded queues in production | `OutOfMemoryError` under load spikes | Bounded `ArrayBlockingQueue`/`LinkedBlockingQueue(capacity)` + a policy |
| Blocking tasks in a small fixed pool | Whole pool stalls on the blocking task | Separate pools for blocking vs CPU-bound, or `CallerRunsPolicy` |
| Ignoring the default `AbortPolicy` | Unexplained `RejectedExecutionException` at peak | Configure a policy; measure drops |
| Interrupting/awaiting termination incorrectly | `ThreadPoolExecutor` hangs or leaks threads | `shutdown()` → `awaitTermination()` → `shutdownNow()` as a fallback |

### Summary

- `ThreadPoolExecutor` packs **`workerCount` (29 bits) + `runState` (3 bits) into one `AtomicInteger ctl`**, so worker creation and lifecycle transitions are single-CAS atomic.
- Workers loop in **`runWorker` → `getTask`**: core workers `take()` (never die), non-core workers `poll(keepAlive)` (die after idle timeout).
- Execution order is **core threads → queue → non-core threads (only when the queue is full) → reject**.
- The four **saturation policies** (`AbortPolicy` default, `CallerRunsPolicy`, `DiscardPolicy`, `DiscardOldestPolicy`) decide what happens when the queue is full and max threads are reached.
- The `Executors` factory shortcuts hide dangerous defaults (unbounded queues / unbounded threads); production pools should be constructed explicitly with bounded queues.

## 191. How does `CompletableFuture` work internally? Explain the `Completion`/`CompletableFuture` node structure (the Treiber-like stack of dependent stages), the `postComplete`/`tryFire` propagation chain, the default common-pool executor, and how `thenApply`/`thenCompose`/`whenComplete` differ in building the dependency graph.

`CompletableFuture` (since Java 8) is Java's primary **composable asynchronous** primitive: it lets you chain dependent operations (`thenApply`, `thenCompose`, `whenComplete`, `thenCombine`, ...) that run when their source completes, without blocking. Under the hood it is a **lock-free dependency graph**: each future is a `Completion` node linked into a stack of dependent actions, and when a source completes it walks that stack and drives the dependents through a state machine. Understanding the data structure explains how all the fluent APIs reduce to the same three transformations.

---

### 1. The Core Fields: Result + Stack of Dependents

```java
public class CompletableFuture<T> implements Future<T>, CompletionStage<T> {
    volatile Object result;          // null | AltResult(ex) | the actual value
    volatile Completion stack;       // LIFO stack of dependent actions
}
```

- **`result`**: the single `volatile` field holding the outcome — either the value, a sentinel `AltResult` wrapping an exception (or `NIL` for null results), or `null` while incomplete.
- **`stack`**: a LIFO stack of **dependent stages** waiting on this future. It is updated via **CAS** (classic Treiber stack / lock-free stack push):

```java
final boolean push(Completion c) {
    for (;;) {
        Completion s = stack;
        if (c.tryMergeStack() ... ) ;   // optimization path
        if (stack == s) { c.next = s; return casStack(s, c); }  // CAS push
    }
}
```

The whole design is: **one future completes, then "fires" its stack of dependents, each of which may push further dependents of its own**, cascading like a wave.

---

### 2. Completion and the `postComplete` Propagation

When a thread calls `complete(value)`, the future transitions incomplete → complete and must awaken the dependents:

```java
public boolean complete(T value) {
    boolean triggered = result == null &&
            UNSAFE.compareAndSwapObject(this, RESULT, null, value);
    if (triggered)
        postComplete();                    // fire all dependent actions
    return triggered;
}
```

`postComplete` walks and drains the `stack`:

```java
private void postComplete() {
    Completion f;
    while ((f = stack) != null) {
        if (casStack(f, null)) {           // take the whole stack
            for (Completion t = f; t != null; ) {
                Completion n = t.next;
                if (t.tryFire(NESTED))     // run the dependent action
                    t = n;                 // continue down the popped list
                else
                    f = null;              // a dependent re-pushed on this future
            }
        }
    }
}
```

**Key facts:**

- Completion uses a **single CAS from `null` → value** so exactly one "completor" wins even under racing `complete`/`completeExceptionally`/`cancel` calls.
- Dependents fire **in LIFO order** (the stack order), matching the order opposite to registration — which is why unordered completions are fine for `thenApply` chains but you must be careful with side-effect ordering.
- `tryFire` returns a status; if a dependent is not yet ready (e.g., it depends on *another* future too, as with `thenCombine`), it is **re-queued** and a later completion of its other source will retry it.

---

### 3. The `Completion` Node Kinds and `tryFire`

Every dependent stage is one of a few `Completion` subclasses; they all share a `tryFire(int mode)` method that the completed future uses to drive them:

| `Completion` subclass | Corresponding API | Behavior on `tryFire` |
| :--- | :--- | :--- |
| `UniCompletion`/`UniApply<T,R>` | `thenApply`, `thenAccept`, `thenRun`, `whenComplete`, `handle` | Applies a **single-source** function to the completed value and completes its `dep` with the result |
| `UniCompose<T,V>` | `thenCompose` | Calls the function to obtain a **new future** and wires that future's completion back into the current one |
| `BiCompletion`/`BiApply`, `BiRelay`, `BiAccept` | `thenCombine`, `thenAcceptBoth`, `runAfterBoth`, `thenApply...Either` | Waits for **both (or either)** sources, then applies the function |
| `OrAccept`, `OrApply` | `applyToEither`, `acceptEither` | Fires when the **first** of two sources completes |
| `Delayer` / `Cancelled` marks | `orTimeout`, `completeOnTimeout`, `cancel` | Schedules a timer / false-completes the future |

A `UniApply` (for `thenApply(fn)`) is conceptually:

```java
final void tryFire(int mode) {
    if (this.dep.result == null) {
        Object r = this.src.result;              // read source result
        if (r != null) {
            // apply fn to r (unwrap AltResult), then complete this.dep with result
            complete(...) ;
        } else {
            // source not done yet → return RETRY; the source will re-push us
        }
    }
}
```

---

### 4. The Default Executor: The Common ForkJoinPool

Unless an explicit `Executor` is provided, dependent actions (`thenApply`, `whenComplete`, etc.) run on **`ForkJoinPool.commonPool()`** (see Q188). Details worth remembering:

- The common pool is a process-wide `ForkJoinPool` sized at `availableProcessors() - 1`.
- **`thenApply` vs `thenApplyAsync`**: `thenApply` may run **inline on the completing thread** (if that thread is a `ForkJoinWorkerThread` or the stack of dependents is drained by the completer), while `thenApplyAsync` **always** submits to the provided executor.
- This means **`thenApply` does not guarantee a separate thread** — a common cause of surprise (and of deadlocks, if you block inside common-pool tasks).

---

### 5. `thenApply` / `thenCompose` / `whenComplete` — Building the Graph

| Method | Returns | Differences |
| :--- | :--- | :--- |
| `thenApply(fn)` | New future with **mapped value** | Synchronous, single-source, wraps result in `CompletionStage`; used for pure transformations |
| `thenAccept(c)` | Completes with `Void` | Like `thenApply` but for side effects |
| `thenCompose(fn)` | The **inner future** returned by `fn` (flatMap) | Flattens nested futures — `cf1.thenCompose(v -> makeFuture(v))` avoids `CompletableFuture<CompletableFuture<T>>` |
| `whenComplete(bi)` | Same future type, **preserves result/exception** | Runs after completion for side effects (logging/cleanup); does not transform the value |
| `handle(bi)` | New future of possibly different type | Like `whenComplete` but **can recover**: using an exception → a value |

The classic interview contrast:

```java
// thenApply — value transform:
CompletableFuture<String> upper =
    future.thenApply(String::toUpperCase);          // returns CF<String>

// thenCompose — flat-maps a future-returning function:
CompletableFuture<Order> order =
    userFuture.thenCompose(user -> fetchOrder(user));  // returns CF<Order>, not CF<CF<Order>>

// whenComplete — observe, don't transform:
future.whenComplete((v, ex) -> log.info("done v={} ex={}", v, ex));  // returns CF<T> unchanged

// handle — observe AND recover:
CompletableFuture<String> safe =
    future.handle((v, ex) -> ex != null ? "fallback" : v);
```

Exception propagation rule: once a `CompletableFuture` completes **exceptionally**, the exception flows down every dependent chain until a stage that *handles* it (`handle`, `exceptionally`, `whenComplete`). Unhandled exceptional completions are reported as uncaught when the chain is garbage collected (a common debugging gotcha).

---

### 6. Why It Matters: Lock-Free and Non-Blocking

`CompletableFuture` never uses `synchronized` for its own transitions — completion and dependent-registration are **CAS-based**, and waiting does not hold a monitor. This is what lets a chain of thousands of dependent stages run with low overhead. `join()`/`get()` block via the same AQS-style waiting (`TimedWait`/`UntimedWait` tasks) only when a caller actually blocks on a not-yet-complete future.

### Summary

- A `CompletableFuture` is a `volatile result` + a **CAS-managed LIFO `stack` of `Completion` dependents**.
- `complete(value)` wins with a single CAS and then **`postComplete` drains the stack**, firing dependents via `tryFire`, which may push new dependents and cascade.
- Dependent kinds — **`UniCompletion`** (single-source), **`BiCompletion`** (both-of-two), **`OrCompletion`** (first-of-two) — cover `thenX`, `thenCombine`, and `either` APIs.
- Default async execution runs on **`ForkJoinPool.commonPool()`**, and `thenApply` may run inline on the completing thread (so never block inside it).
- `thenApply` transforms the value, `thenCompose` **flattens** a future-returning function (avoiding nested futures), and `whenComplete` observes without changing the outcome; only `handle`/`exceptionally` can recover from exceptions.
