# Java Interview Questions (Advanced Level)

## 176. How does `CopyOnWriteArrayList` work internally? Explain copy-on-write semantics, why reads need no locking, the writer's `ReentrantLock`, snapshot iterators, and when to use it vs `ConcurrentLinkedQueue` or a synchronized `ArrayList`.

`CopyOnWriteArrayList` is a thread-safe `List` whose name describes its strategy exactly: **every mutating operation copies the entire backing array** before modifying it, and publishes the new array. This makes reads completely lock-free and never blocking, at the cost of making writes expensive â€” `O(n)` copy plus an array allocation on every add/remove/set.

---

### 1. The Core Data Structure: A `volatile Object[]`

The list holds its elements in a single array field that is declared `volatile`:

```java
public class CopyOnWriteArrayList<E> implements List<E> {
    private transient volatile Object[] array;
}
```

The entire thread-safety of the *read* path rests on that one `volatile` reference:

- **Reads** load `array` once and index into it â€” they never take a lock.
- **Writes** work on a **fresh copy** of the array, and then publish it with a single `volatile` write (`setArray(newArray)`).
- Because a reader either sees the old array or the new array (never a partially-updated one), reads are always consistent.

```java
// The whole read path â€” no lock, no CAS:
@SuppressWarnings("unchecked")
private E get(Object[] a, int index) {
    return (E) a[index];
}

public E get(int index) {
    return get(getArray(), index);   // volatile read of the array ref
}
```

---

### 2. The Write Path: Copy â†’ Modify â†’ Publish

All writes are guarded by a single **`ReentrantLock`** (so that two concurrent writers cannot copy-then-publish out of order) and follow the same three steps:

```java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // 1. copy
        newElements[len] = e;                                     // 2. modify
        setArray(newElements);                                    // 3. publish (volatile write)
        return true;
    } finally {
        lock.unlock();
    }
}
```

`remove` follows the same pattern but uses `System.arraycopy` to skip the removed element. The cost profile:

| Operation | Cost | Why |
| :--- | :--- | :--- |
| `get(i)`, `iterator()` | `O(1)` | Just indexes / wraps the current array â€” no lock. |
| `add(e)`, `add(i, e)`, `remove(i)` | `O(n)` | Copies the whole array, allocates a new one. |
| `set(i, e)` | `O(n)` | Still copies; there is no in-place element write. |
| `size()` | `O(1)` | Reads `array.length`. |

Every single write allocates a new array â€” which is also why `CopyOnWriteArrayList` puts pressure on the young generation of the GC when written frequently.

---

### 3. Snapshot Iterators (Weakly Consistent, Never Fail-Fast)

The `iterator()` (and `listIterator()`) returned by `CopyOnWriteArrayList` hold a **snapshot** of the array captured at creation:

```java
public Iterator<E> iterator() {
    return new COWIterator<E>(getArray(), 0);   // freezes the current array
}
```

Consequences:

- The iterator **never throws `ConcurrentModificationException`**, even if the list is modified while iterating.
- It sees a **consistent point-in-time view** â€” modifications made after the iterator was created are invisible to that iterator.
- The iterator does **not** support `remove()` (throws `UnsupportedOperationException`), because removing from a snapshot would be meaningless.

This is the opposite of `ArrayList`'s fail-fast behavior, and it makes copy-on-write iterators safe to hold across concurrent writes â€” at the cost of the snapshot being stale by design.

---

### 4. Mutations During Iteration: What Actually Happens

Consider two threads: T1 iterating, T2 calling `add(e)`.

1. T2 copies the array, appends `e`, and publishes the new array (volatile write).
2. T1's iterator keeps its reference to the **old** array, so it keeps iterating the old snapshot.
3. T1 is never interrupted and never sees inconsistent data â€” it simply does not see `e`.

This is the fundamental trade-off: **iteration is stable but may miss concurrent updates**, and elements added/removed mid-iteration may not appear (a copy-on-write list is not a live view).

---

### 5. Comparison With Alternatives

| Use case | `CopyOnWriteArrayList` | `Collections.synchronizedList(new ArrayList<>())` | `ConcurrentLinkedQueue` |
| :--- | :--- | :--- | :--- |
| **Reads** | Lock-free `O(1)` | Contended synchronized `get` | Volatile-free traversal |
| **Writes** | `O(n)` array copy + allocation | `O(1)` amortized (locked) | `O(1)` lock-free CAS |
| **Iteration** | Snapshot (never CME) | Fail-fast (CME possible) | Weakly consistent, no CME |
| **Index access** | Yes (`get(i)`) | Yes | No (queue, head-only ops) |
| **Best when** | Read-dominated, iteration-heavy, rare writes (e.g., listener/callback lists) | Simple correctness under modest contention | Producer-consumer hand-offs |

**The rule of thumb:** `CopyOnWriteArrayList` wins when *reads and traversals vastly outnumber writes* â€” classic examples are listener/observer registries in frameworks (each event iterates the whole list; listeners are added rarely). If you write frequently, the array copying dominates and a synchronized or concurrent alternative is better.

---

### 6. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Treating it as a general-purpose thread-safe `ArrayList` | Write-heavy code runs slower than expected | Use a `ConcurrentHashMap` or synchronized list |
| Using stale iterators to read "current" state | Missing recently-added elements | Re-acquire an iterator (or `get(i)`) for fresh data |
| Calling `listIterator.remove()` | `UnsupportedOperationException` | Remove via the list, not the iterator |
| Assuming `addIfAbsent`/`addAllAbsent` are cheap | Unexpected allocation spikes | These also copy on every call |

### Summary

- `CopyOnWriteArrayList` keeps a **`volatile Object[]`**; reads index into it with **no lock at all**.
- **Writes copy the whole array, mutate the copy, and publish it** with one volatile write â€” `O(n)` per mutation, guarded by a single `ReentrantLock`.
- Iterators are **snapshot-based**: weakly consistent, never fail-fast, but invisible to later writes and do not support `remove()`.
- It is the right choice for **read- and iteration-heavy, write-rare** structures (listeners, subscriptions), not for write-hot data.

## 177. How does `ConcurrentLinkedQueue` work internally? Explain the Michael-Scott lock-free queue algorithm, CAS-based `offer`/`poll` with hop-lazy deletion, the ABA problem and its avoidance, and how it differs from `LinkedBlockingQueue`.

`ConcurrentLinkedQueue` is an **unbounded, thread-safe, lock-free FIFO queue** in `java.util.concurrent`. It implements the famous **Michael-Scott queue algorithm** (1996) using **CAS (Compare-And-Swap)** and **volatile fields**, with no locks and no blocking. Its producers and consumers can operate concurrently at full speed, at the cost of slightly relaxed ordering guarantees (`size()` is `O(n)` and approximate).

---

### 1. The Node Structure

Each queue entry is a node with a `volatile` item and a `volatile` next pointer:

```java
private static class Node<E> {
    volatile E item;      // null => node is logically removed
    volatile Node<E> next; // next node in the queue
}
```

The queue itself holds `volatile Node<E> head` and `volatile Node<E> tail`, and performs all mutations via `sun.misc.Unsafe`/`VarHandle`-style `casNext`/`casItem` operations.

---

### 2. `offer(E)` â€” Enqueue at the Tail (CAS Loop)

Enqueueing uses a **CAS loop** on `tail`:

```java
public boolean offer(E e) {
    final Node<E> newNode = new Node<E>(e);
    for (Node<E> t = tail, p = t;;) {
        Node<E> q = p.next;
        if (q == null) {
            // p is the true last node; try to link newNode after it.
            if (p.casNext(null, newNode)) {
                // CAS succeeded. If p was not the tail field's target,
                // move tail forward opportunistically (hop / lazy update).
                if (p != t)
                    casTail(t, newNode);
                return true;
            }
            // CAS lost to another producer -> retry
        }
        else if (p == q)
            // Sentinel: p is a self-link left by a removed node;
            // re-locate the real tail.
            p = (t != (t = tail)) ? t : head;
        else
            // Advance p one step toward the true tail.
            p = (p != t && t != (t = tail)) ? t : q;
    }
}
```

Key design decisions:

- **Multiple producers** race to `casNext(null, newNode)`; exactly one wins each round, others retry â€” **no lock, no blocking**.
- **Lazy tail update**: `tail` is *not* updated on every enqueue; it lags behind. Producers instead walk from `tail` to the true last node. This "hop" policy reduces CAS contention on the single `tail` field (Michael & Scott's `dist` threshold, set to 2 hops).
- A node whose `next` points to itself (`p == q`) is a **sentinel** left behind when a node was removed by `poll`; the algorithm detects it and re-anchors to `head`.

---

### 3. `poll()` â€” Dequeue From the Head (CAS on Item)

Dequeueing CASes the **item field** of the head node to `null` (a logical delete) rather than unlinking nodes:

```java
public E poll() {
    restartFromHead:
    for (;;) {
        for (Node<E> h = head, p = h, q;;) {
            E item = p.item;
            if (item != null && p.casItem(item, null)) {
                // CAS succeeded: this node is dequeued.
                if (p != h)   // hop â€” skip over empty nodes
                    updateHead(h, ((q = p.next) != null) ? q : p);
                return item;
            }
            else if ((q = p.next) == null) {
                updateHead(h, p);   // queue is empty
                return null;
            }
            else if (p == q)
                continue restartFromHead;  // self-link -> restart
            else
                p = q;                     // skip deleted node
        }
    }
}
```

The item-CAS is what makes `poll` safe: only one consumer can flip a given node's `item` from non-null to null, so each element is returned **exactly once** even with many concurrent consumers.

---

### 4. Logical Deletion vs Physical Unlinking

`ConcurrentLinkedQueue` deliberately does **not** physically remove the head node on dequeue:

- `poll` nulls the `item` (logical removal) and later hops `head` past it.
- Nodes are only physically unlinked when `head` moves forward past them; the removed node's `next` is set to itself (`p == q`) â€” the **self-link sentinel** â€” which the enqueue/dequeue loops recognize to re-anchor.

This avoids the otherwise-fatal race where a consumer nulls `item` while a producer still holds a stale reference to `next`, keeping the algorithm linearizable without heavy locking.

---

### 5. The ABA Problem and How It Is Avoided

The **ABA problem** is the classic hazard of CAS-based structures: a thread reads a location as value `A`, another thread changes it `A â†’ B â†’ A`, and the first thread's CAS then succeeds against the *wrong* state.

Michael-Scott-style queues avoid ABA by CASing **immutable `Node` references**, not mutable value fields:

- Each node is created once, and its `next` reference is set **exactly once** (from `null` to the new node). A node reference can never be "reused" for a different purpose.
- The ABA problem requires the same address to be recycled through two different states. Because nodes are never reused (they are GC-managed and never recycled into a free-list), the reference itself is a stable identity â€” the CAS compare-and-swap on `next` is immune to ABA.
- HotSpot additionally relies on `item == null` as a separate linearization point for dequeue, so a consumer never CASes a `null` item onto a non-null one.

The explicit note in the JDK source is that "the main part of this algorithm is to make sure that a node cannot be reused by another thread" â€” GC gives it this property for free (unlike C++, which would need epoch-based reclamation or hazard pointers).

---

### 6. `ConcurrentLinkedQueue` vs `LinkedBlockingQueue`

| Feature | `ConcurrentLinkedQueue` | `LinkedBlockingQueue` |
| :--- | :--- | :--- |
| **Blocking** | Never blocks | `put()`/`take()` block on capacity/emptiness |
| **Locking** | Lock-free (CAS only) | Two `ReentrantLock`s (put lock + take lock) |
| **Capacity** | Unbounded | Optional bounded (default `Integer.MAX_VALUE`) |
| **Backpressure** | None (unbounded memory growth risk) | Yes (bounded capacity) |
| **`size()`** | `O(n)` walk, approximate | `O(1)` via atomic counter |
| **Best for** | Low-contention pipelines, lock-free hand-off | Producer-consumer with capacity limits / backpressure |

**Summary of the comparison:** if you need backpressure or blocking semantics, use `LinkedBlockingQueue` (used by `ThreadPoolExecutor`); if you want a purely lock-free, non-blocking FIFO and accept unbounded growth and an `O(n)` `size()`, use `ConcurrentLinkedQueue`.

---

### 7. Weakly Consistent Iterators

Like most concurrent collections, the iterator is **weakly consistent**:

- It never throws `ConcurrentModificationException`.
- It reflects the queue state at some point during iteration; elements removed concurrently may or may not be visited.
- `iterator().remove()` is supported (it nulls the item via CAS) but the element may already have been removed.

### Summary

- `ConcurrentLinkedQueue` is an **unbounded, lock-free FIFO** based on the **Michael-Scott algorithm**: producers CAS onto `tail`, consumers CAS the head's `item` to `null`.
- `tail`/`head` are **updated lazily** (hop-by-hop) to reduce CAS contention on the shared refs.
- Deletion is **logical first** (`item = null`), with self-link sentinels and `head`-hopping handling physical cleanup.
- The **ABA problem is avoided** by CASing immutable, never-recycled `Node` references (GC-managed), so an address is never reused across two states.
- Unlike `LinkedBlockingQueue`, it is **non-blocking and unbounded** â€” no capacity, no blocking `put`/`take`, but an `O(n)` approximate `size()`.

---

## 178. How does `Phaser` work internally, and how is it more flexible than `CyclicBarrier` and `CountDownLatch`? Explain its phase-based state, party registration (`register`/`bulkRegister`), the `arrive`/`awaitAdvance` protocol, phase numbers, and how `Phaser` supports dynamic participation and a `Phaser` tree.

`Phaser` (`java.util.concurrent`) is a **reusable synchronization barrier** that generalizes both `CyclicBarrier` and `CountDownLatch`. Its central abstraction is a **phase**: a round of work that completes when a countable set of **parties** have each arrived. Unlike the fixed-party `CyclicBarrier` or the one-shot `CountDownLatch`, a `Phaser` lets parties **register and deregister dynamically**, supports a variable barrier count per phase, and can even be arranged into a `Phaser` **tree** for scalability.

---

### 1. The Core State: One `volatile long` Phases Everything

Like many `JUC` synchronization primitives, `Phaser` packs its entire state into a single **`volatile long state`** and mutates it atomically via CAS:

```
state (64-bit long) packed fields:
+-----------+----------+------------------+----------+
|  phase   |  counts  |  unarrived      |  parties |
| (bits 32-62)| (16-31) | (16 bits)       | (16 bits)|
+-----------+----------+------------------+----------+
```

- **`phase`** (upper 32 bits): the current phase number. Increments each time the barrier trips.
- **`parties`** (low 16 bits): the *total* registered parties.
- **`unarrived`** (next 16 bits): how many parties have not yet arrived this phase.
- **`counts`** (16â€“31): derived number of parties that can arrived (used to know when to trip).

A single CAS is used to update `unarrived`, `parties`, and `phase` atomically, so phaser transitionsâ€”"a party arrived", "all parties arrived, bump the phase"â€”are race-free without locks.

---

### 2. Parties Are Dynamic: `register()` / `bulkRegister(int)`

Unlike `CyclicBarrier` (fixed party count at construction), a `Phaser` allows parties to **join or leave over time**:

```java
Phaser phaser = new Phaser();         // initial parties = 0

// A thread joins dynamically:
phaser.register();                    // parties += 1
// Several at once:
phaser.bulkRegister(3);               // parties += 3
```

- `register()` increments the party count for the **next phase** on the current thread.
- `arriveAndDeregister()` decrements it, so the barrier can shrink.
- This dynamic participation is what makes `Phaser` suitable for **fork/join** style work where the "member count" isn't known until runtime.

Because the count can change, the number of `arrive` calls required to trip a phase can **grow or shrink between phases** - the flexibility of `Phaser` that `CyclicBarrier` lacks.

---

### 3. The `arrive` / `awaitAdvance` Protocol

The barrier is driven by two families of methods:

| Method | Effect |
| :--- | :--- |
| `arrive()` | Marks the current thread as arrived, without blocking. Returns the phase number. |
| `arriveAndAwaitAdvance()` | Arrives, then **blocks until the barrier trips**. The standard "join + wait" call. |
| `arriveAndDeregister()` | Arrives and permanently removes this party from the count. |
| `awaitAdvance(phase)` | Blocks (without arriving) until the given `phase` advances. |
| `getPhase()` | Returns the current phase number. |

The central algorithm idea:

```java
// arrive + determine whether this was the last arriving party:
int arrive() {
    // atomically decrement unarrived
    if (cas current -> unarrived-1) {
        if (unarrived == 0) {
            // LAST party arrived => trigger the phase barrier:
            // 1. run any onAdvance(phase, parties) barrier action
            // 2. bump phase (state changed)
            // 3. wake all waiters
        }
        return phase;
    }
}
```

The key behavior of a `Phaser` barrier trip:

1. The **last party to arrive** in a phase trips the barrier.
2. Unlike `CyclicBarrier`, arriving threads **don't block at the barrier point** (unless they call `awaitAdvance`). An `arrive()` is fire-and-forget; only threads that explicitly wait block.
3. When the phase completes, the phase number increments, and **all pending `awaitAdvance` callers unblock**.

#### How `awaitAdvance` works:

```java
public int awaitAdvance(int phase) {
    for (;;) {
        int p = this.phase;      // read current phase
        if (p != phase)          // phase already moved past the one we waited for
            return p;            // done â€” return the new phase
        // else park until the phase changes or a timeout occurs
    }
}
```

This is why `awaitAdvance(phase)` is often the right primitive for **late-arriving** threads (a thread might not be ready to `arrive()` yet; it can still wait for a given phase using the stamp).

---

### 4. CyclicBarrier / CountDownLatch / Phaser Comparison

| Feature | `CountDownLatch` | `CyclicBarrier` | `Phaser` |
| :--- | :--- | :--- | :--- |
| **Reusable** | No (one-shot) | Yes | Yes |
| **Dynamic parties** | No (fixed at construction) | No (fixed) | **Yes** â€” `register`/`deregister` |
| **Blocking model** | `await()` blocks until count 0 | All parties block until all arrive | Arrive is fire-and-forget; only `awaitAdvance` blocks |
| **Advanced features** | â€” | Barrier action (`Runnable`) | **Barrier action**, **tree**, **phase-based** |
| **Work split** | Not reusable after count 0 | Fixed size rounds | Varies across phases |

---

### 5. `Phaser` Tree (Scalability)

Because a single `Phaser` uses one contended `long`, very large party counts cause CAS contention. `Phaser` supports **phase trees**: a parent phaser whose children merge their completed phases into it.

```java
Phaser root = new Phaser();
Phaser child1 = new Phaser(root, 5); // 5 parties in subtree 1
Phaser child2 = new Phaser(root, 5); // 5 parties in subtree 2
```

- When all parties in a child phase arrive, the child forwards a single arrival to its parent.
- This reduces contention: chief contention is spread across subtree phasers, each doing a couple of CASes, rather than all N parties hammering one `long`.
- Used in `ForkJoinPool` internally for its work-stealing dispatch.

---

### 6. Common Uses and Gotchas

**Uses:**
- **Dynamic parallel frameworks** (ForkJoinPool-like slicing), where party count is known only at runtime.
- **Multi-stage/multi-wave processing** â€” a reusable barrier for each wave of work.
- **Larger-scale concurrency** where `CyclicBarrier` at fixed size is too limiting.

**Gotchas:**
- Trivial `arrive()` and a last-party trip means the **guest phase only advances when the final party arrives**; if you `arrive()` without registering correctly, `Phaser.PARTIES_MISMATCH` can be thrown.
- Arrive is **not a blocking wait**: the typical mistake is to `arrive()` and then immediately check state that isn't ready. Use `awaitAdvance` when you need to wait.
- `register()` affects *next* phase, so reading `getRegisteredParties()` mid-cycle can be misleading.

### Summary

- `Phaser` generalizes `CyclicBarrier` and `CountDownLatch` with **reusable, dynamic party registration**.
- State is one `volatile long` packing **phase** (32-bit), **parties** (16-bit), and **unarrived** (16-bit), mutated with CAS.
- The protocol is **`arrive()` (fire-and-forget) + `awaitAdvance(phase)` (wait)**, plus `arriveAndAwaitAdvance()` to both arrive and wait.
- The **last arriver in a phase trips the barrier** and bumps the phase; `arriveAndDeregister` can shrink the count.
- `Phaser` trees (`new Phaser(parent, parties)`) spread CAS contention for very large party counts.

## 179. How does `LockSupport` work, and why is it the foundation for all JUC blocking? Explain `park()`/`unpark(thread)` vs `Object.wait()`/`notify()`, the permit-based model, `parkNanos`/`parkUntil` timeouts, and spurious wakeup handling in `LockSupport.park`.

`LockSupport` (`java.util.concurrent.locks`) provides **thread blocking primitives** — `park()` (block the current thread) and `unpark(Thread)` (resume a specific thread) — that form the low-level foundation for every `JUC` synchronizer. `AQS`, `ReentrantLock`, `Semaphore`, `CountDownLatch`, `Condition`, and `ForkJoinPool` all block threads via `LockSupport`, not via `Object.wait()`. Its core idea is a **per-thread permit**.

---

### 1. The Permit Model (A Tiny Semaphore per Thread)

Every thread has an implicit, internal **permit** (a `count` — 0 or 1) that `park` and `unpark` manipulate:

| Operation | Effect on the permit |
| :--- | :--- |
| `unpark(thread)` | If the thread's permit is 0, **set it to 1** (permit is consumed on next park). If already 1, **no-op** (permits do not accumulate above 1). |
| `park()` | **Consumes** the permit if it is 1 (returns immediately). Otherwise **blocks** until a permit is granted. |

This is fundamentally different from a mutex: a permit has **no ownership**. Any thread may call `unpark(anyOtherThread)`, and permits do not need to be "released" by the same thread that "acquired" them.

```java
// unblocking a parked thread from another thread:
LockSupport.unpark(workerThread);   // grants a permit
```

The "permit pre-grant" property is the crucial difference from `wait/notify`: **`unpark` before `park` is not lost** — the parked thread will return immediately from its next `park` because the permit is already held. With `wait/notify`, a `notify` that happens before `wait` is lost and the waiter blocks forever.

---

### 2. `park()` vs `Object.wait()` — the Key Differences

| Feature | `Object.wait()` | `LockSupport.park()` |
| :--- | :--- | :--- |
| **Monitors** | Requires `synchronized` (a monitor lock must be held) | No monitor — usable anywhere |
| **Target** | Wakes *all* (or one of) the threads waiting on the monitor | Wakes an *exact* named thread (`unpark(thread)`) |
| **Lost wakeup** | `notify` before `wait` is lost | `unpark` before `park` persists (permit) |
| **Interruption** | Throws `InterruptedException` (clears flag) | Sets the interrupted flag, `park` returns, **no exception** |
| **Timeouts** | `wait(millis)` | `parkNanos`, `parkUntil` |
| **Used by** | `synchronized`/legacy code | All of `java.util.concurrent` |

Because `park` doesn't throw `InterruptedException` and doesn't require a monitor, it's the ideal primitive for writing lock-free synchronizers.

---

### 3. `park()` Implementation Details (HotSpot)

`LockSupport.park()` is backed by a native method that ultimately parks the OS thread:

```
LockSupport.park()
  -> UNSAFE.park(false, 0L)           // a "safe point" blocking call
  -> (HotSpot) parks the thread via platform primitives
       (futex on Linux, WaitOnAddress/SleepConditionVariable on Windows)
```

On Linux, `park` uses the **`futex`** system call; on Windows it uses the thread-park emulation. The important point: **parking does not burn CPU** — the OS deschedules the thread until `unpark` (or a timeout) resumes it.

---

### 4. Timeout Variants

```java
// Block until unparked, but no longer than 100ms:
LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(100));

// Block until a deadline (millis since epoch, or nanos since epoch):
LockSupport.parkUntil(System.currentTimeMillis() + 5_000);   // 5s from now
```

- `parkNanos(long nanos)`: relative timeout, granularity is nanos (subject to OS timer resolution).
- `parkUntil(long deadline)`: absolute deadline in millis since epoch.
- These are used extensively by `AQS` (`tryAcquireNanos`, condition `awaitNanos`) and by `ThreadPoolExecutor.getTask()`'s `keepAliveTime` polling.

Note the per-thread permit model means a `parkNanos` that times out simply returns; no exception, no cleanup needed.

---

### 5. The Critical Safety Rule: Park Must Be Guarded by a Condition Loop

`park` has **spurious wakeups** (a thread can return from `park` without any `unpark` — permitted by the JMM). Therefore, correct code **never calls `park` in a bare if**. It must loop while the condition it's waiting for is not yet satisfied:

```java
// WRONG: lost wakeup / spurious wakeup bug
if (!ready) {
    LockSupport.park();   // might wake spuriously, might miss the unperm...
}

// CORRECT:
while (!ready) {
    LockSupport.park();   // re-checks the condition after every wake
}
```

This mirrors the mandatory `while` loop with `Object.wait()`. AQS, `Condition.await`, and all JUC primitives follow this discipline internally.

The associated gotcha: because `park` doesn't throw `InterruptedException`, interrupted waiters rely on **re-checking** the interrupt flag — JUC code typically calls `Thread.interrupted()` in the loop to respond to interrupts.

---

### 6. Practical Example — A Minimal Waiter

```java
import java.util.concurrent.locks.LockSupport;

public class Blocker {
    private volatile boolean ready = false;

    public void waitForReady() {
        while (!ready) {          // guard against spurious + lost wakeup
            LockSupport.park();
        }
    }

    public void signal() {
        ready = true;
        LockSupport.unpark(Thread.currentThread()); // wake the *specific* waiter
    }
}
```

---

### 7. LockSupport vs synchronized Park (Summary Table)

| Need | Use |
| :--- | :--- |
| Block a thread without a monitor, exact-target wake, no lost wakeup | `LockSupport.park/unpark` |
| Legacy monitor-based blocking, multiple conditions via monitor | `Object.wait/notify` |
| High-level reusable barrier / latch | `Phaser`, `CountDownLatch`, `CyclicBarrier` (built on AQS → `LockSupport`) |
| Cooperative CPU yielding, no blocking | `Thread.yield()` |

### Summary

- `LockSupport` provides **permit-based blocking** (`park` consumes, `unpark` grants) with no monitor requirement and no `InterruptedException`.
- The permit is **not owned**, and an `unpark` before a `park` is **not lost** — the exact opposite of `notify`-before-`wait`.
- `parkNanos`/`parkUntil` add timeouts; the OS parks the thread (e.g., `futex` on Linux), so parked threads cost no CPU.
- **Always guard `park` with a condition loop** — spurious wakeups are legal, so a bare `if (!cond) park()` is a bug.
- It is the hidden engine beneath `AQS`, `ReentrantLock`, `Semaphore`, `CountDownLatch`, `Phaser`, `Condition`, and `ForkJoinPool`.

## 180. How do `DelayQueue` and `ScheduledThreadPoolExecutor` implement delayed/timed execution internally? Explain the priority-queue core, the delay leader-wait pattern, the `ScheduledFutureTask` time fields, and why delayed tasks are not removed by a dedicated timer thread.

Both `DelayQueue` and `ScheduledThreadPoolExecutor` implement **timed/delayed execution** using a **priority queue** ordered by deadline, plus a clever **leader-waiter** pattern that avoids waking a thread for every delay tick. Understanding these internals explains why scheduling in Java does not rely on per-task timer threads and how `scheduleAtFixedRate` vs `scheduleWithFixedDelay` really differ.

---

### 1. The Common Core: A Delay-Ordered Priority Queue

Both classes are built on `PriorityQueue` (for `DelayQueue`) or `DelayedWorkQueue` (a private delay-ordered priority queue inside `ScheduledThreadPoolExecutor`). The queue holds tasks implementing `Delayed`:

```java
public interface Delayed extends Comparable<Delayed> {
    long getDelay(TimeUnit unit);   // remaining delay; <= 0 means "expired"
}
```

The queue orders tasks by their **scheduled execution time** (`scheduledFireTime` in `ScheduledFutureTask`), so the **head of the queue is always the next task to run**. `DelayQueue.poll()` blocks until the head's delay expires; `ScheduledThreadPoolExecutor` uses the same structure internally with worker threads.

---

### 2. `DelayQueue` — How It Blocks Until Something Is Due

```java
public E take() throws InterruptedException {
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        for (;;) {
            E first = q.peek();
            if (first == null)
                available.await();          // queue empty: block
            else {
                long delay = first.getDelay(NANOSECONDS);
                if (delay <= 0)
                    return q.poll();        // head is due: return it
                first = null;               // don't retain ref while parked
                if (leader != null)
                    available.await();      // another thread is the leader
                else {
                    Thread thisThread = Thread.currentThread();
                    leader = thisThread;
                    try {
                        available.awaitNanos(delay);  // sleep ONLY until head is due
                    } finally {
                        if (leader == thisThread)
                            leader = null;
                    }
                }
            }
        }
    } finally {
        if (leader == null && q.peek() != null)
            available.signal();             // promote a new leader
        lock.unlock();
    }
}
```

Key points:

- It uses a single `ReentrantLock` + a `Condition available`.
- It **sleeps exactly until the head's delay** (`awaitNanos(delay)`), not a fixed polling interval — so the JVM parks the thread until the deadline via `LockSupport.parkNanos` under the hood.
- The **leader** is the one thread currently sleeping for the head task; all other waiting threads park indefinitely. When the leader wakes and takes the task, it signals to promote a new leader.

---

### 3. The Leader-Waiter Pattern (Avoiding "thundering herd")

Without a leader, **every** waiting thread would time out near-simultaneously when a task becomes due, wake up, and all fight to take the same head — a thundering herd.

The leader pattern fixes it:

1. **Leader** — the single thread that sleeps *exactly* until the head's deadline (`awaitNanos(delay)`).
2. **Waiters** — all other threads park with **no timeout** (`available.await()`); they rely on being signaled.
3. When the leader wakes, takes the head, and it's still the leader, it calls `available.signal()` to promote a new leader.

Result: at most **one thread** wakes at a deadline, so timed wakes scale to many delayed tasks without wakeup storms. (This is the same pattern used in `SynchronousQueue`.)

---

### 4. `ScheduledThreadPoolExecutor` — Tasks on a Worker Thread

`ScheduledThreadPoolExecutor` is a `ThreadPoolExecutor` whose `workQueue` is a `DelayedWorkQueue`, and whose tasks are **`ScheduledFutureTask`** objects:

```
ScheduledFutureTask
  + long sequenceNumber       (FIFO tie-break when deadlines are equal)
  + long time                 (the scheduled execution time, in nanos)
  + long period               (0 => one-shot; >0 => fixed-rate; <0 => fixed-delay)
  + RunnableScheduledFuture<V> outerTask
```

- `submit`/`schedule` enqueue a `ScheduledFutureTask` ordered by `time`.
- Worker threads call `getTask()`, which uses `DelayQueue.take()` semantics: **the worker sleeps until the head task's deadline**, then runs it.
- Because the worker pool threads execute the delayed tasks themselves, **no dedicated timer thread** is needed.

```java
// schedule a one-shot task:
ScheduledFuture<?> f = executor.schedule(
    () -> System.out.println("run after 1s"), 1, TimeUnit.SECONDS);

// schedule a fixed-rate task (runs at t, t+p, t+2p, ...):
executor.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);

// schedule a fixed-delay task (runs delay after each completion):
executor.scheduleWithFixedDelay(task, 0, 1, TimeUnit.SECONDS);
```

---

### 5. Fixed-Rate vs Fixed-Delay (the `period` field)

The `period` field decides what happens after a task finishes:

| Method | `period` | Re-queue behavior |
| :--- | :--- | :--- |
| `schedule` | `0` | One-shot — task not re-queued. |
| `scheduleAtFixedRate` | `> 0` | Re-queue with `time = lastTime + period`. **Runs on a fixed cadence**, ignoring how long the task took; consecutive executions never overlap. |
| `scheduleWithFixedDelay` | `< 0` | Re-queue with `time = now + |period|`. **Runs `delay` after the previous run completes**. |

**Fixed-rate** semantics: the *start* times are spaced `period` apart. If a run is slow, the next run fires as soon as possible after completion (never overlapping), and the schedule drifts but never catches up.

**Fixed-delay** semantics: the gap is measured *between completions* and next start.

`ScheduledFutureTask.run()` checks the `period` and calls `setNextRunTime()` to compute the re-queue time, then returns it to the pool which re-enqueues it.

---

### 6. `scheduleAtFixedRate` vs `scheduleWithFixedDelay` — Comparison

| Aspect | `scheduleAtFixedRate` | `scheduleWithFixedDelay` |
| :--- | :--- | :--- |
| **Next run time** | `previousStart + period` | `completionTime + period` |
| **If task runs long** | Next run fires immediately after completion (no overlap, catches up only partially) | Next run always starts `period` after the last one ended |
| **Cadence** | Drifts when work overruns | Fixed gap between runs |
| **Use for** | Heartbeats, polling metrics | Chained jobs where each run's delay matters |

---

### 7. Why No Dedicated Timer Thread?

A naive design uses one thread per delayed task or one global timer thread that wakes every tick and scans all tasks. `ScheduledThreadPoolExecutor` instead:

1. Uses the delay-ordered priority queue — **only the head's deadline matters**.
2. Uses the **leader-waiter** pattern — only one worker sleeps until a deadline.
3. Reuses the pool's worker threads — the same threads also execute non-delayed tasks, so no per-task thread is spawned.

This gives `O(log n)` enqueue (priority queue) and `O(1)`-ish wakeup behavior, scaling far better than per-task timers.

### Summary

- `DelayQueue` and `ScheduledThreadPoolExecutor` are built on **deadline-ordered priority queues** of `Delayed` tasks.
- `take()` sleeps **exactly until the head's delay** via `awaitNanos(delay)`, using the **leader-waiter** pattern to keep only one thread parked to a deadline.
- `ScheduledFutureTask` stores **`time`** (execution deadline) and **`period`** (`0` one-shot, `>0` fixed-rate, `<0` fixed-delay).
- **Fixed-rate** schedules by start-to-start cadence; **fixed-delay** schedules completion-to-start.
- No dedicated timer thread exists: worker threads self-block on the queue until the next deadline, making it scalable and `O(log n)` per schedule.
