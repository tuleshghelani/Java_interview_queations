## 301. How do you write reliable integration tests for Spring Boot applications using Testcontainers? Explain Docker image selection, container lifecycle, network binding, database operations, and test isolation.

Integration tests verify that components work together as expected, but they traditionally suffer from "it works on my machine" syndrome because they rely on local infrastructure (databases, message brokers, external services) that may differ from production. **Testcontainers** solves this by provisioning disposable containers from Docker images, ensuring the test environment matches production exactly. This question covers how to write reliable integration tests with Testcontainers in a Spring Boot context, from Docker image selection to test isolation and parallel execution.

---

### 1. Why Testcontainers Over Embedded or Local infrastructure

| Approach | Setup | Teardown | Parity with Production | Cost |
| :--- | :--- | :--- | :--- | :--- |
| **Embedded database** (H2, HSQLDB) | None | None | Low — in-memory mode, different optimizer behavior, no Docker/network | Free |
| **Local Docker container** | Manual `docker run` | Manual `docker stop` | Medium — depends on local Docker setup | Free (if Docker running) |
| **Testcontainers** | Programmatic API | Automatic via JUnit rule/support | High — same image, same OS, same network stack | Free (if Docker running) |

Testcontainers guarantees that the database version, configuration, and network behavior are identical to production, while automatically cleaning up after the test.


### 3. Writing an Integration Test with PostgreSQL

```java
@Testcontainers
@SpringBootTest(classes = OrderServiceApplication.class)
@ActiveProfiles("test")
class OrderIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

    @TestDependency
    @Container
    static RedisContainer<?> redis = new RedisContainer<>("redis:7-alpine");

    @Autowired
    OrderRepository orderRepository;

    @Autowired
    TestEntityManager entityManager;

    @Test
    void saveAndFindOrder() {
        // Docker container is automatically started before the test
        String jdbcUrl = postgres.getJdbcUrl();
        String username = postgres.getUsername();
        String password = postgres.getPassword();

        // Configure Spring test profile to use the container
        System.setProperty("spring.datasource.url", jdbcUrl);
        System.setProperty("spring.datasource.username", username);
        System.setProperty("spring.datasource.password", password);

        Order order = new Order("ORD-001", BigDecimal.valueOf(99.99), OrderStatus.PENDING);
        entityManager.persist(order);

        Order found = orderRepository.findById("ORD-001")
            .orElseThrow();

        assertThat(found.getOrderId()).isEqualTo("ORD-001");
        assertThat(found.getAmount()).isEqualByComparingTo(BigDecimal.valueOf(99.99));
    }
}
```

**Key annotations:**

- `@Testcontainers`: Enables Testcontainers support for the test class and its nested classes.
- `@Container`: Defines a Docker container. `static` allows the container to be shared across test methods and inherited by nested test classes.
- The container starts before the test class begins and stops after the test class ends.

**Container configuration:**

```java
static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine")
    .withDatabaseName("testdb")
    .withUsername("testuser")
    .withPassword("testpass");
```

- `withDatabaseName`, `withUsername`, `withPassword` set the database credentials.
- The container exposes ports automatically; Testcontainers maps them to available host ports.

### 4. Network Binding and Service Discovery

Containers run on the Docker bridge network by default. Testcontainers publishes the container's exposed ports to the host.

```java
postgres.getMappedPort(PostgreSQLContainer.DEFAULT_PORT)
// Returns the host port mapped to 5432 inside the container
```

**Connecting from the application:**

```java
@DynamicPropertySource // Spring Boot 2.7+ - auto-registers properties
static void postgresProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url") -> postgres.getJdbcUrl();
    registry.add("spring.datasource.username") -> postgres.getUsername();
    registry.add("spring.datasource.password") -> postgres.getPassword();
}
```

`@DynamicPropertySource` provides the container-derived properties at test runtime, overriding `application-test.yml` settings.

**Sharing containers across tests:**

```java
@Container static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

@Nested @Testcontainers class OrderTest {
    // Inherits the same postgres container
}
```

Shared containers are useful when multiple test classes need the same database instance, but be cautious about test isolation (see the "Test Isolation" section below).

### 5. Test Isolation and Parallel Execution

**Problem:** Running tests in parallel with shared containers can cause race conditions if tests insert/modify the same data.

**Solution 1: Create a new container per test class**

```java
@Container static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

// Each nested test class gets its own container instance
@Nested class OrderTest1 { /* uses postgres */ }
@Nested class OrderTest2 { /* uses a different postgres instance */ }
```

**Solution 2: Use a unique database name per test**

```java
static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine")
    .withDatabaseName("testdb_${UUID.randomUUID().toString().substring(0,8)}");

// Each test gets a uniquely named database, avoiding conflicts
```

**Solution 3: Use the `junit.jupiter.experimental` test instance per method**

```java
@Testfactory
Stream<DynamicTest> tests() {
    return Stream.of(
        dynamicTest("test with isolated DB", () -> {
            // Fresh container per test method
            PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:15-alpine")
                .withDatabaseName("test_" + UUID.randomUUID());
            pg.start();
            // ... test logic
        })
    );
}
}
```

**Best practice:** Prefer Solution 1 (separate container per test class) for most cases; it provides good isolation without the overhead of starting a container per individual test method.

### 7. Lifecycle Management and Timeouts

**Default behavior:** Container starts before the test class and stops after the test class terminates.

**Custom timeout:**

```java
@Container static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine")
    .withStartupTimeout(Duration.ofMinutes(3))  // wait up to 3 min for PostgreSQL to be ready
    .withCommand("--max-connections=200");     // customize startup command
```

**Explicit start/stop (rarely needed):**

```java
@BeforeClass
static void startContainers() {
    postgres.start();
}

@AfterClass
static void stopContainers() {
    postgres.stop();
}
```

**Graceful shutdown:** Testcontainers sends `SIGTERM` to the container's PID, allowing the application to clean up before the container is removed.

### 8. Common Pitfalls and Gotchas

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Shared container state across tests** | Test data leaks; flaky tests due to unexpected rows | Use a unique database name per test class (`withDatabaseName("test_${UUID}")`). |
| **Container fails to start** | `WaitStrategy` timeout exceeded | Ensure Docker has sufficient resources; check `withLog` output for clues. |
| **Port collision** | `BindException: Address already in use` | Use `withExposedPort()` or let Testcontainers auto-assign mapped ports. |
| **Firewall blocks container traffic** | `Connection refused` inside test JVM | Ensure Docker daemon is accessible; on Linux, ensure `iptables` rules allow bridge traffic. |
| **Test runs outside Docker context** | `Cannot connect to Docker daemon` | Run tests on a machine with Docker Desktop/Docker Engine running. |
| **Large container images slow down tests** | Tests take minutes to start | Use `-alpine` tags for smaller images; cache images between test suites. |
| **Test leaks container processes** | Zombie Docker processes after test suite | Ensure `@Testcontainers` is on the class, not just the method; use `static` containers judiciously. |

### Summary

- **Testcontainers** provisions disposable Docker containers for integration tests, ensuring production parity.
- **`@Testcontainers`** and **`@Container`** annotations manage the lifecycle; containers start before tests and stop after.
- **PostgreSQL, Redis, MySQL, MongoDB, Kafka** are available as official Testcontainers images.
- **`@DynamicPropertySource`** (Spring Boot 2.7+) automatically injects container-derived JDBC URLs, usernames, and passwords into the test Spring context.
- **Network binding**: `getMappedPort()` returns the host port mapped to the container's exposed port.
- **Test isolation**: Use unique database names or separate container instances per test class to avoid data leakage.
- **Parallel execution**: Possible with careful container management; separate containers per test class is the safest approach.
- **Pitfalls**: Shared container state, port collisions, Docker daemon accessibility, and image size affect test speed and reliability.
