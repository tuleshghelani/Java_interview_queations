# Java Interview Questions (Advanced Level)

## 201. How does Java Class Loading work? Explain the ClassLoader hierarchy, parent delegation, custom ClassLoaders, and the Java Platform Module System (JPMS).

Class loading is how the JVM turns bytecode (`*.class` files) into live `Class<?>` objects. Every class is loaded by a `ClassLoader` following the **parent delegation** model, and since Java 9 the **Module System (JPMS)** adds a higher-level grouping that controls *which* packages are visible across module boundaries. Understanding delegation, when to break it, and how modules layer on top is essential for frameworks (Spring, OSGi), application servers, and troubleshooting `ClassNotFoundException` / `NoClassDefFoundError`.

---

### 1. When Is a Class Loaded? — The Three Phases

| Phase | What happens |
| :--- | :--- |
| **Loading** | `ClassLoader.loadClass(name)` finds bytecode (`byte[]`) and calls `defineClass` → creates a `Class<?>` object in Metaspace |
| **Linking** | Verification (bytecode is valid) → Preparation (static fields get default values) → Resolution (symbolic references to other classes/methods resolved, lazily by default) |
| **Initialization** | `<clinit>` runs — static initializers and static field initializers execute. Triggered on first active use (`new`, `static` field/method access, `Class.forName`) |

```java
// Class.forName triggers loading + initialization by default:
Class<?> c = Class.forName("com.example.Foo"); // loads, links, initializes
// ClassLoader.loadClass only loads/links by default:
Class<?> c2 = ClassLoader.getSystemClassLoader().loadClass("com.example.Foo"); // not yet initialized
```

Resolution is lazy: `class Foo { Bar bar; }` does not load `Bar` until `Foo` actually touches `Bar`.

---

### 2. The Built-in ClassLoader Hierarchy (Java 8 vs Java 9+)

**Java 8:**

```
Bootstrap ClassLoader (native, loads rt.jar / jrt-fs)
      ↑
Extension ClassLoader (loads ext/*.jar)
      ↑
Application (System) ClassLoader (loads -classpath)
```

**Java 9+ (modules):**

```
Bootstrap ClassLoader (loads java.base and other core modules)
      ↑
Platform ClassLoader (replaces Extension — loads java.sql, java.xml, etc.)
      ↑
Application ClassLoader (loads classpath + unnamed module)
```

```java
System.out.println(String.class.getClassLoader());              // null = bootstrap
System.out.println(Driver.class.getClassLoader());              // platform (java.sql)
System.out.println(MyApp.class.getClassLoader());               // app classloader
System.out.println(ClassLoader.getSystemClassLoader());         // app
System.out.println(ClassLoader.getPlatformClassLoader());       // platform (Java 9+)
```

Each `ClassLoader` has a **parent** pointer (not inheritance — composition). Delegation walks *up* this chain.

---

### 3. Parent Delegation — How `loadClass` Works

```java
// Simplified ClassLoader.loadClass:
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);       // 1. already loaded?
        if (c == null) {
            try {
                if (parent != null)
                    c = parent.loadClass(name, false);  // 2. delegate to parent
                else
                    c = findBootstrapClassOrNull(name); // bootstrap
            } catch (ClassNotFoundException e) { /* parent failed */ }
            if (c == null)
                c = findClass(name);              // 3. try to find it myself
        }
        if (resolve) resolveClass(c);
        return c;
    }
}
```

**Why delegation?**

- **Uniqueness**: `java.lang.String` is always loaded by bootstrap — no app can spoof it.
- **Visibility**: Parent classes are visible to children, but not vice versa (child isolation).
- **Caching**: `findLoadedClass` ensures a class is loaded once per loader; identity is `(ClassLoader, fully-qualified-name)` — same `Foo` loaded by two loaders are **different types** (`ClassCastException` if you mix them).

```
Parent delegation flow:

MyApp wants com.example.Foo
  → App loader delegates to Platform → delegates to Bootstrap
  → Bootstrap: not found
  → Platform: not found
  → App loader: findClass("com.example.Foo") → reads Foo.class from classpath → defines it
```

---

### 4. Breaking Delegation — When and How

Some frameworks need a child to load a class *before* the parent (e.g., web apps bundling their own version of a library).

| Scenario | How it breaks delegation |
| :--- | :--- |
| **Web app isolation** (Tomcat, Jetty) | `WebappClassLoader` checks `WEB-INF/classes` and `WEB-INF/lib` *first*, then delegates — so two webapps can use different versions of the same library |
| **SPI / ServiceLoader** (`java.sql.Driver`, `META-INF/services`) | Parent (bootstrap/platform) needs to load an implementation visible only to the child (app loader). Uses **thread context class loader** (`Thread.currentThread().getContextClassLoader()`) |
| **OSGi / JPMS layers** | Each bundle/module has its own loader; delegation is replaced by explicit `requires`/`exports` wiring |

```java
// Custom child-first (webapp-style) loader:
public class ChildFirstLoader extends URLClassLoader {
    public ChildFirstLoader(URL[] urls, ClassLoader parent) { super(urls, parent); }

    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        synchronized (getClassLoadingLock(name)) {
            Class<?> c = findLoadedClass(name);
            if (c == null && !name.startsWith("java.")) { // never override java.*
                try { c = findClass(name); } catch (ClassNotFoundException ignored) {}
            }
            if (c == null) c = super.loadClass(name, false);
            if (resolve) resolveClass(c);
            return c;
        }
    }
}

// SPI — parent delegates *down* via TCCL:
Thread.currentThread().setContextClassLoader(customLoader);
ServiceLoader<Driver> drivers = ServiceLoader.load(Driver.class); // uses TCCL
```

> Rule: **Never override `java.*`** — the JVM enforces that `java.lang.*` must come from bootstrap (throws `SecurityException`).

### 5. JPMS — Modules on Top of ClassLoaders (Java 9+)

JPMS groups packages into **modules** (`module-info.java`) that declare explicit dependencies and exports:

```java
// module-info.java
module com.example.app {
    requires java.sql;              // depends on java.sql module
    requires transitive com.example.lib; // re-exports lib to downstream
    exports com.example.app.api;    // visible to other modules
    opens com.example.app.impl to com.example.framework; // reflective access only
    uses com.example.spi.Service;  // consumes a service
    provides com.example.spi.Service with com.example.app.impl.ServiceImpl;
}
```

**What JPMS adds over classpath:**

| Classpath (pre-9) | JPMS (post-9) |
| :--- | :--- |
| Flat — all jars on one path, package conflicts silently | **Graph** — module resolution fails fast on missing `requires` |
| `public` means visible to everyone | `public` in a non-`exported` package is **not visible** outside the module |
| Reflective access to everything (`setAccessible(true)`) | Encapsulated by default — `--add-opens` / `opens` needed for deep reflection (Spring, Hibernate need this) |
| One `Application ClassLoader` | Each module still loaded by a loader, but **module layers** (`ModuleLayer`) can create isolated loader graphs |

```
Module graph (resolved at startup):

java.base (bootstrap)
  ↑ requires
java.sql (platform) ── requires ──► com.example.lib (app)
                                        ↑ requires
                                   com.example.app (app)
  exports com.example.lib.api  →  visible
  package com.example.lib.impl →  NOT visible (not exported)
```

**ClassLoaders + Modules:**

- In the common case, there are still three loaders; modules are just a *visibility filter* on top.
- Advanced use: `ModuleLayer.defineModulesWithOneLoader(...)` creates a new layer with its own loader — used by plugins, scripting engines, and `jshell` to load/unload module graphs at runtime.

```java
// Creating an isolated plugin layer:
ModuleFinder finder = ModuleFinder.of(pluginDir);
ModuleLayer parent = ModuleLayer.boot();
Configuration cf = parent.configuration().resolve(finder, ModuleFinder.of(), Set.of("com.example.plugin"));
ClassLoader scl = ClassLoader.getSystemClassLoader();
ModuleLayer layer = parent.defineModulesWithOneLoader(cf, scl);
Class<?> pluginClass = layer.findLoader("com.example.plugin").loadClass("com.example.plugin.Main");
```

### 6. Diagnosing Class Loading Issues

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `ClassNotFoundException` | Loader cannot find the class (wrong classpath/module) | Check `-classpath`, `module-path`, `requires` in `module-info` |
| `NoClassDefFoundError` | Class was found at compile time but failed at runtime (static init threw, or wrong loader) | Check `<clinit>` exception, loader hierarchy with `-verbose:class` |
| `ClassCastException: Foo cannot be cast to Foo` | Same class loaded by two different loaders — different runtime types | Ensure single loader or add proper `exports`/`opens`; dedup jars |
| `IllegalAccessError` / `InaccessibleObjectException` (Java 9+) | JPMS encapsulation blocks access | Add `exports`/`opens` in `module-info`, or `--add-exports`/`--add-opens` as a workaround |
| `LinkageError` | Duplicate class definition across loaders/layers | Isolate via child-first loader or separate `ModuleLayer` |

```bash
# Verbose class loading:
java -verbose:class -Xlog:class+load=info MyApp
# Module resolution:
java --show-module-resolution --module-path mods -m com.example.app
# Dump loaded classes:
jcmd <pid> GC.class_histogram | head
jcmd <pid> VM.classloaders
```

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Calling `Class.forName(name)` without considering TCCL | SPI implementation not found in container (Tomcat) | Use `Class.forName(name, true, Thread.currentThread().getContextClassLoader())` |
| Leaking ClassLoaders (holding a reference to a loader) | Metaspace OOM after hot redeploy — old classes never GC'd | Clear `ThreadLocal`s, JDBC drivers, and `java.beans.Introspector` caches on undeploy; prefer `ModuleLayer` that can be GC'd |
| Using `--add-opens java.base/java.lang=ALL-UNNAMED` everywhere | Silences JPMS but hides real encapsulation issues | Migrate libraries to proper `opens`/`exports`; keep `--add-opens` narrowly scoped |
| Assuming `MyClass.class.getClassLoader() == null` for app classes | `null` means bootstrap — app classes are never null | Check `getPlatformClassLoader()` vs `getSystemClassLoader()` on Java 9+ |

### Summary

- Class loading is **loading → linking (verify/prepare/resolve) → initialization** (`<clinit>`); resolution is lazy.
- The built-in hierarchy is **Bootstrap → Platform → Application**, with **parent delegation** (`loadClass` delegates up, then `findClass` locally) ensuring uniqueness and security.
- Frameworks break delegation via **child-first loaders** (webapps) or **TCCL** (SPI/ServiceLoader) — never for `java.*`.
- **JPMS** adds a module graph (`requires`/`exports`/`opens`/`uses`/`provides`) on top of loaders: non-exported `public` is invisible, reflection needs `opens`, and `ModuleLayer` enables isolated plugin graphs.
- Duplicate-identity is `(loader, name)` — same bytecode in two loaders = two different types; diagnose with `-verbose:class`, `--show-module-resolution`, and `jcmd VM.classloaders`.

## 202. How do Dynamic Proxies work internally? Explain JDK Dynamic Proxies vs CGLIB/ByteBuddy, `InvocationHandler`, and how Spring AOP builds on them.

Dynamic proxies let the JVM generate a class at runtime that implements an interface (or subclasses a class) and intercepts every method call — the foundation for Spring AOP, transactions, security, Hibernate lazy loading, and mocking frameworks. JDK proxies (interface-based, in the JDK) and CGLIB/ByteBuddy (subclass-based, bytecode generation) solve the same problem with different trade-offs that every Spring interview probes.

---

### 1. JDK Dynamic Proxy — Interface-Based, Built Into the JDK

```
Client → Proxy implements UserService → InvocationHandler.invoke() → Real UserService
```

The JDK generates a class like `$Proxy0` at runtime (in `java.lang.reflect.Proxy`):

```java
public interface UserService { User findById(long id); }

UserService real = new UserServiceImpl();
UserService proxy = (UserService) Proxy.newProxyInstance(
    UserService.class.getClassLoader(),
    new Class<?>[]{ UserService.class },
    (p, method, args) -> {
        System.out.println("before " + method.getName());
        Object result = method.invoke(real, args); // or custom logic
        System.out.println("after");
        return result;
    }
);
proxy.findById(1L); // goes through InvocationHandler
```

**What `Proxy.newProxyInstance` does:**

1. Generates bytecode for a class `$Proxy0 extends Proxy implements UserService` (visible with `-Djdk.proxy.ProxyGenerator.saveGeneratedFiles=true` on Java 8 or `-Djdk.proxy.debug.saveGeneratedFiles=true`).
2. Each method body is `return handler.invoke(this, method, args)`.
3. Defines the class via the supplied `ClassLoader`, instantiates it with the `InvocationHandler`.

**Key properties:**

| Feature | JDK Proxy |
| :--- | :--- |
| **Target** | Interface(s) only — cannot proxy a class without an interface |
| **Bytecode** | Generated via `ProxyGenerator` (internal `sun.misc.ProxyGenerator`) |
| **Performance** | One `invoke` indirection + reflection `Method.invoke` — JIT can inline hot handlers but not as well as CGLIB |
| **Identity** | `proxy instanceof Proxy == true` |

---

### 2. CGLIB / ByteBuddy — Subclass-Based Proxies

When the target has no interface (or you need to proxy a concrete class), frameworks generate a **subclass**:

```java
// CGLIB style (Spring's legacy default for class proxies):
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserServiceImpl.class);
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    System.out.println("before");
    Object result = proxy.invokeSuper(obj, args); // calls super.method()
    System.out.println("after");
    return result;
});
UserServiceImpl cglibProxy = (UserServiceImpl) enhancer.create();

// ByteBuddy (modern, used by Mockito 5, Hibernate 6):
Class<? extends UserServiceImpl> bbClass = new ByteBuddy()
    .subclass(UserServiceImpl.class)
    .method(ElementMatchers.any())
    .intercept(MethodDelegation.to(Interceptor.class))
    .make().load(getClass().getClassLoader()).getLoaded();
```

**Generated class (conceptually):**

```java
class UserServiceImpl$$EnhancerByCGLIB$$123 extends UserServiceImpl {
    MethodInterceptor callback;
    @Override public User findById(long id) {
        return (User) callback.intercept(this, findByIdMethod, new Object[]{id}, findByIdProxy);
    }
}
```

| Feature | CGLIB | ByteBuddy |
| :--- | :--- | :--- |
| **Target** | Classes (not `final` class/method) | Classes (more flexible, better API) |
| **Library** | `net.sf.cglib:cglib` (unmaintained, Spring still supports) | `net.bytebuddy:byte-buddy` (actively maintained) |
| **Performance** | `MethodProxy.invokeSuper` uses `FastClass` — faster than reflection after warm-up | Similar, with more optimization hooks |
| **Limitations** | Cannot proxy `final` class/method, needs no-arg constructor (historically) | Same `final` limitation (JVM-enforced) |

---

### 3. JDK Proxy vs CGLIB/ByteBuddy — Head-to-Head

| Aspect | JDK Proxy | CGLIB / ByteBuddy |
| :--- | :--- | :--- |
| **Requires interface?** | Yes | No — subclasses the target |
| **Final handling** | N/A | Cannot proxy `final` class or `final`/`private` methods |
| **Self-invocation** (`this.innerMethod()`) | Bypassed — call stays inside `this`, not via proxy | Also bypassed (same reason — `this` is the real object, not the proxy) |
| **Spring default** | For interface beans | For class beans (since Spring Boot 2, CGLIB is default even for interfaces if `proxyTargetClass=true`) |
| **Serialization** | Proxy serializes handler | Subclass serializes similarly — both need care |

> **Self-invocation pitfall** — the #1 AOP interview trap:
> ```java
> @Transactional
> public void outer() { inner(); } // direct call — @Transactional on inner() is IGNORED
> @Transactional
> public void inner() { ... }
> // Fix: inject self-proxy or split into two beans, or use AspectJ weaving
> ```

---

### 4. How Spring AOP Builds on Proxies

```
@Configuration + @EnableAspectJAutoProxy
      ↓
BeanPostProcessor (AnnotationAwareAspectJAutoProxyCreator)
      ↓ scans @Aspect beans, matches pointcuts
      ↓ wraps matched beans in a Proxy (JDK or CGLIB) with a chain of MethodInterceptors
Client → Proxy → Interceptor chain (TransactionInterceptor, CacheInterceptor, ...) → Target
```

```java
@Aspect @Component
class LoggingAspect {
    @Around("execution(* com.example.service.*.*(..))")
    Object log(ProceedingJoinPoint pjp) throws Throwable {
        System.out.println("before " + pjp.getSignature());
        Object r = pjp.proceed(); // calls next interceptor / target
        System.out.println("after");
        return r;
    }
}

@Service
class UserService {
    @Transactional  // via TransactionInterceptor in the proxy chain
    @Cacheable("users")
    public User findById(long id) { return repo.findById(id).orElseThrow(); }
}
// At runtime UserService is actually a CGLIB proxy; findById goes through
// LoggingAspect → TransactionInterceptor → CacheInterceptor → real method
```

**Proxy creation rules in Spring Boot:**

- `spring.aop.proxy-target-class=false` → JDK proxy if bean implements an interface, otherwise CGLIB.
- `spring.aop.proxy-target-class=true` (default since Boot 2.0) → always CGLIB (via `Objenesis` + ByteBuddy/CGLIB) — consistent behavior, no interface required.

**AspectJ weaving (alternative to proxies):**

- Compile-time or load-time weaving modifies bytecode directly — no proxy, no self-invocation problem, can advise `private`/`final`/`field` access. Enabled via `spring.aop.mode=aspectj` + `aspectjweaver` agent. More powerful but more complex.

---

### 5. Performance and Limitations

```java
// Microbenchmark sketch (JMH) — proxy overhead is one extra method call + handler logic:
@Benchmark public Object direct()     { return real.findById(1L); }
@Benchmark public Object jdkProxy()   { return jdkProxy.findById(1L); }   // ~5-20 ns overhead
@Benchmark public Object cglibProxy() { return cglibProxy.findById(1L); } // similar, FastClass slightly faster
```

- Overhead is **negligible** for I/O-bound (DB, HTTP) advice; matters only for nanosecond-hot loops.
- `final`/`private` methods are never advised — CGLIB cannot override them, JDK proxy never sees them.
- `equals`/`hashCode`/`toString` on proxies can be surprising — Spring's proxy implements them to delegate to the target, but `proxy.getClass() != target.getClass()` breaks `getClass() == Foo.class` checks.

---

### 6. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Self-invocation bypassing AOP | `@Transactional`/`@Cacheable` on `inner()` never triggers | Extract to another bean, inject `self` proxy, or use AspectJ weaving |
| `final` class/method with CGLIB | `Cannot subclass final class` / advice silently ignored | Remove `final`, or expose an interface for JDK proxy, or use AspectJ |
| `proxy.getClass() == MyService.class` | `false` — proxy is `$Proxy0` / `$$EnhancerByCGLIB$$` | Use `instanceof` or `AopUtils.isAopProxy()` / `AopProxyUtils.ultimateTargetClass()` |
| Mocking `final` class with old Mockito | `MockitoException: Cannot mock final class` | Upgrade to Mockito 5 (uses ByteBuddy + `mockito-inline`) |
| Over-advising with broad pointcut `execution(* *.*(..))` | Startup slow, huge proxy chain, stack overflow | Narrow pointcut to `within(com.example.service..*)` |

### Summary

- **JDK proxies** implement interfaces via `Proxy.newProxyInstance` + `InvocationHandler`; **CGLIB/ByteBuddy** subclass concrete classes via `MethodInterceptor`/`FastClass` — the latter is needed when no interface exists.
- Both generate bytecode at runtime and add one indirection per call; self-invocation and `final` are the two universal limitations.
- **Spring AOP** auto-wraps beans with a proxy chain via `AnnotationAwareAspectJAutoProxyCreator`; since Boot 2, **CGLIB is the default** (`proxyTargetClass=true`), AspectJ weaving is the escape hatch for full coverage.
- Mockito, Hibernate lazy loading, and `@Transactional`/`@Cacheable` all rely on the same proxy mechanics — understanding JDK vs subclass proxies explains most AOP surprises.

## 203. How does the Spring Bean lifecycle work? Explain IoC container startup, dependency injection, `BeanPostProcessor`, circular dependencies, and scopes.

The Spring IoC container (`ApplicationContext`) turns your `@Component` classes into a managed object graph. Startup scans bean definitions, creates instances via DI, applies `BeanPostProcessor`s (where AOP proxies are created), and wires everything before the application handles a single request. Understanding this lifecycle explains `@Autowired` ordering, why constructor injection is safer than field injection, and how Spring breaks circular dependencies with a three-level cache.

---

### 1. Container Startup — From `ApplicationContext` to Ready

```
new AnnotationConfigApplicationContext(AppConfig.class)
  → 1. BeanDefinitionRegistry: scan @Component / @Bean / @Configuration → BeanDefinitions
  → 2. BeanFactoryPostProcessor: process @Configuration, @PropertySource, placeholders
  → 3. Instantiate singletons (eager, in dependency order)
  → 4. Populate properties + apply BeanPostProcessors
  → 5. ApplicationReadyEvent
```

```java
@Configuration @ComponentScan("com.example")
class AppConfig { }

var ctx = new AnnotationConfigApplicationContext(AppConfig.class);
UserService svc = ctx.getBean(UserService.class); // already wired proxy (if AOP)
```

- **Lazy vs eager:** Singletons are **eager** by default; `@Lazy` or `spring.main.lazy-initialization=true` defers to first `getBean`.
- **Order:** `BeanFactoryPostProcessor` (e.g., `ConfigurationClassPostProcessor`) runs before any bean is instantiated — it parses `@Configuration` and registers extra `BeanDefinition`s (like those from `@Bean` methods).

---

### 2. Creating a Single Bean — The 5 Steps

For each singleton `BeanDefinition`:

```
1. Instantiate          → constructor (or factory method)
2. Populate properties  → @Autowired / @Value injection
3. Aware callbacks      → BeanNameAware, BeanFactoryAware, ApplicationContextAware
4. BeanPostProcessor.beforeInitialization → @PostConstruct, afterPropertiesSet()
5. BeanPostProcessor.afterInitialization  → AOP proxy wrapping (Q202)
6. Ready                → afterPropertiesSet / init-method done
   ↓ on shutdown
7. Destroy              → @PreDestroy / DisposableBean / destroy-method
```

```java
@Component
class UserService implements BeanNameAware, InitializingBean, DisposableBean {
    private final UserRepository repo;

    // 1. Instantiation — constructor injection (preferred)
    @Autowired
    public UserService(UserRepository repo) { this.repo = repo; }

    // 3. Aware
    @Override public void setBeanName(String name) { System.out.println(name); }

    // 4. Init — three equivalent hooks (use one):
    @PostConstruct void init() { System.out.println("PostConstruct"); }
    @Override public void afterPropertiesSet() { }

    // 7. Destroy
    @PreDestroy void cleanup() { }
    @Override public void destroy() { }
}
```

**Why constructor injection wins:**

| Aspect | Constructor | Field (`@Autowired` on field) |
| :--- | :--- | :--- |
| **Immutability** | `final` field, required dep cannot be null | Mutable, can be null before injection |
| **Testability** | `new UserService(mockRepo)` trivially | Needs reflection / `@InjectMocks` |
| **Circular detection** | Fails fast at startup (good) | Hides cycle until runtime |
| **AOP/proxy safety** | Injected proxy is fully initialized | Same |

---

### 3. Dependency Injection Under the Hood

`AutowiredAnnotationBeanPostProcessor` (a `BeanPostProcessor`) handles `@Autowired`/`@Value`/`@Inject`:

- **By type:** `getBean(UserRepository.class)` — fails if 0 or 2+ candidates (use `@Qualifier` / `@Primary` to disambiguate).
- **By name fallback:** If multiple candidates, matches field name to bean name.

```java
@Component @Primary class JpaUserRepo implements UserRepository { }
@Component class InMemoryUserRepo implements UserRepository { }

@Component
class UserService {
    // picks JpaUserRepo because @Primary; without it: NoUniqueBeanDefinitionException
    @Autowired UserRepository repo;
    // disambiguate explicitly:
    @Autowired @Qualifier("inMemoryUserRepo") UserRepository alt;
}
```

`@Bean` methods inside `@Configuration` are themselves proxied (CGLIB subclass of the `@Configuration` class) to enforce singleton semantics: calling `userService()` twice returns the same instance.

---

### 4. `BeanPostProcessor` — The Extension Point for AOP

```java
interface BeanPostProcessor {
    Object postProcessBeforeInitialization(Object bean, String beanName);
    Object postProcessAfterInitialization(Object bean, String beanName); // can return a wrapper/proxy
}
```

```
Raw bean → postProcessBeforeInitialization (@PostConstruct, @Value)
         → InitializingBean / init-method
         → postProcessAfterInitialization → PROXY (if pointcut matches)
         → final bean in container
```

Key processors in order:

- `AutowiredAnnotationBeanPostProcessor` — injects `@Autowired`.
- `CommonAnnotationBeanPostProcessor` — handles `@PostConstruct`/`@PreDestroy`/`@Resource`.
- `AnnotationAwareAspectJAutoProxyCreator` — **wraps** the bean in a JDK/CGLIB proxy if an `@Aspect` pointcut matches (see Q202). It runs in `postProcessAfterInitialization`, so the proxy sees the fully initialized target.

Add your own:

```java
@Component
class TimingPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean instanceof UserService) {
            // wrap or instrument — must return a bean (original or proxy)
        }
        return bean;
    }
}
```

### 5. Circular Dependencies — The Three-Level Cache

A is being created → needs B → B needs A → cycle.

Spring solves **singleton setter/field cycles** via early exposure with three caches:

```
Level 1: singletonObjects          → fully initialized singletons
Level 2: earlySingletonObjects     → early reference (partially initialized, before init callbacks)
Level 3: singletonFactories        → ObjectFactory that creates the early reference (proxy if needed)
```

```
Create A: instantiate A (raw) → put ObjectFactory(A) in level 3
  → populate A's fields → needs B
  → Create B: instantiate B → needs A
    → getBean("A"): found in level 3 → call factory → early A reference (proxy if AOP) → put in level 2
  → B gets early A, finishes, goes to level 1
→ A gets fully initialized B, finishes, promotes to level 1
```

```java
@Component class A { @Autowired B b; } // field cycle — WORKS (early reference)
@Component class B { @Autowired A a; }

// Constructor cycle — FAILS (no early reference possible):
@Component class A2 { A2(B2 b) {} }
@Component class B2 { B2(A2 a) {} } // BeanCurrentlyInCreationException
```

| Cycle type | Works? | Why |
| :--- | :--- | :--- |
| **Setter/field singletons** | Yes | Early reference via level 2/3 |
| **Constructor injection** | No | Instance not yet created to expose |
| **Prototype scope** | No | Prototypes are not cached |
| **`@Lazy` on one side** | Yes | Injects a lazy proxy that defers resolution |

Fix constructor cycles: extract an interface, use `@Lazy`, refactor to remove the cycle, or use setter injection for one leg.

---

### 6. Scopes

| Scope | Lifecycle | Use |
| :--- | :--- | :--- |
| **singleton** (default) | One instance per container | Stateless services, repos, controllers |
| **prototype** | New instance per `getBean` / injection point | Stateful, non-thread-safe helpers |
| **request** / **session** (web) | Per HTTP request/session | Web controllers, user context (via proxy) |
| **application** | Per `ServletContext` | Rare |

```java
@Component @Scope("prototype") class PrototypeBean { }
@Component @Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
class RequestScopedBean { } // injected as a CGLIB proxy that delegates to current request instance
```

Prototype beans are **not** destroyed by the container — the caller must clean up.

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Field injection hiding a cycle | Startup succeeds but later `NullPointerException` in `@PostConstruct` | Use constructor injection — fails fast |
| Calling `@Bean` method via `this` inside `@Configuration` | New instance each call, singleton broken | Always call through the proxied `@Configuration` (or inject the bean) — never `this.myBean()` |
| `@PostConstruct` depending on AOP proxy | Advice not yet applied in `beforeInitialization` | Move logic to `InitializingBean` / `@EventListener(ApplicationReadyEvent.class)` |
| Prototype bean holding resources and expecting `@PreDestroy` | Resource leak — destroy never called | Manage lifecycle manually or use `ObjectProvider<PrototypeBean>` |
| Circular constructor dependency | `BeanCurrentlyInCreationException` | Break with `@Lazy`, setter injection, or refactor |

### Summary

- Startup: **scan `BeanDefinition`s → `BeanFactoryPostProcessor`s → instantiate singletons** (eager by default) through a 5-step lifecycle (instantiate → populate → aware → beforeInit/`@PostConstruct` → afterInit/proxy → ready → destroy).
- **Constructor injection** is preferred for immutability and fail-fast cycles; field injection hides problems.
- `BeanPostProcessor` (especially `AnnotationAwareAspectJAutoProxyCreator` in `postProcessAfterInitialization`) is where AOP proxies are applied; custom processors can instrument any bean.
- **Circular setter cycles** are resolved via the **three-level cache** (`singletonObjects` / `earlySingletonObjects` / `singletonFactories`); constructor and prototype cycles are not resolvable — use `@Lazy` or refactor.
- Scopes default to **singleton**; `prototype`/`request`/`session` cover stateful cases, with prototypes requiring manual cleanup.

---

## 204. How does `@Transactional` work in Spring? Explain proxy-based transaction management, propagation, isolation, rollback rules, and `PlatformTransactionManager`.

`@Transactional` is the declarative transaction facade of Spring — behind a single annotation hides a proxy interceptor, a `PlatformTransactionManager`, and a `TransactionSynchronization` that binds a JDBC `Connection` (or JPA `EntityManager` / reactive `TransactionalOperator`) to the current thread. Understanding that it is **proxy-based AOP** (Q202–Q203) explains self-invocation, propagation, and why `private`/`final` methods are never transactional.

---

### 1. Proxy-Based Mechanism — Where the Transaction Starts

```
Client → Proxy (JDK/CGLIB) → TransactionInterceptor → Target (@Transactional method)
           │
           └─▶ TransactionManager.getTransaction(definition)
                → bind Connection to ThreadLocal (TransactionSynchronizationManager)
                → set autoCommit=false
                → invoke target
                → commit / rollback, unbind, restore autoCommit
```

```java
@Service
class OrderService {
    @Transactional
    public void placeOrder(Order order) {
        orderRepo.save(order);      // uses thread-bound Connection
        inventoryService.reserve(order); // joins same transaction (REQUIRED)
    }
}
```

Only **public methods called through the Spring proxy** are intercepted. `BeanPostProcessor` `InfrastructureAdvisorAutoProxyCreator` wraps the bean in `postProcessAfterInitialization` (Q203).

```java
// Self-invocation bypass — the classic pitfall:
@Service class OrderService {
    public void outer() { inner(); } // direct this.inner() — NO proxy, NO transaction
    @Transactional public void inner() { ... }
}
// Fix: self-inject proxy, split beans, or AspectJ weaving
@Autowired OrderService self; // injected proxy
void outer() { self.inner(); } // now transactional
```

`private` / `final` / non-public methods are **never** proxied (CGLIB cannot override them) — put `@Transactional` only on `public` service methods.

---

### 2. `PlatformTransactionManager` — The Abstraction

```java
interface PlatformTransactionManager {
    TransactionStatus getTransaction(TransactionDefinition def);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
}
```

| Manager | Resource bound to thread | When to use |
| :--- | :--- | :--- |
| `DataSourceTransactionManager` | JDBC `Connection` via `TransactionSynchronizationManager` (ThreadLocal) | Plain JDBC / `JdbcTemplate` / MyBatis |
| `JpaTransactionManager` | JPA `EntityManager` (+ underlying JDBC Connection) | Spring Data JPA / Hibernate |
| `JtaTransactionManager` | XA `XAResource` (2PC) | Distributed transactions across multiple resources |
| `R2dbcTransactionManager` | Reactive `Connection` via `Context` (not ThreadLocal) | R2DBC reactive |

```java
@Configuration @EnableTransactionManagement
class TxConfig {
    @Bean PlatformTransactionManager txManager(DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }
}
```

`TransactionSynchronizationManager` holds `Map<DataSource, ConnectionHolder>` + `Set<TransactionSynchronization>` (for `afterCommit` / `afterCompletion` callbacks) in a `ThreadLocal` — which is why transactions are **thread-bound** and don't propagate to async threads or virtual threads without explicit transfer.

---

### 3. Propagation — What Happens When a Transactional Method Calls Another

```java
@Transactional(propagation = Propagation.REQUIRED)
void outer() { inner(); }

@Transactional(propagation = Propagation.REQUIRES_NEW)
void inner() { ... }
```

| Propagation | Behavior | Typical use |
| :--- | :--- | :--- |
| **REQUIRED** (default) | Join existing transaction, or create new one if none | 95% of cases — atomic unit of work |
| **REQUIRES_NEW** | Suspend current transaction, start a new one (new Connection, independent commit) | Audit logging that must commit even if outer rolls back |
| **NESTED** | Create a savepoint within the existing transaction | Partial rollback — only supported by some managers (JDBC 3.0 savepoints) |
| **SUPPORTS** | Join if exists, otherwise non-transactional | Read-only helpers |
| **NOT_SUPPORTED** | Suspend transaction, run non-transactionally | Rare — e.g., calling an external system that must not be in a TX |
| **MANDATORY** | Must have an existing transaction, else throw | Enforce that caller already started a TX |
| **NEVER** | Must *not* have a transaction, else throw | Guard against accidental TX |
| **NESTED** vs `REQUIRES_NEW` | `NESTED` shares the outer Connection + savepoint; `REQUIRES_NEW` gets a **new Connection** | Use `NESTED` for cheap partial rollback |

```java
// REQUIRES_NEW example — audit survives outer rollback:
@Transactional
void placeOrder(Order o) {
    orderRepo.save(o);
    try { paymentService.charge(o); }
    catch (PaymentException e) { auditService.logFailure(o); throw e; }
}
@Service class AuditService {
    @Transactional(propagation = REQUIRES_NEW)
    void logFailure(Order o) { auditRepo.save(new Audit(o, "FAILED")); } // commits independently
}
```

---

### 4. Isolation Levels — What the Database Sees

Isolation is delegated to the database (`Connection.setTransactionIsolation`); Spring just sets the level:

| Level | Dirty read | Non-repeatable read | Phantom read | DB behavior |
| :--- | :--- | :--- | :--- | :--- |
| **READ_UNCOMMITTED** | Yes | Yes | Yes | No locks on read |
| **READ_COMMITTED** (default — Postgres, Oracle) | No | Yes | Yes | Read only sees committed data |
| **REPEATABLE_READ** (default — MySQL InnoDB) | No | No | Yes* | Snapshot / gap locks |
| **SERIALIZABLE** | No | No | No | Full serial execution |

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public List<Order> findOrders() { ... }
```

> Spring's `DEFAULT` means "use the database default" — almost always correct. Changing isolation per method is rare; prefer handling phantoms with optimistic locking (`@Version`) or explicit `SELECT ... FOR UPDATE`.

---

### 5. Rollback Rules — When Does Spring Roll Back?

**Default:** Roll back on **unchecked** exceptions (`RuntimeException`, `Error`), **commit** on checked exceptions.

```java
@Transactional                    // rolls back on RuntimeException, commits on IOException
void create() throws IOException { ... }

@Transactional(rollbackFor = IOException.class) // now also rolls back on IOException
void create2() throws IOException { ... }

@Transactional(noRollbackFor = BusinessValidationException.class) // commit even on this RuntimeException
void create3() { ... }
```

Manually mark rollback:

```java
@Transactional
void create() {
    try { externalCall(); }
    catch (ExternalException e) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        // or: throw new RuntimeException(e);
    }
}
```

> Checked exception pitfall: `throws SQLException` inside `@Transactional` **commits** by default — wrap in `DataAccessException` (unchecked) or declare `rollbackFor`.

---

### 6. Read-Only, Timeouts, and Ordering

```java
@Transactional(readOnly = true)  // hint to manager: set Connection readOnly, skip dirty checking (Hibernate flush mode = NEVER)
@Transactional(timeout = 5)       // timeout in seconds — manager calls setQueryTimeout / throws TransactionTimedOutException

@Transactional  // Aspect order matters when multiple advisors apply:
@Order(1) @Aspect class SecurityAspect { @Around("@annotation(RequiresAuth)") ... }
@Order(2) @Aspect class TxAspect { ... } // lower order = outermost — security before TX
```

`readOnly = true` is not just a hint — on JPA it disables dirty checking and on some drivers routes to a read replica.

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Self-invocation | `@Transactional` on `inner()` ignored | Self-inject proxy, split bean, or AspectJ |
| `private`/`final` method | No proxy, no transaction | Make method `public` non-final on a Spring bean |
| Catching exception and not rethrowing | Transaction **commits** despite error | Rethrow or `setRollbackOnly()` |
| Expected rollback on checked exception | Commits — data inconsistency | Add `rollbackFor = Exception.class` or wrap as unchecked |
| Long transaction holding locks | DB lock timeout, connection pool exhaustion | Keep TX short — move I/O / remote calls outside TX, use `@Transactional` at service facade only |
| Mixing `@Async` + `@Transactional` | New thread has no TX context (ThreadLocal not propagated) | Put `@Transactional` inside the `@Async` method, or use `TransactionTemplate` |

### Summary

- `@Transactional` is **proxy-based AOP** (`TransactionInterceptor` → `PlatformTransactionManager.getTransaction` → bind `Connection` to `ThreadLocal` → commit/rollback) — only `public` proxy calls are transactional; self-invocation and `private`/`final` bypass it.
- `PlatformTransactionManager` abstracts the resource (JDBC `DataSourceTransactionManager`, JPA, JTA, R2DBC); `TransactionSynchronizationManager` is the ThreadLocal glue.
- **Propagation** controls nesting (`REQUIRED` join, `REQUIRES_NEW` suspend + new Connection, `NESTED` savepoint); **isolation** is passed to the DB; **rollback** defaults to unchecked only (`rollbackFor`/`noRollbackFor` to override).
- Use `readOnly = true` for read paths, keep transactions short, and remember that async/reactive threads need their own transaction context.

---

## 205. How does Spring Boot auto-configuration work? Explain `@SpringBootApplication`, `@EnableAutoConfiguration`, `@Conditional`, `spring.factories` vs `AutoConfiguration.imports`, and starter mechanics.

Spring Boot auto-configuration turns classpath presence + property values into ready-to-use beans (e.g., `DataSource`, `Jackson ObjectMapper`, `Tomcat`) without explicit `@Bean` definitions. A single `@SpringBootApplication` triggers component scanning, auto-configuration import, and property binding — all gated by `@Conditional` checks that make configuration *conditional* on what is on the classpath.

---

### 1. `@SpringBootApplication` — Three Annotations in One

```java
@SpringBootApplication // on your main class
public class MyApp { public static void main(String[] args) { SpringApplication.run(MyApp.class, args); } }

// Equivalent to:
@Configuration
@EnableAutoConfiguration
@ComponentScan
public class MyApp { }
```

| Meta-annotation | Role |
| :--- | :--- |
| `@Configuration` | Marks the class as a source of `@Bean` definitions |
| `@EnableAutoConfiguration` | Imports auto-configuration classes from `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |
| `@ComponentScan` | Scans the package of the annotated class (and sub-packages) for `@Component`/`@Service`/`@Controller` |

`@SpringBootApplication(scanBasePackages = "com.example")` narrows the scan; without it, Boot scans from the main class package downward.

---

### 2. How Auto-Configuration Is Discovered

**Spring Boot 2.x — `spring.factories`:**

```properties
# META-INF/spring.factories inside spring-boot-autoconfigure.jar
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration,\
  ...
```

**Spring Boot 3.x — `AutoConfiguration.imports`:**

```
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.jackson.JacksonAutoConfiguration
...
```

`AutoConfigurationImportSelector` reads this file (at startup, before singletons are created) and registers each listed class as a `BeanDefinition` — but each class is itself annotated with `@Conditional` so most are skipped.

```bash
# See which auto-configurations were applied / skipped:
# application.properties
debug=true
# or: logging.level.org.springframework.boot.autoconfigure=DEBUG
# Console output: "Positive matches" / "Negative matches" / "Exclusions"
```

Exclude selectively:

```java
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
public class MyApp { }

# or via properties:
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
```

---

### 3. `@Conditional` — The Gatekeeper

Every auto-configuration class is wrapped in conditions that check classpath, beans, properties, and environment:

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(DataSource.class)                          // only if DataSource is on classpath
@ConditionalOnMissingBean(DataSource.class)                    // only if user hasn't defined one
@ConditionalOnProperty(prefix = "spring.datasource", name = "url") // only if property is set
@AutoConfigureAfter(DataSourceAutoConfiguration.class)
public class DataSourceAutoConfiguration {
    @Bean @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties props) { ... }
}
```

| Condition | Checks |
| :--- | :--- |
| `@ConditionalOnClass` / `@ConditionalOnMissingClass` | Class on classpath (via `ClassLoader`) — the primary trigger for starters |
| `@ConditionalOnBean` / `@ConditionalOnMissingBean` | Bean already in container — user bean wins over auto-config |
| `@ConditionalOnProperty` | `spring.*` property value (`havingValue`, `matchIfMissing`) |
| `@ConditionalOnWebApplication` / `@ConditionalOnNotWebApplication` | Servlet vs reactive vs none |
| `@ConditionalOnExpression` | SpEL expression |
| `@Conditional` (custom) | Arbitrary `Condition.matches()` logic |

> Order matters: `@AutoConfigureOrder`, `@AutoConfigureBefore`, `@AutoConfigureAfter` control the sequence — e.g., `DataSourceAutoConfiguration` before `JdbcTemplateAutoConfiguration`.

---

### 4. Starters — Convention Over Dependencies

A **starter** is just a Maven/Gradle POM that pulls in the right jars so conditions fire:

```xml
<!-- pom.xml — one dependency brings the whole web stack -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
<!-- Transitive: spring-web, spring-webmvc, tomcat-embed-core, jackson, validation, ... -->

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<!-- Transitive: spring-data-jpa, hibernate-core, spring-jdbc, HikariCP -->
```

No code in the starter itself — the JAR may be empty except for `pom.xml`. The auto-configuration lives in `spring-boot-autoconfigure`.

Custom starter pattern:

```
my-starter/
  my-autoconfigure/  → MyFeatureAutoConfiguration + META-INF/.../AutoConfiguration.imports
  my-starter/        → pom that depends on my-autoconfigure + required libraries
```

```java
// my-autoconfigure/src/main/java/com/example/MyFeatureAutoConfiguration.java
@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(MyFeature.class)
@EnableConfigurationProperties(MyFeatureProperties.class)
public class MyFeatureAutoConfiguration {
    @Bean @ConditionalOnMissingBean
    MyFeature myFeature(MyFeatureProperties props) { return new MyFeature(props.getEndpoint()); }
}

@ConfigurationProperties(prefix = "my.feature")
class MyFeatureProperties { private String endpoint; /* getters/setters */ }
```

User just adds `my-starter` to the classpath and sets `my.feature.endpoint=...` — Boot does the rest.

---

### 5. `@ConfigurationProperties` — Type-Safe Property Binding

```java
@ConfigurationProperties(prefix = "app.datasource")
@Component // or @EnableConfigurationProperties(AppProperties.class) on @Configuration
public class AppProperties {
    private String url;
    private int poolSize = 10;
    private Duration timeout;
    @NestedConfigurationProperty private Security security;
    // getters/setters (or record with @ConstructorBinding in Boot 2, implicit in Boot 3)
}

# application.yml
app:
  datasource:
    url: jdbc:postgresql://localhost/mydb
    pool-size: 20
    security:
      enabled: true
```

Boot binds `application.properties` / `application.yml` / env vars / command-line args (in well-defined precedence order) into the POJO, with validation via `@Validated` + `jakarta.validation` annotations.

---

### 6. Startup Sequence With Auto-Configuration

```
SpringApplication.run()
  → load spring.factories / AutoConfiguration.imports
  → evaluate @Conditional for each auto-config class
  → register matching @Bean definitions
  → BeanFactoryPostProcessor (parse @Configuration)
  → instantiate singletons (Q203 — 5-step lifecycle, BeanPostProcessors)
  → bind @ConfigurationProperties
  → ApplicationReadyEvent → embedded Tomcat/Netty starts
```

```bash
# Inspect auto-configuration report:
java -jar myapp.jar --debug | grep "Auto-configuration"
# Actuator endpoint (if enabled):
curl http://localhost:8080/actuator/conditions  # positive/negative matches as JSON
curl http://localhost:8080/actuator/beans       # all beans with dependencies
curl http://localhost:8080/actuator/configprops # bound properties
```

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Component scan missing beans (main class in wrong package) | `NoSuchBeanDefinitionException` | Move `@SpringBootApplication` to a parent package, or set `scanBasePackages` |
| Defining `DataSource` bean *and* relying on auto-config that checks `@ConditionalOnMissingBean` | Auto-config silently backs off — no error, but you may expect its extra beans (e.g., `JdbcTemplate`) | Either rely fully on auto-config or define all related beans explicitly |
| `@ConditionalOnClass` referencing a class that is not on classpath at compile time | Compilation error | Use `name` attribute: `@ConditionalOnClass(name = "com.example.OptionalLib")` |
| `application.properties` not picked up | Properties stay at defaults | Check file location (`src/main/resources/`), profile (`application-dev.yml`), and precedence (env var > CLI > file) |
| Fat jar with duplicate `AutoConfiguration.imports` not merged | Auto-config from one library silently missing | Use `spring-boot-maven-plugin` / `gradle` plugin which merges imports correctly; don't shade manually |

### Summary

- `@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`; the last imports auto-configurations listed in `AutoConfiguration.imports` (Boot 3) / `spring.factories` (Boot 2).
- Each auto-configuration is gated by **`@Conditional`** (`OnClass` / `OnMissingBean` / `OnProperty` / `OnWebApplication`) — only matching classes register their `@Bean`s; `@AutoConfigureBefore`/`After` orders them.
- **Starters** are dependency bundles that make conditions fire; custom starters pair an `autoconfigure` module (with conditions) and a `starter` POM.
- `@ConfigurationProperties` binds external config (`application.yml`, env vars) type-safely; `debug=true` and `/actuator/conditions` reveal positive/negative matches.

---

## 206. How does Spring MVC handle an HTTP request? Explain `DispatcherServlet`, `HandlerMapping`, `HandlerAdapter`, interceptors, and the move to Spring WebFlux.

Spring MVC is a **front-controller** framework: a single `DispatcherServlet` receives every HTTP request and dispatches it through a chain of `HandlerMapping` → `HandlerAdapter` → controller method → `HandlerInterceptor` → `ViewResolver` / `HttpMessageConverter`. Understanding this pipeline explains `@RequestMapping` resolution, why interceptors differ from filters, and when to stay on blocking MVC vs move to reactive WebFlux.

---

### 1. The Front Controller — `DispatcherServlet`

```java
// web.xml (Servlet 2.5) or Servlet 3.0 programmatic:
public class MyInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {
    protected Class<?>[] getRootConfigClasses() { return new Class[]{ AppConfig.class }; }
    protected Class<?>[] getServletConfigClasses() { return new Class[]{ WebConfig.class }; }
    protected String[] getServletMappings() { return new String[]{ "/" }; }
}
// Spring Boot: auto-registers DispatcherServlet via DispatcherServletAutoConfiguration
```

```
HTTP Request → Tomcat (or Jetty/Undertow) → Filter chain → DispatcherServlet
                                                            → doDispatch()
                                                              → getHandler()
                                                              → getHandlerAdapter()
                                                              → interceptor.preHandle()
                                                              → handler.handle()  (controller method)
                                                              → interceptor.postHandle()
                                                              → view / message conversion
                                                              → interceptor.afterCompletion()
```

`DispatcherServlet` is a plain `HttpServlet` with `initStrategies()` that looks up these collaborators from the `ApplicationContext`:

| Strategy interface | Default bean | Role |
| :--- | :--- | :--- |
| `HandlerMapping` | `RequestMappingHandlerMapping` | Maps URL + HTTP method + params to a `HandlerExecutionChain` |
| `HandlerAdapter` | `RequestMappingHandlerAdapter` | Invokes the handler (knows how to call a `@RequestMapping` method) |
| `HandlerExceptionResolver` | `ExceptionHandlerExceptionResolver` | Maps exceptions to responses |
| `ViewResolver` | `InternalResourceViewResolver` / `ContentNegotiatingViewResolver` | Resolves view name to `View` |
| `LocaleResolver` | `AcceptHeaderLocaleResolver` | Resolves `Locale` |
| `MultipartResolver` | `StandardServletMultipartResolver` | Handles `multipart/form-data` |

---

### 2. Request Mapping — How `@RequestMapping` Is Resolved

```java
@RestController @RequestMapping("/users")
class UserController {
    @GetMapping("/{id}")           // → GET /users/{id}
    User getUser(@PathVariable long id, @RequestParam(defaultValue = "false") boolean details) { ... }

    @PostMapping(consumes = "application/json", produces = "application/json")
    ResponseEntity<User> create(@Valid @RequestBody UserDto dto) { ... }

    @GetMapping(params = "active=true", headers = "X-Api-Version=2")
    List<User> activeUsersV2() { ... }
}
```

`RequestMappingHandlerMapping` (created by `@EnableWebMvc` / `WebMvcAutoConfiguration`) scans all `@Controller` beans at startup:

1. Reads `@RequestMapping` at class + method level and merges them (`/users` + `/{id}` → `/users/{id}`).
2. Builds `RequestMappingInfo` objects keyed by path pattern (Ant / `PathPattern` since Boot 2.6), HTTP method, params, headers, `consumes`/`produces`.
3. On each request, `getHandler(request)` finds the best matching `RequestMappingInfo` (most specific pattern wins) and returns a `HandlerExecutionChain` (handler method + interceptors).

Content negotiation (`Accept: application/json`) is handled by `ContentNegotiationManager` driving `HttpMessageConverter` selection (see §4).

---

### 3. `HandlerAdapter` — Invoking the Controller Method

`RequestMappingHandlerAdapter` is the bridge between the `DispatcherServlet` and your method signature:

```java
// What the adapter does (simplified):
Object[] args = new Object[parameterCount];
for (int i = 0; i < parameterCount; i++) {
    args[i] = resolver.resolveArgument(param[i], request); // @PathVariable, @RequestParam, @RequestBody, ...
}
Object returnValue = method.invoke(controller, args);
handleReturnValue(returnValue, returnType, request, response); // @ResponseBody, ResponseEntity, View
```

| Annotation | Resolver | Source |
| :--- | :--- | :--- |
| `@PathVariable` | `PathVariableMethodArgumentResolver` | URI template |
| `@RequestParam` | `RequestParamMethodArgumentResolver` | Query param / form |
| `@RequestBody` | `RequestResponseBodyMethodProcessor` | Body via `HttpMessageConverter` |
| `@RequestHeader` / `@CookieValue` | Header/Cookie resolvers | Headers |
| `HttpServletRequest` / `Principal` / `Locale` | Servlet resolvers | Servlet API |

Return value handling:

- `@ResponseBody` / `@RestController` → `RequestResponseBodyMethodProcessor` writes via `HttpMessageConverter` (JSON/XML).
- `String` view name → `ViewResolver`.
- `ResponseEntity<T>` → status + headers + body.
- `void` → assumes response already handled.

---

### 4. Message Conversion and Content Negotiation

```java
// JSON in/out — Jackson is the default HttpMessageConverter:
@RestController
class Api {
    @PostMapping("/echo") User echo(@RequestBody User u) { return u; }
    // Request: Content-Type: application/json → MappingJackson2HttpMessageConverter reads User
    // Response: Accept: application/json       → same converter writes User as JSON
}
```

```
Request Body (JSON bytes) → MappingJackson2HttpMessageConverter (Jackson ObjectMapper) → User object
User object               → MappingJackson2HttpMessageConverter → Response Body (JSON bytes)
```

`ContentNegotiatingViewResolver` picks the converter based on `Accept` header, `?format=json` param, or file extension. Customize via `WebMvcConfigurer`:

```java
@Configuration
class WebConfig implements WebMvcConfigurer {
    @Override public void configureMessageConverters(List<HttpMessageConverter<?>> cs) {
        cs.add(new MappingJackson2HttpMessageConverter(customObjectMapper()));
    }
    @Override public void addInterceptors(InterceptorRegistry r) {
        r.addInterceptor(new AuthInterceptor()).addPathPatterns("/api/**");
    }
}
```

---

### 5. Interceptors vs Filters vs AOP

| Layer | Interface | Scope | Can access handler method? | Order |
| :--- | :--- | :--- | :--- | :--- |
| **Filter** (`jakarta.servlet.Filter`) | `doFilter(ServletRequest, ServletResponse, FilterChain)` | Entire servlet container — runs **before** `DispatcherServlet` | No — only raw request/response | `FilterRegistrationBean` / `@Order` |
| **Interceptor** (`HandlerInterceptor`) | `preHandle` / `postHandle` / `afterCompletion` | Inside `DispatcherServlet`, per `HandlerMapping` | Yes — `handler` is `HandlerMethod` (controller + `Method`) | `InterceptorRegistry` order |
| **AOP Aspect** | `@Around` | Inside the controller bean proxy (Q202) | Yes — but **after** interceptor `preHandle` | Aspect `@Order` |

```java
@Component
class AuthInterceptor implements HandlerInterceptor {
    @Override public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (!isAuthenticated(req)) { res.sendError(401); return false; } // stop dispatch
        return true;
    }
    @Override public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        // always called — cleanup, MDC clear, metrics
    }
}
```

> Choosing: Filter for **servlet-level** concerns (encoding, CORS, logging raw body); Interceptor for **controller-level** concerns (auth, rate limiting with handler info); AOP for **service-level** cross-cutting (transactions, caching).

---

### 6. Exception Handling

```java
@RestControllerAdvice // = @ControllerAdvice + @ResponseBody
class GlobalExceptionHandler {
    @ExceptionHandler(UserNotFoundException.class)
    ResponseEntity<Error> handleNotFound(UserNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(new Error(ex.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<Map<String,String>> handleValidation(MethodArgumentNotValidException ex) { ... }
}
// Per-controller: @ExceptionHandler inside the @Controller class takes precedence
```

`DispatcherServlet` catches any exception from the handler chain and delegates to the ordered `HandlerExceptionResolver` list — `ExceptionHandlerExceptionResolver` (for `@ExceptionHandler`) wins first.

---

### 7. Spring MVC vs WebFlux — When to Switch

| Aspect | Spring MVC (blocking) | Spring WebFlux (reactive) |
| :--- | :--- | :--- |
| **Concurrency** | One thread per request (or virtual thread — Q195) | Few event-loop threads (Netty), non-blocking I/O |
| **Programming model** | Imperative, `User` / `List<User>` | Reactive, `Mono<User>` / `Flux<User>` |
| **Backpressure** | None (blocking) | Built-in (Reactive Streams) |
| **Best for** | CRUD, JPA/Hibernate (blocking JDBC), team familiarity | High-concurrency I/O-bound, streaming, gateway, `WebClient` fan-out |
| **Dispatcher** | `DispatcherServlet` (Servlet API) | `DispatcherHandler` (no Servlet — Netty directly) |

```java
// WebFlux handler (non-blocking):
@RestController
class ReactiveUserController {
    @GetMapping("/users/{id}")
    Mono<User> getUser(@PathVariable long id) { return userRepo.findById(id); } // R2DBC reactive repo
}
```

> Since Java 21 virtual threads, **blocking MVC scales to millions of concurrent requests** — WebFlux's main remaining edge is streaming/backpressure and non-blocking `WebClient` pipelines. Many teams stay on MVC unless they need reactive end-to-end.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Ambiguous mapping (`@GetMapping("/users")` twice) | `IllegalStateException: Ambiguous mapping` at startup | Make paths / HTTP methods distinct; use `params` / `headers` to disambiguate |
| `@RequestBody` on GET | `HttpMessageNotReadableException` — GET has no body | Use `@RequestParam` / `@PathVariable` for GET |
| Filter ordering wrong (auth after logging) | Unauthenticated requests still logged as success | Set explicit `@Order` on `FilterRegistrationBean` |
| Returning `String` from `@RestController` | Written as JSON string `"hello"` not view name | Intended — `@RestController` implies `@ResponseBody`; use `@Controller` for view names |
| Blocking call inside WebFlux `Mono` | Event loop blocked, throughput collapses | Wrap with `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` or use R2DBC |

### Summary

- `DispatcherServlet` is the **front controller** that delegates to `HandlerMapping` (URL → handler) → `HandlerAdapter` (invoke controller) → `HttpMessageConverter`/`ViewResolver` (render response), with filters outside and interceptors inside the dispatch.
- `RequestMappingHandlerMapping` builds `RequestMappingInfo` from `@RequestMapping` at startup; `RequestMappingHandlerAdapter` resolves `@PathVariable`/`@RequestParam`/`@RequestBody` via argument resolvers.
- **Filter** (servlet-level) → **Interceptor** (`preHandle`/`postHandle`/`afterCompletion`, has handler info) → **AOP** (service-level) — choose by layer.
- `ContentNegotiation` drives `HttpMessageConverter` selection; `@RestControllerAdvice` + `@ExceptionHandler` centralize errors.
- **MVC (blocking)** remains the default — with virtual threads it scales to high concurrency; **WebFlux (reactive)** wins for streaming, backpressure, and reactive data stores.

## 207. How does Spring Security work? Explain the filter chain, `SecurityFilterChain`, authentication vs authorization, JWT/OAuth2, and method security.

Spring Security is a **filter-chain framework** that sits in front of `DispatcherServlet` (Q206) and enforces authentication (who are you?) and authorization (what can you do?) for every request. A `SecurityFilterChain` bean configures an ordered chain of `jakarta.servlet.Filter`s — `SecurityContextPersistenceFilter`, `UsernamePasswordAuthenticationFilter`, `BearerTokenAuthenticationFilter`, `ExceptionTranslationFilter`, `AuthorizationFilter` — backed by an `AuthenticationManager` / `UserDetailsService` and an `AccessDecisionManager`. Understanding the chain explains why `SecurityConfig` replaces `WebSecurityConfigurerAdapter`, how JWT replaces sessions, and how `@PreAuthorize` works.

---

### 1. Where Spring Security Sits — The Filter Chain

```
HTTP Request → Tomcat → DelegatingFilterProxy (springSecurityFilterChain)
                          → SecurityFilterChain (ordered Filters)
                            → SecurityContextPersistenceFilter
                            → UsernamePasswordAuthenticationFilter / BearerTokenAuthenticationFilter
                            → ExceptionTranslationFilter
                            → AuthorizationFilter (or FilterSecurityInterceptor)
                          → DispatcherServlet → Controller
```

```java
@Configuration @EnableWebSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable()) // stateless API
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults())
            .formLogin(form -> form.loginPage("/login").permitAll())
            .logout(logout -> logout.logoutUrl("/logout"));
        return http.build();
    }
}
```

- `DelegatingFilterProxy` bridges the Servlet container (`web.xml` / `FilterRegistrationBean`) to the Spring-managed `SecurityFilterChain`.
- Since Spring Security 5.7, `WebSecurityConfigurerAdapter` is **deprecated** — define a `SecurityFilterChain` `@Bean` instead.
- Multiple `SecurityFilterChain` beans can be ordered with `@Order` for different URL patterns (e.g., API chain vs actuator chain).

---

### 2. Authentication — `AuthenticationManager` and `SecurityContext`

```
UsernamePasswordAuthenticationFilter
  → Authentication (unauthenticated: username + password)
  → AuthenticationManager.authenticate()
    → DaoAuthenticationProvider → UserDetailsService.loadUserByUsername()
                                 → PasswordEncoder.matches()
  → Authentication (authenticated: principal + authorities + credentials erased)
  → SecurityContextHolder.getContext().setAuthentication(auth)
```

```java
@Service
class JpaUserDetailsService implements UserDetailsService {
    @Override public UserDetails loadUserByUsername(String username) {
        return userRepo.findByUsername(username)
            .map(u -> User.withUsername(u.getUsername())
                          .password(u.getPasswordHash())
                          .roles(u.getRoles().toArray(String[]::new))
                          .build())
            .orElseThrow(() -> new UsernameNotFoundException(username));
    }
}

@Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }
```

- `SecurityContext` is stored in a `ThreadLocal` (`SecurityContextHolder`) for blocking MVC, or in Reactor `Context` for WebFlux (`ReactiveSecurityContextHolder`).
- `SecurityContextPersistenceFilter` saves/restores the context from `HttpSession` (stateful) or leaves it empty per request (stateless JWT — see §4).

---

### 3. Authorization — URL Rules and Method Security

**URL-based (inside the filter chain):**

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/api/**").hasAuthority("READ")
    .requestMatchers(HttpMethod.POST, "/api/**").hasAuthority("WRITE")
    .anyRequest().denyAll()
);
```

**Method-level (via AOP proxy — Q202/Q203):**

```java
@Configuration @EnableMethodSecurity // replaces @EnableGlobalMethodSecurity
class MethodSecurityConfig { }

@Service
class ReportService {
    @PreAuthorize("hasRole('ADMIN') or #owner == authentication.name")
    Report getReport(long id, String owner) { ... }

    @PostAuthorize("returnObject.owner == authentication.name")
    Report updateReport(Report r) { ... }

    @Secured("ROLE_MANAGER")
    void approve(long id) { ... }
}
```

- `@EnableMethodSecurity` creates a CGLIB/JDK proxy around the bean (same mechanism as `@Transactional` — Q204) that checks `AuthorizationManager` before/after method invocation.
- Self-invocation bypass applies here too — `this.securedMethod()` inside the same bean is **not** checked.

---

### 4. JWT and OAuth2 — Stateless Authentication

**JWT (self-contained token):**

```
Client → POST /login {user, pass} → Server validates → signs JWT (header.payload.signature)
Client → GET /api/data  Authorization: Bearer <jwt>
         → BearerTokenAuthenticationFilter
           → JwtDecoder (verifies signature via JWK / HMAC)
           → JwtAuthenticationToken → SecurityContext
```

```java
@Configuration @EnableWebSecurity
class JwtConfig {
    @Bean SecurityFilterChain api(HttpSecurity http, JwtDecoder decoder) throws Exception {
        http.securityMatcher("/api/**")
            .authorizeHttpRequests(a -> a.anyRequest().authenticated())
            .oauth2ResourceServer(oauth -> oauth.jwt(jwt -> jwt.decoder(decoder)))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
        return http.build();
    }
    @Bean JwtDecoder jwtDecoder() {
        return NimbusJwtDecoder.withJwkSetUri("https://auth.example.com/.well-known/jwks.json").build();
    }
}
```

**OAuth2 login (authorization code flow):**

```java
http.oauth2Login(oauth -> oauth
    .userInfoEndpoint(u -> u.userService(customOAuth2UserService))
    .successHandler((req, res, auth) -> res.sendRedirect("/dashboard"))
);
```

| Mode | Token stored where | Session | Use |
| :--- | :--- | :--- | :--- |
| **Session** (`JSESSIONID`) | Server `HttpSession` | Stateful | Traditional web app, `formLogin` |
| **JWT** (`Bearer`) | Client (localStorage / cookie) | Stateless | SPA / mobile API, microservices |
| **OAuth2 Authorization Server** | Auth server issues JWT / opaque token | Either | SSO, third-party login (Google, GitHub) |

> Stateless JWT means no server-side logout — use short expiry + refresh token rotation, or a revocation list.

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| `hasRole("ADMIN")` vs `hasAuthority("ROLE_ADMIN")` | `AccessDeniedException` — off-by-one prefix | `hasRole` auto-adds `ROLE_` prefix; `hasAuthority` does not |
| `SecurityContext` lost in `@Async` / new thread | `authentication == null` in async task | Use `DelegatingSecurityContextExecutor` or `@Async` with `SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)` |
| CSRF enabled on stateless JWT API | POST returns 403 Forbidden | `http.csrf(csrf -> csrf.disable())` when using `SessionCreationPolicy.STATELESS` |
| Method security not applied (self-invocation) | `@PreAuthorize` ignored | Call through Spring proxy — inject `self` or move method to another bean |
| Storing JWT in `localStorage` vulnerable to XSS | Token stolen via injected script | Prefer `HttpOnly` `Secure` cookie for JWT, or use short-lived token + refresh flow |
| Forgetting `@EnableMethodSecurity` | `@PreAuthorize` silently ignored | Add `@EnableMethodSecurity` (Boot 3) — not `@EnableGlobalMethodSecurity` (deprecated) |

### Summary

- Spring Security is a **`SecurityFilterChain` of servlet Filters** in front of `DispatcherServlet`; `SecurityConfig` builds the chain via `HttpSecurity` — `WebSecurityConfigurerAdapter` is deprecated in favor of `SecurityFilterChain` beans.
- **Authentication** flows through `AuthenticationManager` → `UserDetailsService` + `PasswordEncoder` → `SecurityContextHolder` (ThreadLocal / Reactor Context).
- **Authorization** is URL-based (`authorizeHttpRequests`) or method-level (`@PreAuthorize`/`@PostAuthorize` via AOP proxy) — self-invocation bypass applies.
- **JWT/OAuth2** replaces `HttpSession` for stateless APIs: `BearerTokenAuthenticationFilter` + `JwtDecoder` (JWK) + `SessionCreationPolicy.STATELESS`.
- Test with `@WithMockUser` / `MockMvc` JWT headers; remember `ROLE_` prefix, async context propagation, and `HttpOnly` cookie storage.

## 208. How does JPA/Hibernate work internally? Explain the persistence context, entity lifecycle, first/second-level cache, lazy loading, N+1, and flushing.

JPA (via Hibernate as the default provider in Spring Boot) is not a thin SQL wrapper — it is a **state-tracking persistence context** that manages entity lifecycles, transparently translates field changes into SQL, and hides JDBC behind a session-bound cache and proxy-based lazy loading. Understanding the persistence context explains why `save()` sometimes issues no SQL, what `LazyInitializationException` really means, and how a single missing `JOIN FETCH` creates an N+1 storm.

---

### 1. The Persistence Context — A First-Level Cache and Change Tracker

```
EntityManager (PersistenceContext)
  ├── entitiesById  : Map<EntityKey, ManagedEntity>  // first-level cache, mandatory
  ├── snapshots     : Map<EntityKey, Object[]>        // copy taken at load time
  ├── actionQueue   : InsertAction / UpdateAction / DeleteAction / CollectionAction
  └── persistenceContextType: TRANSACTION or EXTENDED
```

```java
@Transactional
public void updateName(long id, String newName) {
    User user = em.find(User.class, id); // SELECT ... WHERE id=?  (if not already cached)
    user.setName(newName);                // no SQL yet — dirty flag set in snapshot comparison
} // commit → flush → dirty check → UPDATE users SET name=? WHERE id=? AND version=?
```

- `em.find()` / `repository.findById()` first checks the **first-level cache** (per-`EntityManager` / per-transaction). `find()` twice in one transaction issues **one** SQL.
- At **flush** time (before commit, before query, or on explicit `em.flush()`), Hibernate compares each managed entity's current state against its snapshot — **dirty checking** — and queues `UPDATE`s for every dirty entity.
- The first-level cache cannot be disabled; `em.clear()` / `em.detach(entity)` evicts it.

---

### 2. Entity Lifecycle States

```
new (transient) ──persist()──► managed ──detach()/clear()/close──► detached
                    ▲              │  │
                    │              │  └──remove()──► removed (→ DELETE on flush)
                    │              └──flush/commit──► DB synchronized
                    └────merge(detached)────────────┘
```

| State | In persistence context? | Tracked for dirty check? | Example |
| :--- | :--- | :--- | :--- |
| **Transient** | No | No | `new User()` before `persist` |
| **Managed** | Yes | Yes | After `persist`, `find`, or `merge` inside TX |
| **Detached** | No (was managed) | No | After `em.detach()`, after TX commits, or serialized to a controller response |
| **Removed** | Yes (marked for deletion) | — | After `em.remove(managed)` — `DELETE` on flush |

```java
User u = new User("alice");          // transient
em.persist(u);                       // managed — INSERT queued, id assigned
em.detach(u);                        // detached — changes to u are ignored
u.setName("bob");                    // no SQL
User managed = em.merge(u);          // managed copy — UPDATE queued for "bob"
```

> Spring Data's `repository.save(entity)` is `persist` if `entity.isNew()` (null id or `Persistable.isNew()`), otherwise `merge` — which is why `save()` on a detached entity with an existing id issues a `SELECT` + `UPDATE` (or just `UPDATE` with `saveAndFlush`).

---

### 3. Flush Modes and When SQL Is Actually Sent

| Flush trigger | Behavior |
| :--- | :--- |
| `FlushMode.AUTO` (default) | Flush before commit **and** before any JPQL/HQL query that might be affected by pending changes |
| `FlushMode.COMMIT` | Only before commit — queries may see stale state within the same TX |
| `em.flush()` | Immediate — force all queued actions to DB (still inside TX, not yet committed) |
| `transaction commit` | Implicit flush + `COMMIT` |

```java
@Transactional
void batch() {
    for (int i = 0; i < 1000; i++) {
        em.persist(new User("u" + i));
        if (i % 50 == 0) { em.flush(); em.clear(); } // flush + evict to avoid OOM
    }
} // without flush/clear, 1000 entities stay in first-level cache → memory bloat + huge flush
```

In Spring Boot, `spring.jpa.properties.org.hibernate.flushMode=COMMIT` is **not** recommended — keep `AUTO` unless you manually control every query.

---

### 4. Lazy Loading, Proxies, and `LazyInitializationException`

```java
@Entity class Order {
    @ManyToOne(fetch = FetchType.LAZY) User user;          // proxy
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY) List<Item> items; // PersistentBag
}
```

```java
Order order = orderRepo.findById(1L).orElseThrow(); // SELECT * FROM orders WHERE id=1 (items NOT loaded)
order.getUser().getName(); // triggers: SELECT * FROM users WHERE id=?  (proxy initialized)
order.getItems().size();   // triggers: SELECT * FROM items WHERE order_id=? (collection initialized)
```

Hibernate implements `LAZY` with:

- **Entity proxy** (`User` is a `HibernateProxy` subclass) — intercepts method calls, loads on first access.
- **Collection wrapper** (`PersistentBag`/`PersistentSet`) — intercepts `size()`, `iterator()`, etc.

**`LazyInitializationException: could not initialize proxy — no Session`** means the persistence context is already closed (typical: accessing a lazy association in a controller or `@Async` thread after the `@Transactional` method returned).

| Fix | When to use |
| :--- | :--- |
| `JOIN FETCH` in JPQL / `@EntityGraph` | Fetch association eagerly for this query only (preferred) |
| `@Transactional` on the caller (service) | Keep session open while building the response (beware long TX) |
| DTO projection (`select new com.example.UserDto(u.name, ...)`) | Avoid entity graph entirely |
| `spring.jpa.open-in-view=false` | Disable OSIV anti-pattern (see below) |

> **Open Session In View (OSIV)**: Spring Boot enables `spring.jpa.open-in-view=true` by default — the `EntityManager` stays open for the entire HTTP request (through the view). It hides `LazyInitializationException` but holds the DB connection for the whole request and masks N+1. Set `open-in-view=false` and fetch explicitly.

---

### 5. N+1 — The Classic Performance Trap

```java
// N+1: 1 query for orders + N queries for items
List<Order> orders = orderRepo.findAll(); // SELECT * FROM orders
for (Order o : orders) { o.getItems().size(); } // N × SELECT * FROM items WHERE order_id=?

// Fix 1: JOIN FETCH (JPQL)
@Query("SELECT DISTINCT o FROM Order o LEFT JOIN FETCH o.items")
List<Order> findAllWithItems();

// Fix 2: EntityGraph
@EntityGraph(attributePaths = "items")
List<Order> findAll();

// Fix 3: Batch fetching (application.yml)
spring.jpa.properties.hibernate.default_batch_fetch_size=16
// → Hibernate batches lazy loads: SELECT * FROM items WHERE order_id IN (?, ?, ..., ?)
```

Detect N+1 with `spring.jpa.properties.hibernate.stat=DEBUG`, `datasource-proxy`, or `p6spy` — look for a spike of identical queries.

---

### 6. Second-Level Cache and Query Cache

| Cache | Scope | What it caches | Invalidation |
| :--- | :--- | :--- | :--- |
| **First-level** (mandatory) | Per `EntityManager` / TX | Entities by id + snapshots | `clear()` / TX end |
| **Second-level** (opt-in, e.g., EhCache, Caffeine) | Per `SessionFactory` (cross-TX) | Entities by id, collections | TTL / explicit evict |
| **Query cache** (opt-in) | Per `SessionFactory` | JPQL result ids + timestamps | Any write to the queried table |

```java
@Entity @Cacheable @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
class Country { @Id String code; String name; } // reference data — good candidate

@QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
List<Country> findAllCached();
```

Second-level cache helps only for **read-mostly, shared reference data** — not for frequently written entities (cache invalidation cost > benefit). Most Spring Boot apps leave it **off** and rely on application-level caching (Redis — `@Cacheable`).

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Accessing `LAZY` outside TX | `LazyInitializationException` | `JOIN FETCH` / `@EntityGraph` / DTO projection; `open-in-view=false` |
| `equals`/`hashCode` using auto-generated `id` | Two new entities with `id=null` compare equal | Use business key in `equals`, or use `instanceof` + `id` check with `id != null` guard |
| `CascadeType.ALL` + `orphanRemoval=true` on `@OneToMany` | Deleting parent deletes all children unexpectedly | Use `CascadeType.PERSIST` / `MERGE` narrowly; enable `orphanRemoval` only when parent owns lifecycle |
| `findAll()` on large table | `OutOfMemoryError` — all rows in first-level cache | Paginate (`Pageable`), `Stream` with `flush`/`clear`, or use `JdbcTemplate` for bulk reads |
| N+1 hidden by OSIV | Latency spikes, DB overloaded with identical queries | Set `open-in-view=false`, test with Hibernate `STATISTICS`, add `JOIN FETCH` / batch size |

### Summary

- The **persistence context** is a per-transaction first-level cache + snapshot map + action queue — `find()` hits the cache, field changes are **dirty-checked** and flushed as SQL before commit/query.
- Entities cycle through **transient → managed → detached → removed**; `persist` vs `merge` maps to `save()`'s new-vs-existing check.
- `LAZY` uses **proxy / `PersistentBag`** wrappers; accessing outside the session throws `LazyInitializationException` — fix with `JOIN FETCH`/`@EntityGraph`/DTO, not by keeping OSIV open.
- **N+1** is fixed by fetch joins, entity graphs, or `default_batch_fetch_size`; the second-level cache is opt-in for read-mostly reference data only.

## 209. How do you test Spring Boot applications effectively? Explain test slices, `@MockBean` vs `@MockitoBean`, `MockMvc`/`WebTestClient`, and Testcontainers.

Spring Boot's test support is built to keep tests **fast and isolated** — loading only the slice of the context you need, mocking collaborators with `@MockitoBean`, and replacing infrastructure (DB, Kafka, Redis) with Docker containers via Testcontainers. Understanding test slices vs full `@SpringBootTest`, when mocks help vs hurt, and how Testcontainers brings real dependencies into tests is what separates unit-level from production-confident testing.

---

### 1. The Test Pyramid in Spring Boot

```
End-to-end (few)   →  @SpringBootTest + Testcontainers + real DB/browser  (slow, high confidence)
Integration (some) →  @WebMvcTest / @DataJpaTest / @SpringBootTest(webEnvironment=RANDOM_PORT)
Unit (many)        →  plain JUnit + Mockito, no Spring context              (fast, low confidence)
```

- **Unit** — no Spring, instantiate the class under test, mock dependencies. Milliseconds.
- **Slice** — load a *slice* of the context (web layer, JPA layer, etc.). Seconds.
- **Full** — load the entire `ApplicationContext` with real or container-backed dependencies. Tens of seconds — use sparingly.

---

### 2. Test Slices — Load Only What You Need

| Annotation | What it loads | Typical use |
| :--- | :--- | :--- |
| `@WebMvcTest(Controller.class)` | Controllers, `@ControllerAdvice`, `MockMvc`, `Jackson`, Security filter chain — **not** `@Service`/`@Repository` | Test controller routing, validation, serialization, Security |
| `@DataJpaTest` | JPA entities, `DataSource` (embedded H2 by default), `TestEntityManager`, `JpaRepository` | Test queries, mappings, `@EntityGraph` |
| `@DataJdbcTest` | JDBC + repositories | JDBC-based repos |
| `@RestClientTest(Service.class)` | `RestTemplate` / `RestClient` + Jackson | Test HTTP clients with `MockRestServiceServer` |
| `@JsonTest` | Jackson `ObjectMapper` | Test JSON serialization |
| `@SpringBootTest` | **Full** context | End-to-end, or when you need everything |

```java
@WebMvcTest(UserController.class)
class UserControllerTest {
    @Autowired MockMvc mockMvc;
    @MockitoBean UserService userService; // mock the service layer — controller is the SUT

    @Test
    void getUser_returns200() throws Exception {
        when(userService.findById(1L)).thenReturn(new User(1L, "alice"));
        mockMvc.perform(get("/users/1").accept(MediaType.APPLICATION_JSON))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.name").value("alice"));
        verify(userService).findById(1L);
    }
}

@DataJpaTest
class UserRepositoryTest {
    @Autowired TestEntityManager em;
    @Autowired UserRepository repo;

    @Test
    void findByEmail_usesIndex() {
        em.persist(new User("alice@example.com", "alice"));
        assertThat(repo.findByEmail("alice@example.com")).isPresent();
    }
}
```

`@MockitoBean` (Boot 3.4+, replaces deprecated `@MockBean`) registers a Mockito mock in the `ApplicationContext` so `@Autowired` injection points receive the mock.

---

### 3. `MockMvc` vs `WebTestClient` vs `TestRestTemplate` vs `RestAssured`

| Tool | Stack | Style | When to use |
| :--- | :--- | :--- | :--- |
| `MockMvc` | MVC (blocking) | No real HTTP — dispatches through `DispatcherServlet` | Slice tests for controllers, filters, interceptors |
| `WebTestClient` | WebFlux or MVC | Fluent, reactive assertions | WebFlux controllers, or `@SpringBootTest` with real server |
| `TestRestTemplate` / `RestClient` | Either | Real HTTP against `RANDOM_PORT` | Full integration with real server |
| `RestAssured` | Either | BDD `given/when/then` | E2E with expressive assertions |

```java
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class FullIntegrationTest {
    @Autowired TestRestTemplate rest;
    @Test void health() {
        var response = rest.getForEntity("/actuator/health", String.class);
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
    }
}

// WebTestClient (also works against MockMvc in MVC apps via @AutoConfigureMockMvc):

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| `@SpringBootTest` for every test | Suite takes minutes, flaky due to shared state | Use slices (`@WebMvcTest`, `@DataJpaTest`) for most tests; reserve full context for a few E2E |
| `@MockBean` overuse (now `@MockitoBean`) | Mocks hide real wiring errors; `NoSuchBeanDefinitionException` in prod | Prefer real beans for collaborators in integration tests; mock only at boundaries |
| H2 for Postgres-specific queries (`jsonb`, `ILIKE`) | Tests pass, prod fails — dialect mismatch | Use Testcontainers Postgres |
| Forgetting `@WithMockUser` on secured endpoint | `401` / `403` in `MockMvc` test | Add `@WithMockUser` or `SecurityMockMvcRequestPostProcessors.jwt()` |
| Shared mutable state between tests | Order-dependent failures | Keep tests stateless; use `@DirtiesContext` sparingly, prefer `@Transactional` rollback or Testcontainers per class |
| Not flushing in JPA test | Constraint violation only appears at commit, not in test | Call `em.flush()` explicitly before assertions |

### Summary

- **Test pyramid:** many plain unit tests (no Spring), some **slice tests** (`@WebMvcTest`/`@DataJpaTest` — fast, partial context), few full `@SpringBootTest` + Testcontainers E2E (slow, high confidence).
- `MockMvc` dispatches through `DispatcherServlet` without real HTTP; `WebTestClient`/`TestRestTemplate`/`RestAssured` hit a real `RANDOM_PORT` server.
- `@MockitoBean` (replaces `@MockBean`) injects mocks into the context; mock at boundaries (external HTTP), use real DB via **Testcontainers** + `@ServiceConnection` for persistence tests.
- `@Transactional` tests roll back by default — good for isolation but call `flush()` to surface commit-time errors; Testcontainers gives production-parity without H2 dialect gaps.

## 210. How does caching work in Spring Boot? Explain `@Cacheable`, `CacheManager`, Caffeine vs Redis, cache patterns, and pitfalls.

Caching trades memory for latency — Spring's `spring-cache` abstraction decouples the declarative `@Cacheable` API from the backing store (in-memory Caffeine, distributed Redis, or simple `ConcurrentMap`). Understanding the AOP proxy that intercepts cache calls, the `CacheManager` / `Cache` SPI, and the consistency trade-offs between local and distributed caches explains thundering-herd protection, eviction, and why `@Cacheable` on a `private` method never works.

---

### 1. Declarative Caching — Proxy-Based AOP

```java
@Configuration @EnableCaching
class CacheConfig { }

@Service
class UserService {
    @Cacheable(value = "users", key = "#id")               // cache on first call, return cached after
    public User findById(long id) { return repo.findById(id).orElseThrow(); }

    @CachePut(value = "users", key = "#result.id")          // always execute, then update cache
    public User update(User user) { return repo.save(user); }

    @CacheEvict(value = "users", key = "#id")               // remove entry
    public void delete(long id) { repo.deleteById(id); }

    @CacheEvict(value = "users", allEntries = true)         // clear entire cache
    public void clearAll() { }

    @Caching(cacheable = @Cacheable("users"), put = @CachePut(value = "usersByEmail", key = "#result.email"))
    public User findOrCreate(long id) { ... }
}
```

```
Client → Proxy (CacheInterceptor) → Cache lookup (key = SpEL evaluation)
         ├─ hit  → return cached value (target not called)
         └─ miss → invoke target → put result in cache → return
```

Same AOP mechanics as `@Transactional` (Q202–Q204): proxy via `BeanPostProcessor` in `postProcessAfterInitialization`. Only `public` methods called **through the proxy** are cached — self-invocation (`this.findById()`) bypasses the cache.

> Key SpEL: `#id`, `#result`, `#root.methodName`, `condition = "#id > 0"`, `unless = "#result == null"` (don't cache nulls).

---

### 2. `CacheManager` and `Cache` — The SPI

```java
interface CacheManager { Cache getCache(String name); Collection<String> getCacheNames(); }
interface Cache {
    ValueWrapper get(Object key);
    void put(Object key, Object value);
    void evict(Object key);
    void clear();
}
```

| Manager | Backing store | Dependency |
| :--- | :--- | :--- |
| `ConcurrentMapCacheManager` | `ConcurrentHashMap` | No extra dep — default in Boot |
| `CaffeineCacheManager` | Caffeine (W-TinyLFU, bounded, expiration) | `com.github.ben-manes.caffeine:caffeine` |
| `RedisCacheManager` | Redis (distributed) | `spring-boot-starter-data-redis` |
| `EhCacheCacheManager` / `JCacheCacheManager` | EhCache / JSR-107 | `net.sf.ehcache:ehcache` |

```java
// Caffeine (local, per-JVM):
@Bean CacheManager cacheManager() {
    CaffeineCacheManager m = new CaffeineCacheManager("users", "products");
    m.setCaffeine(Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(Duration.ofMinutes(10)).recordStats());
    return m;
}

// Redis (distributed, shared across instances):
@Bean RedisCacheManager cacheManager(RedisConnectionFactory cf) {
    RedisCacheConfiguration conf = RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(5))
        .serializeKeysWith(SerializationPair.fromSerializer(new StringRedisSerializer()))
        .serializeValuesWith(SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer()));
    return RedisCacheManager.builder(cf).cacheDefaults(conf).build();
}
```

Spring Boot auto-configures the manager: if `Caffeine` is on the classpath, it picks `CaffeineCacheManager`; if `Redis` is configured, it picks `RedisCacheManager` — governed by `@ConditionalOnClass` (Q205).

---

### 3. Caffeine vs Redis — Local vs Distributed

| Aspect | Caffeine (local) | Redis (distributed) |
| :--- | :--- | :--- |
| **Scope** | Per JVM instance — each pod has its own cache | Shared across all instances |
| **Latency** | ~10–100 ns (in-process) | ~0.5–2 ms (network RTT) |
| **Consistency** | No cross-instance invalidation — stale reads across pods until TTL | Consistent — one source of truth |
| **Memory** | Bounded by `maximumSize` + `expireAfterWrite` | Bounded by Redis `maxmemory` + eviction policy |
| **Eviction** | W-TinyLFU (high hit rate) + TTL/TTI | TTL + LRU/LFU (`maxmemory-policy`) |
| **Best for** | Reference data, hot keys, per-instance computed results | Shared sessions, rate limiting, cross-instance coordination |

**Two-level (multi-tier) caching:**

```java
// Caffeine L1 (local) + Redis L2 (distributed) via custom CacheManager or spring-cache-plus:
Cache (L1 Caffeine, 30s TTL) → on miss → Cache (L2 Redis, 5m TTL) → on miss → DB
// On write: evict/invalidate both levels; or use Redis pub/sub to broadcast invalidation
```

---

### 4. Cache Patterns and Consistency

| Pattern | Flow | Consistency |
| :--- | :--- | :--- |
| **Cache-aside** (Spring default) | App checks cache → on miss loads from DB and puts | Eventual — stale until TTL/evict |
| **Write-through** (`@CachePut`) | App writes to cache and DB in one call | Stronger — but still needs eviction on external DB writes |
| **Write-behind** | App writes to cache, async flush to DB | Fast, but risk of data loss on crash — rare in Spring |
| **Read-through** | Cache loader loads on miss transparently | Similar to cache-aside, via `CacheLoader` (Caffeine) |

For strong consistency across instances with Redis, pair TTL with explicit invalidation:

```java
@Transactional
public User updateUser(long id, String name) {
    User u = repo.save(new User(id, name)); // DB write
    cacheManager.getCache("users").evict(id); // or @CacheEvict — ensure eviction after commit
    // Better: use @CacheEvict + TransactionSynchronization.afterCommit to avoid evicting before commit
    return u;
}
```

> Tie eviction to **after commit** (`@TransactionalEventListener(phase = AFTER_COMMIT)` or `TransactionSynchronization`) so a rolled-back transaction doesn't leave a stale cache.

---

### 5. Thundering Herd, Null Caching, and Stampede Protection

```java
// Without protection: 100 concurrent requests for same missing key → 100 DB queries
@Cacheable(value = "users", key = "#id", sync = true) // sync = true → one thread loads, others block
public User findById(long id) { return repo.findById(id).orElseThrow(); }

// Don't cache nulls (avoid cache penetration from random ids):
@Cacheable(value = "users", key = "#id", unless = "#result == null")
public User findByIdOrNull(long id) { return repo.findById(id).orElse(null); }

// For Redis: set a short TTL for nulls ("negative cache") instead of permanent miss:
@Cacheable(value = "users", key = "#id")
public User findById(long id) {
    return repo.findById(id).orElse(null); // cache null with 30s TTL via Redis config
}
```

Caffeine's `refreshAfterWrite` (async reload) keeps hot entries fresh without blocking readers.

---

### 6. Observability and Tuning

```java
// Caffeine stats via Micrometer / Actuator:
management.endpoints.web.exposure.include=metrics,caches
management.metrics.cache.enabled=true
// Endpoints:
GET /actuator/caches          // cache names + sizes
GET /actuator/metrics/cache.gets  // hit/miss metrics (if recordStats() enabled)

// Redis monitoring:
redis-cli --latency
redis-cli info stats          // evicted_keys, keyspace_hits/misses
```

Tune `maximumSize` to fit heap (each entry ~100–500 bytes + value), and set TTL based on **freshness SLA** (e.g., product catalog 10m, user profile 1m). Monitor `hitRate = hits / (hits + misses)` — below 80% suggests wrong TTL or too-small cache.

---

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| `@Cacheable` on `private`/`final` or self-invoked method | Never cached — proxy bypass (Q202) | Make method `public` non-final, call through Spring proxy |
| Caching mutable objects | Caller mutates cached instance → all readers see corruption | Cache immutable copies / DTOs, or `List.copyOf(value)` before caching |
| No TTL (unbounded `ConcurrentMapCache`) | `OutOfMemoryError` as cache grows forever | Always set `maximumSize` + `expireAfterWrite` (Caffeine) or TTL (Redis) |
| Stale reads across instances with local cache | Instance A updates DB, instance B serves stale Caffeine entry | Use Redis for shared cache, or broadcast invalidation via Redis pub/sub / Kafka |
| Thundering herd on cold start | DB spike when cache is empty | Use `sync = true` (single loader), or warm cache on startup |
| Caching `null` permanently | Random id probes fill cache with nulls, or legitimate new rows never appear | `unless = "#result == null"` or negative cache with short TTL |

### Summary

- Spring caching is **AOP proxy-based** (`CacheInterceptor` → `CacheManager.getCache` → `Cache.get/put`) — same proxy rules as `@Transactional`: only `public` proxy calls are cached, self-invocation bypasses.
- `CacheManager` abstracts the store: `ConcurrentMapCacheManager` (default), `CaffeineCacheManager` (bounded local, W-TinyLFU), `RedisCacheManager` (distributed, shared) — Boot picks via `@ConditionalOnClass`.
- **Caffeine** is nanosecond-local but per-JVM (stale across pods); **Redis** is millisecond-distributed but consistent — two-level (Caffeine L1 + Redis L2) combines both.
- Prevent herds with `sync = true`, avoid permanent null caching with `unless`, evict **after commit**, and expose metrics via `/actuator/caches` + Micrometer (`recordStats()`).

## 211. How do `@Async` and `@Scheduled` work in Spring? Explain thread-pool executors, proxy-based async dispatch, scheduling modes, and error handling.

`@Async` and `@Scheduled` turn ordinary Spring beans into concurrent and periodic task runners — both via the same proxy-based AOP that powers `@Transactional` and `@Cacheable` (Q202–Q204, Q210). Understanding the underlying `TaskExecutor` / `TaskScheduler`, the proxy that offloads calls to a thread pool, and the cron/fixed-rate semantics explains thread starvation, self-invocation bypass, and why blocking code in a virtual-thread executor needs different tuning.

---

### 1. `@Async` — Fire-and-Forget (or Future-Based) Execution

```java
@Configuration @EnableAsync
class AsyncConfig implements AsyncConfigurer {
    @Bean(name = "ioExecutor")
    public Executor ioExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(20);
        ex.setMaxPoolSize(100);
        ex.setQueueCapacity(500);
        ex.setThreadNamePrefix("io-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.initialize();
        return ex;
    }
    @Override public Executor getAsyncExecutor() { return ioExecutor(); }
    @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> log.error("async failed: " + method, ex);
    }
}

@Service
class EmailService {
    @Async("ioExecutor")                          // runs on ioExecutor thread pool
    public CompletableFuture<Void> sendAsync(String to, String body) {
        mailSender.send(to, body);                // blocking I/O — off the MVC thread
        return CompletableFuture.completedFuture(null);
    }

    @Async
    public void fireAndForget(String event) {     // void — caller doesn't wait
        eventBus.publish(event);
    }
}
```

```
Client → Proxy (AsyncExecutionInterceptor) → submits Callable to TaskExecutor
         ↳ returns immediately (Future/CompletableFuture or void)
                                           ↳ target method runs on pool thread
```

Return types:

| Signature | What caller gets | Error propagation |
| :--- | :--- | :--- |
| `void` | Nothing — fire-and-forget | Via `AsyncUncaughtExceptionHandler` (uncaught exception lost without it) |
| `Future<T>` / `CompletableFuture<T>` | Future that completes on pool thread | `future.get()` throws `ExecutionException`; `CompletableFuture` exceptionally |
| `ListenableFuture<T>` (deprecated) | Spring's old future | — |

> Only `public` methods called **through the Spring proxy** are async — self-invocation (`this.sendAsync()`) runs synchronously on the caller thread (same proxy bypass as Q202/Q204/Q210).

---

### 2. The Executor — Where Threads Come From

```java
// ThreadPoolTaskExecutor wraps java.util.concurrent.ThreadPoolExecutor (Q190):
ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
ex.setCorePoolSize(10);      // always kept alive
ex.setMaxPoolSize(50);       // created under load when queue is full
ex.setQueueCapacity(200);    // LinkedBlockingQueue size
ex.setKeepAliveSeconds(60);  // extra threads beyond core are reaped
ex.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy()); // or CallerRunsPolicy
ex.setTaskDecorator(r -> {   // propagate MDC / SecurityContext / ScopedValue
    Map<String,String> mdc = MDC.getCopyOfContextMap();
    return () -> { try { MDC.setContextMap(mdc); r.run(); } finally { MDC.clear(); } };
});
```

| Pool behavior | When it happens |
| :--- | :--- |
| Thread count < `corePoolSize` | New thread per task |
| `corePoolSize` ≤ threads < `maxPoolSize`, queue full | New thread per task |
| Threads == `maxPoolSize`, queue full | `RejectedExecutionHandler` kicks in |

**Choosing sizes:**

- **CPU-bound** (`compute()`, JSON parsing): `core ≈ Ncpu`, `max ≈ Ncpu`, small queue.
- **I/O-bound** (HTTP, JDBC, mail): `core ≈ 20–50`, `max ≈ 100–200`, larger queue, or — since Java 21 — use `Executors.newVirtualThreadPerTaskExecutor()` as the `@Async` executor to avoid pool sizing altogether.

```java
@Bean Executor asyncExecutor() {
    return Executors.newVirtualThreadPerTaskExecutor(); // virtual threads — no pool tuning needed (Q195)
}
```

---

### 3. `@Scheduled` — Declarative Periodic Tasks

```java
@Configuration @EnableScheduling
class SchedulingConfig implements SchedulingConfigurer {
    @Override public void configureTasks(ScheduledTaskRegistrar r) {
        r.setScheduler(taskScheduler()); // custom scheduler, else single-thread default
    }
    @Bean TaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler s = new ThreadPoolTaskScheduler();
        s.setPoolSize(4);
        s.setThreadNamePrefix("sched-");
        s.setErrorHandler(t -> log.error("scheduled task failed", t));
        return s;
    }
}

@Component
class ReportJob {
    @Scheduled(fixedRate = 60_000)                // every 60s from start of previous execution
    void everyMinute() { generateReport(); }

    @Scheduled(fixedDelay = 30_000)               // 30s after previous execution *completes*
    void withDelay() { cleanup(); }

    @Scheduled(fixedDelayString = "${jobs.cleanup.delay:30000}")
    void configurableDelay() { }

    @Scheduled(cron = "0 0 2 * * MON-FRI", zone = "Europe/Paris") // 2am weekdays
    void nightly() { sendDigest(); }

    @Scheduled(cron = "${jobs.nightly.cron:-}", zone = "UTC")
    void conditionalCron() { } // if property missing, cron = "-" → disabled
}
```

| Attribute | Semantics | Overlap |
| :--- | :--- | :--- |
| `fixedRate` | Period measured from **start** of last execution | **Can overlap** — next run starts even if previous still running (needs pool size >1) |
| `fixedDelay` | Delay measured from **end** of last execution | **No overlap** — next run waits for previous to finish + delay |
| `cron` | Cron expression (6 fields with seconds: `sec min hour day month weekday`) | Depends on execution time vs schedule |

```java
// Prevent overlap explicitly:
@Scheduled(fixedRate = 5000)
@SchedulerLock(name = "reportJob", lockAtMostFor = "10m") // ShedLock — distributed lock via DB/Redis
void lockedJob() { ... }
```

The default `TaskScheduler` is **single-threaded** — one slow `@Scheduled` task blocks all others. Always configure a `ThreadPoolTaskScheduler` with `poolSize ≥ number of scheduled jobs that may overlap`.

---

### 4. Context Propagation — MDC, Security, Transactions

`@Async` runs on a **different thread** — `ThreadLocal` state is **not** propagated by default:

| Context | Propagated? | Fix |
| :--- | :--- | :--- |
| `MDC` (SLF4J logging) | No | `TaskDecorator` that copies `MDC.getCopyOfContextMap()` (see §2) |
| `SecurityContext` | No | `DelegatingSecurityContextAsyncTaskExecutor` or `TaskDecorator` with `SecurityContextHolder` |
| `Transaction` (`@Transactional`) | No | Put `@Transactional` **inside** the `@Async` method — new thread starts its own TX (Q204) |
| `ScopedValue` (Java 21+) | No (by design) | Bind explicitly: `ScopedValue.where(CTX, v).run(() -> asyncMethod())` or use `StructuredTaskScope` |

```java
@Async
@Transactional // new transaction on the async thread
public void asyncWithTx(Order order) { orderRepo.save(order); }
```

---

### 5. Error Handling

```java
// void @Async — exception is swallowed unless you set AsyncUncaughtExceptionHandler:
@Async
public void voidAsync() { throw new RuntimeException("lost without handler"); }

// Future-returning @Async — exception is captured in the Future:
@Async
public CompletableFuture<String> futureAsync() {
    if (fail) throw new RuntimeException("captured");
    return CompletableFuture.completedFuture("ok");
}
// Caller:
futureAsync().exceptionally(ex -> { log.error("failed", ex); return "fallback"; });

// @Scheduled — exception is logged by TaskScheduler's ErrorHandler, but does NOT stop future executions:
@Scheduled(fixedRate = 5000)
void scheduled() {
    try { doWork(); }
    catch (Exception e) { log.error("scheduled failed, will retry next tick", e); }
}
```

Always set `AsyncUncaughtExceptionHandler` and `TaskScheduler.setErrorHandler` — otherwise failures are silent.

### 6. Testing Async and Scheduled Tasks

```java
@SpringBootTest
class AsyncTest {
    @Autowired EmailService emailService;
    @SpyBean MailSender mailSender; // real bean, spy on method calls

    @Test
    void asyncSendsEmail() throws Exception {
        CompletableFuture<Void> f = emailService.sendAsync("a@b.com", "hi");
        f.get(5, TimeUnit.SECONDS); // await async completion
        verify(mailSender).send("a@b.com", "hi");
    }
}

// For @Scheduled in tests — disable or await:
@TestPropertySource(properties = "scheduling.enabled=false") // gate with @ConditionalOnProperty

// Or use Awaitility:
await().atMost(Duration.ofSeconds(5)).untilAsserted(() -> assertThat(repo.count()).isGreaterThan(0));
```

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Self-invocation `@Async` / `@Scheduled` on `private`/`final` | Runs synchronously on caller thread, never async/scheduled | Make method `public` non-final, call through Spring proxy |
| Single-thread default scheduler | One slow job blocks all scheduled tasks | Configure `ThreadPoolTaskScheduler` with `poolSize` ≥ concurrent jobs |
| `void @Async` exception swallowed | Failure invisible, no log | Set `AsyncUncaughtExceptionHandler`; prefer `CompletableFuture` return |
| Blocking I/O on small `corePoolSize` | Pool exhausted, `RejectedExecutionException` or `CallerRunsPolicy` blocks MVC thread | Size pool for I/O-bound (larger core/max/queue), or use virtual-thread executor (Java 21+) |
| `@Transactional` on caller, `@Async` on callee expecting same TX | Async method has no transaction (ThreadLocal not propagated) | Put `@Transactional` inside the `@Async` method |
| `fixedRate` overlapping without protection | Same job runs concurrently, data race | Use `fixedDelay`, or distributed lock via ShedLock, or make job idempotent |

### Summary

- `@Async` and `@Scheduled` are **AOP proxies** (`AsyncExecutionInterceptor` / `ScheduledAnnotationBeanPostProcessor`) — only `public` proxy calls are async/scheduled; self-invocation bypasses.
- `@Async` offloads to a `TaskExecutor` (`ThreadPoolTaskExecutor` wrapping `ThreadPoolExecutor` — core/max/queue/rejection policy); `void` needs `AsyncUncaughtExceptionHandler`, `CompletableFuture` captures exceptions.
- `@Scheduled` runs on a `TaskScheduler` — default is single-threaded, so configure `ThreadPoolTaskScheduler`; `fixedRate` can overlap, `fixedDelay` cannot, `cron` adds calendar semantics.
- `ThreadLocal` state (MDC, `SecurityContext`, transactions) is **not** propagated to async/scheduled threads — use `TaskDecorator`, `DelegatingSecurityContextExecutor`, or put `@Transactional` inside the async method.

## 212. How does messaging with Kafka work in Spring Boot? Explain producers, consumers, reliability, and Spring Kafka (`KafkaTemplate` / `@KafkaListener`).

Apache Kafka is the de facto distributed log for event-driven microservices — a partitioned, replicated, append-only commit log that decouples producers from consumers via topics. Spring Kafka (`spring-kafka`) wraps the native `KafkaProducer`/`KafkaConsumer` with `KafkaTemplate`, `@KafkaListener`, and Spring-managed transactions, adding serialization, error handling (`DeadLetterPublishingRecoverer`), and observability. Understanding producer acks, consumer groups/offsets, and exactly-once semantics explains most Kafka interview questions.

---

### 1. Core Concepts — Topics, Partitions, and the Log

```
Producer → Topic (e.g., orders) → [ Partition 0 | Partition 1 | Partition 2 ] → Consumers (group: order-service)
                                   append-only log per partition, ordered by offset
                                   replication factor 3 → leader + 2 followers (ISR)
```

| Concept | Meaning |
| :--- | :--- |
| **Topic** | Named log (e.g., `orders`, `payments`) |
| **Partition** | Ordered, append-only segment of a topic — unit of parallelism |
| **Offset** | Monotonic index within a partition |
| **Producer** | Appends records (`key`, `value`, headers) to a partition (by key hash or round-robin) |
| **Consumer group** | Set of consumers that share partitions — each partition is consumed by **one** member of a group; different groups get all partitions (fan-out) |
| **Offset commit** | Consumer's position — committed to `__consumer_offsets` topic (auto or manual) |
| **Replication / ISR** | In-Sync Replicas that have caught up — `acks` controls durability |

```bash
# Create topic:
kafka-topics --create --topic orders --partitions 6 --replication-factor 3 --bootstrap-server kafka:9092
```

---

### 2. Producer — `KafkaTemplate` and Reliability

```java
@Configuration
class KafkaConfig {
    @Bean ProducerFactory<String, Order> producerFactory() {
        Map<String,Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);
        props.put(ProducerConfig.ACKS_CONFIG, "all");          // wait for ISR
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true); // exactly-once per producer session
        props.put(ProducerConfig.RETRIES_CONFIG, 3);
        props.put(ProducerConfig.LINGER_MS_CONFIG, 10);         // batch up to 10ms
        return new DefaultKafkaProducerFactory<>(props);
    }
    @Bean KafkaTemplate<String, Order> kafkaTemplate(ProducerFactory<String, Order> pf) {
        return new KafkaTemplate<>(pf);
    }
}

@Service
class OrderProducer {
    private final KafkaTemplate<String, Order> kafka;
    CompletableFuture<SendResult<String, Order>> send(Order order) {
        // key = orderId → same key always lands on same partition (ordering per key)
        return kafka.send("orders", order.getId(), order);
    }
}
```

| `acks` | Durability | Latency | Use |
| :--- | :--- | :--- | :--- |
| `0` | Fire-and-forget — may lose data | Lowest | Metrics, logs where loss is OK |
| `1` | Leader ack only — survives leader failure only if follower already replicated | Medium | Default, balanced |
| `all` / `-1` | Wait for **all ISR** — survives `min.insync.replicas - 1` broker failures | Highest | Orders, payments — don't lose data |

`enable.idempotence=true` (requires `acks=all`, `retries>0`, `max.in.flight=5`) deduplicates retries via producer id + sequence — **exactly-once per partition within a producer session** (no duplicates from retries).

### 3. Consumer — `@KafkaListener` and Consumer Groups

```java
@Component
class OrderConsumer {
    @KafkaListener(topics = "orders", groupId = "order-service",
                   concurrency = "3", // 3 threads → 3 partitions in parallel
                   properties = "auto.offset.reset=earliest")
    void handle(Order order, @Header(KafkaHeaders.RECEIVED_KEY) String key,
                Acknowledgment ack) {
        process(order);
        ack.acknowledge(); // manual commit — only if AckMode.MANUAL
    }
}

@Configuration
class ConsumerConfig {
    @Bean ConsumerFactory<String, Order> consumerFactory() {
        Map<String,Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-service");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, JsonDeserializer.class);
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(JsonDeserializer.TRUSTED_PACKAGES, "com.example");
        return new DefaultKafkaConsumerFactory<>(props);
    }
    @Bean ConcurrentKafkaListenerContainerFactory<String, Order> factory(ConsumerFactory<String, Order> cf) {
        var f = new ConcurrentKafkaListenerContainerFactory<String, Order>();
        f.setConsumerFactory(cf);
        f.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
        f.setCommonErrorHandler(new DefaultErrorHandler(
            new DeadLetterPublishingRecoverer(kafkaTemplate(), (r, e) -> new TopicPartition("orders.DLT", 0)),
            new FixedBackOff(1000L, 3L))); // 3 retries with 1s backoff → then DLT
        return f;
    }
}
```

**Group semantics:**

```
Topic orders — 6 partitions
Group order-service: 3 consumers → each gets 2 partitions (load-balanced, rebalanced on join/leave)
Group analytics:     1 consumer  → gets all 6 partitions (fan-out — both groups see all messages)
```

| AckMode | When offset is committed |
| :--- | :--- |
| `BATCH` (default) | After each `poll()` batch |
| `RECORD` | After each record |
| `MANUAL` / `MANUAL_IMMEDIATE` | When you call `ack.acknowledge()` — needed for transactional / at-least-once control |

---

### 4. Delivery Semantics — At-Most-Once vs At-Least-Once vs Exactly-Once

| Semantics | How to achieve | Trade-off |
| :--- | :--- | :--- |
| **At-most-once** | `enable.auto.commit=true`, auto commit before processing | May lose message if crash after commit, before processing |
| **At-least-once** (default, recommended) | Manual ack **after** processing; `acks=all` on producer | May reprocess on crash/rebalance — make consumer **idempotent** |
| **Exactly-once** | Transactional producer (`transactional.id`) + `isolation.level=read_committed` on consumer + consume-transform-produce in one TX | Requires Kafka transactions (see §5), slower |

Idempotent consumer pattern:

```java
@KafkaListener(topics = "orders")
void handle(Order order) {
    if (processedRepo.existsById(order.getId())) return; // dedup by business key
    process(order);
    processedRepo.save(new Processed(order.getId()));
}
```

---

### 5. Transactions — Consume-Transform-Produce Exactly Once

```java
@Configuration @EnableTransactionManagement
class TxKafkaConfig {
    @Bean ProducerFactory<String, Order> pf() {
        DefaultKafkaProducerFactory<String, Order> pf = new DefaultKafkaProducerFactory<>(producerProps());
        pf.setTransactionIdPrefix("tx-"); // enables transactions
        return pf;
    }
    @Bean KafkaTransactionManager<String, Order> txManager(ProducerFactory<String, Order> pf) {
        return new KafkaTransactionManager<>(pf);
    }
}

@Service
class OrderPipeline {
    @Transactional("kafkaTransactionManager") // ChainedKafkaTransactionManager for DB+Kafka
    @KafkaListener(topics = "orders", groupId = "pipeline")
    void transform(Order order) {
        Order enriched = enrich(order);
        kafkaTemplate.send("orders-enriched", enriched.getId(), enriched); // part of same TX
        // offsets are committed transactionally — no lost or duplicate produce
    }
}
```

With `isolation.level=read_committed`, downstream consumers don't see aborted transactional records.

For **DB + Kafka** atomicity, use `ChainedKafkaTransactionManager` (or the newer `KafkaTransactionManager` with `transactional.id` + outbox pattern). The outbox pattern (write event to DB table in the same DB TX, then relay to Kafka via Debezium/CDC) is often preferred over XA.

### 6. Error Handling — Retries, DLT, and Backpressure

```java
// Non-blocking retry via dedicated retry topic (Spring Kafka 2.8+):
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 2.0),
                dltStrategy = DltStrategy.FAIL_ON_ERROR,
                autoCreateTopics = "false")
@KafkaListener(topics = "orders")
void handleWithRetry(Order order) { process(order); }
// After 4 attempts → forwarded to orders-retry-... → finally orders-dlt

// Blocking retry (DefaultErrorHandler) — pauses partition during backoff:
factory.setCommonErrorHandler(new DefaultErrorHandler(
    new DeadLetterPublishingRecoverer(kafkaTemplate),
    new FixedBackOff(1000L, 3L)));
```

Monitor consumer lag: `kafka-consumer-groups --describe --group order-service` — `LAG` is the key metric; alert if growing.

### 7. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Not setting `acks=all` for critical data | Message loss on broker failure | `acks=all` + `min.insync.replicas=2` on broker |
| `auto.offset.reset=latest` on new group | Misses existing messages | Use `earliest` for new consumers that need history |
| Large `max.poll.interval.ms` exceeded by slow processing | Consumer kicked from group, rebalance storm | Increase `max.poll.interval.ms`, or offload work via `CompletableFuture` + `pause`/`resume` |
| Non-idempotent consumer with at-least-once | Duplicate side effects on retry/rebalance | Dedup by business key (idempotent consumer) or transactional consume |
| Sharing one `KafkaTemplate` without `transactional.id` for exactly-once | Duplicates from producer retries | `enable.idempotence=true` for per-session; `transactional.id` prefix for cross-session |
| Forgetting `JsonDeserializer.TRUSTED_PACKAGES` | `IllegalArgumentException: The class is not in the trusted packages` | Set `spring.kafka.consumer.properties.spring.json.trusted.packages=com.example` |

### Summary

- Kafka is a **partitioned, replicated commit log** — topics split into partitions (parallelism/ordering per key), consumed by groups (one member per partition, fan-out across groups), with offsets in `__consumer_offsets`.
- Producer reliability is `acks` (0/1/all) + `enable.idempotence` (dedup retries) + `linger.ms` batching via `KafkaTemplate`; consumer is `@KafkaListener` with `concurrency` and `AckMode` (manual for control).
- **At-least-once** (manual ack after processing + idempotent consumer) is the pragmatic default; **exactly-once** needs transactional `transactional.id` + `read_committed`.
- Error handling uses `DefaultErrorHandler` / `@RetryableTopic` → **DLT** (`DeadLetterPublishingRecoverer`); monitor **consumer lag** and set `acks=all` + `min.insync.replicas` for durability.

## 213. How do you build resilience in Spring Boot microservices? Explain retry, circuit breaker, bulkhead, and rate limiter with Resilience4j.

Microservices fail independently — a slow downstream can cascade and take down the entire call graph. Resilience4j (the successor to Netflix Hystrix, auto-configured via `spring-boot-starter-aop` + `resilience4j-spring-boot3`) provides **retry, circuit breaker, bulkhead, rate limiter, and time limiter** as declarative AOP annotations that wrap any Spring bean method. Understanding their state machines, thread-pool isolation, and fallback composition explains most resilience interview questions.

---

### 1. The Five Resilience4j Patterns at a Glance

| Pattern | Problem it solves | How it works |
| :--- | :--- | :--- |
| **Retry** | Transient failures (network blip) | Re-invoke the method N times with backoff |
| **Circuit Breaker** | Cascading failures from a repeatedly failing downstream | Trip open after failure threshold → fail fast without calling downstream |
| **Bulkhead** | Thread-pool exhaustion from one slow dependency | Isolate concurrency with semaphore or thread-pool bulkhead |
| **Rate Limiter** | Overload from too many callers | Token-bucket — reject or wait when limit exceeded |
| **Time Limiter** | Hanging calls that never return | Timeout via `CompletableFuture` / virtual thread |

```java
// All patterns are applied via AOP — same proxy mechanism as @Transactional (Q204):
@Service
class PaymentService {
    @CircuitBreaker(name = "payment", fallbackMethod = "fallback")
    @Retry(name = "payment")
    @Bulkhead(name = "payment", type = Bulkhead.Type.SEMAPHORE)
    @RateLimiter(name = "payment")
    public PaymentResult charge(Order order) { return paymentClient.charge(order); }

    PaymentResult fallback(Order order, Exception ex) { return PaymentResult.degraded(order); }
}
```

Order (outermost → innermost): `RateLimiter` → `Bulkhead` → `CircuitBreaker` → `Retry` → `TimeLimiter` → target. Configure with `resilience4j.circuitbreaker.configs.*.registerHealthIndicator=true` to expose health.

---

### 2. Retry — Exponential Backoff for Transient Failures

```yaml
resilience4j.retry.configs.default:
  max-attempts: 3
  wait-duration: 200ms
  enable-exponential-backoff: true
  exponential-backoff-multiplier: 2   # 200ms → 400ms → 800ms
  retry-exceptions:
    - java.net.ConnectException
    - java.util.concurrent.TimeoutException
  ignore-exceptions:
    - com.example.BusinessValidationException # don't retry business errors
```

```java
@Retry(name = "payment", fallbackMethod = "fallback")
public PaymentResult charge(Order order) { return client.charge(order); }
```

- Retry is **synchronous** — the caller thread blocks during backoff. For non-blocking, combine with `@Async` or `CompletableFuture`.
- Always make retried operations **idempotent** (use idempotency key) — otherwise retries create duplicates.

---

### 3. Circuit Breaker — Fail Fast When Downstream Is Sick

```
State machine:

  CLOSED (normal) ── failure rate ≥ threshold ──► OPEN (fail fast, no calls)
     ▲                                              │
     │  success rate ≥ threshold in half-open       │ after waitDurationInOpenState
     └──────────────────────────────────────────────┘
                        HALF_OPEN (probe: allow N calls to test recovery)
```

```yaml
resilience4j.circuitbreaker.configs.default:
  sliding-window-type: COUNT_BASED
  sliding-window-size: 10              # last 10 calls
  failure-rate-threshold: 50           # open if ≥50% failed
  slow-call-rate-threshold: 80
  slow-call-duration-threshold: 2s
  wait-duration-in-open-state: 30s     # stay open 30s before probing half-open
  permitted-number-of-calls-in-half-open-state: 3
  minimum-number-of-calls: 5           # don't evaluate until 5 calls
  automatic-transition-from-open-to-half-open-enabled: true
```

```java
@CircuitBreaker(name = "inventory", fallbackMethod = "inventoryFallback")
public Stock checkStock(String sku) { return inventoryClient.check(sku); }

Stock inventoryFallback(String sku, CallNotPermittedException ex) {
    // circuit is OPEN — return cached / degraded response without calling downstream
    return Stock.unknown(sku);
}
Stock inventoryFallback(String sku, Exception ex) { return Stock.unknown(sku); }
```

**Key metrics** (via `/actuator/circuitbreakers` + Micrometer): `state`, `failureRate`, `slowCallRate`, `bufferedCalls`. Alert on `state == OPEN`.

---

### 4. Bulkhead — Isolate Concurrency

| Type | How it limits | Thread model | When to use |
| :--- | :--- | :--- | :--- |
| **Semaphore** (`SEMAPHORE`) | Max concurrent calls via `Semaphore` counter — caller thread executes | No extra thread pool — lightweight | In-process limiting, fast calls |
| **Thread-pool** (`THREADPOOL`) | Dedicated `ThreadPoolExecutor` per bulkhead — caller thread queues | Extra thread hop | Slow I/O that must not block caller (e.g., legacy blocking client) |

```yaml
resilience4j.bulkhead.configs.default:
  max-concurrent-calls: 20
  max-wait-duration: 10ms  # how long to wait for a permit before BulkheadFullException

resilience4j.thread-pool-bulkhead.configs.default:
  core-thread-pool-size: 10
  max-thread-pool-size: 20
  queue-capacity: 50
```

```java
@Bulkhead(name = "catalog", type = Bulkhead.Type.SEMAPHORE, fallbackMethod = "catalogFallback")
public Catalog getCatalog(String id) { return catalogClient.get(id); }
```

Bulkhead prevents one slow downstream from consuming all MVC threads (Q206) — the classic thread-pool starvation problem.

---

### 5. Rate Limiter — Token Bucket

```yaml
resilience4j.ratelimiter.configs.default:
  limit-for-period: 100        # 100 permits
  limit-refresh-period: 1s     # per second
  timeout-duration: 0          # fail immediately if no permit (0 = no wait)
```

```java
@RateLimiter(name = "search", fallbackMethod = "rateLimitedFallback")
public SearchResult search(String q) { return searchClient.query(q); }

SearchResult rateLimitedFallback(String q, RequestNotPermitted ex) {
    return SearchResult.throttled(q);
}
```

Rate limiter is **client-side** (per instance) — for distributed rate limiting across instances, use Redis (`Bucket4j` + Redis) or an API gateway (Kong, Spring Cloud Gateway).

---

### 6. Time Limiter — Timeout for Async Calls

```java
@TimeLimiter(name = "payment")
public CompletableFuture<PaymentResult> chargeAsync(Order order) {
    return CompletableFuture.supplyAsync(() -> paymentClient.charge(order));
}
// YAML:
resilience4j.timelimiter.configs.default:
  timeout-duration: 3s
  cancel-running-future: true
```

Time limiter only works with `CompletableFuture` / `Mono` / `Flux` — it times out the future, not a blocking call. For blocking code, use `@Transactional(timeout)` or `Future.get(timeout)`.

---

### 7. Composing Patterns and Fallbacks

```java
@Service
class OrderFacade {
    // Compose: rate limit → bulkhead → circuit breaker → retry → time limiter → call
    @CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
    @Retry(name = "payment")
    @Bulkhead(name = "payment")
    @RateLimiter(name = "payment")
    public PaymentResult chargeWithResilience(Order order) {
        return paymentClient.charge(order);
    }
    // Fallback signature must match return type + extra Exception param:
    PaymentResult paymentFallback(Order order, Exception ex) { return PaymentResult.cached(order); }
}

// Programmatic composition (more control):
CircuitBreaker cb = circuitBreakerRegistry.circuitBreaker("payment");
Supplier<PaymentResult> decorated = Decorators.ofSupplier(() -> paymentClient.charge(order))
    .withCircuitBreaker(cb)
    .withRetry(Retry.ofDefaults("payment"))
    .withBulkhead(Bulkhead.ofDefaults("payment"))
    .withFallback(List.of(CallNotPermittedException.class), e -> PaymentResult.cached(order))
    .decorate();
PaymentResult result = Try.ofSupplier(decorated).recover(e -> PaymentResult.failed(e)).get();
```

Fallbacks can be **chained** — the outer fallback handles `CallNotPermittedException` (circuit open), inner handles `TimeoutException`.

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| Retrying non-idempotent POST | Duplicate orders/charges | Add idempotency key; retry only idempotent or safe exceptions |
| Circuit breaker on too-small window | Flaps open/closed on a few failures | Increase `sliding-window-size` / `minimum-number-of-calls` |
| `sync = true` confusion with bulkhead | Caller thread blocked waiting for bulkhead permit | Set `max-wait-duration` low; use `THREADPOOL` bulkhead for isolation |
| Rate limiter per instance, not distributed | Each pod allows 100/s → 10 pods allow 1000/s globally | Use distributed limiter (Redis/Bucket4j) or gateway limiting |
| Fallback that also fails | `CallNotPermittedException` → fallback throws → unhandled | Make fallbacks trivial (cached value, empty result) — never call another failing downstream |
| Forgetting `@EnableAspectJAutoProxy` equivalent | Annotations silently ignored | Ensure `resilience4j-spring-boot3` + `spring-boot-starter-aop` are on classpath |

### Summary

- Resilience4j provides **retry (backoff), circuit breaker (CLOSED→OPEN→HALF_OPEN), bulkhead (semaphore/thread-pool), rate limiter (token bucket), and time limiter (future timeout)** as AOP annotations — same proxy mechanism as `@Transactional`.
- **Retry** handles transient blips (idempotent only); **circuit breaker** fails fast after a failure threshold (sliding window, `wait-duration-in-open-state`, `fallbackMethod` for degraded response).
- **Bulkhead** isolates concurrency (semaphore vs thread-pool); **rate limiter** caps throughput per instance (distributed needs Redis/gateway); **time limiter** wraps `CompletableFuture`.
- Compose patterns (rate limit → bulkhead → circuit breaker → retry → call) and make fallbacks trivial; observe via `/actuator/health` + Micrometer metrics.
