## 276. How do you version a Spring Boot API without breaking clients? Explain breaking vs non-breaking changes, URI vs media-type versioning, deprecation headers, and contract checks in CI.

Versioning is not a feature you add at the end; it is what you do when **compatibility cannot be preserved**. Every new version doubles the surface you must test, secure, and eventually retire, so the default should be **evolution**: additive changes, tolerant readers, and a documented deprecation window. A version number is the escape hatch for the rare change that cannot be made compatible - a field whose meaning must change, a required parameter, a response shape that clients parse positionally. Getting this wrong shows up as a mobile app that crashes on an old build, a partner integration that silently reads the wrong field, or a v1 endpoint that nobody can delete because there is no telemetry on who still calls it.

---

### 1. Compatibility First, Versioning Second

| Approach | Cost | When to use |
| :--- | :--- | :--- |
| **Compatible evolution** | Lowest: one version, tolerant clients | Default for everything you control |
| **Deprecation + migration window** | Medium: telemetry, comms, dual support | External consumers you can reach |
| **Parallel versions** | High: duplicated tests, docs, security surface | Genuinely incompatible semantics |
| **Hard cutover** | Highest risk | Only for consumers you own and deploy atomically |

The cheapest breaking change is the one you design out. Before adding `/v2`, ask whether the change can be expressed as a **new optional field**, a **new endpoint**, or a **new media type** alongside the old one.

---

### 2. Breaking vs Non-Breaking Changes

| Change | Breaking? | Why |
| :--- | :--- | :--- |
| Add an optional **response** field | No | Tolerant clients ignore unknown fields |
| Add an optional **request** field | No | Old clients simply omit it |
| Add a new endpoint | No | Nothing existing changes |
| Remove or rename a field | **Yes** | Clients deserialize `null` or fail |
| Change a type (`int` → `string`, number → object) | **Yes** | Parse errors |
| Add a value to an enum | **Usually yes** | Java `switch` exhaustiveness, client validation, UI mapping |
| Make an optional field required | **Yes** | Existing requests start failing |
| Tighten validation (max length, regex, range) | **Yes** | Previously valid requests rejected |
| Change a default value | **Yes** | Behaviour changes without a shape change |
| Change an error code, status, or error body | **Yes** | Clients branch on them |
| Change pagination defaults or ordering | **Yes** | Silent data loss or duplicates for clients |
| Change **semantics** of an existing field | **Yes, and the worst kind** | Nothing fails to parse; the meaning silently changes |
| Add a required header | **Yes** | Unprepared clients get `400`/`415` |
| Reorder JSON properties | No | Object order is not significant |
| Add a new HTTP method to an existing path | No | Unless it changes caching/authorization assumptions |

The "semantics" row is the one code review misses: renaming `amount` from cents to dollars keeps the type and breaks every consumer. Treat units, time zones, and currency as part of the contract.

Two client-side defaults decide whether additive changes are actually safe:

```java
// Jackson's default is true; Spring Boot sets it to false for you.
// Do not re-enable it on a client that talks to an evolving API.
@JsonIgnoreProperties(ignoreUnknown = true)
public record OrderResponse(String id, BigDecimal total, String currency) { }
```

```yaml
spring:
  jackson:
    deserialization:
      fail-on-unknown-properties: false   # default in Boot; keep it that way
```

Publish the schema (OpenAPI/JSON Schema) so consumers can generate tolerant clients instead of hand-parsing maps.

---

### 3. Choosing a Versioning Strategy

| Strategy | Example | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **URI path** | `/api/v2/orders/42` | Visible in logs, cache keys, routing; trivial to route at the gateway | URL churn; clients hardcode; "not RESTful" by some readings |
| **Custom media type** | `Accept: application/vnd.acme.v2+json` | Clean URLs; proper content negotiation | Invisible in most logs; needs `Vary: Accept`; harder to test with `curl` |
| **Custom header** | `X-API-Version: 2` | Clean URLs; easy to add | Same invisibility; proxies must not strip it |
| **Query parameter** | `/api/orders/42?version=2` | Trivial to try | Pollutes cache keys and links; easy to forget |
| **No version, evolve** | additive fields only | One code path | Requires discipline and contract tests |

Rules of thumb:

- **External/partner API** → URI versioning is the least ambiguous and the easiest to support operationally.
- **Internal service-to-service** → do not version; use tolerant readers, contract tests (Q258), and deploy ordering.
- **Content negotiation** is a good fit when the same resource genuinely has multiple representations rather than multiple contracts.
- **Spring Framework 7** adds first-class `version` support on `@RequestMapping`, with a configurable resolver (path segment, header, query parameter, or media-type parameter). If you are on Boot 4/Framework 7, prefer that over hand-rolled header checks; on Boot 3, the patterns below are the standard approach.

```java
// Boot 3: media-type versioning
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v1+json")
    OrderV1 getV1(@PathVariable String id) { ... }

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v2+json")
    OrderV2 getV2(@PathVariable String id) { ... }
}
```

```java
// Boot 3: header versioning (mapping is more specific when the header is present)
@GetMapping(value = "/{id}", headers = "X-API-Version=2")
OrderV2 getV2(@PathVariable String id) { ... }
```

```java
// Spring Framework 7: built-in version attribute
@GetMapping(path = "/{id}", version = "2.0")
OrderV2 getV2(@PathVariable String id) { ... }
```

Whichever you choose, **route at the edge**: the gateway can send `/v1/*` to the old deployment and `/v2/*` to the new one, which is what makes a gradual migration possible (Q239).

---

### 4. Do Not Fork the Domain, Fork the Contract

The failure mode of versioning is two controllers with copy-pasted logic that drift: a bug fixed in v2 but not v1, or v1 writing different data than v2.

```java
// One domain model, thin per-version adapters
@RestController
@RequestMapping("/api/orders")
class OrderController {

    private final OrderService orders;   // single source of truth

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v1+json")
    OrderV1 getV1(@PathVariable String id) {
        return OrderV1.from(orders.get(id));      // v1 shape: flat total in cents
    }

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v2+json")
    OrderV2 getV2(@PathVariable String id) {
        return OrderV2.from(orders.get(id));      // v2 shape: amount { value, currency }
    }
}
```

| Layer | Shared? | Notes |
| :--- | :--- | :--- |
| Domain/service/persistence | **Yes** | One behaviour, one set of invariants |
| DTOs and mappers | No | Version-specific shapes |
| Validation | Partly | v2 may be stricter; keep the rule in the service where it is a true invariant |
| Error mapping | Shared with a versioned envelope | If the envelope changes, that is a breaking change |

Version the **contract**, not the business logic. If a rule differs between versions, that is a product decision that must be explicit in the service, not an accident of duplicated code.

---

### 5. Deprecation Is a Lifecycle, Not an Annotation

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.acme.v1+json
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://developer.acme.com/api/v2/migration>; rel="deprecation"; type="text/html"
Warning: 299 - "v1 is deprecated; migrate to v2 before 2027-06-30"
```

| Header | Meaning |
| :--- | :--- |
| `Deprecation` | When the endpoint became deprecated (RFC 9745 structured date) |
| `Sunset` | When it will be removed (RFC 8594 HTTP date) |
| `Link ... rel="deprecation"` | Where the migration guide lives |
| `Warning` | Human-readable hint for older clients and logs |

A workable timeline:

| Phase | Action | Exit criterion |
| :--- | :--- | :--- |
| **Announce** | Publish guide, add headers, tag metrics by version | Consumers notified |
| **Instrument** | Dashboard of calls per version, per client id | You can name who still calls v1 |
| **Migrate** | Support both versions; fix v1 only for security/data-loss bugs | v1 traffic below an agreed threshold |
| **Freeze** | No changes to v1 except critical fixes | Threshold reached for N weeks |
| **Sunset** | Return `410 Gone` (or redirect where safe) | Removal date passes |
| **Remove** | Delete code, tests, docs, gateway routes | Cleanup complete |

Telemetry is the whole game:

```java
meterRegistry.counter("api_requests_total",
        "route", "orders.get",
        "version", requestVersion,          // from path, header, or media type
        "client_id", clientId(request)).increment();
```

Without a per-version, per-client metric you cannot answer "can we delete v1?" and the answer becomes "never".

---

### 6. Contract Checks in CI

Humans do not reliably spot breaking changes in a diff, so automate it:

```bash
# Fails when the new OpenAPI document removes fields, tightens types, or adds required params
oasdiff breaking api/openapi-v1.yaml api/openapi-v2.yaml --fail-on ERR

# Consumer-driven contracts: the provider must satisfy every consumer's expectations (Q258)
./mvnw verify -Dpact.verifier.publishResults=true
```

| Check | Catches |
| :--- | :--- |
| **OpenAPI diff** (`oasdiff`, `openapi-diff`) | Removed fields, type changes, new required parameters |
| **Consumer-driven contracts** (Pact, Q258) | Provider changes that violate real consumer usage |
| **JSON Schema validation in tests** | Response shape drift not captured by the spec |
| **Golden-file / snapshot tests** | Serialization changes (date formats, null handling) |
| **Canary with version tags** | Runtime errors only the old client triggers |

Make the diff part of the pull request: a change that fails `oasdiff breaking` either gets redesigned or gets an explicit, reviewed version bump.

---

### 7. Cross-Protocol Notes

**GraphQL** has no URL versions. Evolve additively and deprecate in the schema:

```graphql
type Order {
  id: ID!
  totalCents: Int @deprecated(reason: "Use amount { value currency }")
  amount: Money!
}
```

- Adding a nullable field or a new type is safe.
- Removing a field, changing nullability, or **adding a non-null argument without a default** is breaking.
- Clients can send persisted queries, which means a removed field can break them even if no human wrote the query recently (Q254).

**gRPC/protobuf** versions by package and by field number:

```proto
package acme.orders.v2;

message Order {
  reserved 4, 6;              // never reuse a removed field number
  reserved "customer_name";
  string customer_id = 7;
}
```

- Adding fields is safe; removing or renaming is not.
- Never reuse a tag number; `reserved` prevents accidental reuse (Q255).
- `google.protobuf.Any` moves the compatibility problem into the payload, where no schema check will catch it.

**Events** are an API too. Version the envelope and keep consumers tolerant:

```json
{ "eventType": "order.created", "schemaVersion": 3, "occurredAt": "2026-11-03T09:00:00Z", "payload": { } }
```

Use a schema registry with an explicit compatibility mode (for example Avro `BACKWARD_TRANSITIVE`), and remember that the **consumer deploy order** matters: deploy readers that understand the new field before producers start emitting it (Q251).

---

### 8. Coupling to Data and Deployments

- **Do not let two API versions write the same column with different semantics.** If v1 means cents and v2 means a decimal amount, store one canonical representation and convert at the adapter.
- **Schema changes follow expand/contract** (Q248/Q272): add nullable columns, backfill, switch reads, then remove. API versions do not remove the need for migration discipline.
- **Deploy order for additive changes**: consumers first, producers second. For removals: stop producing, verify, then remove.
- **Feature flags** can route a subset of clients to v2 for a canary before a full cutover (Q247).
- **Auth and tenancy must behave identically across versions**; a v2 endpoint that forgets a tenant predicate is a new vulnerability, not a new feature (Q275).

---

### 9. Testing Matrix

| Test | What it protects |
| :--- | :--- |
| Contract tests per supported version | Provider still satisfies v1 and v2 consumers |
| Serialization tests per version | Field names, date formats, null/empty semantics |
| Deprecation header assertions | Clients and proxies see the sunset signal |
| Gateway routing tests | `/v1` and `/v2` reach the right deployment |
| Old-client integration test (pinned SDK/fixture) | Real-world tolerance, not just generated clients |
| Load test with mixed versions | Connection pools, caches, and DB queries stay within budget |

Keep one **pinned old client** in CI. Generated clients from the current spec will happily accept a breaking change that a real, older SDK cannot.

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Changing field semantics** | No parse error; wrong money/units downstream | Treat units, currency, and time zones as contract |
| **Adding an enum value** | Client `switch` throws or defaults incorrectly | Document as potentially breaking; version if consumers are strict |
| **Tightening validation** | Old valid requests now `400` | New version, or make the rule opt-in |
| **Copy-pasted v1/v2 controllers** | Bug fixed in one, not the other | Shared service, thin adapters |
| **Versioning everything** | N versions, N test suites, slow delivery | Evolve compatibly; version only real breaks |
| **No per-version telemetry** | Cannot retire v1 | Tag metrics by route, version, client |
| **`Deprecation` without `Sunset`** | Clients ignore an open-ended warning | Publish a date and enforce it |
| **Removing fields before traffic hits zero** | Late-night rollback | Gate removal on measured traffic |
| **GraphQL non-null argument added** | Queries fail validation | Add nullable with a default; deprecate |
| **Reusing a protobuf field number** | Silent data corruption across versions | `reserved` old tags |
| **Jackson strictness on clients** | Adding a response field breaks clients | `FAIL_ON_UNKNOWN_PROPERTIES=false` |
| **Media-type versioning without `Vary: Accept`** | CDN serves the wrong representation | Add `Vary: Accept`; test through the CDN |
| **Two versions writing different semantics** | Data corruption after cutover | One canonical store; convert in adapters |
| **No contract check in CI** | Breaking change ships on a Friday | `oasdiff breaking` + Pact gates |

### Summary

- **Compatibility is the default; a version is the exception.** Add optional fields, new endpoints, and new representations before forking the API.
- **Know what actually breaks**: removed/renamed fields, type changes, tightened validation, enum additions, error-shape changes, and - most dangerous - unchanged shapes with changed semantics.
- **Pick one strategy and make it visible**: URI versioning for external APIs, no versioning for internal services with contract tests, media types when representations genuinely differ; Framework 7's `version` attribute removes the hand-rolled plumbing.
- **Version the contract, not the domain**: one service, one set of invariants, thin per-version DTOs and mappers.
- **Deprecation needs a date, headers (`Deprecation`/`Sunset`), and per-version telemetry**; without the metric you can never delete the old code.
- **Automate compatibility**: OpenAPI diff and consumer-driven contracts in CI (Q258), plus a pinned old client; document GraphQL, gRPC, and event-schema rules separately because each breaks differently.

## 277. How do you run chaos engineering experiments on Spring Boot microservices? Explain steady-state hypotheses, blast radius, fault injection with Chaos Monkey/Toxiproxy/Litmus, and gating experiments in CI.

Chaos engineering is **controlled, hypothesis-driven fault injection**, not randomly deleting pods in production. The point is to replace "we think the timeout and circuit breaker work" with evidence: define a measurable steady state, inject one realistic fault inside a bounded blast radius, and observe whether the system keeps its SLO or degrades in the way you designed. It is the natural next step after resilience patterns (Q213), load shedding (Q270), and SLOs (Q230): those tell you what *should* happen; an experiment tells you what *does*.

---

### 1. The Experiment, Not the Tool

```text
1. Hypothesis    "If payments adds 800 ms latency, checkout error rate stays < 0.5%
                  and p99 < 2 s, because the 500 ms timeout + circuit breaker shed fast."
2. Steady state  error rate < 0.5%, p99 < 800 ms, duplicate charges = 0
3. Injection     Toxiproxy / Chaos Mesh adds latency to payments for 5 minutes
4. Observation   compare experiment window against baseline window
5. Verdict       hypothesis holds / fails; if it fails, file the fix before the next experiment
6. Automation    keep the reproducible ones in CI; retire the rest
```

Without a written hypothesis you are just breaking things and calling it science. Without a **baseline window** you cannot tell whether a p99 change came from the fault or from normal traffic.

| Element | Bad example | Good example |
| :--- | :--- | :--- |
| **Hypothesis** | "Kill a pod and see" | "Killing one orders pod causes < 30 s of elevated errors because readiness drains first (Q261)" |
| **Steady state** | "It's up" | Error rate, p99, consumer lag, duplicate count, DB saturation |
| **Blast radius** | All pods, all AZs | One pod, one AZ, one dependency, 5 minutes |
| **Abort** | None | Error budget burn > 2%, manual kill switch, on-call veto |
| **Verdict** | "Looks fine" | Metric comparison with a pass/fail threshold |

---

### 2. Prerequisites Before the First Experiment

Chaos without observability is vandalism. You need:

- **SLOs and error budgets** (Q230) so "did it degrade?" has a numeric answer.
- **Distributed tracing** (Q266) so you can see *where* the latency appeared, not just that checkout got slower.
- **Idempotency and reconciliation** (Q263) so a retried or duplicated request does not corrupt data - and a way to verify it after the experiment.
- **A kill switch** that removes the fault immediately (Toxiproxy toxic delete, Chaos Mesh experiment delete, `chaos.monkey.enabled=false`).
- **A rollback path** for anything that could persist state (schema changes, queues, scheduled jobs).
- **An incident channel and on-call awareness**, even in production during business hours.

---

### 3. Fault Catalogue

| Fault | What it validates | Tooling |
| :--- | :--- | :--- |
| **Latency on a dependency** | Timeouts, circuit breakers, load shedding, thread/connection exhaustion | Toxiproxy, Chaos Mesh `NetworkChaos` delay, chaos-monkey latency assault |
| **Error responses (500/503/429)** | Retry policy, jitter, fallback, `Retry-After` handling (Q270) | Toxiproxy, WireMock, mesh fault injection |
| **Network partition / packet loss** | Timeouts vs hangs, retry storms, split-brain assumptions | Chaos Mesh `NetworkChaos` partition, Toxiproxy `timeout`/`reset_peer` |
| **Pod kill / restart** | Graceful shutdown, readiness, Kafka rebalance (Q261), in-flight requests | Chaos Mesh `PodChaos`, Litmus `pod-delete`, `kubectl delete pod` |
| **CPU / memory stress** | GC behaviour, throttling, OOMKilled budgets, adaptive limits (Q270) | Chaos Mesh `StressChaos`, `stress-ng` |
| **DNS failure** | Client caching, failover to another endpoint | Chaos Mesh `DNSChaos` |
| **Disk latency / full disk** | Logging backpressure, WAL/queue behaviour | `StressChaos`, `tc`, filesystem fill |
| **AZ / node failure** | Multi-AZ failover, replica promotion, capacity headroom (Q268) | Cloud FIS, node drain, zone-scoped experiments |
| **Broker/leader kill** | Consumer rebalance, producer retries, duplicate handling (Q259) | Kill a broker pod; `kafka-leader-election.sh` for controlled leader moves |
| **Certificate/credential expiry** | Rotation, TLS failure mode, fail-closed behaviour (Q243) | Short-lived certs in staging; revoke a credential |
| **Dependency throttle/quota** | Backoff, `429` handling, per-tenant fairness (Q238) | Proxy responding `429` with `Retry-After` |

Start with **latency and errors on a dependency**. They are reversible, cheap, and expose the majority of real incidents. Pod kills and infrastructure faults come later, once the application-level behaviour is trustworthy.

---

### 4. Spring-Level Injection: Chaos Monkey for Spring Boot

For testing a single service's method-level resilience, `chaos-monkey-spring-boot` injects latency, exceptions, memory/CPU pressure, or kills the app based on a watched layer (service, controller, repository).

```xml
<dependency>
    <groupId>de.codecentric</groupId>
    <artifactId>chaos-monkey-spring-boot</artifactId>
    <version>${chaos-monkey.version}</version>
    <scope>runtime</scope>
</dependency>
```

```yaml
spring:
  profiles:
    include: chaos-monkey          # never active by default; enabled per environment
chaos:
  monkey:
    enabled: true
    assaults:
      level: 2                     # 1 (rare) .. 5 (always); higher = more calls hit
      latency-active: true
      latency-range-start: 500
      latency-range-end: 2000
      exceptions-active: true
    watcher:
      service: true                # scope to @Service beans
      controller: false
      repository: false            # keep persistence out of the blast radius
management:
  endpoint:
    chaosmonkey:
      enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,chaosmonkey
```

```bash
# Query and change the assault configuration at runtime
curl -s localhost:8080/actuator/chaosmonkey/assaults
curl -s -X POST localhost:8080/actuator/chaosmonkey/assaults \
  -H 'Content-Type: application/json' \
  -d '{"latencyActive":true,"latencyRangeStart":800,"latencyRangeEnd":800,"level":3}'
```

Rules:

- **Never enable it unconditionally in production.** Gate it behind a profile plus the actuator endpoint, protected like any admin surface (Q275).
- **Watch the narrowest layer** that produces the behaviour you are testing. Injecting into repositories multiplies the fault across every query and makes results uninterpretable.
- **Use `level` as a dial**, not a switch: a fraction of calls is closer to real degradation than 100% failure.
- **Verify it actually fires** - a watched bean that is never called produces a green experiment that proves nothing. Count injected faults in a metric.

---

### 5. Dependency-Level Injection: Toxiproxy in Tests

Toxiproxy sits between the app and a dependency and lets you add latency, bandwidth limits, timeouts, or connection resets without touching the dependency or the app.

```java
@Testcontainers
class PaymentTimeoutExperiment {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Container
    static ToxiproxyContainer toxiproxy =
            new ToxiproxyContainer("ghcr.io/shopify/toxiproxy:2.9.0");

    static ToxiproxyContainer.ContainerProxy dbProxy;

    @DynamicPropertySource
    static void datasource(DynamicPropertyRegistry registry) {
        dbProxy = toxiproxy.getProxy(postgres, 5432);
        registry.add("spring.datasource.url", () -> "jdbc:postgresql://%s:%d/test"
                .formatted(dbProxy.getHost(), dbProxy.getProxyPort()));
        registry.add("spring.datasource.hikari.connection-timeout", () -> "500");
    }

    @Test
    void requestFailsFastWhenDatabaseHangs() {
        dbProxy.toxics().latency("db-delay", ToxicDirection.DOWNSTREAM, 1_500);

        // Hypothesis: the 500 ms connection timeout + circuit breaker
        // return 503 within ~600 ms instead of hanging for the full 1.5 s.
        assertThat(api.get("/orders/1"))
                .hasStatus(503)
                .hasHeader("Retry-After");

        dbProxy.toxics().get("db-delay").remove();   // always clean up
    }
}
```

This belongs in CI: it is deterministic, fast, and runs on every change to the resilience configuration. The same idea at the network level is a Toxiproxy sidecar in staging, or Chaos Mesh in Kubernetes.

### 6. Cluster-Level Injection: Chaos Mesh / Litmus

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: orders-to-payments-latency
  namespace: shop
spec:
  action: delay
  mode: one                       # one pod, not the whole deployment
  selector:
    namespaces: [shop]
    labelSelectors: { app: orders }
  delay:
    latency: "800ms"
    jitter: "200ms"
    correlation: "50"
  direction: to
  target:
    mode: all
    selector:
      namespaces: [shop]
      labelSelectors: { app: payments }
  duration: "5m"
```

Litmus expresses the same experiment as a `ChaosEngine` with an experiment name (`pod-delete`, `pod-network-latency`), plus probes that assert steady state before, during, and after. Cloud providers offer managed equivalents (AWS FIS, Azure Chaos Studio) that can target an AZ or a managed database, which is the only practical way to rehearse regional failure (Q268).

| Control | Setting |
| :--- | :--- |
| **Namespace/labels** | Only the intended workload, never `mode: all` on a shared deployment |
| **Duration** | Minutes, with an explicit end |
| **Probes** | Steady-state checks that abort the experiment on violation |
| **Schedule** | Business hours, announced, with on-call present |
| **Kill switch** | Delete the CR / disable the experiment; verify the fault is gone |

```bash
kubectl -n shop get networkchaos
kubectl -n shop delete networkchaos orders-to-payments-latency
# Confirm: latency back to baseline, no lingering tc rules / sidecar config
```

---

### 7. Blast Radius and Safety

| Dimension | Start | Later |
| :--- | :--- | :--- |
| **Environment** | Local Testcontainers | Staging → canary subset → production |
| **Scope** | One dependency, one method | One pod, one AZ |
| **Traffic** | Synthetic tests | 1% of real traffic tagged by header/tenant |
| **Duration** | Seconds in a test | 5-15 minutes |
| **Faults** | Latency, errors | Kills, partitions, AZ loss |
| **Approval** | Developer | Team + on-call + change record |

Production rules:

- **Tag and route**: use a header or tenant id to send only a small cohort through the faulted path (Q247), so experiments do not become incidents for everyone.
- **Never inject into data-mutating paths without a reconciliation check**; a duplicate charge that "recovered" is still a duplicate charge (Q263).
- **Abort automatically on error-budget burn**, not on a human noticing a dashboard.
- **Exclude** payment capture, irreversible migrations, and anything with no rollback until you have rehearsed it in staging.
- **Freeze chaos during deploys, incidents, and peak** - one variable at a time.

---

### 8. Reading the Result

Compare the experiment window to the same-length baseline window, not to "how it feels".

| Signal | Baseline | Abort / fail threshold |
| :--- | :--- | :--- |
| HTTP error rate | < 0.5% | > 2% for 2 minutes |
| p99 latency | < 800 ms | > 2 s |
| Circuit breaker state | closed | open > 1 minute (unless shedding is the design, Q270) |
| Consumer lag | < 1k | > 50k and growing (Q259) |
| DB pool pending | 0 | > 0 sustained (Q232) |
| Duplicate/incorrect records | 0 | any |
| SLO burn rate | < 1× | > 2× (Q230) |

Correlate with traces: an 800 ms payment delay should show up as a specific span, with the circuit breaker's fallback span next to it (Q266). If the trace shows the request waiting on the full 800 ms, the timeout is misconfigured - the experiment found a real bug, which is the point.

---

### 9. Putting It in CI/CD

```text
PR pipeline        → Toxiproxy/WireMock fault tests (seconds, deterministic)
Nightly staging    → one Chaos Mesh experiment per critical dependency
Weekly game day    → one cross-service experiment with on-call, hypothesis, write-up
Production         → manual, approved, tagged cohort, business hours
```

- **Assert the design, not just survival**: 503 + `Retry-After`, breaker opens, fallback returns cached data, queue drains after recovery.
- **Fail the pipeline on a violated hypothesis**; otherwise the experiment becomes a dashboard nobody reads.
- **Keep a catalog** of experiments with owner, hypothesis, tooling, and last result - chaos maturity is measured by the fixes it produced, not the number of experiments run.
- **Rotate experiments**: once a fault is handled automatically (test proves it), move to the next unknown instead of re-running the same green test forever.

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **No hypothesis or baseline** | "Nothing broke" with no evidence | Define metric, window, and pass/fail first |
| **No observability** | Cannot tell whether the fault fired | SLOs, traces, and injected-fault counters (Q230/Q266) |
| **Fault in dead code** | Experiment passes, real path untested | Verify the injection metric; scope the watcher correctly |
| **Blast radius too large** | Real incident instead of experiment | One pod/AZ, tagged cohort, duration limit |
| **No kill switch** | Fault persists after the experiment | Toxic delete / CR delete / feature toggle; verify baseline |
| **Leftover toxics** | Staging mysteriously slow for days | `finally` cleanup; assert baseline after each test |
| **Data-mutating fault without reconciliation** | Duplicate charges, lost events | Idempotency keys + post-experiment reconciliation (Q263) |
| **Retry storm during injection** | Load amplification looks like a capacity bug | Retry budget and jitter (Q270); measure request rate too |
| **Testing production first** | Learning on customers | Local/CI → staging → tagged production cohort |
| **Running during a deploy/incident** | Two variables, no diagnosis | Freeze experiments during change windows |
| **Chaos as a checkbox** | Same green experiment for a year | Retire proven ones; target the next unknown |
| **Only measuring availability** | System "up" but charging twice | Assert correctness invariants, not just 200s |
| **Ignoring recovery** | Error rate returns, but lag never drains | Measure drain time and backlog after the fault ends |

### Summary

- **Chaos engineering is an experiment with a hypothesis, a steady state, a bounded blast radius, and an abort condition** - otherwise it is just an outage with a name.
- **Start at the dependency boundary**: latency and errors via Toxiproxy in CI, then pods and networks via Chaos Mesh/Litmus, then AZ/region faults via cloud tooling.
- **Spring-specific injection** (chaos-monkey-spring-boot) is useful for method-level behaviour, but only when gated, scoped to the right layer, and verified to actually fire.
- **Keep the blast radius small and reversible**: one pod/AZ, tagged traffic, minutes, business hours, automatic abort on error-budget burn, and a kill switch you have tested.
- **Judge the result against baseline SLOs and correctness invariants** (duplicates, lag, pool saturation), using traces to find where the design failed (Q230/Q266).
- **Automate the proven experiments in CI, rehearse the rest as game days, and retire them once fixed** - the output of chaos engineering is a shorter list of unknowns, not a collection of scripts.

## 278. How do you operate Elasticsearch at scale with Spring Boot? Explain shard sizing, index lifecycle management, aliases, zero-downtime reindexing, and keeping the index consistent with the database.

Elasticsearch is a **derived, rebuildable index** (Q225), not a system of record. Once you accept that, the operational questions become concrete: how many shards per index, when to roll over to a new index, how to change a mapping without downtime, and how to prove the index still matches the database after a failed bulk load or a missed event. Getting these wrong produces the classic failures - a cluster with 4,000 tiny shards and an unstable cluster state, a single 2 TB index that takes hours to recover, or a reindex that silently drops documents because nobody compared counts.

---

### 1. Shard Sizing: The Decision You Cannot Undo

A shard is a Lucene index; `number_of_shards` is fixed at creation (changing it requires `_split`, `_shrink`, or a full reindex).

| Rule of thumb | Value | Why |
| :--- | :--- | :--- |
| **Shard size** | 10-50 GB | Smaller = overhead per shard; larger = slow recovery and rebalancing |
| **Docs per shard** | < 200 million | Lucene segment and merge cost grows |
| **Shards per node** | roughly ≤ 20 per GB of heap | Each shard costs heap for segment metadata and cluster state |
| **Replicas** | 1 minimum in production | HA plus search throughput, at 2× disk |
| **Total shards per cluster** | keep in the hundreds/low thousands | Cluster state and master work scale with shard count |

```text
200 GB of searchable data
├─ 6 primary shards × ~33 GB   ← reasonable
└─ 1 replica each              ← 12 shards total
vs.
2000 primary shards × 100 MB   ← cluster-state churn, slow recovery, wasted heap
```

Prefer **time-based indices plus ILM** over one giant index: it gives retention by deleting whole indices (the same reasoning as table partitioning, Q272) and keeps each shard in the healthy size range.

```java
@Document(indexName = "orders", createIndex = false)  // templates/ILM own the index
@Setting(shards = 3, replicas = 1)
public class OrderDocument {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String tenantId;

    @Field(type = FieldType.Keyword)
    private String status;

    @Field(type = FieldType.Scaled_Float, scalingFactor = 100)
    private BigDecimal total;

    @Field(type = FieldType.Date, format = DateFormat.date_optional_time)
    private Instant createdAt;
}
```

`createIndex = false` matters in production: letting the application auto-create an index means it may be created without the template, with default shards and dynamic mappings, and the mistake is only discovered after data arrives.

---

### 2. Index Templates and ILM

```json
PUT _index_template/orders-template
{
  "index_patterns": ["orders-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 1,
      "index.lifecycle.name": "orders-policy",
      "index.lifecycle.rollover_alias": "orders-write",
      "refresh_interval": "5s"
    },
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "id":        { "type": "keyword" },
        "tenantId":  { "type": "keyword" },
        "status":    { "type": "keyword" },
        "total":     { "type": "scaled_float", "scaling_factor": 100 },
        "createdAt": { "type": "date" },
        "description": { "type": "text",
                         "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } }
      }
    }
  }
}
```

```json
PUT _ilm/policy/orders-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_primary_shard_size": "30gb", "max_age": "1d" }
        }
      },
      "warm": {
        "min_age": "7d",
        "actions": {
          "forcemerge": { "max_num_segments": 1 },
          "shrink": { "number_of_shards": 1 }
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "searchable_snapshot": { "snapshot_repository": "s3-repo" }
        }
      },
      "delete": { "min_age": "365d", "actions": { "delete": {} } }
    }
  }
}
```

Bootstrap the first write index so the rollover alias exists:

```json
PUT orders-000001
{ "aliases": { "orders-write": { "is_write_index": true } } }
```

Design notes:

- **Rollover on `max_primary_shard_size`**, not only on age; a quiet day should not produce a 2 GB shard and a busy day a 60 GB one.
- **`forcemerge` only on read-only indices**; merging a live index fights ongoing segment creation.
- **`shrink` reduces shard count for older data** but needs the index to be relocated onto one node first; it is not free.
- **`searchable_snapshot`** moves cold data to object storage; queries still work, at higher latency and with a repository dependency.
- **`dynamic: strict`** turns an unexpected field into a visible indexing error instead of silent mapping growth - catch it in staging, not in production.

---

### 3. Aliases: The Only Way to Change an Index Safely

```text
orders-write  ──► orders-000042   (is_write_index = true, one target)
orders-read   ──► orders-000041, orders-000042   (read across the transition)
orders-*      ──► all time-based indices (queries, dashboards)
```

| Alias | Purpose |
| :--- | :--- |
| **Write alias** | Exactly one index receives new documents; ILM rollover updates it atomically |
| **Read alias** | One or more indices; during a migration it covers old and new |
| **Wildcard** | Ad-hoc queries and Kibana; avoid in application code because it hides mapping changes |

Application code should **write to the alias, never to a concrete index**. That is what makes rollover and reindex invisible to the application.

```java
// Spring Data writes go to the alias name
operations.save(orderDocument, IndexCoordinates.of("orders-write"));
```

---

### 4. Zero-Downtime Mapping Changes

Adding a field is safe. Changing a field's type, analyzer, or meaning is not, and Elasticsearch will reject documents (`mapper_parsing_exception`) rather than convert them.

```text
1. Create orders-000043 with the new template/mapping
2. Backfill from the source of truth (DB) or reindex from the old index
3. Verify counts, checksums, and spot-check queries
4. Atomically swap the write alias
5. Keep the old index readable for rollback (orders-read covers both)
6. Delete the old index after the rollback window
```

```json
POST _aliases
{
  "actions": [
    { "add":    { "index": "orders-000043", "alias": "orders-write", "is_write_index": true } },
    { "remove": { "index": "orders-000042", "alias": "orders-write" } },
    { "add":    { "index": "orders-000043", "alias": "orders-read" } }
  ]
}
```

`_aliases` is atomic: clients see either the old or the new target, never neither.

Two backfill options:

| Source | When | Trade-off |
| :--- | :--- | :--- |
| **Database** (paged read + bulk index) | Mapping/semantics changed; index is derivable | Slowest, but authoritative and repeatable |
| **`_reindex` from the old index** | Only analyzers/settings changed, documents are correct | Fast, but copies any existing corruption |

For continuous correctness during the migration, run **dual writes** (or CDC via the outbox, Q260) into both indices until the swap, then stop writing the old one. Verify with per-tenant counts and a sample of document hashes, not just `_count` on the whole index.

```json
POST _reindex?wait_for_completion=false
{
  "source": { "index": "orders-000042" },
  "dest":   { "index": "orders-000043" },
  "script": {
    "source": "ctx._source.migratedAt = params.now",
    "params": { "now": "2026-11-06T00:00:00Z" }
  }
}
```

Reindex is asynchronous: track it with `GET _tasks/<task-id>`, and expect throttling (`requests_per_second`) so it does not starve live traffic.

---

### 5. Keeping the Index Consistent with the Database

The index drifts for mundane reasons: a bulk request partially failed, a consumer crashed after committing, a delete was missed, or an event arrived out of order.

| Control | Implementation |
| :--- | :--- |
| **Idempotent upserts by id** | Always index with the business id, never generate a random document id |
| **Monotonic versioning** | Reject stale writes with `version_type=external` or `if_seq_no`/`if_primary_term` |
| **Reliable publication** | Transactional outbox or CDC, not a dual write in the request thread (Q260) |
| **Consumer dedup** | Transactional inbox when the same event can arrive twice (Q262) |
| **Reconciliation job** | Nightly compare `updated_at` watermarks, counts per tenant, and sample hashes; reindex missing ids |
| **Delete tombstones** | Delete by id in the same order as the source; a resurrected document is a stale event |
| **Read-your-writes** | Use `refresh=wait_for` for critical writes, or accept near-real-time reads (default 1 s) |

```java
// Bulk indexing: batch, do not send one request per document
List<IndexQuery> queries = orders.stream()
        .map(o -> new IndexQueryBuilder().withId(o.id()).withObject(o).build())
        .toList();

operations.bulkIndex(queries, IndexCoordinates.of("orders-write"));
```

Bulk sizing: **1,000-5,000 documents or 5-15 MB per request**, whichever comes first. Watch for `es_rejected_execution_exception` (write queue full) and back off with jitter (Q270); retrying at the same rate turns a slow node into a failing cluster.

```java
// Do not ignore partial failures: some documents in the batch may have failed
try {
    operations.bulkIndex(queries, IndexCoordinates.of("orders-write"));
} catch (BulkFailureException e) {
    // log failed ids, retry only those, then alert if the failure rate is non-trivial
    failedIds.addAll(e.getFailedDocuments().keySet());
}
```

Reconciliation is not optional. A weekly job that compares counts and hashes catches the drift that no amount of retry logic prevents.

---

### 6. Query and Pagination Discipline

| Problem | Symptom | Fix |
| :--- | :--- | :--- |
| **Deep pagination** (`from` + `size` > 10k) | `Result window is too large` / heap pressure | `search_after` with a stable sort, plus a point-in-time (PIT) |
| **Sorting/aggregating on `text`** | `Fielddata is disabled` or heap blow-up | Use a `keyword` subfield, not `fielddata=true` |
| **Exact counting on every query** | Slow responses on large indices | `track_total_hits: false` when the UI does not need the exact total |
| **Wildcard queries on analyzed text** | Full scans, high CPU | `keyword` fields, prefix queries, or a dedicated n-gram field |
| **Huge `terms` queries** | Coordinator overhead, timeouts | Batch, or precompute memberships |
| **`nested` everywhere** | Expensive joins per document | Flatten the model or denormalize where possible |

```json
GET orders-read/_search
{
  "size": 100,
  "track_total_hits": false,
  "sort": [ { "createdAt": "desc" }, { "id": "asc" } ],
  "search_after": [ "2026-11-05T12:00:00Z", "ord-9182" ],
  "query": { "term": { "tenantId": "acme" } }
}
```

The sort must be **totally ordered** (`createdAt` plus a tiebreaker id) or `search_after` can skip or repeat documents at page boundaries.

---

### 7. Cluster Health and Monitoring

```bash
GET _cluster/health?wait_for_status=yellow&timeout=30s
GET _cat/indices?v&s=store.size:desc
GET _cat/shards?v
GET _cat/allocation?v
GET _nodes/stats/thread_pool
GET _nodes/stats/indices/indexing_pressure
GET _slm/policy
```

| Metric | Healthy | Act |
| :--- | :--- | :--- |
| JVM heap used | < 75% | More heap rarely fixes it; reduce shards/fielddata |
| `write` thread pool rejections | 0 | Slow down bulk, add data nodes |
| `search` queue rejections | 0 | Reduce expensive queries, add replicas |
| Disk watermark | < 85% | At 95% indices go read-only (flood stage) |
| Unassigned shards | 0 | Check allocation explain, node capacity |
| Segment count per shard | bounded | `forcemerge` read-only indices |
| Snapshot success | daily | Test restores, not just snapshots |

Spring Boot's Elasticsearch health indicator checks connectivity, not cluster health. Add a custom gauge for `cluster.status` and for indexing rejections; a `yellow` cluster with unassigned replicas is a real availability risk even though the app still serves reads.

Rolling restarts: one node at a time, wait for `green`/`yellow` and no relocating shards, and keep master-eligible nodes at three so a restart never loses quorum.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Over-sharding** | Unstable cluster state, slow recovery, heap pressure | 10-50 GB per shard; fewer, larger indices |
| **One giant index** | Hours to recover, no retention | Time-based indices + ILM |
| **Changing `number_of_shards` in place** | Not possible | New index + reindex + alias swap |
| **Mapping change on a live index** | Documents rejected, fields missing | New index + backfill + alias swap |
| **`fielddata=true` on text** | Heap exhaustion, node restarts | `keyword` subfield |
| **Writing to a concrete index** | Rollover/reindex breaks the app | Always write to the alias |
| **No read alias** | Migration requires downtime | `orders-read` covering old and new |
| **Reindex without verification** | Silent data loss | Count per tenant + hashes + sample queries |
| **Bulk without backoff** | 429s, rejected executions, lag | Smaller batches, jittered backoff (Q270) |
| **Refresh per document** | Terrible indexing throughput | Batch + `refresh_interval` tuning |
| **`dynamic: true` in production** | Mapping explosion | `strict` or explicit mappings |
| **Random document ids** | Duplicates on retry | Business id as `_id` |
| **No reconciliation** | Index drifts from DB for months | Watermark + count/hash job |
| **Disk above flood watermark** | Index becomes read-only, writes fail | Capacity alerts at 80%, cleanup/ILM |
| **No snapshot restore drill** | Backups exist but cannot be restored | SLM + periodic restore test |

### Summary

- **Elasticsearch is derived data**: design for rebuild, index by business id, and treat the database as the source of truth (Q225/Q260).
- **Shard count is a one-way decision**: target 10-50 GB per shard, keep total shards modest, and use time-based indices plus ILM instead of one giant index (the search equivalent of partitioning, Q272).
- **Aliases decouple clients from indices**: one write alias, one read alias, and an atomic `_aliases` swap for every mapping change.
- **Zero-downtime reindex = new index + backfill/dual-write + verification + atomic alias swap + rollback window**, not `_reindex` into the live index.
- **Consistency needs idempotent upserts, version checks, reliable publication (outbox/CDC), and a reconciliation job** that compares counts and hashes, because partial bulk failures are normal.
- **Operate the cluster, not just the client**: watch heap, thread-pool rejections, disk watermarks, unassigned shards, and snapshot restores; paginate with `search_after`, avoid `fielddata`, and keep mappings strict.

## 279. How do you build a modular monolith with Spring Modulith? Explain module boundaries, named interfaces, verification tests, transactional events, and when to extract a microservice.

Most "microservices" failures start as a **distributed monolith**: services that share a database schema, call each other synchronously in chains, and cannot be deployed independently. Spring Modulith takes the opposite order - **define and enforce module boundaries inside one deployable first**, observe where the seams actually are, and extract services only when a module has a reason to leave (independent scaling, team ownership, compliance, different availability). The boundaries are not documentation; they are verified in tests, so a violation fails the build instead of quietly becoming a coupling problem.

---

### 1. Three Shapes, One Set of Boundaries

| Shape | Deployment | Boundary enforcement | Cost of a wrong boundary |
| :--- | :--- | :--- | :--- |
| **Layered monolith** | One unit | Convention only | Cheap to fix, easy to erode |
| **Modular monolith** | One unit | Code + tests (Modulith/ArchUnit) | Cheap to fix, hard to erode |
| **Microservices** | Many units | Network + contracts + org structure | Expensive: data migration, versioning, ops |

The modular monolith is the cheapest place to discover boundaries. If two modules keep sharing entities and calling each other in cycles, that is evidence the split is wrong - much cheaper to learn in one process than across a network.

```text
com.acme.shop
├── orders          ← own API, own tables, publishes OrderPlaced
├── inventory       ← consumes OrderPlaced, owns stock
├── payments        ← own API, own tables
├── catalog         ← exposes ProductCatalog (named interface)
└── shared          ← pure value types, no business logic
```

---

### 2. Declaring a Module

```java
// src/main/java/com/acme/shop/orders/package-info.java
@org.springframework.modulith.ApplicationModule(
        displayName = "Orders",
        allowedDependencies = { "catalog::api", "shared" }
)
package com.acme.shop.orders;
```

Everything under `com.acme.shop.orders` is the module. By default a module may use **other modules' root packages**, but `allowedDependencies` narrows that to an explicit list - ideally named interfaces rather than whole modules.

| Element | Meaning |
| :--- | :--- |
| **Module root package** | The boundary; subpackages are internal unless exposed |
| **`allowedDependencies`** | The only modules this one may reference |
| **Named interface** | A deliberately exposed slice of a module |
| **`shared`** | Value objects and primitives; never repositories or services |

The boundary is only real if the compiler or the test suite enforces it. Spring Modulith does that at test time:

```java
class ModularityTests {

    @Test
    void moduleBoundariesAreRespected() {
        ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
        modules.verify();                 // fails on cycles and illegal dependencies
    }
}
```

`verify()` reports:

- **Cycles** between modules (`orders → inventory → orders`).
- **Violations** of `allowedDependencies`.
- **Access to internal types** of another module.

Run it in the normal test suite, not a nightly job. A boundary violation that lives for a week becomes an accepted design.

For finer rules (naming, annotations, layering inside a module), add **ArchUnit** tests on top; Modulith checks module-level dependencies, ArchUnit checks the rest.

---

### 3. Named Interfaces: Expose Less Than You Think

A module's root package is public by accident unless you narrow it. `@NamedInterface` makes the public surface explicit:

```java
// src/main/java/com/acme/shop/catalog/api/package-info.java
@org.springframework.modulith.NamedInterface("api")
package com.acme.shop.catalog.api;

// src/main/java/com/acme/shop/catalog/internal/package-info.java
@org.springframework.modulith.ApplicationModule(
        type = ApplicationModule.Type.OPEN)   // internal subpackage, not a module
package com.acme.shop.catalog.internal;
```

```java
// Orders depends on the published API only
@ApplicationModule(allowedDependencies = "catalog::api")
package com.acme.shop.orders;
```

```java
// catalog/api/ProductCatalog.java - the contract
public interface ProductCatalog {
    Optional<ProductView> find(String productId);
    List<ProductView> search(String query, int limit);
}
```

Rules that keep the boundary honest:

- **Expose interfaces and immutable DTOs**, not entities or repositories.
- **No JPA entity leaks** across modules: an `@Entity` in the API package couples schemas and lazy-loading behaviour.
- **No shared repositories**: if two modules need the same table, one owns it and exposes a query method.
- **`shared` holds value types only** (money, ids, result types), never services.

---

### 4. Communicating Between Modules

Two options, and the choice matters:

| Style | Use when | Cost |
| :--- | :--- | :--- |
| **Synchronous API call** | The caller needs an answer to continue (validate a product exists) | Runtime coupling; caller waits |
| **Domain event** | The caller only needs to announce a fact (order placed) | Eventually consistent; needs idempotency and observability |

```java
// orders module: publish inside the transaction, after the state change
@Service
class OrderService {

    private final ApplicationEventPublisher events;
    private final OrderRepository orders;

    @Transactional
    public Order place(PlaceOrderCommand cmd) {
        Order order = orders.save(Order.create(cmd));
        events.publishEvent(new OrderPlaced(order.id(), cmd.lines(), order.total()));
        return order;
    }
}
```

```java
// inventory module: react after the publisher commits
@Component
class InventoryListener {

    @ApplicationModuleListener            // @Async + @Transactional(REQUIRES_NEW)
    void on(OrderPlaced event) {          // @TransactionalEventListener(AFTER_COMMIT)
        stock.reserve(event.orderId(), event.lines());
    }
}
```

`@ApplicationModuleListener` is the important semantic bundle:

| Property | Consequence |
| :--- | :--- |
| **After commit** | The listener never sees an order that rolled back |
| **New transaction** | A listener failure does not roll back the order |
| **Asynchronous** | The publisher does not wait; failures are invisible to the caller |
| **At-least-once** | The same event can be delivered twice; the listener must be idempotent (Q262) |

The **event publication registry** (enabled by the JPA starter) persists incomplete publications and republishes them after a crash or restart, so an event is not lost between "order committed" and "inventory listener ran". That is the in-process equivalent of the transactional outbox (Q260) - and it has the same requirement: consumers must be idempotent.

```yaml
spring:
  modulith:
    events:
      # Persist publications so a crash between commit and listener does not lose the event
      jpa:
        enabled: true
```

---

### 5. Events Do Not Remove the Need for Design

| Pitfall | Why it bites | Fix |
| :--- | :--- | :--- |
| **Publishing before commit** | Listener acts on state that later rolls back | Publish after the state change, inside the transaction; use `@ApplicationModuleListener` |
| **Listener assumed synchronous** | Caller returns before inventory reserved | Accept eventual consistency in the API contract, or call synchronously when the answer is required |
| **Non-idempotent listener** | Duplicate reservation after republish | Unique constraint or inbox table (Q262) |
| **Listener throws silently** | Event marked incomplete forever, or lost after retries | Metrics/alerts on failed publications; dead-letter handling |
| **Event carrying entities** | Serialization and coupling problems | Events carry ids and immutable values |
| **Ordering assumptions** | `OrderPlaced` and `OrderCancelled` race | Include sequence/version; make the consumer state-based |
| **Giant events** | Slow serialization, schema lock-in | Reference the aggregate; let the consumer query what it needs |

The registry solves durability, not semantics. If a listener fails permanently, the publication stays incomplete: that needs an alert and a retry/DLQ policy, exactly like a Kafka consumer group (Q259).

---

### 6. Testing Modules, Not Just Classes

```java
@ApplicationModuleTest                        // boots the module, not the whole application
class OrdersModuleTests {

    @Test
    void placingOrderPublishesEvent(Scenario scenario) {
        scenario.stimulate(() -> orders.place(command()))
                .andWaitForEventOfType(OrderPlaced.class)
                .toArrive();
    }
}
```

| Bootstrap mode | What is started | Use for |
| :--- | :--- | :--- |
| **`STANDALONE`** | The module alone, dependencies mocked | Pure unit-of-module tests |
| **`DIRECT_DEPENDENCIES`** (default) | The module plus modules it depends on | Most integration tests |
| **`ALL_DEPENDENCIES`** | The full application context | End-to-end flows |

`Scenario` gives you a deterministic way to assert event flows without sleeping: `stimulate(...)`, `andWaitForEventOfType(...)`, `andWaitForStateChange(...)`. Combined with `ApplicationModules.verify()` and `Documenter` output, module boundaries become testable and visible:

```java
@Test
void writeArchitectureDocs() {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
    new Documenter(modules)
            .writeModulesAsPlantUml()
            .writeDocumentation();          // Asciidoc/C4 component diagrams
}
```

Treat the generated diagram as a build artifact: a diff in the diagram is a design change worth reviewing.

---

### 7. The Extraction Path

A module becomes a candidate for extraction when it has at least one of these:

- **Independent scaling**: inventory spikes during sales while catalog is idle.
- **Different availability/SLO**: checkout cannot share a deployment with reporting.
- **Ownership**: a separate team can own the schema, release cadence, and on-call.
- **Compliance/data residency**: the data must live in another region or account (Q268).
- **Technology fit**: the workload needs a different runtime or store.

Extraction checklist:

1. **The module already owns its tables** and no other module reads them directly.
2. **Cross-module calls go through the named interface or events**, not shared entities.
3. **The outbox pattern is in place** for events that must survive the split (Q260).
4. **Idempotency and ordering** are already handled, because the network makes duplicates certain (Q262).
5. **Observability is per-module** (metrics/traces tagged by module) so you can compare before and after (Q230/Q266).
6. **The first step is a separate schema and a network API; the last step is a separate deployment** - not the other way round.

If a module fails step 1 or 2, extraction will produce a distributed monolith. Keep it in the monolith until the boundary is real.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Boundaries only in docs** | Modules import each other freely | `ApplicationModules.verify()` in CI |
| **Shared JPA entities** | Schema coupling, lazy-loading leaks | DTOs at the boundary; one owner per table |
| **`shared` becomes a dumping ground** | Every module depends on it; cycles return | Value types only; split by concept |
| **Cycle "solved" by moving code** | A new god module | Redesign the dependency direction; use events |
| **Wide `allowedDependencies`** | `allowedDependencies = "*"` | Depend on `module::api` named interfaces |
| **Listener assumed sync** | API returns success before stock is reserved | Contractual eventual consistency, or a synchronous call |
| **Non-idempotent listener** | Double reservation after restart/republish | Unique key or inbox table (Q262) |
| **Failed publications ignored** | Silent data loss or stuck registry | Alert on incomplete publications; DLQ/retry |
| **Event carries an entity** | Serialization failures, tight coupling | Ids + values; consumer queries if needed |
| **Module test boots everything** | Slow, flaky, no boundary feedback | `@ApplicationModuleTest(DIRECT_DEPENDENCIES)` |
| **Extracting too early** | Distributed monolith with network latency | Prove boundaries in-process first |
| **Extracting too late** | One module's load affects all; deployment queue | Extract on a concrete driver (scaling/team/compliance) |
| **No module-level metrics** | Cannot attribute latency or cost | Tag metrics/spans by module (Q230/Q266) |

### Summary

- **Spring Modulith makes boundaries enforceable in one deployable**: package roots define modules, `allowedDependencies` and `verify()` reject cycles and illegal access at build time.
- **Expose named interfaces, not packages of entities**: `module::api` with interfaces and immutable DTOs; keep `shared` to value types.
- **`@ApplicationModuleListener` means after-commit, async, new transaction, at-least-once** - the event registry adds durability, but the listener must be idempotent (Q262).
- **Test at module altitude** with `@ApplicationModuleTest` and `Scenario`, and generate diagrams as reviewable build artifacts.
- **Extract a service only on a concrete driver** (scaling, ownership, compliance, availability) and only after the module already owns its data and communicates through APIs/events.
- **A modular monolith is not a stepping stone you must leave**; it is a valid architecture whose boundaries make a later extraction cheap rather than a rewrite.

## 280. How do you scale Kafka consumers and keep lag under control in Spring Boot? Explain partition parallelism, poll budgets, backpressure, hot partitions, and lag-based autoscaling.

Consumer lag is a **rate** problem that people usually diagnose as a **count** problem. A group sitting at 50,000 messages is healthy if it drains in ten seconds and an emergency if it drains in six hours; the count alone tells you nothing. Lag grows when arrival rate exceeds processing rate for long enough, and the fixes are ordered: find the bottleneck (partition count, per-record cost, downstream saturation, rebalance churn), remove it, and only then add consumers - because adding consumers beyond the partition count does nothing at all. This is the throughput companion to the retry and DLQ design in Q259 and the shutdown/rebalance mechanics in Q261.

---

### 1. Lag: Count, Rate, and Age

```text
lag_records   = log_end_offset - committed_offset        (per partition)
lag_seconds   ≈ lag_records / consumption_rate_per_sec   (rough)
lag_age       = now - timestamp_of_next_unconsumed_record (most actionable)
```

| Signal | What it tells you | Trap |
| :--- | :--- | :--- |
| **Record lag** | Backlog size | Looks alarming during a normal burst |
| **Time lag / age** | How stale the consumer is | Requires offset-to-timestamp lookup; the number users feel |
| **Lag trend** | Whether you are catching up | A flat high lag is stable; a rising one is an incident |
| **Per-partition lag** | Hot partition, stuck consumer | Averages hide one partition at 10× the others |
| **Consumption rate vs production rate** | Whether the system can ever catch up | Rate measured over a window, not a spike |

Alert on **age and trend**, not on a raw threshold like "lag > 10,000". A consumer that is 30 seconds behind at peak traffic is fine; one that is 30 minutes behind at 3 a.m. is not.

```bash
kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --describe --group inventory
# CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
```

---

### 2. The Hard Ceiling: Partitions

```text
consumers actually doing work = min(total consumer threads, partitions)
```

| Partitions | Max useful consumer threads | Effect of more threads |
| :--- | :--- | :--- |
| 6 | 6 | Extra threads sit idle |
| 6, 3 pods × `concurrency=2` | 6 | Balanced |
| 6, 3 pods × `concurrency=4` | 6 | 6 idle threads, more memory, same throughput |

Partition count also caps **per-key ordering**: all records with the same key go to one partition and are processed by one consumer thread, in order. That is a feature for `orderId` events and a bottleneck for a celebrity key.

```yaml
spring:
  kafka:
    listener:
      concurrency: 4          # per instance; total ≤ partitions
```

Rules:

- **Size partitions for peak parallelism plus growth**, not for today's pod count. Increasing partitions later is possible but breaks key-to-partition stability and ordering guarantees during the transition.
- **Do not set `concurrency` above `partitions / replicas`**; you pay for threads and connections that can never be assigned work.
- **Know your target**: `partitions = max_pods × concurrency_per_pod` at peak, with headroom for a pod restart.

---

### 3. The Poll Budget

The consumer must call `poll()` within `max.poll.interval.ms`, or the broker removes it from the group, triggering a rebalance and redelivery.

```text
max.poll.records × p99_processing_time_per_record  <  max.poll.interval.ms × safety_factor
```

```text
500 records × 20 ms  = 10 s      ✓  (default max.poll.interval = 300 s)
500 records × 500 ms = 250 s     ✗  one slow batch and the consumer is kicked out
```

```yaml
spring:
  kafka:
    consumer:
      max-poll-records: 500
      fetch-min-size: 1MB
      fetch-max-wait: 500ms
      properties:
        max.poll.interval.ms: 300000
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
        group.instance.id: ${HOSTNAME}       # static membership (Q261)
    listener:
      type: batch
      ack-mode: manual
      concurrency: 4
```

| Knob | Raising it | Lowering it |
| :--- | :--- | :--- |
| **`max.poll.records`** | Higher throughput per poll, longer processing window | Safer poll interval, more round trips |
| **`fetch.min.bytes`** | Fewer fetch requests, higher latency | Lower latency, more requests |
| **`fetch.max.wait.ms`** | Lets a fetch fill up to `min.bytes` | Returns sooner with less data |
| **`max.partition.fetch.bytes`** | Handles large records | A record larger than this can stall the consumer |
| **`concurrency`** | More partitions consumed | Wasted threads above the partition count |
| **`ack-mode`** | Batch = fewer commits, more duplicates on failure | Record = more commits, lower throughput |
| **`max.poll.interval.ms`** | Tolerates slow batches | Delays detection of a genuinely stuck consumer |

The poll interval is a **hard deadline, not a target**. Keep the expected batch well under it, and make the failure mode explicit: if a batch can occasionally exceed it, lower `max.poll.records` rather than raising the interval to hours.

---

### 4. Acknowledgments That Do Not Lose Data

| Ack mode | Commit point | Duplicate window | Use |
| :--- | :--- | :--- | :--- |
| **`BATCH`** (default) | After the whole poll batch | Entire batch reprocessed on failure | Fast, idempotent consumers |
| **`RECORD`** | After each record | One record | Simpler reasoning, more commits |
| **`MANUAL`** | When you call `acknowledge()` | From last commit to the failure | Side effects must be committed first (Q262) |
| **`MANUAL_IMMEDIATE`** | Immediately on `acknowledge()` | Same, but commit per call | Precise control, more overhead |

```java
@KafkaListener(id = "inventory", topics = "orders", groupId = "inventory")
public void onBatch(List<ConsumerRecord<String, OrderEvent>> records, Acknowledgment ack) {
    // 1. Apply idempotently in one DB transaction (inbox/dedup, Q262)
    inventory.applyAll(records);
    // 2. Only after the transaction commits
    ack.acknowledge();
}
```

Never acknowledge before the side effect. With batch mode, one poison record rolls back the commit for the whole batch and every record is redelivered - which is fine only if the consumer is idempotent, and expensive if the batch is large. That is the trade-off between batching for throughput and batching for failure granularity.

---

### 5. Backpressure: Pause, Do Not Buffer

When the downstream (database, HTTP dependency) is saturated, the consumer should **stop fetching**, not accumulate records in memory.

```java
@Autowired
KafkaListenerEndpointRegistry registry;

void pauseConsumption() {
    registry.getListenerContainer("inventory").pause();
}

void resumeConsumption() {
    registry.getListenerContainer("inventory").resume();
}
```

| Approach | Effect | Risk |
| :--- | :--- | :--- |
| **Pause/resume the container** | Stops fetching; lag grows visibly | Lag alerts fire - which is correct |
| **Lower `max.poll.records`** | Smaller in-flight batch | Lower throughput |
| **Reduce `concurrency`** | Fewer partitions consumed | Under-utilises the group |
| **Unbounded in-memory queue** | "Keeps up" briefly | OOM, offset/commit ambiguity, data loss |
| **Block inside the listener** | Natural backpressure | Exceeds `max.poll.interval.ms` and rebalances |

Pausing is the honest signal: the broker keeps the data, the group's lag reflects reality, and autoscaling or a downstream fix can respond. Buffering hides the problem until the process dies.

---

### 6. Hot Partitions and Key Skew

Aggregate lag can look healthy while one partition is hours behind.

```text
24 partitions: 23 at lag 0, one at lag 2,000,000
→ the group is "fine" on average and broken for one key
```

Causes and fixes:

| Cause | Detection | Fix |
| :--- | :--- | :--- |
| **Celebrity key** (one customer/tenant dominates) | Per-partition lag, key distribution | Split the key (`customerId#shard`), aggregate downstream |
| **Null keys** | Even spread but no ordering | Accept round-robin; do not assume per-key order |
| **Custom partitioner bug** | One partition receives most records | Test the partitioner; prefer the default murmur2 |
| **Large records for one key** | Fetch/processing time per partition | Chunk payloads or store the blob and pass a reference |
| **Slow per-key processing** | One consumer's CPU pinned | Optimise the per-record work; parallelism inside a key is not free |

Splitting a hot key trades ordering for throughput: `orderId` stays ordered, but `customerId#0..N` shards are processed independently. Only do this when the business rule tolerates it (for example, aggregations that are commutative).

```java
// Keyless or sharded key: spread the load, lose strict per-key ordering
String key = customerId + "#" + ThreadLocalRandom.current().nextInt(8);
```

---

### 7. Rebalances: Make Them Rare and Cheap

| Setting | Recommendation | Why |
| :--- | :--- | :--- |
| **`partition.assignment.strategy`** | `CooperativeStickyAssignor` | Incremental revocation instead of stop-the-world |
| **`group.instance.id`** | Pod name / stable id | Static membership: a restart within the session timeout does not rebalance |
| **`session.timeout.ms`** | 10-45 s (broker default tuned) | Too low = false failures; too high = slow detection |
| **`heartbeat.interval.ms`** | ~1/3 of session timeout | Keeps liveness without churn |
| **`max.poll.interval.ms`** | Batch time × safety factor | The usual cause of "random" rebalances |
| **Deploy strategy** | Rolling, one pod at a time (Q261) | Avoids the whole group leaving at once |

A rebalance is not free: it stops consumption, revokes partitions, and can redeliver in-flight batches. On a large topic it can take tens of seconds, which is exactly when lag spikes and alerts fire.

---

### 8. Autoscaling on Lag

CPU-based autoscaling is the wrong signal for a consumer: a lagging consumer can be at 20% CPU because it is waiting on the database.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: inventory-consumer
spec:
  scaleTargetRef:
    name: inventory
  minReplicaCount: 2
  maxReplicaCount: 12              # ≤ partitions / concurrency
  cooldownPeriod: 300
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: broker:9092
        consumerGroup: inventory
        topic: orders
        lagThreshold: "1000"
        activationLagThreshold: "100"
```

| Rule | Reason |
| :--- | :--- |
| **`maxReplicaCount × concurrency ≤ partitions`** | Extra pods cannot get partitions |
| **Scale on lag, not CPU** | Lag reflects the actual backlog |
| **Set `activationLagThreshold`** | Avoid flapping around zero |
| **Use a cooldown** | Scale-in triggers a rebalance; do it slowly |
| **Prefer static membership** | Rolling scale events do not each cost a full rebalance |
| **Watch downstream** | More consumers can overwhelm the DB pool (Q232) or a dependency (Q270) |

If partitions = 12 and `concurrency` = 2, the useful maximum is 6 pods. Turning `maxReplicaCount` to 20 just creates pods that never receive work.

---

### 9. Catching Up Without Breaking Things

When lag is already hours deep, the order of operations matters:

1. **Confirm the consumer is progressing**, not stuck: per-partition offsets advancing, no rebalance loop, no repeated poison record.
2. **Remove the bottleneck**: slow DB writes (batch/upsert, Q271), synchronous HTTP per record, lock contention, GC pauses (Q227).
3. **Increase batch efficiency**: `max.poll.records`, batch listener, one DB transaction per batch, bulk writes.
4. **Scale to the partition ceiling**, with static membership and cooperative assignment.
5. **Only then add partitions**, and only for keyless or re-keyable topics; otherwise accept the ceiling and optimise.
6. **Watch the downstream**: a catch-up burst is a load spike for the database (Q232), caches (Q229), and any API the consumer calls (Q270).
7. **Do not skip records** to reduce lag. If a record is poison, route it to a DLT and continue (Q259); losing it silently is a data incident.

```text
Healthy catch-up: consumption rate > production rate, lag monotonically decreasing,
                  downstream latency within SLO, no rebalance churn.
Unhealthy:        lag flat while CPU is high  → bottleneck inside the consumer
                  lag flat while CPU is low   → waiting on downstream / fetch starvation
                  lag oscillating             → rebalance loop (max.poll.interval, GC)
```

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **More consumers than partitions** | Idle pods, no throughput gain | Cap replicas × concurrency at partition count |
| **`concurrency` above DB pool** | Pool exhaustion, timeouts (Q232) | Align concurrency with pool and downstream limits |
| **`max.poll.records` too high** | Rebalance loop, duplicate batches | Batch time well under `max.poll.interval.ms` |
| **Ack before side effect** | Silent data loss on crash | Ack after commit (Q262) |
| **Auto-commit with async work** | Offsets advance past unprocessed records | Disable auto-commit; manual ack |
| **Blocking retries in the listener** | Poll interval exceeded, group churn | Backoff off the poll thread or DLT (Q259) |
| **Aggregate lag only** | One hot partition hidden | Per-partition lag dashboard |
| **Alerting on lag count** | Noise at peak, misses slow drift | Alert on age/trend |
| **CPU-based autoscaling** | Scales while blocked on I/O | KEDA lag scaler |
| **Scaling to zero** | Cold start plus rebalance | Minimum replicas |
| **Adding partitions to a keyed topic** | Ordering broken mid-migration | Re-key or accept the ceiling |
| **Unbounded in-memory buffering** | OOM under sustained lag | Pause the container instead |
| **Ignoring consumer group churn** | Lag spikes on every deploy | Cooperative sticky + static membership (Q261) |

### Summary

- **Lag is a rate problem**: track age and trend per partition, not a single count, and alert on how stale the consumer is.
- **Parallelism is capped by partitions**; size partitions for peak `pods × concurrency`, and remember that more threads than partitions is wasted capacity.
- **Respect the poll budget**: `max.poll.records × p99 processing` must stay comfortably under `max.poll.interval.ms`, or you get rebalances and duplicate batches.
- **Ack after the side effect**, make consumers idempotent (Q262), and choose batch vs record acknowledgment based on failure granularity, not just throughput.
- **Backpressure means pause the container**, not buffer records: lag is the honest signal that downstream is saturated (Q232/Q270).
- **Autoscale on lag within the partition ceiling**, use cooperative sticky assignment plus static membership to keep rebalance costs low, and fix the bottleneck before adding consumers (Q259/Q261).

## 281. How do you sample distributed traces without losing the signal? Explain head-based vs tail-based sampling, OpenTelemetry Collector pipelines, and cost and cardinality control.

Tracing every request is affordable only at small scale. At 1,000 requests/second with ten spans each and roughly 1 KB per span, you are producing about **860 GB of trace data per day** before indexing overhead - and most of it is uninteresting. Sampling is unavoidable, but naive sampling destroys exactly the traces you need: the rare failures and the slow outliers. The design question is therefore not "what percentage?" but **where the decision is made and what it is allowed to know**. This builds on the context propagation in Q266 and the SLO design in Q230.

---

### 1. The Cost Arithmetic

```text
spans/sec  = RPS × spans per request
GB/day     = spans/sec × 86,400 × bytes/span / 1e9

1,000 RPS × 10 spans × 1 KB  ≈ 864 GB/day
sampled at 1%                ≈   8.6 GB/day
```

| Lever | Effect | Risk |
| :--- | :--- | :--- |
| **Sampling rate** | Linear reduction in volume | Loses rare events |
| **Span count per request** | Removes noise (framework/DB spans) | Loses diagnostic depth |
| **Attribute trimming** | Smaller spans, lower cardinality | Loses context if overdone |
| **Retention tiers** | Cheap long-term storage, expensive short-term | Query complexity |
| **Tail sampling** | Keeps 100% of errors/slow traces, drops the boring majority | Collector CPU/RAM |

Traces are for **diagnosis**, not for accounting. If a number must be exact - error rate, request count, latency percentiles - derive it from metrics or logs, not from sampled traces.

---

### 2. Head-Based Sampling: Decide at the Start

The root service decides before the request outcome is known, and propagates the decision in the trace flags. Downstream services honour it via a **parent-based** sampler, so a trace is either fully sampled or fully dropped.

```yaml
management:
  tracing:
    sampling:
      probability: 0.1        # 10% of root requests; parent-based by default
  otlp:
    tracing:
      endpoint: http://otel-agent:4318/v1/traces
```

| Property | Behaviour |
| :--- | :--- |
| **Cheap** | A random number at the root; no buffering |
| **Consistent** | Whole trace in or out |
| **Blind** | Does not know if the request will fail or take 30 s |
| **Uniform** | Rare endpoints get 10% of a small number - often zero |

Consequences:

- **A 1% error rate sampled at 1%** gives you one failing trace per 10,000 requests. Debugging a rare bug from that is hopeless.
- **Low-traffic endpoints** (webhooks, admin operations) may never appear.
- **SLO dashboards built from traces** become noise at low sample rates.

Head sampling is still the right default for high-volume, well-understood traffic: it is predictable, costs almost nothing, and keeps collectors simple. Use it as a **baseline**, then add tail sampling for the exceptions.

---

### 3. Tail-Based Sampling: Decide After the Trace Ends

A tail-sampling collector buffers all spans of a trace, waits for it to complete, then applies policies to the **whole trace**:

| Policy | Keeps |
| :--- | :--- |
| **`status_code: ERROR`** | Every failed trace, regardless of volume |
| **`latency > threshold`** | Slow outliers |
| **`probabilistic 1%`** | A baseline sample of healthy traffic |
| **`rate_limiting`** | Caps a policy so a failure storm cannot flood storage |
| **`string_attribute`** | Traces for a specific tenant, version, or feature flag |

```yaml
processors:
  tail_sampling:
    decision_wait: 10s              # must exceed p99 trace duration
    num_traces: 100000              # in-memory trace buffer
    expected_new_traces_per_sec: 2000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 500 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }
```

The catch is structural: **all spans of a trace must reach the same collector instance**, or each instance makes a decision on a partial trace and you get broken traces. That is why tail sampling is a two-tier topology, not a processor you drop on every agent.

| Aspect | Head-based | Tail-based |
| :--- | :--- | :--- |
| **Decision time** | Root span start | After trace completion |
| **Knows errors/latency** | No | Yes |
| **Buffering** | None | All spans, for `decision_wait` |
| **Topology** | Any | Trace-affinity routing required |
| **Cost** | Negligible | Collector RAM/CPU |
| **Typical use** | Baseline volume control | Error/outlier capture |

---

### 4. Two-Tier Collector Topology

```text
app pods ──OTLP──► agent (DaemonSet, per node)
                     │  batch, memory_limiter, k8s attributes
                     │  loadbalancing exporter: hash(trace_id)
                     ▼
                 gateway (StatefulSet/Deployment, headless service)
                     │  tail_sampling, redaction
                     ▼
                 Tempo / Jaeger / vendor backend
```

The agent does cheap work and routes by trace id; the gateway holds the buffers and makes the sampling decision. A headless service is required so the load-balancing exporter can see individual gateway pods.

```yaml
# agent
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 400
    spike_limit_mib: 100
  batch:
    timeout: 5s
    send_batch_size: 8192
  k8sattributes: {}

exporters:
  loadbalancing:
    routing_key: traceID
    resolver:
      dns:
        hostname: otel-gateway.observability.svc.cluster.local
    protocol:
      otlp:
        tls: { insecure: true }

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, k8sattributes, batch]
      exporters: [loadbalancing]
```

```yaml
# gateway
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 2048
    spike_limit_mib: 512
  tail_sampling:
    decision_wait: 10s
    num_traces: 200000
    expected_new_traces_per_sec: 2000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 500 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }
  batch:
    timeout: 5s

exporters:
  otlphttp/backend:
    endpoint: https://traces.example.com
    headers:
      authorization: "Bearer ${env:TRACE_TOKEN}"

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, tail_sampling, batch]
      exporters: [otlphttp/backend]
```

| Component | Why it is there |
| :--- | :--- |
| **`memory_limiter`** | Drops data before the process OOMs; the first processor in every pipeline |
| **`batch`** | Fewer, larger exports; lower network overhead |
| **`k8sattributes`** | Adds pod/namespace/node attributes without app changes |
| **`loadbalancing`** | Trace-affinity routing to gateways |
| **`tail_sampling`** | Whole-trace policy decisions |
| **Headless service** | DNS returns gateway pod IPs for the resolver |

---

### 5. Sampling Interacts With Everything Else

| Interaction | Consequence | Guidance |
| :--- | :--- | :--- |
| **SLO metrics derived from spans** | Sampled traces under-count errors and skew percentiles | Compute SLOs from server metrics (Q230); use traces for diagnosis |
| **Span metrics connector** | RED metrics inherit the sampling policy; errors may be over-represented if tail sampling keeps all of them | Either use a separate metrics pipeline or document the bias |
| **Exemplars** | Link a metric point to a sampled trace | Keep exemplar sampling independent of bulk sampling |
| **Head + tail** | 10% head then 10% tail = 1% overall; error traces are still capped by the head decision | Use head sampling high enough (or 100%) when tail policies must see every error |
| **Late spans** | Arrive after `decision_wait`; trace is split or dropped | Set `decision_wait` above p99 duration; keep clock skew small |
| **Collector restart** | In-memory trace buffer is lost | Accept sampling loss, or buffer upstream; gateways should be recreated gracefully |
| **Multiple gateways** | Without trace-id routing, traces are partial | Load-balance by `traceID`, never round-robin |

The head/tail interaction is the one that surprises teams: tail sampling can only keep what head sampling forwarded. If the SDK drops 90% at the root, the "keep all errors" policy sees only 10% of errors.

---

### 6. Cardinality and Privacy

Span attributes are a data store with no schema police.

| Attribute | Safe? | Why |
| :--- | :--- | :--- |
| `http.request.method`, `http.route` (`/orders/{id}`) | Yes | Bounded values |
| `http.url` with raw path/query | No | Unbounded, may contain tokens or PII |
| `user.id`, `order.id`, `session.id` | No | Massive cardinality, privacy risk |
| `tenant.id` | Only if bounded and necessary | Thousands of tenants still explode indexes (Q253) |
| `db.statement` with literals | No | PII plus cardinality; use sanitized templates |
| Error message with user input | No | PII, secrets, unbounded text |

Controls:

- **Prefer route templates** over concrete paths: `/orders/{id}`, not `/orders/123`.
- **Allow-list attributes** at the collector; drop the rest rather than trusting every SDK.
- **Redact before export**: emails, tokens, auth headers, card numbers (Q269).
- **Bound span names**: `GET /orders/{id}` is fine; `GET /orders/9182?token=...` is a cardinality bomb.
- **Keep logs and traces correlated by ids, not by embedding payloads**; logs have their own retention and redaction rules.

```yaml
processors:
  attributes/redact:
    actions:
      - key: http.request.header.authorization
        action: delete
      - key: user.email
        action: delete
      - key: url.query
        action: delete
```

---

### 7. Diagnosing Sampling Problems

| Symptom | Likely cause |
| :--- | :--- |
| Traces have missing spans | Not all spans reached the same tail-sampling collector |
| Errors never appear in traces | Head sampling too low; tail policy never sees them |
| Trace volume did not drop after adding tail sampling | Head sampling is already 100% and policies keep too much |
| Gateway OOM/restarts | `num_traces` or `decision_wait` too large for the span rate |
| Latency spikes in the app | Exporter queue full / synchronous export path |
| Span count explodes after a release | A new high-cardinality attribute or per-row span |
| Percentiles differ between traces and metrics | Metrics and traces sample different populations |

Operational checks:

```bash
# Collector internal telemetry (enable the prometheus exporter on :8888)
curl -s localhost:8888/metrics | grep -E 'otelcol_(receiver|processor|exporter)'
# Look for: refused_spans, dropped_spans, queue_size, send_failed
```

Alert on **dropped spans** and **queue saturation**, not just on backend ingestion. A collector silently dropping 40% of spans makes every dashboard subtly wrong.

---

### 8. A Practical Default

| Traffic | Strategy |
| :--- | :--- |
| **Low volume (< 100 spans/s)** | 100% head sampling; no tail collector needed |
| **Medium, error-sensitive** | 100% head at the edge? No - use 20-50% head plus tail policies for errors/slow |
| **High volume** | 5-10% head baseline, tail sampling for errors, latency, and a small probabilistic baseline |
| **Regulated data** | Redact at the SDK or agent before export; tail sampling must not become a PII reservoir |
| **Cost-constrained** | Tail sampling at the gateway, attribute allow-list, shorter retention for healthy traces |

A common production setup is: **head 10% for baseline cost control, tail policies that keep every error and every trace over the latency SLO, plus 1% of healthy traces** - and metrics for anything that must be exact.

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **1% head sampling, expecting rare errors** | No failing traces to debug | Tail sampling, or raise head rate for critical paths |
| **Tail sampling on every agent** | Partial traces, decisions per node | Two-tier: agent → gateway by trace id |
| **Round-robin to gateways** | Spans split across buffers | Load-balance on `traceID`, headless service |
| **`decision_wait` shorter than p99 trace** | Late spans dropped; split traces | Increase wait; cap trace duration |
| **No `memory_limiter`** | Collector OOM under burst | Memory limiter first in the pipeline |
| **No `num_traces` budget** | Gateway restarts, sampling gaps | Size buffer to `rate × wait` plus headroom |
| **SLOs computed from sampled spans** | Error rate and p99 drift from reality | Use metrics for SLOs (Q230) |
| **Span metrics inherit error-biased tail policy** | Error ratio looks inflated | Separate metrics pipeline or document bias |
| **High-cardinality attributes** | Backend indexing cost explosion | Route templates, allow-list, redaction |
| **PII in spans** | Compliance incident | Redact at collector (Q269) |
| **Double sampling** | 10% head × 10% tail = 1%, surprises everyone | Compute the combined rate explicitly |
| **Collector drop not monitored** | Silent blind spots | Alert on dropped/refused spans |
| **Changing sampling during an incident** | Baselines shift mid-debug | Change deliberately, record the change |

### Summary

- **Sampling is a design decision about what you must never lose**, not a percentage: keep errors and latency outliers, sample the boring majority.
- **Head-based sampling is cheap and blind**: it decides at the root, cannot see the outcome, and can miss rare failures entirely; use it for baseline volume, not for guarantees.
- **Tail-based sampling sees the whole trace** and can keep all errors plus a latency threshold, but requires trace-affinity routing and a buffering budget.
- **Run two tiers**: agents batch and route by `traceID`; gateways run `tail_sampling` with a `memory_limiter` and export to the backend.
- **Never derive exact SLOs from sampled traces**; metrics are authoritative, traces are for diagnosis (Q230), and span-derived metrics inherit the sampling policy.
- **Control cardinality and privacy at the collector** with route templates, attribute allow-lists, and redaction, and alert on dropped spans so blind spots are visible (Q269).

## 282. How do you design backups and prove they work? Explain RPO/RTO, point-in-time recovery, immutable copies, restore drills, and application-level validation.

A replica is not a backup. Replication protects against a **node** failure and faithfully reproduces a `DELETE`, a bad migration, or ransomware within milliseconds. A backup protects against **logical and human** disasters, and a disaster recovery plan protects against losing an entire region or account. The only meaningful measure of a backup is a **measured restore**: how long it took, to which point in time, and whether the application actually worked afterwards. Everything else - retention dashboards, green backup jobs, "100% success" graphs - is a claim you have not tested.

---

### 1. Replication, Backup, and DR Are Different Things

| Mechanism | Protects against | RPO | RTO | Does **not** protect against |
| :--- | :--- | :--- | :--- | :--- |
| **Synchronous replica** | Node/AZ failure | ~0 | seconds-minutes | Bad writes, `DROP TABLE`, ransomware |
| **Async replica / cross-region** | Region failure | seconds | minutes | Logical corruption (propagates) |
| **PITR backup (base + WAL)** | Corruption, bad migration, deletion | minutes | 30 min - hours | Region loss if stored only there |
| **Cross-account immutable backup** | Ransomware, account compromise | minutes-hours | hours | Everything if keys are lost |
| **Rebuild from source of truth** | Derived stores (search, cache) | n/a | hours | Source-of-truth loss |

The trap is treating replication as DR: a replicated `DELETE FROM payments` is on every replica before anyone notices, and a compromised production account can delete the backups stored in the same account.

---

### 2. RPO and RTO, per Data Class

- **RPO (Recovery Point Objective)**: how much data you can afford to lose, expressed in time.
- **RTO (Recovery Time Objective)**: how long the service can be down, measured from declaration to working traffic.

| Tier | Data | RPO | RTO | Mechanism |
| :--- | :--- | :--- | :--- | :--- |
| **T0** | Payments ledger, audit trail | 0-5 min | 1 h | Sync replica + PITR + WORM copies |
| **T1** | Orders, inventory | 5 min | 2 h | PITR + cross-region copies |
| **T2** | User profiles, preferences | 1 h | 4 h | Daily snapshot + WAL |
| **T3** | Analytics, reports | 24 h | 24 h | Nightly export to warehouse |
| **Derived** | Search index (Q278), cache (Q274) | n/a | 4 h | Rebuild from source |
| **Ephemeral** | Sessions, rate-limit counters | acceptable loss | minutes | Recreate |

RTO is **end-to-end**, not just "database restored". It includes DNS, TLS certificates, secrets and KMS access, IAM roles, queue configuration, container images, and the first successful request through the load balancer. Most failed DR tests fail on one of those, not on the data restore.

---

### 3. Backup Types and What They Actually Give You

| Type | Example | Restore granularity | Cost/Time |
| :--- | :--- | :--- | :--- |
| **Logical dump** | `pg_dump`, `mysqldump` | Whole DB or selected tables | Slow for TB-scale; portable across versions |
| **Physical base backup + WAL** | `pg_basebackup` + archive | Any point in time | Fast restore; version/architecture bound |
| **Storage snapshot** | EBS/RDS/CSI snapshot | Snapshot instant | Instant to create, needs consistency |
| **Managed PITR** | RDS/Aurora/Cloud SQL | Point in time within retention | Easy, but vendor-bound and retention-capped |
| **Application export** | Parquet/CSV to object storage | Dataset/table | Good for archives (Q272), not for RTO |

**Crash-consistent snapshots are not application-consistent.** A volume snapshot of a running database without WAL/redo can restore to a torn state. For PostgreSQL, either take the snapshot in a backup mode that captures the WAL position, or rely on `pg_basebackup`/managed PITR.

---

### 4. PostgreSQL PITR: The Mechanics

```conf
# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'aws s3 cp %p s3://acme-pg-wal/%f --sse aws:kms'
archive_timeout = 60          # bound the RPO for low-traffic periods
```

```bash
# Weekly (or daily) base backup, WAL streamed alongside it
pg_basebackup -h primary.internal -D /backup/base -Ft -z -X stream -P
aws s3 cp /backup/base/base.tar.gz s3://acme-pg-backup/2026-11-09/
```

```bash
# Restore into an isolated environment
export PGDATA=/restore/pgdata
mkdir -p "$PGDATA" && tar -xzf base.tar.gz -C "$PGDATA"

cat >> "$PGDATA/postgresql.auto.conf" <<'EOF'
restore_command = 'aws s3 cp s3://acme-pg-wal/%f %p'
recovery_target_time = '2026-11-09 10:00:00+00'
recovery_target_action = 'promote'
EOF

touch "$PGDATA/recovery.signal"
pg_ctl start -D "$PGDATA"
```

Verification is not optional:

```sql
-- Reached the requested point, not the end of the WAL
SELECT pg_last_wal_replay_lsn(), now();

-- Business-level checks, not just "the server started"
SELECT count(*) FROM payments WHERE created_at >= now() - interval '1 day';
SELECT count(*) FROM orders WHERE status = 'PAID'
  AND id NOT IN (SELECT order_id FROM payments);
SELECT max(created_at) FROM audit_log;
```

| Failure | Symptom at restore time |
| :--- | :--- |
| **WAL archive gap** | `could not find file ...`; restore stops before the target |
| **Missing base backup** | Nothing to start from |
| **Wrong timeline** | `requested timeline ... not found` after a failover |
| **Extensions/roles missing** | App fails on first query even though data is present |
| **Sequences not advanced** | Duplicate key errors after cutover |

`archive_command` failures are silent unless monitored. Alert on `pg_stat_archiver.failed_count`, archived-WAL age, and base-backup age - not on "the cron job exited 0".

---

### 5. Beyond PostgreSQL

| Store | Backup mechanism | Restore reality |
| :--- | :--- | :--- |
| **Kafka** | Replication + MirrorMaker 2 / cluster linking; topic data is not usually "restored" | Replay from the source/outbox, not from a backup; consumer offsets matter (Q262) |
| **Elasticsearch** | Snapshot repository (SLM) | Restore snapshots or rebuild from the DB (Q278) |
| **Redis** | RDB/AOF if durable, otherwise rebuild | Cache: rebuild; locks/ephemeral state: accept loss (Q274) |
| **Object storage** | Versioning + cross-region replication + Object Lock | Restore previous versions; enforce immutability |
| **Kubernetes state** | GitOps for manifests; Velero/CSI snapshots for PVs | Recreate from Git; PVs only if they hold unique data |
| **Secrets** | Vault/secret manager backup or re-seed | Losing the root key loses everything |

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: orders-pvc-2026-11-09
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: orders-data
```

```bash
velero backup create cluster-2026-11-09 --include-namespaces shop
velero restore create --from-backup cluster-2026-11-09
```

**Kafka does not have a "restore to 10:00" button.** If events are the source of truth, back up the outbox table and the consumer offsets, and make replay idempotent (Q260/Q262). If the database is the source of truth, Kafka is rebuildable.

---

### 6. Immutability: Make the Backups Unreachable

The threat model is not only disk failure; it is a compromised credential with delete permission.

- **3-2-1 rule**: three copies, two media/accounts, one off-site.
- **Separate account/project** for backups, with a write-only role from production and no delete permission.
- **Object Lock in compliance mode** for the retention window: even the root account cannot delete before it expires.
- **Versioning + lifecycle** on object storage, so an overwrite is recoverable.
- **KMS key custody**: encrypt backups with a key the production account cannot delete; losing the key is data loss (Q269 crypto-shredding is a feature for erasure, a disaster for backups).
- **Audit access**: every restore attempt and every delete on the backup bucket is logged (Q269).

```bash
# Bucket-level protection; retention cannot be shortened in compliance mode
aws s3api put-object-lock-configuration \
  --bucket acme-pg-backup \
  --object-lock-configuration '{"ObjectLockEnabled":"Enabled",
      "Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":35}}}'
```

Also protect the **recovery path**: if restoring requires a credential stored only in the compromised account, the backup is not isolated.

---

### 7. The Restore Drill

A backup is a hypothesis until you run a restore. Do it on a schedule, not during the incident.

```text
1. Pick a scenario: "restore orders to 10:00, 30 minutes before the bad migration"
2. Provision an isolated account/network from IaC (no access to production)
3. Restore base + replay WAL to the target timestamp
4. Validate data: counts, checksums, foreign keys, business invariants
5. Start the application against the restored DB and run smoke tests
6. Measure wall-clock RTO: declaration → first successful request
7. Record gaps, file fixes, destroy the environment
```

| Validation | Why counts alone are not enough |
| :--- | :--- |
| **Row counts per tenant/table** | Detects partial restores |
| **Checksums on critical columns** | Detects silent corruption |
| **Referential integrity** | Orphans after a partial restore |
| **Business invariants** | Paid orders have payments; stock never negative |
| **Sequence/identity state** | Post-restore inserts do not collide |
| **App smoke test** | Schema, extensions, roles, config all present |
| **RTO measurement** | The only number that matters for the objective |

Frequency: **quarterly** for T0/T1, **annually** for archives, and after any change to backup tooling, schema, or infrastructure. Automate the drill so it runs unattended and reports a pass/fail plus duration.

---

### 8. Cutover Without Breaking Things

Restoring is only half the job; putting it into service is the other half.

- **Freeze writes** or accept a defined RPO gap during cutover; document which.
- **Fence the old primary** so two writers cannot diverge (split-brain is worse than downtime).
- **Reset sequences** after a logical restore.
- **Rebuild derived stores** (search, cache) rather than restoring them (Q278/Q274).
- **Republish or reconcile events** that were produced but not consumed; use the outbox and idempotent consumers (Q260/Q262).
- **Recreate credentials and rotate** anything exposed during the incident (Q243).
- **Warm caches and connection pools** before sending full traffic (Q232).

```text
Restore timeline (measured, not estimated):
T+0    declare
T+5    provision isolated network + DB instance
T+25   base restore complete
T+45   WAL replay to target
T+55   validation queries pass
T+75   app smoke test passes
T+90   traffic cut over (RTO = 90 min, target was 120)
```

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Backups never restored** | First restore is during the incident | Scheduled, automated drills |
| **Replica treated as backup** | Corruption/deletion replicated instantly | PITR + immutable copies |
| **Backups in the same account/region** | Ransomware or region loss takes both | Cross-account, cross-region, Object Lock |
| **Crash-consistent DB snapshot** | Torn pages / inconsistent restore | Base backup + WAL, or managed PITR |
| **WAL archive gap** | Restore stops before the target | Alert on archive failures and age |
| **No base backup for the window** | Cannot restore to the desired point | Retention must cover the RPO window |
| **Keys stored with the backups** | Encryption provides no protection | Separate KMS account/key, tested access |
| **KMS key deleted during cleanup** | Backups unreadable forever | Deletion protection; separate key lifecycle |
| **RTO measured only for the DB** | "Restore took 40 min" but service down 6 h | Measure end-to-end, including DNS/TLS/secrets |
| **Sequences/identity not reset** | Duplicate key errors after cutover | Reset sequences, validate inserts |
| **Derived stores restored from backup** | Stale index/cache after cutover | Rebuild from source |
| **Old primary still writable** | Split-brain, divergent data | Fence before restore |
| **Retention shorter than the incident** | Backup expired before anyone noticed | Retention exceeds detection window |
| **Drill environment has production access** | Test becomes an incident | Isolated account/network, read-only copies |
| **No runbook ownership** | Everyone assumes someone else knows | Named owner, reviewed quarterly |

### Summary

- **Replication is availability; backups are recovery from logical damage; DR is recovery from losing a region or account** - you need all three, and they have different RPO/RTO.
- **Define RPO/RTO per data class**, and measure RTO end-to-end: data plus DNS, TLS, secrets, IAM, queues, and the first successful request.
- **PITR needs a base backup plus a gap-free WAL archive**, and the archive must be monitored; a green backup job proves nothing.
- **Make copies immutable and isolated** (separate account, Object Lock, independent KMS custody), because the realistic threat is a credential that can delete.
- **Drill the restore on a schedule**, into an isolated environment, and validate counts, checksums, integrity, sequences, and application smoke tests - not just "server started".
- **Cutover is part of the plan**: fence the old primary, reset sequences, rebuild derived stores, reconcile events, and rotate credentials (Q243/Q260/Q274/Q278).

## 283. How do you evolve Kafka event schemas safely? Explain Avro and Protobuf, Schema Registry compatibility modes, serializer configuration, and rolling consumer upgrades.

In a request/response API the provider and consumer are deployed by different teams on different schedules - and events are worse, because the broker stores messages written by **old producers** and delivers them to **new consumers** long after the deploy. A schema change that is "obviously safe" (a renamed field, a new enum value, a reused protobuf tag) fails at 2 a.m. as a poison pill that blocks a partition (Q259). The goal is a schema contract with **automated compatibility checks**, a defined **upgrade order**, and a migration path for the changes that genuinely cannot be made compatible. This is the event-stream counterpart of the API rules in Q276.

---

### 1. What "Compatible" Actually Means

A schema change is compatible if **old data can be read by the new consumer** and/or **new data can be read by the old consumer** - and the answer differs by direction.

| Mode | Meaning | Deploy order |
| :--- | :--- | :--- |
| **BACKWARD** | New schema can read data written with the previous schema | **Consumers first**, then producers |
| **FORWARD** | Old schema can read data written with the new schema | **Producers first**, then consumers |
| **FULL** | Both directions | Either order |
| **BACKWARD_TRANSITIVE** | New schema can read **all** previous versions | Consumers first |
| **FORWARD_TRANSITIVE** | All previous versions can read the new schema | Producers first |
| **FULL_TRANSITIVE** | Both, against every version | Either |

Transitive modes matter because a consumer may be **three versions behind**; checking only against the latest version lets a change through that breaks a straggler.

```text
BACKWARD (the common default):
  1. deploy consumers that understand v2
  2. wait until no v1 consumers remain (lag drained, old pods gone)
  3. deploy producers that write v2

FORWARD:
  1. deploy producers that write v2 (old consumers must tolerate it)
  2. deploy consumers later
```

Choosing the mode is choosing the rollout choreography. `BACKWARD` fits "consumers are upgraded first"; `FORWARD` fits "producers ship first". `FULL_TRANSITIVE` is the safest for long-lived public topics and costs the most design discipline.

---

### 2. Choosing a Format

| Format | Schema | Strengths | Weaknesses |
| :--- | :--- | :--- | :--- |
| **JSON (no schema)** | None | Trivial, human-readable | No contract; unknown types; silent breakage |
| **JSON Schema** | In registry | Familiar, readable | Larger payloads; validation only |
| **Avro** | In registry, resolved by writer/reader | Compact binary, strong evolution rules, defaults | Requires codegen or generic records; schema resolution subtleties |
| **Protobuf** | In registry (or embedded file descriptors) | Compact, field numbers, many languages, gRPC alignment (Q255) | Never reuse tag numbers; `Any` hides the contract |

Avro is the common choice for Kafka because **schema resolution is built in**: the writer schema is identified by an ID in the registry, and the reader resolves it against its own schema, filling defaults and ignoring unknown fields.

```text
Confluent wire format:
[ magic byte 0x00 ][ 4-byte schema id ][ Avro/Protobuf payload ]
```

The schema ID is what makes "old data, new consumer" possible; the deserializer fetches that schema once and caches it.

---

### 3. Avro Rules That Matter

```json
{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "com.acme.events",
  "fields": [
    { "name": "orderId",    "type": "string" },
    { "name": "totalCents", "type": "long" },
    { "name": "currency",   "type": "string", "default": "USD" },
    { "name": "channel",    "type": ["null", "string"], "default": null }
  ]
}
```

| Change | BACKWARD | FORWARD | Notes |
| :--- | :--- | :--- | :--- |
| **Add a field with a default** | Yes | Yes | Old readers ignore unknown fields |
| **Add a field without a default** | **No** | Yes | New reader cannot fill old data |
| **Remove a field** | Yes | Only if the old schema had a default | Old readers need a value |
| **Rename a field** | No | No | Use `aliases` for a compatible rename |
| **Promote `int` → `long`** | Yes | Yes | Also `float` → `double` |
| **Change `string` ↔ `bytes`** | Yes | Yes | Limited promotion rules |
| **Add an enum symbol** | Yes | **No** | Old readers without the symbol fail |
| **Remove an enum symbol** | No | Yes | Depends on direction |
| **Change a default value** | Yes (shape) | Yes (shape) | **Semantics change** - see Q276 |

`aliases` is the only safe rename:

```json
{ "name": "currencyCode", "type": "string", "default": "USD",
  "aliases": ["currency"] }
```

Defaults are the mechanism that makes old data readable by new code; a required field added to a live topic is a breaking change by definition.

---

### 4. Protobuf Rules That Matter

```proto
syntax = "proto3";

message OrderPlaced {
  reserved 3, 5;              // never reuse these numbers
  reserved "legacy_total";

  string order_id    = 1;
  int64  total_cents = 2;
  string currency    = 4;
  optional string channel = 6;
}
```

| Change | Wire-compatible? | Why |
| :--- | :--- | :--- |
| **Add a field** | Yes | Unknown fields are ignored/preserved |
| **Remove a field** | Yes, if number is `reserved` | Old data still parses |
| **Reuse a removed tag number** | **No** | Silent type confusion |
| **Rename a field** | Yes (name is not on the wire) | JSON mapping changes, though |
| **Change `int32` → `int64`** | Usually yes | Varint compatible |
| **Change numeric → string** | **No** | Different wire type |
| **Change `optional`/required semantics** | **No** (proto2) | Presence contract |
| **Wrap payload in `google.protobuf.Any`** | Hides compatibility | No schema check can see inside |

Protobuf's wire compatibility is excellent for additive change and terrible for tag reuse; `reserved` is the guard rail, and CI should fail if a removed number reappears.

---

### 5. Schema Registry and Spring Kafka Configuration

```yaml
spring:
  kafka:
    producer:
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
      properties:
        schema.registry.url: https://schema-registry.internal:8081
        auto.register.schemas: false        # production: CI registers, not the app
        use.latest.version: true
        latest.compatibility.strict: true   # fail fast on an incompatible latest
    consumer:
      value-deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
      properties:
        schema.registry.url: https://schema-registry.internal:8081
        specific.avro.reader: true
```

| Property | Why it matters |
| :--- | :--- |
| **`auto.register.schemas=false`** | Stops a producer from silently creating an incompatible version in production |
| **`use.latest.version=true`** | Serializer uses the latest registered schema instead of an embedded one |
| **`latest.compatibility.strict=true`** | Rejects a producer whose schema is incompatible with the subject's latest |
| **`specific.avro.reader=true`** | Deserializes into generated classes rather than `GenericRecord` |
| **`value.subject.name.strategy`** | How the subject is derived; default `TopicNameStrategy` → `orders-value` |

Subject strategies:

| Strategy | Subject | Use |
| :--- | :--- | :--- |
| **`TopicNameStrategy`** (default) | `orders-value` | One event type per topic |
| **`RecordNameStrategy`** | `com.acme.events.OrderPlaced` | Many event types per topic, per-type compatibility |
| **`TopicRecordNameStrategy`** | `orders-com.acme.events.OrderPlaced` | Many types per topic, per-topic+type |

One schema per topic is simple but breaks as soon as the topic carries `OrderPlaced` and `OrderCancelled`; then you need record-name subjects, or separate topics.

---

### 6. Make Compatibility a Build Gate

Do not rely on the serializer at deploy time. Register and verify in CI:

```xml
<plugin>
    <groupId>io.confluent</groupId>
    <artifactId>kafka-schema-registry-maven-plugin</artifactId>
    <version>${confluent.version}</version>
    <configuration>
        <schemaRegistryUrls>
            <schemaRegistryUrl>http://localhost:8081</schemaRegistryUrl>
        </schemaRegistryUrls>
        <subjects>
            <orders-value>src/main/avro/OrderPlaced.avsc</orders-value>
        </subjects>
    </configuration>
    <executions>
        <execution>
            <id>check-compatibility</id>
            <phase>verify</phase>
            <goals><goal>test-compatibility</goal></goals>
        </execution>
    </executions>
</plugin>
```

```bash
# Locally, against a throwaway registry from Testcontainers
docker run -d -p 8081:8081 confluentinc/cp-schema-registry:7.6.0 ...
./mvnw verify          # fails if orders-value is not BACKWARD/FULL compatible
```

The CI gate should also:

- **Deserialize old fixtures** (real records captured from production or generated from previous schemas) with the new code.
- **Check protobuf field numbers** with `buf breaking` or equivalent.
- **Verify subject naming** stayed stable (a changed strategy creates a new subject and silently skips compatibility).
- **Forbid `auto.register`** in production config with a test/static check.

---

### 7. When the Change Is Incompatible

Some changes cannot be made compatible: changing a field's meaning, deleting a concept, or reshaping an event. Treat it like an API version:

```text
1. Publish orders.v2 (or a new record type) alongside orders.v1
2. Dual-publish during the migration window, or build v2 readers that can
   consume both (adapter at the boundary)
3. Migrate consumers topic by topic; track lag per group to know who is done
4. Stop producing v1 after the last consumer moves
5. Retain v1 data for the replay window (consumers may still need to rebuild)
6. Delete the topic/schema only after the retention window passes
```

| Approach | Cost | Notes |
| :--- | :--- | :--- |
| **Additive change + defaults** | Lowest | Always try this first |
| **New record type in the same topic** | Medium | Needs `RecordNameStrategy` |
| **New topic `orders.v2`** | High | New consumer groups, dual publish, migration tracking |
| **Recreate the topic** | Highest | Only for short-retention, fully controlled streams |

Do not "fix" an incompatible schema by bumping the registry compatibility mode to `NONE`. That converts a visible governance problem into a runtime poison pill and destroys the only automated protection you have.

---

### 8. Operating the Registry Itself

- **HA**: schema registry is on the critical path for cold starts; run at least two instances behind a load balancer.
- **Caching**: producers/consumers cache schemas by ID, so a registry outage during steady state is usually survivable; a cold start during an outage is not.
- **Fail fast**: prefer a startup failure over silently falling back to unvalidated JSON.
- **Backups**: export subjects and versions; the registry is a small but critical dataset (Q282).
- **Access control**: producers should not be able to change compatibility or delete subjects; CI/service accounts only, with audit logs.
- **Tombstones**: compacted topics use null values for deletion; make sure deserializers handle null and that the serializer does not try to resolve a schema for it.

```bash
# Inspect and export
curl -s localhost:8081/subjects
curl -s localhost:8081/subjects/orders-value/versions
curl -s localhost:8081/subjects/orders-value/versions/latest | jq .
curl -s localhost:8081/config/orders-value
```

---

### 9. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **`auto.register.schemas=true` in prod** | Incompatible schema registered by a random deploy | `false`; CI registers |
| **Compatibility mode `NONE`** | No protection; consumers break at runtime | `BACKWARD`/`FULL_TRANSITIVE` |
| **Required field added without default** | Old data cannot be read | Add with a default, or version the topic |
| **Field renamed without alias** | `null`/missing values in consumers | `aliases` in Avro |
| **Protobuf tag number reused** | Silent type confusion, corrupted data | `reserved`; CI check |
| **Enum symbol added under FULL** | Old consumers fail on new value | Version, or make consumers tolerant |
| **Consumer/producer upgrade order reversed** | Deserialization failures during rollout | Match the mode's rollout order |
| **One subject for multiple event types** | Conflicting schemas on `orders-value` | `RecordNameStrategy` or separate topics |
| **Changed subject naming strategy** | Compatibility skipped for a "new" subject | Keep naming stable; verify in CI |
| **Registry down at cold start** | Pod crash loop | HA registry, sane timeouts, cache warm |
| **Tombstone treated as a value** | Deserialization error on compacted topics | Handle null explicitly |
| **Semantics changed, shape unchanged** | Wrong units/currency downstream | Treat meaning as part of the contract (Q276) |
| **Old fixtures never tested** | New code cannot read historical records | Replay captured records in CI |

### Summary

- **Events are long-lived contracts**: old producers and new consumers coexist, so compatibility is directional and must be declared per subject.
- **Pick a mode and match the rollout**: `BACKWARD` → consumers first; `FORWARD` → producers first; `FULL_TRANSITIVE` is the safe default for long-lived topics.
- **Avro compatibility lives in defaults and aliases** (add with default, never rename without alias); **Protobuf compatibility lives in field numbers** (never reuse, always `reserved`).
- **Register schemas in CI, not in production**: `auto.register.schemas=false`, `use.latest.version=true`, `latest.compatibility.strict=true`, plus old-fixture deserialization tests.
- **Incompatible changes get a new topic or record type with dual-publish and a tracked migration**, never a registry mode of `NONE`.
- **Operate the registry as critical infrastructure**: HA, backups, access control, schema caches, and explicit null/tombstone handling (Q282).

## 284. How do you run GraphQL at scale across teams with federation? Explain subgraphs, entity resolution, schema composition, batching, authorization, and schema evolution.

A single GraphQL schema owned by one team works until five teams need to contribute. Then the schema file becomes a merge-conflict battlefield, every deploy is a coordinated release, and one team's slow resolver degrades everyone's queries. **Federation** splits the schema into independently deployed **subgraphs** and composes them into one **supergraph** served by a router. Clients see one graph; teams own their slice. The cost is that the hard parts move: entity resolution across services, query planning, cross-subgraph authorization, and schema changes that must remain composable. This extends the single-service GraphQL setup in Q254 and the API evolution rules in Q276.

---

### 1. Why Federation, and When Not To

| Approach | Ownership | Deploy | Failure mode |
| :--- | :--- | :--- | :--- |
| **Monolithic schema** | One team | Coordinated | Every change blocks on one repo |
| **Schema stitching** | Central team wires services | Central changes | Stitching logic becomes a second monolith |
| **Federation** | Per-subgraph teams | Independent | Router/query planning and entity hop latency |
| **BFF per client** | Per-client team | Independent | Duplicate logic; no unified graph |

Federation is worth it when **multiple teams own different domains** and clients need to traverse them in one query. It is overkill for a single team: the router, composition pipeline, entity resolvers, and cross-service tracing are real operational cost.

---

### 2. The Moving Parts

```text
client ──► router (supergraph) ──► users subgraph
                    │
                    ├────────────► reviews subgraph
                    │
                    └────────────► inventory subgraph

supergraph = composition of all subgraph schemas
entity     = a type identified by a key and resolvable by multiple subgraphs
```

| Concept | Meaning |
| :--- | :--- |
| **Subgraph** | A GraphQL service owning part of the schema |
| **Supergraph** | The composed schema the router executes |
| **Router** | Plans and fans out queries to subgraphs, merges results |
| **Entity** | A type with `@key(fields: "id")`, resolvable by reference |
| **`_entities`** | The synthetic field a subgraph implements to resolve entity references |
| **Query plan** | The router's ordered fetch tree for one operation |

---

### 3. Entity Resolution: What Actually Crosses the Wire

Suppose `me` comes from the users subgraph, but `reviews` lives in the reviews subgraph:

```graphql
query {
  me {
    name
    reviews { body }
  }
}
```

```text
QueryPlan {
  Sequence {
    Fetch(service: "users") {
      { me { __typename id name } }
    },
    Flatten(path: "me") {
      Fetch(service: "reviews") {
        { ... on User { __typename id } } =>
        { ... on User { reviews { body } } }
      }
    }
  }
}
```

The router does not call a REST endpoint; it calls the reviews subgraph with **entity representations**:

```json
{
  "query": "query($representations: [_Any!]!) { _entities(representations: $representations) { ... on User { reviews { body } } } }",
  "variables": {
    "representations": [
      { "__typename": "User", "id": "u-1" },
      { "__typename": "User", "id": "u-2" }
    ]
  }
}
```

Two details make or break performance:

- **Representations are batched** for all users in the current level, so the reviews subgraph sees one `_entities` call, not one per user.
- **The key must be sufficient**; if the reviews subgraph needs a field it does not own, you either add it to the key or use `@requires`.

---

### 4. Subgraph Schemas and a Spring/DGS Entity Fetcher

```graphql
# users subgraph
type Query {
  me: User
  user(id: ID!): User
}

type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}
```

```graphql
# reviews subgraph
type Review @key(fields: "id") {
  id: ID!
  body: String!
  author: User!
}

type User @key(fields: "id") {
  id: ID!
  reviews: [Review!]!
}
```

```java
@DgsComponent
public class UserReviewsFetcher {

    private final ReviewRepository reviews;

    // Resolves a User reference sent by the router in _entities
    @DgsEntityFetcher(name = "User")
    public User user(Map<String, Object> representation) {
        return new User((String) representation.get("id"));
    }

    @DgsData(parentType = "User", field = "reviews")
    public CompletableFuture<List<Review>> reviews(DgsDataFetchingEnvironment env) {
        User user = env.getSource();
        DataLoader<String, List<Review>> loader = env.getDataLoader("reviewsByUser");
        return loader.load(user.getId());
    }
}
```

```java
@DgsDataLoader(name = "reviewsByUser")
public class ReviewsByUserLoader implements BatchLoader<String, List<Review>> {

    private final ReviewRepository repository;

    @Override
    public CompletionStage<List<List<Review>>> load(List<String> userIds) {
        return CompletableFuture.supplyAsync(() -> {
            Map<String, List<Review>> byUser = repository.findByAuthorIdIn(userIds)
                    .collect(Collectors.groupingBy(Review::getAuthorId));
            return userIds.stream()
                    .map(id -> byUser.getOrDefault(id, List.of()))
                    .toList();
        });
    }
}
```

If you use Spring GraphQL instead of DGS, the equivalent is the federation support around `@EntityMapping`; the mechanics - a batched `_entities` call and per-request `DataLoader` - are identical.

---

### 5. Directives You Will Actually Use

| Directive | Purpose | Trap |
| :--- | :--- | :--- |
| **`@key(fields: "id")`** | Declares an entity and its key | Key must be resolvable in every subgraph that references it |
| **`@external`** | Field is owned by another subgraph | Referencing an external field without `@requires` |
| **`@requires(fields: "weight")`** | Fetch fields from another subgraph first | Adds a sequential hop; costs latency |
| **`@provides(fields: "name")`** | This subgraph can return a field itself | Must actually return consistent values |
| **`@shareable`** | Multiple subgraphs may resolve the same field | Divergent implementations return different values for the same entity |
| **`@override(from: "reviews")`** | Move a field to another subgraph | Removing the old implementation before traffic moves |
| **`@inaccessible`** | Hide a field from clients but keep it composable | Leaking internal keys into the public schema |
| **`@tag(name: "public")`** | Build contract variants | Assuming tags enforce authorization |

`@requires` is a latency decision, not a modeling convenience:

```graphql
type Product @key(fields: "id") {
  id: ID!
  weight: Int @external
  shippingEstimate: Int @requires(fields: "weight")
}
```

The router must fetch `weight` first, then call the shipping subgraph with a representation containing it. Prefer duplicating stable data with `@shareable`, or putting the calculation where the data already lives.

### 6. Composition and the CI Gate

```yaml
# supergraph.yaml
federation_version: =2.9.3
subgraphs:
  users:
    routing_url: http://users:8080/graphql
    schema:
      file: ./users/src/main/resources/schema/users.graphqls
  reviews:
    routing_url: http://reviews:8080/graphql
    schema:
      file: ./reviews/src/main/resources/schema/reviews.graphqls
```

```bash
# Compose locally or in CI; fails on composition errors
rover supergraph compose --config supergraph.yaml > supergraph.graphql

# With GraphOS, also run a schema check against the live graph
rover subgraph check my-graph@current \
  --name reviews \
  --schema ./reviews/src/main/resources/schema/reviews.graphqls
```

| Gate | Catches |
| :--- | :--- |
| **Composition** | Duplicate fields without `@shareable`, missing keys, invalid `@requires` |
| **Breaking-change diff** | Removing a field clients use, changing nullability, changing argument types (Q276) |
| **Contract tests** | Router-level queries still resolve after a subgraph change (Q258) |
| **Schema lint** | Naming, descriptions, unbounded lists |
| **Entity resolver tests** | `_entities` returns the right entity for a representation |

Deploy order follows the same expand/contract logic as any API:

```text
Additive field:
  1. deploy subgraph code that can resolve it
  2. compose and roll out the supergraph that exposes it

Removing a field:
  1. mark @deprecated, observe usage
  2. compose without it (clients stop seeing it)
  3. remove the resolver and code
```

Composing before the subgraph can resolve a field produces a supergraph that advertises a field it cannot serve - the GraphQL equivalent of deploying a contract first and the implementation later.

---

### 7. Performance: The Router Is a Distributed Query Engine

| Lever | Effect |
| :--- | :--- |
| **Batched entity fetches** | One `_entities` call per level per subgraph |
| **`@provides`** | Avoids a round trip when the data is already present |
| **Query plan review** | Reveals accidental sequential hops and fan-out |
| **Persisted queries (APQ)** | Smaller requests, allow-listing, CDN-cacheable GETs |
| **Depth/complexity limits** | Stops `{ a { b { c ... } } }` denial-of-service |
| **Per-subgraph timeouts** | One slow subgraph does not hold the whole query forever |
| **Response caching** | Only for genuinely public, non-user-specific fields |
| **Pagination** | Cursor-based connections, never unbounded lists |

```java
// graphql-java guards; tune per schema
@Bean
Instrumentation maxDepth() {
    return new MaxQueryDepthInstrumentation(12);
}
```

```json
{
  "query": "query Me { me { id name } }",
  "extensions": {
    "persistedQuery": { "version": 1, "sha256Hash": "..." }
  }
}
```

Partial failure is normal in federation: the router returns `data` with `null` for the failed field plus an `errors` array. Clients must handle it, and dashboards must alert on **error rate per subgraph**, not just on HTTP 200 from the router. Propagate trace context from router to subgraphs so a slow query can be attributed to a hop (Q266/Q281).

---

### 8. Authorization Across Subgraphs

The router authenticates the client once; every subgraph must still enforce its own rules. Trusting a header such as `x-user-id` from the network is a privilege-escalation bug.

```text
Client ──JWT──► Router (validate signature, scopes)
                   │  forwards validated identity (signed/internal)
                   ▼
              Subgraph A ──► checks field + entity-level access
              Subgraph B ──► checks its own data, never trusts A's decision
```

| Layer | Responsibility |
| :--- | :--- |
| **Router** | Token validation, scopes, query cost limits, persisted-query allow-list |
| **Subgraph** | Field-level and entity-level authorization on the data it owns |
| **Entity resolver** | Re-check that this caller may see the referenced entity |
| **Data layer** | Tenant/row filters; defense in depth (Q253/Q275) |

A subtle federation-specific risk: the users subgraph decides the caller may see `User:u-1`, but the reviews subgraph receives `{__typename: "User", id: "u-1"}` and must decide for itself whether to return that user's reviews. Entity references are **not** an authorization token.

Also:

- **Disable introspection** in production, or restrict it to internal callers.
- **Enforce query depth and cost** at the router, not only per subgraph.
- **Allow-list persisted queries** for public clients; arbitrary queries plus deep nesting is a cheap DoS.
- **Do not expose internal keys or join fields** - use `@inaccessible` and keep them out of the public contract.

---

### 9. Evolving the Supergraph

GraphQL has no URL versions. Evolution is additive plus deprecation:

| Change | Compatible? | Notes |
| :--- | :--- | :--- |
| **Add a field/type** | Yes | Clients using older queries ignore it |
| **Add a nullable argument** | Yes | Existing calls still work |
| **Make a nullable field non-null** | **No** | Breaks clients handling `null` |
| **Remove a field** | **No** | Deprecate, measure usage, then remove |
| **Rename a field** | **No** | Add new, deprecate old, migrate |
| **Change an enum value** | Depends | Clients with exhaustive switches break |
| **Move a field between subgraphs** | Yes, with `@override` | Progressive override needs monitoring |
| **Change entity key** | **No** | Effectively a new entity; version it |

```graphql
type User @key(fields: "id") {
  id: ID!
  name: String! @deprecated(reason: "Use displayName")
  displayName: String!
}
```

For a multi-team graph, **schema checks in CI are the contract test**. A subgraph that composes successfully but changes field nullability or removes a type can still break clients that nobody tracked. Treat the supergraph artifact as a deployed, versioned artifact: review the diff, roll it out with the router, and keep the previous one for rollback.

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **N+1 at the entity boundary** | Hundreds of `_entities` calls per query | Batch representations; DataLoader per request |
| **Missing key field** | `_entities` returns `null` for some entities | Ensure the key is resolvable from the representation |
| **Sequential `@requires` chains** | p99 grows with graph depth | Move computation to where data lives; duplicate with `@shareable` |
| **Auth only at the router** | Any internal caller can read anything | Enforce in every subgraph and entity resolver |
| **Trusting identity headers** | Privilege escalation | Signed/internal identity, mTLS, verify at each hop |
| **No depth/complexity limit** | One query exhausts the pool | Router cost limits, persisted queries |
| **Unbounded lists** | Memory blow-up on large entities | Cursor pagination with a max page size |
| **Composition before deploy** | Supergraph advertises an unresolvable field | Deploy subgraph first for additions |
| **Silent partial failures** | Router returns 200 with `errors` | Alert per subgraph; clients handle `errors` |
| **Divergent `@shareable` fields** | Same entity has different values in one query | Single owner, or strict consistency |
| **`@override` without monitoring** | Traffic moved to an untested implementation | Progressive override, compare error/latency |
| **Introspection exposed publicly** | Schema disclosure, attack surface | Disable or restrict |
| **No supergraph rollback** | A bad composition takes down all clients | Version and retain the previous supergraph |
| **Leaking internal keys** | Clients depend on join fields | `@inaccessible`, contract variants |
| **No trace propagation** | Cannot attribute latency to a subgraph | Propagate `traceparent`, per-subgraph spans (Q266) |

### Summary

- **Federation buys independent team ownership at the cost of entity resolution, query planning, and cross-service operations**; use it when several teams own distinct domains, not for a single service.
- **Entities are the seam**: `@key` defines what can be referenced, and the router resolves them through batched `_entities` calls - batch or you reintroduce N+1 at the network level.
- **Composition is a build gate**: run `rover supergraph compose` and breaking-change checks in CI, and deploy additive subgraph changes before exposing them in the supergraph.
- **Performance is a query-plan problem**: review plans, avoid `@requires` chains, use `@provides`, cap depth/cost, and paginate everything.
- **Authorization is per subgraph and per entity**, never a router-only decision or a trusted identity header.
- **Evolve additively with deprecation and `@override`**, keep the supergraph versioned for rollback, and alert on partial errors per subgraph (Q266/Q276/Q281).
