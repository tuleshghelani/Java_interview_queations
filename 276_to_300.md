## 276. How do you version a Spring Boot API without breaking clients? Explain breaking vs non-breaking changes, URI vs media-type versioning, deprecation headers, and contract checks in CI.

Versioning is not a feature you add at the end; it is what you do when **compatibility cannot be preserved**. Every new version doubles the surface you must test, secure, and eventually retire, so the default should be **evolution**: additive changes, tolerant readers, and a documented deprecation window. A version number is the escape hatch for the rare change that cannot be made compatible - a field whose meaning must change, a required parameter, a response shape that clients parse positionally. Getting this wrong shows up as a mobile app that crashes on an old build, a partner integration that silently reads the wrong field, or a v1 endpoint that nobody can delete because there is no telemetry on who still calls it.

---

### 1. Compatibility First, Versioning Second

| Approach | Cost | When to use |
| :--- | :--- | :--- |
| **Compatible evolution** | Lowest: one version, tolerant clients | Default for everything you control |
| **Deprecation + migration window** | Medium: telemetry, comms, dual support | External consumers you can reach |
| **Parallel versions** | High: duplicated tests, docs, security surface | Genuinely incompatible semantics |
| **Hard cutover** | Highest risk | Only for consumers you own and deploy atomically |

The cheapest breaking change is the one you design out. Before adding `/v2`, ask whether the change can be expressed as a **new optional field**, a **new endpoint**, or a **new media type** alongside the old one.

---

### 2. Breaking vs Non-Breaking Changes

| Change | Breaking? | Why |
| :--- | :--- | :--- |
| Add an optional **response** field | No | Tolerant clients ignore unknown fields |
| Add an optional **request** field | No | Old clients simply omit it |
| Add a new endpoint | No | Nothing existing changes |
| Remove or rename a field | **Yes** | Clients deserialize `null` or fail |
| Change a type (`int` → `string`, number → object) | **Yes** | Parse errors |
| Add a value to an enum | **Usually yes** | Java `switch` exhaustiveness, client validation, UI mapping |
| Make an optional field required | **Yes** | Existing requests start failing |
| Tighten validation (max length, regex, range) | **Yes** | Previously valid requests rejected |
| Change a default value | **Yes** | Behaviour changes without a shape change |
| Change an error code, status, or error body | **Yes** | Clients branch on them |
| Change pagination defaults or ordering | **Yes** | Silent data loss or duplicates for clients |
| Change **semantics** of an existing field | **Yes, and the worst kind** | Nothing fails to parse; the meaning silently changes |
| Add a required header | **Yes** | Unprepared clients get `400`/`415` |
| Reorder JSON properties | No | Object order is not significant |
| Add a new HTTP method to an existing path | No | Unless it changes caching/authorization assumptions |

The "semantics" row is the one code review misses: renaming `amount` from cents to dollars keeps the type and breaks every consumer. Treat units, time zones, and currency as part of the contract.

Two client-side defaults decide whether additive changes are actually safe:

```java
// Jackson's default is true; Spring Boot sets it to false for you.
// Do not re-enable it on a client that talks to an evolving API.
@JsonIgnoreProperties(ignoreUnknown = true)
public record OrderResponse(String id, BigDecimal total, String currency) { }
```

```yaml
spring:
  jackson:
    deserialization:
      fail-on-unknown-properties: false   # default in Boot; keep it that way
```

Publish the schema (OpenAPI/JSON Schema) so consumers can generate tolerant clients instead of hand-parsing maps.

---

### 3. Choosing a Versioning Strategy

| Strategy | Example | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **URI path** | `/api/v2/orders/42` | Visible in logs, cache keys, routing; trivial to route at the gateway | URL churn; clients hardcode; "not RESTful" by some readings |
| **Custom media type** | `Accept: application/vnd.acme.v2+json` | Clean URLs; proper content negotiation | Invisible in most logs; needs `Vary: Accept`; harder to test with `curl` |
| **Custom header** | `X-API-Version: 2` | Clean URLs; easy to add | Same invisibility; proxies must not strip it |
| **Query parameter** | `/api/orders/42?version=2` | Trivial to try | Pollutes cache keys and links; easy to forget |
| **No version, evolve** | additive fields only | One code path | Requires discipline and contract tests |

Rules of thumb:

- **External/partner API** → URI versioning is the least ambiguous and the easiest to support operationally.
- **Internal service-to-service** → do not version; use tolerant readers, contract tests (Q258), and deploy ordering.
- **Content negotiation** is a good fit when the same resource genuinely has multiple representations rather than multiple contracts.
- **Spring Framework 7** adds first-class `version` support on `@RequestMapping`, with a configurable resolver (path segment, header, query parameter, or media-type parameter). If you are on Boot 4/Framework 7, prefer that over hand-rolled header checks; on Boot 3, the patterns below are the standard approach.

```java
// Boot 3: media-type versioning
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v1+json")
    OrderV1 getV1(@PathVariable String id) { ... }

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v2+json")
    OrderV2 getV2(@PathVariable String id) { ... }
}
```

```java
// Boot 3: header versioning (mapping is more specific when the header is present)
@GetMapping(value = "/{id}", headers = "X-API-Version=2")
OrderV2 getV2(@PathVariable String id) { ... }
```

```java
// Spring Framework 7: built-in version attribute
@GetMapping(path = "/{id}", version = "2.0")
OrderV2 getV2(@PathVariable String id) { ... }
```

Whichever you choose, **route at the edge**: the gateway can send `/v1/*` to the old deployment and `/v2/*` to the new one, which is what makes a gradual migration possible (Q239).

---

### 4. Do Not Fork the Domain, Fork the Contract

The failure mode of versioning is two controllers with copy-pasted logic that drift: a bug fixed in v2 but not v1, or v1 writing different data than v2.

```java
// One domain model, thin per-version adapters
@RestController
@RequestMapping("/api/orders")
class OrderController {

    private final OrderService orders;   // single source of truth

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v1+json")
    OrderV1 getV1(@PathVariable String id) {
        return OrderV1.from(orders.get(id));      // v1 shape: flat total in cents
    }

    @GetMapping(value = "/{id}", produces = "application/vnd.acme.v2+json")
    OrderV2 getV2(@PathVariable String id) {
        return OrderV2.from(orders.get(id));      // v2 shape: amount { value, currency }
    }
}
```

| Layer | Shared? | Notes |
| :--- | :--- | :--- |
| Domain/service/persistence | **Yes** | One behaviour, one set of invariants |
| DTOs and mappers | No | Version-specific shapes |
| Validation | Partly | v2 may be stricter; keep the rule in the service where it is a true invariant |
| Error mapping | Shared with a versioned envelope | If the envelope changes, that is a breaking change |

Version the **contract**, not the business logic. If a rule differs between versions, that is a product decision that must be explicit in the service, not an accident of duplicated code.

---

### 5. Deprecation Is a Lifecycle, Not an Annotation

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.acme.v1+json
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://developer.acme.com/api/v2/migration>; rel="deprecation"; type="text/html"
Warning: 299 - "v1 is deprecated; migrate to v2 before 2027-06-30"
```

| Header | Meaning |
| :--- | :--- |
| `Deprecation` | When the endpoint became deprecated (RFC 9745 structured date) |
| `Sunset` | When it will be removed (RFC 8594 HTTP date) |
| `Link ... rel="deprecation"` | Where the migration guide lives |
| `Warning` | Human-readable hint for older clients and logs |

A workable timeline:

| Phase | Action | Exit criterion |
| :--- | :--- | :--- |
| **Announce** | Publish guide, add headers, tag metrics by version | Consumers notified |
| **Instrument** | Dashboard of calls per version, per client id | You can name who still calls v1 |
| **Migrate** | Support both versions; fix v1 only for security/data-loss bugs | v1 traffic below an agreed threshold |
| **Freeze** | No changes to v1 except critical fixes | Threshold reached for N weeks |
| **Sunset** | Return `410 Gone` (or redirect where safe) | Removal date passes |
| **Remove** | Delete code, tests, docs, gateway routes | Cleanup complete |

Telemetry is the whole game:

```java
meterRegistry.counter("api_requests_total",
        "route", "orders.get",
        "version", requestVersion,          // from path, header, or media type
        "client_id", clientId(request)).increment();
```

Without a per-version, per-client metric you cannot answer "can we delete v1?" and the answer becomes "never".

---

### 6. Contract Checks in CI

Humans do not reliably spot breaking changes in a diff, so automate it:

```bash
# Fails when the new OpenAPI document removes fields, tightens types, or adds required params
oasdiff breaking api/openapi-v1.yaml api/openapi-v2.yaml --fail-on ERR

# Consumer-driven contracts: the provider must satisfy every consumer's expectations (Q258)
./mvnw verify -Dpact.verifier.publishResults=true
```

| Check | Catches |
| :--- | :--- |
| **OpenAPI diff** (`oasdiff`, `openapi-diff`) | Removed fields, type changes, new required parameters |
| **Consumer-driven contracts** (Pact, Q258) | Provider changes that violate real consumer usage |
| **JSON Schema validation in tests** | Response shape drift not captured by the spec |
| **Golden-file / snapshot tests** | Serialization changes (date formats, null handling) |
| **Canary with version tags** | Runtime errors only the old client triggers |

Make the diff part of the pull request: a change that fails `oasdiff breaking` either gets redesigned or gets an explicit, reviewed version bump.

---

### 7. Cross-Protocol Notes

**GraphQL** has no URL versions. Evolve additively and deprecate in the schema:

```graphql
type Order {
  id: ID!
  totalCents: Int @deprecated(reason: "Use amount { value currency }")
  amount: Money!
}
```

- Adding a nullable field or a new type is safe.
- Removing a field, changing nullability, or **adding a non-null argument without a default** is breaking.
- Clients can send persisted queries, which means a removed field can break them even if no human wrote the query recently (Q254).

**gRPC/protobuf** versions by package and by field number:

```proto
package acme.orders.v2;

message Order {
  reserved 4, 6;              // never reuse a removed field number
  reserved "customer_name";
  string customer_id = 7;
}
```

- Adding fields is safe; removing or renaming is not.
- Never reuse a tag number; `reserved` prevents accidental reuse (Q255).
- `google.protobuf.Any` moves the compatibility problem into the payload, where no schema check will catch it.

**Events** are an API too. Version the envelope and keep consumers tolerant:

```json
{ "eventType": "order.created", "schemaVersion": 3, "occurredAt": "2026-11-03T09:00:00Z", "payload": { } }
```

Use a schema registry with an explicit compatibility mode (for example Avro `BACKWARD_TRANSITIVE`), and remember that the **consumer deploy order** matters: deploy readers that understand the new field before producers start emitting it (Q251).

---

### 8. Coupling to Data and Deployments

- **Do not let two API versions write the same column with different semantics.** If v1 means cents and v2 means a decimal amount, store one canonical representation and convert at the adapter.
- **Schema changes follow expand/contract** (Q248/Q272): add nullable columns, backfill, switch reads, then remove. API versions do not remove the need for migration discipline.
- **Deploy order for additive changes**: consumers first, producers second. For removals: stop producing, verify, then remove.
- **Feature flags** can route a subset of clients to v2 for a canary before a full cutover (Q247).
- **Auth and tenancy must behave identically across versions**; a v2 endpoint that forgets a tenant predicate is a new vulnerability, not a new feature (Q275).

---

### 9. Testing Matrix

| Test | What it protects |
| :--- | :--- |
| Contract tests per supported version | Provider still satisfies v1 and v2 consumers |
| Serialization tests per version | Field names, date formats, null/empty semantics |
| Deprecation header assertions | Clients and proxies see the sunset signal |
| Gateway routing tests | `/v1` and `/v2` reach the right deployment |
| Old-client integration test (pinned SDK/fixture) | Real-world tolerance, not just generated clients |
| Load test with mixed versions | Connection pools, caches, and DB queries stay within budget |

Keep one **pinned old client** in CI. Generated clients from the current spec will happily accept a breaking change that a real, older SDK cannot.

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Changing field semantics** | No parse error; wrong money/units downstream | Treat units, currency, and time zones as contract |
| **Adding an enum value** | Client `switch` throws or defaults incorrectly | Document as potentially breaking; version if consumers are strict |
| **Tightening validation** | Old valid requests now `400` | New version, or make the rule opt-in |
| **Copy-pasted v1/v2 controllers** | Bug fixed in one, not the other | Shared service, thin adapters |
| **Versioning everything** | N versions, N test suites, slow delivery | Evolve compatibly; version only real breaks |
| **No per-version telemetry** | Cannot retire v1 | Tag metrics by route, version, client |
| **`Deprecation` without `Sunset`** | Clients ignore an open-ended warning | Publish a date and enforce it |
| **Removing fields before traffic hits zero** | Late-night rollback | Gate removal on measured traffic |
| **GraphQL non-null argument added** | Queries fail validation | Add nullable with a default; deprecate |
| **Reusing a protobuf field number** | Silent data corruption across versions | `reserved` old tags |
| **Jackson strictness on clients** | Adding a response field breaks clients | `FAIL_ON_UNKNOWN_PROPERTIES=false` |
| **Media-type versioning without `Vary: Accept`** | CDN serves the wrong representation | Add `Vary: Accept`; test through the CDN |
| **Two versions writing different semantics** | Data corruption after cutover | One canonical store; convert in adapters |
| **No contract check in CI** | Breaking change ships on a Friday | `oasdiff breaking` + Pact gates |

### Summary

- **Compatibility is the default; a version is the exception.** Add optional fields, new endpoints, and new representations before forking the API.
- **Know what actually breaks**: removed/renamed fields, type changes, tightened validation, enum additions, error-shape changes, and - most dangerous - unchanged shapes with changed semantics.
- **Pick one strategy and make it visible**: URI versioning for external APIs, no versioning for internal services with contract tests, media types when representations genuinely differ; Framework 7's `version` attribute removes the hand-rolled plumbing.
- **Version the contract, not the domain**: one service, one set of invariants, thin per-version DTOs and mappers.
- **Deprecation needs a date, headers (`Deprecation`/`Sunset`), and per-version telemetry**; without the metric you can never delete the old code.
- **Automate compatibility**: OpenAPI diff and consumer-driven contracts in CI (Q258), plus a pinned old client; document GraphQL, gRPC, and event-schema rules separately because each breaks differently.

## 277. How do you run chaos engineering experiments on Spring Boot microservices? Explain steady-state hypotheses, blast radius, fault injection with Chaos Monkey/Toxiproxy/Litmus, and gating experiments in CI.

Chaos engineering is **controlled, hypothesis-driven fault injection**, not randomly deleting pods in production. The point is to replace "we think the timeout and circuit breaker work" with evidence: define a measurable steady state, inject one realistic fault inside a bounded blast radius, and observe whether the system keeps its SLO or degrades in the way you designed. It is the natural next step after resilience patterns (Q213), load shedding (Q270), and SLOs (Q230): those tell you what *should* happen; an experiment tells you what *does*.

---

### 1. The Experiment, Not the Tool

```text
1. Hypothesis    "If payments adds 800 ms latency, checkout error rate stays < 0.5%
                  and p99 < 2 s, because the 500 ms timeout + circuit breaker shed fast."
2. Steady state  error rate < 0.5%, p99 < 800 ms, duplicate charges = 0
3. Injection     Toxiproxy / Chaos Mesh adds latency to payments for 5 minutes
4. Observation   compare experiment window against baseline window
5. Verdict       hypothesis holds / fails; if it fails, file the fix before the next experiment
6. Automation    keep the reproducible ones in CI; retire the rest
```

Without a written hypothesis you are just breaking things and calling it science. Without a **baseline window** you cannot tell whether a p99 change came from the fault or from normal traffic.

| Element | Bad example | Good example |
| :--- | :--- | :--- |
| **Hypothesis** | "Kill a pod and see" | "Killing one orders pod causes < 30 s of elevated errors because readiness drains first (Q261)" |
| **Steady state** | "It's up" | Error rate, p99, consumer lag, duplicate count, DB saturation |
| **Blast radius** | All pods, all AZs | One pod, one AZ, one dependency, 5 minutes |
| **Abort** | None | Error budget burn > 2%, manual kill switch, on-call veto |
| **Verdict** | "Looks fine" | Metric comparison with a pass/fail threshold |

---

### 2. Prerequisites Before the First Experiment

Chaos without observability is vandalism. You need:

- **SLOs and error budgets** (Q230) so "did it degrade?" has a numeric answer.
- **Distributed tracing** (Q266) so you can see *where* the latency appeared, not just that checkout got slower.
- **Idempotency and reconciliation** (Q263) so a retried or duplicated request does not corrupt data - and a way to verify it after the experiment.
- **A kill switch** that removes the fault immediately (Toxiproxy toxic delete, Chaos Mesh experiment delete, `chaos.monkey.enabled=false`).
- **A rollback path** for anything that could persist state (schema changes, queues, scheduled jobs).
- **An incident channel and on-call awareness**, even in production during business hours.

---

### 3. Fault Catalogue

| Fault | What it validates | Tooling |
| :--- | :--- | :--- |
| **Latency on a dependency** | Timeouts, circuit breakers, load shedding, thread/connection exhaustion | Toxiproxy, Chaos Mesh `NetworkChaos` delay, chaos-monkey latency assault |
| **Error responses (500/503/429)** | Retry policy, jitter, fallback, `Retry-After` handling (Q270) | Toxiproxy, WireMock, mesh fault injection |
| **Network partition / packet loss** | Timeouts vs hangs, retry storms, split-brain assumptions | Chaos Mesh `NetworkChaos` partition, Toxiproxy `timeout`/`reset_peer` |
| **Pod kill / restart** | Graceful shutdown, readiness, Kafka rebalance (Q261), in-flight requests | Chaos Mesh `PodChaos`, Litmus `pod-delete`, `kubectl delete pod` |
| **CPU / memory stress** | GC behaviour, throttling, OOMKilled budgets, adaptive limits (Q270) | Chaos Mesh `StressChaos`, `stress-ng` |
| **DNS failure** | Client caching, failover to another endpoint | Chaos Mesh `DNSChaos` |
| **Disk latency / full disk** | Logging backpressure, WAL/queue behaviour | `StressChaos`, `tc`, filesystem fill |
| **AZ / node failure** | Multi-AZ failover, replica promotion, capacity headroom (Q268) | Cloud FIS, node drain, zone-scoped experiments |
| **Broker/leader kill** | Consumer rebalance, producer retries, duplicate handling (Q259) | Kill a broker pod; `kafka-leader-election.sh` for controlled leader moves |
| **Certificate/credential expiry** | Rotation, TLS failure mode, fail-closed behaviour (Q243) | Short-lived certs in staging; revoke a credential |
| **Dependency throttle/quota** | Backoff, `429` handling, per-tenant fairness (Q238) | Proxy responding `429` with `Retry-After` |

Start with **latency and errors on a dependency**. They are reversible, cheap, and expose the majority of real incidents. Pod kills and infrastructure faults come later, once the application-level behaviour is trustworthy.

---

### 4. Spring-Level Injection: Chaos Monkey for Spring Boot

For testing a single service's method-level resilience, `chaos-monkey-spring-boot` injects latency, exceptions, memory/CPU pressure, or kills the app based on a watched layer (service, controller, repository).

```xml
<dependency>
    <groupId>de.codecentric</groupId>
    <artifactId>chaos-monkey-spring-boot</artifactId>
    <version>${chaos-monkey.version}</version>
    <scope>runtime</scope>
</dependency>
```

```yaml
spring:
  profiles:
    include: chaos-monkey          # never active by default; enabled per environment
chaos:
  monkey:
    enabled: true
    assaults:
      level: 2                     # 1 (rare) .. 5 (always); higher = more calls hit
      latency-active: true
      latency-range-start: 500
      latency-range-end: 2000
      exceptions-active: true
    watcher:
      service: true                # scope to @Service beans
      controller: false
      repository: false            # keep persistence out of the blast radius
management:
  endpoint:
    chaosmonkey:
      enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,chaosmonkey
```

```bash
# Query and change the assault configuration at runtime
curl -s localhost:8080/actuator/chaosmonkey/assaults
curl -s -X POST localhost:8080/actuator/chaosmonkey/assaults \
  -H 'Content-Type: application/json' \
  -d '{"latencyActive":true,"latencyRangeStart":800,"latencyRangeEnd":800,"level":3}'
```

Rules:

- **Never enable it unconditionally in production.** Gate it behind a profile plus the actuator endpoint, protected like any admin surface (Q275).
- **Watch the narrowest layer** that produces the behaviour you are testing. Injecting into repositories multiplies the fault across every query and makes results uninterpretable.
- **Use `level` as a dial**, not a switch: a fraction of calls is closer to real degradation than 100% failure.
- **Verify it actually fires** - a watched bean that is never called produces a green experiment that proves nothing. Count injected faults in a metric.

---

### 5. Dependency-Level Injection: Toxiproxy in Tests

Toxiproxy sits between the app and a dependency and lets you add latency, bandwidth limits, timeouts, or connection resets without touching the dependency or the app.

```java
@Testcontainers
class PaymentTimeoutExperiment {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Container
    static ToxiproxyContainer toxiproxy =
            new ToxiproxyContainer("ghcr.io/shopify/toxiproxy:2.9.0");

    static ToxiproxyContainer.ContainerProxy dbProxy;

    @DynamicPropertySource
    static void datasource(DynamicPropertyRegistry registry) {
        dbProxy = toxiproxy.getProxy(postgres, 5432);
        registry.add("spring.datasource.url", () -> "jdbc:postgresql://%s:%d/test"
                .formatted(dbProxy.getHost(), dbProxy.getProxyPort()));
        registry.add("spring.datasource.hikari.connection-timeout", () -> "500");
    }

    @Test
    void requestFailsFastWhenDatabaseHangs() {
        dbProxy.toxics().latency("db-delay", ToxicDirection.DOWNSTREAM, 1_500);

        // Hypothesis: the 500 ms connection timeout + circuit breaker
        // return 503 within ~600 ms instead of hanging for the full 1.5 s.
        assertThat(api.get("/orders/1"))
                .hasStatus(503)
                .hasHeader("Retry-After");

        dbProxy.toxics().get("db-delay").remove();   // always clean up
    }
}
```

This belongs in CI: it is deterministic, fast, and runs on every change to the resilience configuration. The same idea at the network level is a Toxiproxy sidecar in staging, or Chaos Mesh in Kubernetes.

### 6. Cluster-Level Injection: Chaos Mesh / Litmus

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: orders-to-payments-latency
  namespace: shop
spec:
  action: delay
  mode: one                       # one pod, not the whole deployment
  selector:
    namespaces: [shop]
    labelSelectors: { app: orders }
  delay:
    latency: "800ms"
    jitter: "200ms"
    correlation: "50"
  direction: to
  target:
    mode: all
    selector:
      namespaces: [shop]
      labelSelectors: { app: payments }
  duration: "5m"
```

Litmus expresses the same experiment as a `ChaosEngine` with an experiment name (`pod-delete`, `pod-network-latency`), plus probes that assert steady state before, during, and after. Cloud providers offer managed equivalents (AWS FIS, Azure Chaos Studio) that can target an AZ or a managed database, which is the only practical way to rehearse regional failure (Q268).

| Control | Setting |
| :--- | :--- |
| **Namespace/labels** | Only the intended workload, never `mode: all` on a shared deployment |
| **Duration** | Minutes, with an explicit end |
| **Probes** | Steady-state checks that abort the experiment on violation |
| **Schedule** | Business hours, announced, with on-call present |
| **Kill switch** | Delete the CR / disable the experiment; verify the fault is gone |

```bash
kubectl -n shop get networkchaos
kubectl -n shop delete networkchaos orders-to-payments-latency
# Confirm: latency back to baseline, no lingering tc rules / sidecar config
```

---

### 7. Blast Radius and Safety

| Dimension | Start | Later |
| :--- | :--- | :--- |
| **Environment** | Local Testcontainers | Staging → canary subset → production |
| **Scope** | One dependency, one method | One pod, one AZ |
| **Traffic** | Synthetic tests | 1% of real traffic tagged by header/tenant |
| **Duration** | Seconds in a test | 5-15 minutes |
| **Faults** | Latency, errors | Kills, partitions, AZ loss |
| **Approval** | Developer | Team + on-call + change record |

Production rules:

- **Tag and route**: use a header or tenant id to send only a small cohort through the faulted path (Q247), so experiments do not become incidents for everyone.
- **Never inject into data-mutating paths without a reconciliation check**; a duplicate charge that "recovered" is still a duplicate charge (Q263).
- **Abort automatically on error-budget burn**, not on a human noticing a dashboard.
- **Exclude** payment capture, irreversible migrations, and anything with no rollback until you have rehearsed it in staging.
- **Freeze chaos during deploys, incidents, and peak** - one variable at a time.

---

### 8. Reading the Result

Compare the experiment window to the same-length baseline window, not to "how it feels".

| Signal | Baseline | Abort / fail threshold |
| :--- | :--- | :--- |
| HTTP error rate | < 0.5% | > 2% for 2 minutes |
| p99 latency | < 800 ms | > 2 s |
| Circuit breaker state | closed | open > 1 minute (unless shedding is the design, Q270) |
| Consumer lag | < 1k | > 50k and growing (Q259) |
| DB pool pending | 0 | > 0 sustained (Q232) |
| Duplicate/incorrect records | 0 | any |
| SLO burn rate | < 1× | > 2× (Q230) |

Correlate with traces: an 800 ms payment delay should show up as a specific span, with the circuit breaker's fallback span next to it (Q266). If the trace shows the request waiting on the full 800 ms, the timeout is misconfigured - the experiment found a real bug, which is the point.

---

### 9. Putting It in CI/CD

```text
PR pipeline        → Toxiproxy/WireMock fault tests (seconds, deterministic)
Nightly staging    → one Chaos Mesh experiment per critical dependency
Weekly game day    → one cross-service experiment with on-call, hypothesis, write-up
Production         → manual, approved, tagged cohort, business hours
```

- **Assert the design, not just survival**: 503 + `Retry-After`, breaker opens, fallback returns cached data, queue drains after recovery.
- **Fail the pipeline on a violated hypothesis**; otherwise the experiment becomes a dashboard nobody reads.
- **Keep a catalog** of experiments with owner, hypothesis, tooling, and last result - chaos maturity is measured by the fixes it produced, not the number of experiments run.
- **Rotate experiments**: once a fault is handled automatically (test proves it), move to the next unknown instead of re-running the same green test forever.

---

### 10. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **No hypothesis or baseline** | "Nothing broke" with no evidence | Define metric, window, and pass/fail first |
| **No observability** | Cannot tell whether the fault fired | SLOs, traces, and injected-fault counters (Q230/Q266) |
| **Fault in dead code** | Experiment passes, real path untested | Verify the injection metric; scope the watcher correctly |
| **Blast radius too large** | Real incident instead of experiment | One pod/AZ, tagged cohort, duration limit |
| **No kill switch** | Fault persists after the experiment | Toxic delete / CR delete / feature toggle; verify baseline |
| **Leftover toxics** | Staging mysteriously slow for days | `finally` cleanup; assert baseline after each test |
| **Data-mutating fault without reconciliation** | Duplicate charges, lost events | Idempotency keys + post-experiment reconciliation (Q263) |
| **Retry storm during injection** | Load amplification looks like a capacity bug | Retry budget and jitter (Q270); measure request rate too |
| **Testing production first** | Learning on customers | Local/CI → staging → tagged production cohort |
| **Running during a deploy/incident** | Two variables, no diagnosis | Freeze experiments during change windows |
| **Chaos as a checkbox** | Same green experiment for a year | Retire proven ones; target the next unknown |
| **Only measuring availability** | System "up" but charging twice | Assert correctness invariants, not just 200s |
| **Ignoring recovery** | Error rate returns, but lag never drains | Measure drain time and backlog after the fault ends |

### Summary

- **Chaos engineering is an experiment with a hypothesis, a steady state, a bounded blast radius, and an abort condition** - otherwise it is just an outage with a name.
- **Start at the dependency boundary**: latency and errors via Toxiproxy in CI, then pods and networks via Chaos Mesh/Litmus, then AZ/region faults via cloud tooling.
- **Spring-specific injection** (chaos-monkey-spring-boot) is useful for method-level behaviour, but only when gated, scoped to the right layer, and verified to actually fire.
- **Keep the blast radius small and reversible**: one pod/AZ, tagged traffic, minutes, business hours, automatic abort on error-budget burn, and a kill switch you have tested.
- **Judge the result against baseline SLOs and correctness invariants** (duplicates, lag, pool saturation), using traces to find where the design failed (Q230/Q266).
- **Automate the proven experiments in CI, rehearse the rest as game days, and retire them once fixed** - the output of chaos engineering is a shorter list of unknowns, not a collection of scripts.

## 278. How do you operate Elasticsearch at scale with Spring Boot? Explain shard sizing, index lifecycle management, aliases, zero-downtime reindexing, and keeping the index consistent with the database.

Elasticsearch is a **derived, rebuildable index** (Q225), not a system of record. Once you accept that, the operational questions become concrete: how many shards per index, when to roll over to a new index, how to change a mapping without downtime, and how to prove the index still matches the database after a failed bulk load or a missed event. Getting these wrong produces the classic failures - a cluster with 4,000 tiny shards and an unstable cluster state, a single 2 TB index that takes hours to recover, or a reindex that silently drops documents because nobody compared counts.

---

### 1. Shard Sizing: The Decision You Cannot Undo

A shard is a Lucene index; `number_of_shards` is fixed at creation (changing it requires `_split`, `_shrink`, or a full reindex).

| Rule of thumb | Value | Why |
| :--- | :--- | :--- |
| **Shard size** | 10-50 GB | Smaller = overhead per shard; larger = slow recovery and rebalancing |
| **Docs per shard** | < 200 million | Lucene segment and merge cost grows |
| **Shards per node** | roughly ≤ 20 per GB of heap | Each shard costs heap for segment metadata and cluster state |
| **Replicas** | 1 minimum in production | HA plus search throughput, at 2× disk |
| **Total shards per cluster** | keep in the hundreds/low thousands | Cluster state and master work scale with shard count |

```text
200 GB of searchable data
├─ 6 primary shards × ~33 GB   ← reasonable
└─ 1 replica each              ← 12 shards total
vs.
2000 primary shards × 100 MB   ← cluster-state churn, slow recovery, wasted heap
```

Prefer **time-based indices plus ILM** over one giant index: it gives retention by deleting whole indices (the same reasoning as table partitioning, Q272) and keeps each shard in the healthy size range.

```java
@Document(indexName = "orders", createIndex = false)  // templates/ILM own the index
@Setting(shards = 3, replicas = 1)
public class OrderDocument {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String tenantId;

    @Field(type = FieldType.Keyword)
    private String status;

    @Field(type = FieldType.Scaled_Float, scalingFactor = 100)
    private BigDecimal total;

    @Field(type = FieldType.Date, format = DateFormat.date_optional_time)
    private Instant createdAt;
}
```

`createIndex = false` matters in production: letting the application auto-create an index means it may be created without the template, with default shards and dynamic mappings, and the mistake is only discovered after data arrives.

---

### 2. Index Templates and ILM

```json
PUT _index_template/orders-template
{
  "index_patterns": ["orders-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 1,
      "index.lifecycle.name": "orders-policy",
      "index.lifecycle.rollover_alias": "orders-write",
      "refresh_interval": "5s"
    },
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "id":        { "type": "keyword" },
        "tenantId":  { "type": "keyword" },
        "status":    { "type": "keyword" },
        "total":     { "type": "scaled_float", "scaling_factor": 100 },
        "createdAt": { "type": "date" },
        "description": { "type": "text",
                         "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } }
      }
    }
  }
}
```

```json
PUT _ilm/policy/orders-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_primary_shard_size": "30gb", "max_age": "1d" }
        }
      },
      "warm": {
        "min_age": "7d",
        "actions": {
          "forcemerge": { "max_num_segments": 1 },
          "shrink": { "number_of_shards": 1 }
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "searchable_snapshot": { "snapshot_repository": "s3-repo" }
        }
      },
      "delete": { "min_age": "365d", "actions": { "delete": {} } }
    }
  }
}
```

Bootstrap the first write index so the rollover alias exists:

```json
PUT orders-000001
{ "aliases": { "orders-write": { "is_write_index": true } } }
```

Design notes:

- **Rollover on `max_primary_shard_size`**, not only on age; a quiet day should not produce a 2 GB shard and a busy day a 60 GB one.
- **`forcemerge` only on read-only indices**; merging a live index fights ongoing segment creation.
- **`shrink` reduces shard count for older data** but needs the index to be relocated onto one node first; it is not free.
- **`searchable_snapshot`** moves cold data to object storage; queries still work, at higher latency and with a repository dependency.
- **`dynamic: strict`** turns an unexpected field into a visible indexing error instead of silent mapping growth - catch it in staging, not in production.

---

### 3. Aliases: The Only Way to Change an Index Safely

```text
orders-write  ──► orders-000042   (is_write_index = true, one target)
orders-read   ──► orders-000041, orders-000042   (read across the transition)
orders-*      ──► all time-based indices (queries, dashboards)
```

| Alias | Purpose |
| :--- | :--- |
| **Write alias** | Exactly one index receives new documents; ILM rollover updates it atomically |
| **Read alias** | One or more indices; during a migration it covers old and new |
| **Wildcard** | Ad-hoc queries and Kibana; avoid in application code because it hides mapping changes |

Application code should **write to the alias, never to a concrete index**. That is what makes rollover and reindex invisible to the application.

```java
// Spring Data writes go to the alias name
operations.save(orderDocument, IndexCoordinates.of("orders-write"));
```

---

### 4. Zero-Downtime Mapping Changes

Adding a field is safe. Changing a field's type, analyzer, or meaning is not, and Elasticsearch will reject documents (`mapper_parsing_exception`) rather than convert them.

```text
1. Create orders-000043 with the new template/mapping
2. Backfill from the source of truth (DB) or reindex from the old index
3. Verify counts, checksums, and spot-check queries
4. Atomically swap the write alias
5. Keep the old index readable for rollback (orders-read covers both)
6. Delete the old index after the rollback window
```

```json
POST _aliases
{
  "actions": [
    { "add":    { "index": "orders-000043", "alias": "orders-write", "is_write_index": true } },
    { "remove": { "index": "orders-000042", "alias": "orders-write" } },
    { "add":    { "index": "orders-000043", "alias": "orders-read" } }
  ]
}
```

`_aliases` is atomic: clients see either the old or the new target, never neither.

Two backfill options:

| Source | When | Trade-off |
| :--- | :--- | :--- |
| **Database** (paged read + bulk index) | Mapping/semantics changed; index is derivable | Slowest, but authoritative and repeatable |
| **`_reindex` from the old index** | Only analyzers/settings changed, documents are correct | Fast, but copies any existing corruption |

For continuous correctness during the migration, run **dual writes** (or CDC via the outbox, Q260) into both indices until the swap, then stop writing the old one. Verify with per-tenant counts and a sample of document hashes, not just `_count` on the whole index.

```json
POST _reindex?wait_for_completion=false
{
  "source": { "index": "orders-000042" },
  "dest":   { "index": "orders-000043" },
  "script": {
    "source": "ctx._source.migratedAt = params.now",
    "params": { "now": "2026-11-06T00:00:00Z" }
  }
}
```

Reindex is asynchronous: track it with `GET _tasks/<task-id>`, and expect throttling (`requests_per_second`) so it does not starve live traffic.

---

### 5. Keeping the Index Consistent with the Database

The index drifts for mundane reasons: a bulk request partially failed, a consumer crashed after committing, a delete was missed, or an event arrived out of order.

| Control | Implementation |
| :--- | :--- |
| **Idempotent upserts by id** | Always index with the business id, never generate a random document id |
| **Monotonic versioning** | Reject stale writes with `version_type=external` or `if_seq_no`/`if_primary_term` |
| **Reliable publication** | Transactional outbox or CDC, not a dual write in the request thread (Q260) |
| **Consumer dedup** | Transactional inbox when the same event can arrive twice (Q262) |
| **Reconciliation job** | Nightly compare `updated_at` watermarks, counts per tenant, and sample hashes; reindex missing ids |
| **Delete tombstones** | Delete by id in the same order as the source; a resurrected document is a stale event |
| **Read-your-writes** | Use `refresh=wait_for` for critical writes, or accept near-real-time reads (default 1 s) |

```java
// Bulk indexing: batch, do not send one request per document
List<IndexQuery> queries = orders.stream()
        .map(o -> new IndexQueryBuilder().withId(o.id()).withObject(o).build())
        .toList();

operations.bulkIndex(queries, IndexCoordinates.of("orders-write"));
```

Bulk sizing: **1,000-5,000 documents or 5-15 MB per request**, whichever comes first. Watch for `es_rejected_execution_exception` (write queue full) and back off with jitter (Q270); retrying at the same rate turns a slow node into a failing cluster.

```java
// Do not ignore partial failures: some documents in the batch may have failed
try {
    operations.bulkIndex(queries, IndexCoordinates.of("orders-write"));
} catch (BulkFailureException e) {
    // log failed ids, retry only those, then alert if the failure rate is non-trivial
    failedIds.addAll(e.getFailedDocuments().keySet());
}
```

Reconciliation is not optional. A weekly job that compares counts and hashes catches the drift that no amount of retry logic prevents.

---

### 6. Query and Pagination Discipline

| Problem | Symptom | Fix |
| :--- | :--- | :--- |
| **Deep pagination** (`from` + `size` > 10k) | `Result window is too large` / heap pressure | `search_after` with a stable sort, plus a point-in-time (PIT) |
| **Sorting/aggregating on `text`** | `Fielddata is disabled` or heap blow-up | Use a `keyword` subfield, not `fielddata=true` |
| **Exact counting on every query** | Slow responses on large indices | `track_total_hits: false` when the UI does not need the exact total |
| **Wildcard queries on analyzed text** | Full scans, high CPU | `keyword` fields, prefix queries, or a dedicated n-gram field |
| **Huge `terms` queries** | Coordinator overhead, timeouts | Batch, or precompute memberships |
| **`nested` everywhere** | Expensive joins per document | Flatten the model or denormalize where possible |

```json
GET orders-read/_search
{
  "size": 100,
  "track_total_hits": false,
  "sort": [ { "createdAt": "desc" }, { "id": "asc" } ],
  "search_after": [ "2026-11-05T12:00:00Z", "ord-9182" ],
  "query": { "term": { "tenantId": "acme" } }
}
```

The sort must be **totally ordered** (`createdAt` plus a tiebreaker id) or `search_after` can skip or repeat documents at page boundaries.

---

### 7. Cluster Health and Monitoring

```bash
GET _cluster/health?wait_for_status=yellow&timeout=30s
GET _cat/indices?v&s=store.size:desc
GET _cat/shards?v
GET _cat/allocation?v
GET _nodes/stats/thread_pool
GET _nodes/stats/indices/indexing_pressure
GET _slm/policy
```

| Metric | Healthy | Act |
| :--- | :--- | :--- |
| JVM heap used | < 75% | More heap rarely fixes it; reduce shards/fielddata |
| `write` thread pool rejections | 0 | Slow down bulk, add data nodes |
| `search` queue rejections | 0 | Reduce expensive queries, add replicas |
| Disk watermark | < 85% | At 95% indices go read-only (flood stage) |
| Unassigned shards | 0 | Check allocation explain, node capacity |
| Segment count per shard | bounded | `forcemerge` read-only indices |
| Snapshot success | daily | Test restores, not just snapshots |

Spring Boot's Elasticsearch health indicator checks connectivity, not cluster health. Add a custom gauge for `cluster.status` and for indexing rejections; a `yellow` cluster with unassigned replicas is a real availability risk even though the app still serves reads.

Rolling restarts: one node at a time, wait for `green`/`yellow` and no relocating shards, and keep master-eligible nodes at three so a restart never loses quorum.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Over-sharding** | Unstable cluster state, slow recovery, heap pressure | 10-50 GB per shard; fewer, larger indices |
| **One giant index** | Hours to recover, no retention | Time-based indices + ILM |
| **Changing `number_of_shards` in place** | Not possible | New index + reindex + alias swap |
| **Mapping change on a live index** | Documents rejected, fields missing | New index + backfill + alias swap |
| **`fielddata=true` on text** | Heap exhaustion, node restarts | `keyword` subfield |
| **Writing to a concrete index** | Rollover/reindex breaks the app | Always write to the alias |
| **No read alias** | Migration requires downtime | `orders-read` covering old and new |
| **Reindex without verification** | Silent data loss | Count per tenant + hashes + sample queries |
| **Bulk without backoff** | 429s, rejected executions, lag | Smaller batches, jittered backoff (Q270) |
| **Refresh per document** | Terrible indexing throughput | Batch + `refresh_interval` tuning |
| **`dynamic: true` in production** | Mapping explosion | `strict` or explicit mappings |
| **Random document ids** | Duplicates on retry | Business id as `_id` |
| **No reconciliation** | Index drifts from DB for months | Watermark + count/hash job |
| **Disk above flood watermark** | Index becomes read-only, writes fail | Capacity alerts at 80%, cleanup/ILM |
| **No snapshot restore drill** | Backups exist but cannot be restored | SLM + periodic restore test |

### Summary

- **Elasticsearch is derived data**: design for rebuild, index by business id, and treat the database as the source of truth (Q225/Q260).
- **Shard count is a one-way decision**: target 10-50 GB per shard, keep total shards modest, and use time-based indices plus ILM instead of one giant index (the search equivalent of partitioning, Q272).
- **Aliases decouple clients from indices**: one write alias, one read alias, and an atomic `_aliases` swap for every mapping change.
- **Zero-downtime reindex = new index + backfill/dual-write + verification + atomic alias swap + rollback window**, not `_reindex` into the live index.
- **Consistency needs idempotent upserts, version checks, reliable publication (outbox/CDC), and a reconciliation job** that compares counts and hashes, because partial bulk failures are normal.
- **Operate the cluster, not just the client**: watch heap, thread-pool rejections, disk watermarks, unassigned shards, and snapshot restores; paginate with `search_after`, avoid `fielddata`, and keep mappings strict.

## 279. How do you build a modular monolith with Spring Modulith? Explain module boundaries, named interfaces, verification tests, transactional events, and when to extract a microservice.

Most "microservices" failures start as a **distributed monolith**: services that share a database schema, call each other synchronously in chains, and cannot be deployed independently. Spring Modulith takes the opposite order - **define and enforce module boundaries inside one deployable first**, observe where the seams actually are, and extract services only when a module has a reason to leave (independent scaling, team ownership, compliance, different availability). The boundaries are not documentation; they are verified in tests, so a violation fails the build instead of quietly becoming a coupling problem.

---

### 1. Three Shapes, One Set of Boundaries

| Shape | Deployment | Boundary enforcement | Cost of a wrong boundary |
| :--- | :--- | :--- | :--- |
| **Layered monolith** | One unit | Convention only | Cheap to fix, easy to erode |
| **Modular monolith** | One unit | Code + tests (Modulith/ArchUnit) | Cheap to fix, hard to erode |
| **Microservices** | Many units | Network + contracts + org structure | Expensive: data migration, versioning, ops |

The modular monolith is the cheapest place to discover boundaries. If two modules keep sharing entities and calling each other in cycles, that is evidence the split is wrong - much cheaper to learn in one process than across a network.

```text
com.acme.shop
├── orders          ← own API, own tables, publishes OrderPlaced
├── inventory       ← consumes OrderPlaced, owns stock
├── payments        ← own API, own tables
├── catalog         ← exposes ProductCatalog (named interface)
└── shared          ← pure value types, no business logic
```

---

### 2. Declaring a Module

```java
// src/main/java/com/acme/shop/orders/package-info.java
@org.springframework.modulith.ApplicationModule(
        displayName = "Orders",
        allowedDependencies = { "catalog::api", "shared" }
)
package com.acme.shop.orders;
```

Everything under `com.acme.shop.orders` is the module. By default a module may use **other modules' root packages**, but `allowedDependencies` narrows that to an explicit list - ideally named interfaces rather than whole modules.

| Element | Meaning |
| :--- | :--- |
| **Module root package** | The boundary; subpackages are internal unless exposed |
| **`allowedDependencies`** | The only modules this one may reference |
| **Named interface** | A deliberately exposed slice of a module |
| **`shared`** | Value objects and primitives; never repositories or services |

The boundary is only real if the compiler or the test suite enforces it. Spring Modulith does that at test time:

```java
class ModularityTests {

    @Test
    void moduleBoundariesAreRespected() {
        ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
        modules.verify();                 // fails on cycles and illegal dependencies
    }
}
```

`verify()` reports:

- **Cycles** between modules (`orders → inventory → orders`).
- **Violations** of `allowedDependencies`.
- **Access to internal types** of another module.

Run it in the normal test suite, not a nightly job. A boundary violation that lives for a week becomes an accepted design.

For finer rules (naming, annotations, layering inside a module), add **ArchUnit** tests on top; Modulith checks module-level dependencies, ArchUnit checks the rest.

---

### 3. Named Interfaces: Expose Less Than You Think

A module's root package is public by accident unless you narrow it. `@NamedInterface` makes the public surface explicit:

```java
// src/main/java/com/acme/shop/catalog/api/package-info.java
@org.springframework.modulith.NamedInterface("api")
package com.acme.shop.catalog.api;

// src/main/java/com/acme/shop/catalog/internal/package-info.java
@org.springframework.modulith.ApplicationModule(
        type = ApplicationModule.Type.OPEN)   // internal subpackage, not a module
package com.acme.shop.catalog.internal;
```

```java
// Orders depends on the published API only
@ApplicationModule(allowedDependencies = "catalog::api")
package com.acme.shop.orders;
```

```java
// catalog/api/ProductCatalog.java - the contract
public interface ProductCatalog {
    Optional<ProductView> find(String productId);
    List<ProductView> search(String query, int limit);
}
```

Rules that keep the boundary honest:

- **Expose interfaces and immutable DTOs**, not entities or repositories.
- **No JPA entity leaks** across modules: an `@Entity` in the API package couples schemas and lazy-loading behaviour.
- **No shared repositories**: if two modules need the same table, one owns it and exposes a query method.
- **`shared` holds value types only** (money, ids, result types), never services.

---

### 4. Communicating Between Modules

Two options, and the choice matters:

| Style | Use when | Cost |
| :--- | :--- | :--- |
| **Synchronous API call** | The caller needs an answer to continue (validate a product exists) | Runtime coupling; caller waits |
| **Domain event** | The caller only needs to announce a fact (order placed) | Eventually consistent; needs idempotency and observability |

```java
// orders module: publish inside the transaction, after the state change
@Service
class OrderService {

    private final ApplicationEventPublisher events;
    private final OrderRepository orders;

    @Transactional
    public Order place(PlaceOrderCommand cmd) {
        Order order = orders.save(Order.create(cmd));
        events.publishEvent(new OrderPlaced(order.id(), cmd.lines(), order.total()));
        return order;
    }
}
```

```java
// inventory module: react after the publisher commits
@Component
class InventoryListener {

    @ApplicationModuleListener            // @Async + @Transactional(REQUIRES_NEW)
    void on(OrderPlaced event) {          // @TransactionalEventListener(AFTER_COMMIT)
        stock.reserve(event.orderId(), event.lines());
    }
}
```

`@ApplicationModuleListener` is the important semantic bundle:

| Property | Consequence |
| :--- | :--- |
| **After commit** | The listener never sees an order that rolled back |
| **New transaction** | A listener failure does not roll back the order |
| **Asynchronous** | The publisher does not wait; failures are invisible to the caller |
| **At-least-once** | The same event can be delivered twice; the listener must be idempotent (Q262) |

The **event publication registry** (enabled by the JPA starter) persists incomplete publications and republishes them after a crash or restart, so an event is not lost between "order committed" and "inventory listener ran". That is the in-process equivalent of the transactional outbox (Q260) - and it has the same requirement: consumers must be idempotent.

```yaml
spring:
  modulith:
    events:
      # Persist publications so a crash between commit and listener does not lose the event
      jpa:
        enabled: true
```

---

### 5. Events Do Not Remove the Need for Design

| Pitfall | Why it bites | Fix |
| :--- | :--- | :--- |
| **Publishing before commit** | Listener acts on state that later rolls back | Publish after the state change, inside the transaction; use `@ApplicationModuleListener` |
| **Listener assumed synchronous** | Caller returns before inventory reserved | Accept eventual consistency in the API contract, or call synchronously when the answer is required |
| **Non-idempotent listener** | Duplicate reservation after republish | Unique constraint or inbox table (Q262) |
| **Listener throws silently** | Event marked incomplete forever, or lost after retries | Metrics/alerts on failed publications; dead-letter handling |
| **Event carrying entities** | Serialization and coupling problems | Events carry ids and immutable values |
| **Ordering assumptions** | `OrderPlaced` and `OrderCancelled` race | Include sequence/version; make the consumer state-based |
| **Giant events** | Slow serialization, schema lock-in | Reference the aggregate; let the consumer query what it needs |

The registry solves durability, not semantics. If a listener fails permanently, the publication stays incomplete: that needs an alert and a retry/DLQ policy, exactly like a Kafka consumer group (Q259).

---

### 6. Testing Modules, Not Just Classes

```java
@ApplicationModuleTest                        // boots the module, not the whole application
class OrdersModuleTests {

    @Test
    void placingOrderPublishesEvent(Scenario scenario) {
        scenario.stimulate(() -> orders.place(command()))
                .andWaitForEventOfType(OrderPlaced.class)
                .toArrive();
    }
}
```

| Bootstrap mode | What is started | Use for |
| :--- | :--- | :--- |
| **`STANDALONE`** | The module alone, dependencies mocked | Pure unit-of-module tests |
| **`DIRECT_DEPENDENCIES`** (default) | The module plus modules it depends on | Most integration tests |
| **`ALL_DEPENDENCIES`** | The full application context | End-to-end flows |

`Scenario` gives you a deterministic way to assert event flows without sleeping: `stimulate(...)`, `andWaitForEventOfType(...)`, `andWaitForStateChange(...)`. Combined with `ApplicationModules.verify()` and `Documenter` output, module boundaries become testable and visible:

```java
@Test
void writeArchitectureDocs() {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
    new Documenter(modules)
            .writeModulesAsPlantUml()
            .writeDocumentation();          // Asciidoc/C4 component diagrams
}
```

Treat the generated diagram as a build artifact: a diff in the diagram is a design change worth reviewing.

---

### 7. The Extraction Path

A module becomes a candidate for extraction when it has at least one of these:

- **Independent scaling**: inventory spikes during sales while catalog is idle.
- **Different availability/SLO**: checkout cannot share a deployment with reporting.
- **Ownership**: a separate team can own the schema, release cadence, and on-call.
- **Compliance/data residency**: the data must live in another region or account (Q268).
- **Technology fit**: the workload needs a different runtime or store.

Extraction checklist:

1. **The module already owns its tables** and no other module reads them directly.
2. **Cross-module calls go through the named interface or events**, not shared entities.
3. **The outbox pattern is in place** for events that must survive the split (Q260).
4. **Idempotency and ordering** are already handled, because the network makes duplicates certain (Q262).
5. **Observability is per-module** (metrics/traces tagged by module) so you can compare before and after (Q230/Q266).
6. **The first step is a separate schema and a network API; the last step is a separate deployment** - not the other way round.

If a module fails step 1 or 2, extraction will produce a distributed monolith. Keep it in the monolith until the boundary is real.

---

### 8. Common Pitfalls

| Pitfall | Symptom | Fix |
| :--- | :--- | :--- |
| **Boundaries only in docs** | Modules import each other freely | `ApplicationModules.verify()` in CI |
| **Shared JPA entities** | Schema coupling, lazy-loading leaks | DTOs at the boundary; one owner per table |
| **`shared` becomes a dumping ground** | Every module depends on it; cycles return | Value types only; split by concept |
| **Cycle "solved" by moving code** | A new god module | Redesign the dependency direction; use events |
| **Wide `allowedDependencies`** | `allowedDependencies = "*"` | Depend on `module::api` named interfaces |
| **Listener assumed sync** | API returns success before stock is reserved | Contractual eventual consistency, or a synchronous call |
| **Non-idempotent listener** | Double reservation after restart/republish | Unique key or inbox table (Q262) |
| **Failed publications ignored** | Silent data loss or stuck registry | Alert on incomplete publications; DLQ/retry |
| **Event carries an entity** | Serialization failures, tight coupling | Ids + values; consumer queries if needed |
| **Module test boots everything** | Slow, flaky, no boundary feedback | `@ApplicationModuleTest(DIRECT_DEPENDENCIES)` |
| **Extracting too early** | Distributed monolith with network latency | Prove boundaries in-process first |
| **Extracting too late** | One module's load affects all; deployment queue | Extract on a concrete driver (scaling/team/compliance) |
| **No module-level metrics** | Cannot attribute latency or cost | Tag metrics/spans by module (Q230/Q266) |

### Summary

- **Spring Modulith makes boundaries enforceable in one deployable**: package roots define modules, `allowedDependencies` and `verify()` reject cycles and illegal access at build time.
- **Expose named interfaces, not packages of entities**: `module::api` with interfaces and immutable DTOs; keep `shared` to value types.
- **`@ApplicationModuleListener` means after-commit, async, new transaction, at-least-once** - the event registry adds durability, but the listener must be idempotent (Q262).
- **Test at module altitude** with `@ApplicationModuleTest` and `Scenario`, and generate diagrams as reviewable build artifacts.
- **Extract a service only on a concrete driver** (scaling, ownership, compliance, availability) and only after the module already owns its data and communicates through APIs/events.
- **A modular monolith is not a stepping stone you must leave**; it is a valid architecture whose boundaries make a later extraction cheap rather than a rewrite.
